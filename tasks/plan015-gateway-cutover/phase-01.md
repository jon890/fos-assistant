# Phase 01. 주소를 공유 listener 로 옮긴다

**Execution profile**: standard

## 목표

에이전트의 `api_base_url` 에서 호스트와 포트를 공유 listener 쪽으로 바꾼다.
옮긴 뒤 대화와 스트리밍과 Memory 본문 조회와 모델 조회가 도는 것을 운영에서 확인한다.

**범위 외**:
profile 전용 gateway 를 내리는 것과 포트 설정을 지우는 것은 이 저장소가 하지 않는다.
비공개 저장소 `fos-home-infra` 의 plan10 phase 04 와 05 가 그것을 소유한다.

## 컨텍스트

profile 마다 gateway 프로세스와 포트를 두던 것을 공유 listener 하나로 옮기는 중이다.
네 단계 가운데 셋째의 뒷부분이 이 phase 다.

| 단계 | 누가 | 무엇 | 상태 |
| --- | --- | --- | --- |
| 1 | 인프라 | 공유 listener 를 세운다 | 끝남 |
| 2 | 인프라 | 컨테이너 밖에서 닿게 연다 | 끝남 |
| 3a | 이 저장소 | 주소에 `/p/<profile>` 접두를 붙인다 | 끝남 |
| **3b** | **이 저장소** | **호스트와 포트를 공유 listener 로 바꾼다** | **이 phase** |
| 4 | 인프라 | 운영 스크립트에서 포트 입력을 없앤다 | 이 phase 뒤 |
| 5 | 인프라 | 전용 gateway 를 내린다 | 그 뒤 |

주소가 이렇게 바뀐다.

```text
지금    http://<호스트>:<그 profile 의 포트>/p/<profile>
뒤      http://<호스트>:<공유 listener 의 포트>/p/<profile>
```

**바꾸는 것은 호스트와 포트뿐이다.** 접두는 3a 가 이미 붙여 두었다.

### 왜 두 걸음으로 나뉘었나

원래 계획은 한 걸음이었다.
3a 를 하고 3b 를 하려 했을 때 공유 listener 가 Hermes 컨테이너 안쪽에만 묶여 있어
Control Plane 이 닿지 못했다. 인프라가 그것을 열어 이 phase 가 가능해졌다.

### 확인된 것

인프라 쪽에서 Control Plane 이 도는 자리에서 보내 확인했다.

| 요청 | 응답 |
| --- | --- |
| 자기 profile 의 key | 200 |
| 남의 profile 의 key | 401 |
| 없는 profile | 404 |

**근거 문서**: 비공개 저장소 `fos-home-infra` 의 `docs/hermes-multiplex-gateway.md` 와
`tasks/plan10-shared-gateway/`.
공유 listener 의 주소는 그 저장소가 소유한다. **이 저장소에 적지 않는다.**

## 의도 메모

- 모든 에이전트를 한 번에 옮기는 안을 버렸다.
  하나를 옮겨 확인하고 나머지를 옮긴다.
  한 번에 옮기면 무엇 때문에 깨졌는지 좁히지 못한다.
- 전용 gateway 를 곧바로 내리는 안을 버렸다.
  되돌릴 곳이 사라진다. 이 phase 가 끝나고 지켜본 뒤에 인프라가 내린다.
- 3a 를 되돌리고 접두 없이 옮기는 안도 버렸다.
  공유 listener 는 접두로 profile 을 구분한다. 접두가 없으면 listener 주인에게 간다.

## 작업 항목

### 1. 동시 실행 한도를 먼저 올린다

**이 phase 가 그 한도를 바꾼다.** 지금은 profile 마다 따로인데 옮기면 함께 쓴다.

| 구조 | 동시 실행 한도 |
| --- | --- |
| 지금 | profile 마다 10. 서로 빌리지 못한다 |
| 옮긴 뒤 | 전체 합쳐 하나 |

지금 값이 16 이고 그것은 Python 기본 thread pool 크기에 맞춘 값이다.
Hermes 가 실행 하나를 `run_in_executor(None, ...)` 로 그 pool 에 던지기 때문이다.

**그 값을 올린다.** 근거는 이렇다.

실행이 붙잡고 있는 시간의 대부분은 LLM 응답을 기다리는 시간이고 CPU 를 쓰지 않는다.
pool 크기를 넘겨도 넘친 실행은 앞의 것이 끝날 때까지 줄을 설 뿐이다.
실행 하나가 몇 초에서 십몇 초이므로 줄을 서도 그만큼이다.
**즉시 실패하는 것보다 잠깐 기다리는 편이 낫다.**

**이 값은 이 저장소가 갖지 않는다.** `fos-home-infra` 에 요청한다.
요청할 때 위 근거와 함께 얼마로 올릴지 제안하고, 그쪽 판단을 따른다.

이 항목이 끝나기 전에는 2번으로 가지 마라.

### 2. 에이전트 하나를 먼저 옮긴다

관리 화면에서 주소의 호스트와 포트를 바꾼다.
**가장 덜 쓰는 에이전트로 한다.**

저장할 때 화면이 그 주소로 한 번 불러 닿는지 확인한다. 200 이 아니면 저장되지 않는다.

옮긴 뒤 확인할 것이다.

| 무엇 | 어떻게 |
| --- | --- |
| 대화 한 번 | 화면에서 보내고 답이 온다 |
| 스트리밍 | 답 조각이 흐르고 `done` 뒤 이력이 맞다 |
| 모델 조회 | 관리 화면의 동기화가 **그 profile 의** 모델을 읽는다 |
| 실행 기록 | 사용량 목록에 토큰과 금액이 남는다 |
| Memory 본문 조회 | 색인에 있는 항목의 본문을 도구로 읽는다 |

**모델 조회를 눈여겨본다.** listener 주인의 모델이 오면 접두가 먹지 않은 것이다.

**Memory 본문 조회가 가장 무겁다.**
Hermes 에서 Control Plane 으로 거꾸로 오는 경로라 포트가 바뀌어도 살아 있어야 한다.
기억 본문에만 있는 문구를 답으로 받는 방식으로 판정한다.
제목만 주입되므로 그 문구는 도구로 본문을 읽어야 알 수 있다.

### 3. 나머지를 옮긴다

하나씩 옮기고 그때마다 대화를 한 번 보낸다.

**옮기기 전 주소를 적어 둔다.** 되돌릴 때 필요하다.
**이 저장소에 적지 않는다.** 주소에 포트가 들어 있다. 보고에만 적는다.

### 4. 붐빔이 나오는지 본다

사용량 화면의 실행 목록에서 `HERMES_BUSY` 로 실패한 실행을 찾는다.
그 코드는 Hermes 가 429 를 준 것, 곧 동시 실행 한도에 닿은 것이다.

| 나왔나 | 무엇을 하나 |
| --- | --- |
| 없다 | 그대로 둔다 |
| 있다 | 몇 번 언제 났는지 적어 인프라에 넘긴다. 한도를 더 올려야 한다 |

응답이 느려졌는지도 본다. 사용량 목록의 소요 시간을 옮기기 전과 견준다.

**얼마나 지켜볼지는 사용자가 정한다.** 이 phase 는 한 번 보고 결과를 적는 것까지다.

### 5. 되돌리는 방법을 남긴다

옮기기 전 주소와 옮긴 주소를 짝지어 보고에 적는다.
되돌리는 것은 관리 화면에서 그 값을 되돌리는 것뿐이고 재배포가 필요 없다.

## 검증

```bash
# cwd: 저장소 root
cd backend && ./gradlew test
cd web && pnpm typecheck && pnpm build
cd web && pnpm test:browser
node test/e2e/run.ts
scripts/check-public-safe.sh
```

앞의 넷은 함께 돌려도 된다. 검사마다 빈 포트를 받아 쓰므로 서로 다투지 않는다.

**이 phase 는 코드를 거의 바꾸지 않는다. 배포 뒤 확인이 본체다.**
작업 항목 2번과 3번을 하지 않으면 끝난 것이 아니다.
