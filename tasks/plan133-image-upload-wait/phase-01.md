# Phase 01. 사진 업로드 응답 대기

**Execution profile**: standard

## 목표

모델을 먼저 고른 뒤 사진 업로드가 5초보다 오래 걸려도 실제 응답을 확인하고 전송한다.

**범위 외**: 운영 코드, Hermes, 다른 업로드 검사와 공통 helper.

## 컨텍스트

**근거 문서**: `docs/features/attachment.md`. 업로드 컨트롤러는 원본 저장 뒤 사본 준비를 시도하고 그 호출이 끝난 뒤 응답한다. 슬롯은 최대 30초 기다리지만 준비 실패에도 업로드 성공 응답이 가능하다.
실패 CI는 업로드 표시가 5000ms 내 사라지지 않았다. 최신 main의 같은 검사는 retry 0으로 통과했다.

## 의도 메모

운영 결함으로 단정하지 않는다. 응답 대기는 45초로 한정하고 응답 본문, 상태, 첨부 식별자, UI와 실제 메시지를 검증한다.
5.5초 지연 응답은 기존 기본 대기가 충분하지 않음을 검증하는 입력이다. 실패 응답에서도 오류를 확인하고 사진을 지운 뒤 전송 결과를 확인한다.
번호 확보 스크립트는 HTTPS 일회성 helper로 실행했다. 다음 번호 121보다 큰 코디네이터 예약 범위 119~132를 피해 133을 사용하고 완료 뒤 계획을 지운다.

## 작업 항목

### 1. test/browser/model-choice.spec.ts 테스트

기존 모델 선택 뒤 업로드 검사를 성공과 실패 응답으로 실행한다. POST만 식별하고 입력 전에 응답 대기를 등록한다.
성공 응답은 실제 서버 응답을 5.5초 늦춰 전달하고 본문 id와 업로드 종료, 오류 부재, 메시지의 첨부 1개를 검증한다.
실패는 502 응답을 늦춰 전달하며 오류 표시와 사진 없는 메시지를 검증한다.
전체 테스트 기한은 응답 대기와 모델 선택, 메시지 전송을 포함하도록 90초로 둔다.

### 2. docs/features/attachment.md 계약

원본 저장 뒤 사본 준비를 시도하고 그 호출이 끝난 뒤 응답한다는 계약을 기존 사진 첨부 흐름에 적는다. 사본 준비 실패에도 업로드 자체는 성공할 수 있으며, 슬롯 대기 최대 30초는 전송·저장·변환을 합친 전체 업로드 기한이 아님을 명시한다.

## 검증

```bash
pnpm --dir web test:browser model-choice.spec.ts --grep '새 대화에서 모델을 먼저' --repeat-each=3 --retries=0
scripts/check-local.sh model-choice chat-attachment
```
- 모든 검사 종료 코드 0. 성공과 실패 검사는 desktop/mobile에서 재시도 없이 통과한다.
