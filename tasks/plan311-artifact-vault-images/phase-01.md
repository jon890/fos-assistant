# Phase 01. 이미지가 포함된 완성 HTML 묶음과 독립 이미지를 보관한다

**Execution profile**: standard

## 목표

PR 1 이 거절하는 이미지 의존 HTML 을 보관한다. HTML 이 상대 경로로 부르는 사진과 CSS 를 한 묶음으로 보관하고, 독립 이미지도 보관한다.
새 테이블을 만들지 않는다(2026-11-01 사용자 결정). PR 1 이 만든 `chat_artifact` 의 보관 사본 행을 쓴다.

**범위 외**: turn 완료 때 자동 보관(PR 3), 원고 revision, PDF·문서(PR 4 이후), 외부 Drive 내보내기, 그룹 공유.

## 컨텍스트

**근거 문서**: `docs/adr/ADR-20261101-artifact-vault.md`, `docs/features/workspace.md` 의 「보관한 결과물」, `backend/docs/data-schema.md` 의 `chat_artifact`

- PR 1 은 `ArtifactVaultService.DEPENDENCY` 정규식이 사진·스타일·프레임을 부르는 HTML 을 거절한다. 이 계획이 그 거절을 묶음 보관으로 바꾼다
- 본문은 텍스트(`TextCipher`)라 PR 1 이 문자열 암호화를 썼다. 이미지는 바이너리라 `AesGcm` 의 `byte[]` 경로를 쓰는 제한된 인터페이스를 `crypto` 에 더한다. key 원문을 chat 모듈에 넘기지 않는다
- 묶음 상한은 100MiB, 1,000파일, 개별 5MiB 를 첫 값으로 제안한다. 한 파일씩 상한 안에서만 메모리에 올린다
- 의존 파일은 정규식으로 주소를 바꾸지 않고 제한된 parser 로 참조를 확인한다. 외부 주소와 data URI 는 내려받아 보관하지 않고 묶음 전체를 거절한다. 누락 파일과 상한 초과도 묶음 전체 실패다
- 묶음 한 건과 그 안의 파일을 어떻게 기존 칸에 담을지(묶음 행 하나와 `vault_*` 의 자식 행, 또는 본문 칸의 묶음 형식)는 새 테이블 없이 정한다. 새 테이블이 꼭 필요하면 만들기 전에 까닭을 정리해 사용자에게 묻는다
- 보관 중 원본 정리가 바이트를 지우지 못하게 하는 장벽이 필요한지 정한다(원본 30일 만료와 보관 요청의 경쟁)

## 작업 항목

1. 묶음 형식과 저장 칸을 정하고 ADR 의 대상 절을 고친다
2. 의존 파일 확인(제한된 parser), 묶음 상한, 바이너리 암호화 인터페이스
3. 묶음 미리보기(상대 주소마다 소유권 확인, 기존 CSP 유지)와 묶음 내려받기
4. 독립 이미지 보관
5. 웹: 보관 목록에 묶음과 이미지 표시, 거절 문구 갱신

## 검증

- CSS·이미지 상대 주소, 미참조 파일 제외, 부분 묶음 성공 금지
- 첨부 사진 복제의 소유권, 만료와 삭제 경쟁, 메모리와 동시 요청 상한
- 남의 묶음 읽기 차단, 대화 삭제 뒤 보존, 용량 초과 거절이 PR 1 과 같은 수준으로 있다
