## ADR-20261009: 이번 메시지의 사진은 줄인 사본을 실행 입력에 직접 싣고, 원본 파일은 그대로 둔다

- **status**: `accepted`
- Date: 2026-10-09
- [ADR-020](ADR-020-사진은-공유-디렉터리에-두고-에이전트가-파일로-읽는다.md) 의 「대화 본문에 사진을 실을 수 없다」 를 바꾼다.
  사진을 공유 디렉터리에 두고 실행 공간에 붙이는 것([ADR-091](ADR-091-사진-첨부는-사용자별로-저장하고-실행-공간에는-그-사용자만-붙인다.md))은 그대로다.

### 결정

**보내는 메시지에 붙은 사진은 긴 변 1600px JPEG 로 줄여 `POST /v1/runs` 의 `input` 에 이미지 파트로 싣는다.**
원본은 지금처럼 실행 공간의 사용자 폴더에 두고, 실행 입력의 파일 목록도 그대로 적는다.
편집, 업로드처럼 파일이 필요한 도구는 원본을 쓴다.

| 무엇 | 어떻게 |
| --- | --- |
| 싣는 모양 | `input` 을 user 메시지 하나의 목록으로 보낸다. `content` 는 글 파트(지금의 입력 전체), 그 뒤로 사진마다 「N번째 사진」 글 파트와 `image_url` 파트(`data:image/jpeg;base64,...`)를 잇는다 |
| 사진이 없을 때 | `input` 을 지금처럼 문자열로 보낸다. 사진 없는 실행의 요청은 바뀌지 않는다 |
| 줄이는 법 | Control Plane 이 보낼 때 메모리에서 만든다. 긴 변 1600px 이하, JPEG 품질 0.85, EXIF 회전 반영, 투명 배경은 흰색으로 채운다. 작은 사진은 키우지 않는다 |
| 한 턴 상한 | 10장, base64 합계 7MB 가운데 먼저 닿는 쪽까지 싣는다. 코드 상수다 |
| 싣지 못한 사진 | 상한을 넘었거나, JDK 가 읽지 못하는 형식(WebP)이거나, 디코딩에 실패한 사진이다. 파일 목록에만 남고 실행은 실패하지 않는다 |
| 다음 턴 | 이번 메시지의 사진만 싣는다. 지난 사진은 다시 싣지 않는다 |
| 지시문 | 「함께 실은 사진은 이미 보인다. 싣지 못한 사진과 지난 메시지의 사진은 `vision_analyze` 로 파일을 본다」 로 바꾼다 |

### 근거

운영판 Hermes v0.21.5(`v2026.9.24`)의 소스를 읽어 확인했다. 근거 줄은 [`hermes/runs-api.md`](../hermes/runs-api.md) 의 「`/v1/runs` 에 사진을 싣는 법」 이 갖는다.

- `/v1/runs` 는 `input` 의 마지막 항목의 `content` 를 목록 그대로 에이전트에 넘긴다. provider 어댑터가 `image_url` 파트를 그 provider 의 모양으로 바꾼다
- 모델이 이미지를 받지 않거나 판정하지 못하면 Hermes 가 보조 vision 모델의 설명 글로 바꿔 보낸다. 상류가 이미지를 거절하면 이미지를 뗀 사본으로 다시 시도한다.
  그래서 Control Plane 이 모델마다 지원 여부를 판정하지 않는다
- session 기록에는 이미지 대신 `[screenshot]` 자리표시자가 남는다. 다음 턴에 이미지가 다시 실리지 않는다

### 상한의 근거

| 상한 | 까닭 |
| --- | --- |
| base64 합계 7MB | Hermes API server 의 요청 본문 상한이 10MB(`MAX_REQUEST_BYTES`)다. 넘으면 413 으로 실행이 시작되지 않는다. 기억 문맥과 지시문, 입력 글이 남은 3MB 안에 든다 |
| 10장 | 같은 턴 안에서는 도구를 부를 때마다 이미지가 다시 실린다. 사용자가 올린 이미지는 Hermes 가 요청에서 빼지 않는다. 긴 변 1600px 한 장은 약 1,100~1,500 토큰이라 30장을 모두 실으면 도구 호출 한 번에 약 4만 토큰이다 |
| 긴 변 1600px | 원본이 3MB 를 넘으면 실행 공간의 파일 읽기가 가끔 잘려 `vision_analyze` 가 실패했다(운영에서 5장 중 2장). 줄인 사본은 수백 KB 다. Hermes 의 `vision_analyze` 도 1568px 로 줄여 싣는다 |

### 위협과 보관

- **줄인 사본을 저장하지 않는다.** 보낼 때 메모리에서 만들고 요청이 끝나면 버린다. 지울 파일이 생기지 않는다. 다시 생성하면 다시 만든다
- 싣는 사진은 그 실행의 대화 주인이 그 대화에 올린 첨부뿐이다. 실행 입력을 만드는 자리에서 첨부의 대화와 올린 사용자를 확인한다(지금의 판정을 그대로 쓴다)
- Control Plane 데이터베이스에는 실행 입력을 저장하지 않으므로 이미지가 남지 않는다. 메시지 암호화([ADR-20261008 / data-encryption](ADR-20261008-data-encryption.md))와 겹치지 않는다
- Hermes 쪽: API 오류가 나면 Hermes 가 요청 전체를 진단 파일(`request_dump_*.json`)로 남겨 base64 가 그 안에 들어간다.
  압축이 그 턴에 돌면 원본 파트가 session 기록에 남을 수 있다. 둘 다 그 profile 의 저장소이고, 원본 사진 파일도 이미 평문으로 실행 공간에 있다.
  ADR-20261008 / data-encryption 의 「Hermes 의 저장은 평문」 범위 안이다. 대화를 지우면 session 은 지우지만 진단 파일은 남는다([`hermes/runs-api.md`](../hermes/runs-api.md) 의 「session 을 지우는 경로」)
- 모델 공급자에게는 전에도 `vision_analyze` 로 사진이 갔다. 받는 곳은 같다

### 대안 기각

- **원본을 그대로 싣는다**: 한 장 10MB 상한이라 한 장만으로 요청 상한을 넘을 수 있다. 토큰도 크다
- **올릴 때 줄인 사본을 파일로 만들어 둔다**: 보낼 때 계산이 빠르다. 그러나 지우기, 만료, 사용자별 경로를 사본에도 맞춰야 한다. 보낼 때 몇 장을 줄이는 비용은 크지 않다
- **대화의 모든 사진을 매 턴 다시 싣는다**: 지난 사진을 다시 볼 수 있다. 그러나 사진 많은 대화는 매 턴 요청 상한과 토큰 비용에 닿는다
- **모델의 vision 지원을 Control Plane 이 판정해 싣지 않는다**: Hermes 가 이미 판정하고 대체한다. 같은 판정을 두 곳에 두면 어긋난다
- **`vision_analyze` 지시를 없앤다**: 싣지 못한 사진과 지난 사진을 볼 길이 없어진다

### 얻는 것과 감당할 것

- 얻는 것: 큰 사진의 파일 읽기 잘림과 관계없이 모델이 사진을 본다. 사진마다 `vision_analyze` 호출이 없어져 턴이 짧다
- 감당할 것: 11번째 사진부터와 지난 메시지의 사진은 여전히 파일 읽기에 기대 잘림 문제가 남는다
- 감당할 것: 보낼 때 사진을 디코딩한다. 디코딩은 원본 해상도를 줄여 읽어(subsampling) 메모리를 결과 크기에 가깝게 둔다
- 감당할 것: 이미지 토큰이 실행 사용량의 입력 토큰에 섞여 따로 보이지 않는다
