## ADR-20261013 / financial-order-opening: 토스 일반 주문의 생성과 취소를 준비 도구 하나로 열고, 계좌는 한 사용자에게만 묶는다

- **status**: `accepted`
- Date: 2026-10-13
- [ADR-20261010 / financial-execution-guard](ADR-20261010-financial-execution-guard.md) 의 snapshot 과 claim, [ADR-20261012 / financial-unsent-proof](ADR-20261012-financial-unsent-proof.md) 의 미전송 판정 위에 선다.
  금융 해시 key 교체는 [ADR-20261013 / financial-digest-key-rotation](../../backend/docs/adr/ADR-20261013-financial-digest-key-rotation.md) 을 그대로 따른다.

### 맥락

금융 준비(`ConnectorFinancialProducer`)와 금융 승인(`ConnectorFinancialApproval`)은 구현돼 있었지만 공개 진입점에 이어지지 않았다.
정책 판정은 `FINANCIAL` 을 `RISK_NOT_OPEN` 으로 거절했고, 토스 서버는 주문 도구를 등록하지 않았다.
소유자가 2026-10-13 에 매매 개방을 명시적으로 승인했다. kill switch 는 두지 않으므로 이 결정을 담은 PR 의 머지가 곧 개방이다.
운영에서는 key 파일, 허용 목록, 0 이 아닌 상한이 채워질 때까지 `ConnectorFinancialGate` 가 계속 거절한다.

정할 것이 넷이었다.

1. 모델이 무엇을 불러 승인 줄이 생기는가
2. 같은 계좌를 두 사용자가 각자 연결하면 하루 상한이 사용자 수만큼 늘어나는 문제
3. 가격이 없는 미국 금액 주문(`orderAmount`, USD)을 원화 상한과 어떻게 견주는가
4. 승인 카드가 무엇을 보이는가

### 결정

#### 모델은 준비 도구만 부르고 Control Plane 이 그 호출을 금융 준비로 넘긴다

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| 실행 도구(`create_order`)를 모델 목록에 두고 hook 이 준비로 넘긴다 | 모델이 부르는 이름과 승인 줄의 도구가 같다 | plugin 이 `always` 도구를 모델 목록에서 빼는 동작과, `FINANCIAL` 을 설치 정의에서 다시 숨기는 동작을 함께 풀어야 한다. 실행 도구가 모델 목록에 생긴다 |
| **준비 도구(`prepare_trade`)만 모델 목록에 두고, 그 호출을 Control Plane 이 금융 준비로 넘긴다** | plugin 을 고치지 않는다. 실행 도구는 지금처럼 모델 목록에 없고 승인 뒤 claim 으로만 불린다 | 모델이 부른 도구와 승인 줄의 도구 이름이 다르다 |

둘째를 고른다.

- 정책 hook 이 커넥터의 `execution_guard.prepare_tool` 을 부른 호출을 받으면, 인자를 `{v: 1, tool, args}` 로 엄격히 읽는다.
  중복 키, 추가 키, 다른 타입은 거절한다.
- `tool` 이 그 선언의 `operations` 에 있고, 그 동작이 지금 여는 `CREATE` 나 `CANCEL` 이며 종류가 `ORDER` 일 때만 `ConnectorFinancialProducer` 로 넘긴다.
  넘길 때 등록 이름은 그 실행 도구의 이름이고 인자 글은 `args` 다. 그 밖은 기록 없이 거절한다.
- hook 의 답은 언제나 막힘이다. 준비가 되면 승인 번호를 함께 돌려주고, 거절은 어느 검사에 걸렸는지 밝히지 않는다.
- 살펴보기(먼저 살펴보기, 예약 작업) 트리 안의 호출은 쓰기를 허용한 살펴보기여도 넘기지 않는다. 사람이 보지 않는 실행이 외부 글에 속아 주문 승인 요청을 쌓지 않게 한다.
- 같은 `tool_call_id` 로 다시 부르면 같은 승인 번호다. 같은 의도를 다른 호출로 다시 부르면 같은 의도 차단에 걸려 거절되고, 모델에게는 승인 카드와 토스증권 앱을 확인해 달라고 안내하게 한다.
- 실행 도구를 직접 부른 호출은 지금처럼 `RISK_NOT_OPEN` 이다. `ToolPolicyDecision` 의 금융 차단은 바꾸지 않는다.
- 승인 API 는 저장 위험도가 `FINANCIAL` 인 줄을 `ConnectorFinancialApproval` 로 보낸다. 상시 허락과 대화 허락을 함께 보낸 요청은 입력 오류다.

토스 서버는 `prepare_trade`, `create_order`, `cancel_order` 셋을 등록하고 `modify_order` 는 등록하지 않는다.
manifest 의 `execution_guard.operations` 도 두 도구만 선언한다.

#### 허용 목록 항목에 사용자를 함께 적어 한 계좌를 한 사용자에게만 연다

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| 하루 합계를 (계좌, KST 날짜) 단위로도 묶는다 | 가족이 한 계좌를 함께 연결해도 상한이 한 번만 적용된다 | 다른 사용자의 줄을 그 사용자의 데이터 key 로 열어야 한다. 사용자 경계를 넘는 복호화가 생긴다 |
| **허용 목록 항목을 `계좌 순번:사용자 메일` 로 적는다** | 한 계좌의 주문이 한 사용자의 하루 합계에만 쌓인다. 남의 줄을 열지 않는다 | 가족이 한 계좌를 함께 주문하지 못한다 |

소유자가 둘째를 골랐다(「한 계좌는 한 사용자만」).

- 항목은 `<계좌 순번>:<사용자 메일>` 이다. 계좌 순번은 숫자뿐이라 첫 `:` 에서 나눈다. 메일은 대소문자를 가리지 않고 비교한다.
- 형식이 틀리거나, 같은 계좌가 두 번 나오면 기동을 멈춘다. 잘못 넣은 값이 조용히 닫히거나 열리지 않게 한다.
- 준비, 승인, claim 이 실행 scope 의 계좌와 함께 그 줄의 사용자를 보고, 그 계좌의 항목이 그 사용자의 메일일 때만 지난다.
- 하루 합계는 지금처럼 사용자 단위다. 계좌가 한 사용자에게만 열리므로 계좌 단위 합계는 만들지 않는다.

#### 금액 주문은 환율로 바꾸지 않고 USD 상한과만 견준다

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| `orderAmount` 를 환율로 원화로 바꿔 원화 상한과 견준다 | 상한이 하나다 | 토스의 환율 API 는 참고용 표시 환율이고 체결 환율을 보장하지 않는다. 승인과 claim 사이에 환율이 바뀌면 같은 주문의 판정이 달라진다. 환율 조회가 실패하면 판정할 수 없다 |
| **통화마다 따로 둔 상한(`max-order-amount-usd`, `max-daily-amount-usd`)과 견준다** | 저장한 실행 원문만으로 판정이 정해진다. 외부 값에 기대지 않는다 | 원화와 달러 합계를 하나로 묶지 못한다 |

둘째를 고른다. 두 USD 상한은 이미 있다.

- 한 건 상한은 `orderAmount` 그대로, 하루 합계는 같은 날 USD 주문의 `orderAmount` 와 `수량 × 가격` 을 더해 본다.
- 가격이 없는 주문은 금액을 미리 알 수 없어 닫는다. 수량을 준 `MARKET` 주문이 그렇다. 금액 주문은 `orderAmount` 가 곧 금액이므로 이 규칙에 걸리지 않는다.
- 원화 상한이 0 이어도 USD 주문은 USD 상한만 본다. 통화별 상한은 서로를 열거나 닫지 않는다.

#### 소수점 거래는 미국 `MARKET` 금액 주문으로만 연다

공식 명세 1.2.24 의 `OrderCreateRequest` 는 `oneOf` 두 갈래다.

- 금액 갈래(`OrderCreateAmountBased`)는 `symbol`, `side`, `orderType=MARKET`, `orderAmount` 를 받는다. 미국 시장 전용이고 매수와 매도를 모두 받는다. `timeInForce` 와 `price` 는 없다.
- 수량 갈래의 소수 수량은 미국 `MARKET` 매도에만 허용되고 소수 6자리까지다. 지정가와 매수, 국내의 소수 수량은 `400 invalid-request` 다.
- 금액 주문과 소수 수량 주문은 정규장 시작부터 정규장 종료 1시간 전까지만 접수한다. 그 밖은 `422` 다.
- 명세는 금액 주문의 최소 금액과 소수 자리 제한을 적지 않는다. 서버가 판정하고, 거절은 `FAILED` 로 남는다.

소수 수량 매도는 가격이 없어 위 상한 규칙에 닫힌다. 소수점 매도도 금액 주문(`side=SELL`)으로 한다.
소수 수량 지정가는 명세가 막으므로 커넥터도 준비에서 거절한다.

#### 승인 카드는 저장한 summary 와 실행 scope 의 계좌를 보인다

- 카드는 저장한 summary 의 종목, 방향, 수량이나 금액, 가격, 통화, 주문 유형, 정규화를 보인다.
- 계좌는 summary 의 끝 네 자리가 아니라 저장 scope 의 `account_seq` 로 보인다. 그 값이 실제 전송 계좌이고, 승인과 claim 이 연결의 공개 칸과 허용 목록에 다시 대조한다.
- summary 를 열지 못하면 승인 단추를 그리지 않고 거절만 남긴다. 서버의 승인도 같은 snapshot 을 열지 못하면 거절한다.
- 위험도가 `FINANCIAL` 인 PENDING 줄에 요약이 없어도 승인 단추를 그리지 않는다. 옛 서버나 응답 경로에서 요약이 빠져도 인자만 보고 승인하지 않게 한다.
- 금융 줄은 다른 줄과 묶지 않고 한 장씩 그린다. 「모두 승인」 에는 지금처럼 넣지 않는다.
- 계좌 순번은 사용자에게 익숙한 값이 아니다. 허용 목록에 그 순번을 적은 운영자와 연결 화면의 계좌 선택지로 대조한다. 끝 네 자리를 Control Plane 이 계산하지 못하는 한계를 감수한다.

### 결과

- 개방 PR 의 머지 뒤에도 key 파일, 허용 목록, 0 이 아닌 상한이 없으면 금융 전송은 0회다.
- 미국 금액 주문은 즉시 체결될 수 있어 같은 주문으로 취소를 확인하지 못한다. 취소의 실제 확인은 소유자가 정하는 별도 지정가 주문으로 한다.
- 정정(`modify_order`)과 조건주문 쓰기는 이 결정으로 열리지 않는다. 열 때 이 ADR 의 가로채기 조건과 관문의 동작 제한을 함께 넓힌다.
- 테스트 통과는 실제 거래 성공이 아니다. 배포 뒤 첫 실제 호출은 [토스증권 커넥터](../features/tossinvest-connector.md#첫-실제-호출-절차) 의 절차를 따른다.
