## ADR-20261007: backend 통합 검사는 Spring 컨텍스트 하나를 함께 쓰고, 설정과 대역은 검사마다 바꿔 끼운다

- **status**: `accepted`
- Date: 2026-10-07
- **결정**: backend 의 Spring 통합 검사는 공통 메타 주석 `@BackendIntegrationTest` 하나로 컨텍스트를 함께 쓴다.
  `./gradlew test` 가 띄우는 컨텍스트는 3개 이하로 둔다.
  - 검사마다 달라야 하는 운영 설정은 컨텍스트를 새로 띄우지 않고, 운영 코드가 읽는 「현재 설정」 을 검사가 바꾼다([ADR-20261007 / live-properties](ADR-20261007-live-properties.md)).
    검사는 선언형 주석 `@OverrideProperties` 로 값을 정하고, 공통 확장이 검사 전에 적용하고 검사 뒤에 기동 값으로 되돌린다.
  - Hermes 대역, 시험 시계, 백그라운드 작업 실행기, Hermes 클라이언트 mock, 검사가 동작을 바꾸는 운영 빈의 spy 는 기반 한곳에 둔다.
  - 검사 하나만 쓰던 mock 은 기반의 spy 로 올린다. 검사 하나만 쓰던 대역 설정은 꺼 두면 아무것도 하지 않는 대역으로 기반에 올리고, 그 검사가 켠다.
  - 검사 클래스 안에 `@MockitoBean`, `@MockitoSpyBean`, `@Import`, `@TestPropertySource`, `@DynamicPropertySource` 를 두지 않는다. 구조 규칙으로 확인한다.
  - 컨텍스트를 함께 쓰는 검사 사이의 격리는 JUnit 확장 하나가 맡는다.
- **맥락**:
  - 2026-10-07 측정에서 `@SpringBootTest` 검사 141개(MySQL 태그 제외)가 컨텍스트를 77번 띄웠다.
    기동 합계가 약 64초에서 78초로, 검사 클래스 시간 합계의 절반 가까이였다.
  - 컨텍스트가 나뉜 까닭은 한 가지가 아니었다. 클래스마다 둔 같은 모양의 Hermes 대역 설정 38종,
    `@MockitoBean` 16종, `@MockitoSpyBean` 20종, 속성 30개 키, 웹 환경 차이, 클래스마다 둔 `@DynamicPropertySource` 가 함께 컨텍스트를 나눴다.
  - 컨텍스트 하나가 힙을 약 30MB 쥔다. 보존 상한 32 에서는 1g 힙이 GC 뒤에도 거의 찼고,
    시간 상한이 짧은 검사가 흔들리고 `OutOfMemoryError` 로 컨텍스트를 띄우지 못했다(PR #223 에서 상한을 16 으로 낮춰 막았다).
  - 먼저 기반 주석으로 대역과 웹 환경만 모으고, 기동 설정이 다른 검사는 이름 있는 변형으로 따로 두었다.
    기동은 79번에서 40번으로 줄었지만 서로 다른 컨텍스트가 38개 남았고, Full GC 는 main 의 2번에서 6번에서 8번 사이로 늘었다.
    보존 상한 16 인데도 실행 끝 무렵 컨텍스트 37개가 힙에 살아 있었다. 밀려나 닫힌 컨텍스트가 메모리에서 풀리지 않는 것이다.
    기반의 spy 를 빼면 Full GC 가 1번으로 줄어 spy 가 닫힌 컨텍스트를 붙잡는 것으로 보이지만, 붙잡는 경로는 확정하지 못했다.
  - 남은 38개의 대부분은 기동할 때 읽는 `@ConfigurationProperties` 값이 다른 것이었다. 운영 코드는 그 값 대부분을 기동 뒤에도 요청마다 읽는다.
- **대안 기각**:
  - **기동 설정이 다른 검사를 이름 있는 변형 컨텍스트로 따로 둔다.** 위 측정대로 컨텍스트가 38개 남고, 닫힌 컨텍스트가 풀리지 않아 힙이 오히려 더 찼다.
  - **보존 상한을 낮추거나 힙을 올린다.** 닫힌 컨텍스트가 풀리지 않으면 상한을 낮춰도 남는 수가 줄지 않는다(상한 8 에서도 Full GC 뒤 935MB). 힙을 올리면 원인을 덮을 뿐이다.
  - **닫힌 컨텍스트를 붙잡는 경로를 찾아 끊는다.** 경로를 확정하지 못했고, 끊어도 기동 38번은 그대로다. 컨텍스트를 닫을 일을 없애면 그 경로가 문제되지 않는다.
  - **`hermes.run-timeout` 과 살펴보기 `max-duration` 의 검사 기본값을 올린다.** `hermes.run-timeout` 은 스트림 대기, 재기동 정리, 사용자 자리를 쥐는 상한의 기본값으로도 쓰여 다른 검사의 의미와 시간이 바뀐다. 그 값을 바꾸는 검사만 `@OverrideProperties` 로 바꾼다.
- **결과**:
  - 얻는 것:
    - 기동이 한두 번으로 줄고 컨텍스트를 닫을 일이 없어, 닫힌 컨텍스트가 힙을 붙잡는 문제가 생기지 않는다.
    - 새 검사가 대역 설정을 복사하지 않는다. 값만 다른 검사가 컨텍스트를 늘리지 않는다.
  - 감당할 것:
    - **검사가 띄운 백그라운드 작업은 그 검사 안에서 끝난다.** 공통 확장이 검사가 끝날 때 그 검사가 띄운 작업을 모두 join 한다([ADR-20261007 / background-tasks](ADR-20261007-background-tasks.md)).
      시간을 추측해 기다리지 않는다. 상한은 멈춘 작업을 잡는 데만 쓰고, 넘으면 남은 작업의 이름과 함께 그 검사를 실패로 둔다.
    - **검사가 바꾼 설정과 대역 상태는 검사 뒤에 되돌린다.** 공통 확장이 설정을 기동 값으로, `StubHermesRunsClient` 와 시험 시계와 기반의 꺼 둔 대역을 처음 상태로 되돌린다. Mockito mock 과 spy 는 Spring 이 검사마다 초기화한다.
    - **검사는 앞 검사가 남긴 데이터에 기대지 않는다.** 스키마가 검사 클래스마다 새로 만들어지지 않는다. 고정된 유일 값을 쓰는 검사는 지운 것을 먼저 내보내거나 값을 검사마다 새로 만든다.
    - **운영 빈이 JVM 메모리에 두는 캐시는 다음 검사에 남는다.** 보관 시간을 test profile 에서 짧게 두거나 시험 시계로 지나가게 한다.
    - **기반의 spy 는 모든 통합 검사에서 spy 다.** 그 빈의 메서드를 `verify(...)` 의 matcher 사이에서 부르면 Mockito 가 matcher 수를 잘못 센다. mock 에서 spy 로 올린 빈은 정하지 않은 메서드가 실제로 돈다.
    - **기반에 대역을 더하면 모든 검사가 바뀐다.** 꺼 둔 상태에서 아무것도 하지 않아야 하고, 더할 때는 전체 검사로 확인한다.
- **적용 범위**: `backend/src/test` 의 Spring 통합 검사. MySQL 태그 검사의 기준 클래스는 이 결정 밖이다. 쓰는 방법은 [`docs/backend/testing.md`](../backend/testing.md) 가 갖는다.
