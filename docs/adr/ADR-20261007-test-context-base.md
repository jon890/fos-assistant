## ADR-20261007: backend 통합 검사는 공통 기반 컨텍스트 하나를 함께 쓰고, 기동 설정이 다른 검사만 변형을 둔다

- **status**: `accepted`
- Date: 2026-10-07
- **결정**: backend 의 `@SpringBootTest` 검사는 공통 메타 주석 `@BackendIntegrationTest` 하나로 Spring 컨텍스트를 함께 쓴다.
  Hermes 대역, 시험 시계, 웹 환경, 자주 쓰는 Mockito mock 과 spy 를 그 주석 한곳에 모은다.
  기동할 때 정해지는 운영 설정이 달라야 하는 검사만 이름 있는 변형으로 컨텍스트를 따로 둔다.
  운영 설정을 검사 때문에 실행 중에 바꿀 수 있게 만들어 컨텍스트를 하나로 합치지는 않는다.
  컨텍스트를 함께 쓰는 검사 사이의 격리는 JUnit 확장 하나가 맡는다.
- **맥락**:
  - 2026-10-07 측정에서 `@SpringBootTest` 검사 141개(MySQL 태그 제외)가 컨텍스트를 77번 띄웠다.
    기동 합계가 약 64~78초로, 검사 클래스 시간 합계의 절반 가까이였다.
  - 컨텍스트가 나뉜 까닭은 한 가지가 아니었다. 클래스마다 둔 같은 모양의 Hermes 대역 설정 38종,
    `@MockitoBean` 16종, `@MockitoSpyBean` 20종, 속성 30개 키, 웹 환경 차이, 클래스마다 둔 `@DynamicPropertySource` 가 함께 컨텍스트를 나눴다.
  - 컨텍스트 하나가 힙을 약 30MB 쥔다. 보존 상한 32 에서는 1g 힙이 GC 뒤에도 거의 찼고,
    시간 상한이 짧은 검사가 흔들리고 `OutOfMemoryError` 로 컨텍스트를 띄우지 못했다(PR #223 에서 상한을 16 으로 낮춰 막았다).
  - 컨텍스트들은 H2 메모리 DB 하나를 함께 쓴다. `create-drop` 이라, 새 컨텍스트가 뜨거나 밀려난 컨텍스트가 닫힐 때 스키마가 다시 만들어지거나 지워진다.
  - 따로 둘 수밖에 없는 차이는 대부분 기동할 때 읽는 `@ConfigurationProperties` 값이다.
    백그라운드 작업 켜기(위임 깨우기, 추천 질문, memory 제안), 사용자 실행 한도, 암호화 끄기, 살펴보기의 시간 상한이 그렇다.
- **대안 기각**:
  - **컨텍스트 하나로 모든 검사를 돌린다.** 위 운영 설정을 실행 중에 바꿀 수 있는 값으로 만들어야 한다.
    운영 설계를 검사에 맞추는 일이고, 바꾼 값이 다음 검사에 남는 새 누수 경로가 생긴다.
  - **`hermes.run-timeout` 과 살펴보기 `max-duration` 을 검사 기본값으로 올려 살펴보기 검사를 기반에 합친다.**
    `hermes.run-timeout` 은 한 번에 받는 경로의 스트림 대기 상한, 재기동 정리의 기다림 상한,
    끝났는지 모르는 run 의 사용자 자리를 쥐는 상한의 기본값으로도 쓰인다.
    올리면 그 값에 기대는 다른 검사의 의미와 시간이 바뀐다.
  - **기반에 Hermes 대역만 두고 spy 는 각 검사에 남긴다.** spy 대상 조합마다 컨텍스트가 하나씩 남아 10개 안팎이 더 뜬다.
  - **보존 상한만 낮춘다.** 힙은 막지만, 밀려난 컨텍스트를 다시 띄우는 일이 늘고 기동 시간은 줄지 않는다.
  - **검사 하나만 쓰는 대역도 기반에 둔다.** 모든 검사의 동작이 바뀐다. 그런 대역은 그 검사의 `@Import` 로 남기고 변형으로 센다.
- **결과**:
  - 얻는 것:
    - 기동 횟수가 절반 아래로 준다. 2026-10-07 측정에서 77번이 39번이 됐고(보존 상한 16 에서 다시 뜬 하나 포함), 검사 클래스 대부분이 기반 하나를 함께 쓴다.
      남은 서로 다른 컨텍스트는 대부분 기동 설정 변형과 검사 하나만 쓰는 mock 이다.
    - 서로 다른 컨텍스트가 38개로 줄었지만 모두 보존하면 1g 힙에 들어가지 않는다. 보존 상한은 다시 뜨는 수와 Full GC 수를 측정해 정하고, 근거는 `backend/build.gradle.kts` 의 주석에 둔다.
    - 새 검사가 대역 설정을 복사하지 않는다.
  - 감당할 것:
    - **검사가 띄운 백그라운드 작업은 그 검사 안에서 끝난다.** turn 과 위임, 살펴보기는 가상 스레드에서 돈다. 끝나지 않은 작업은 다음 검사가 넣어 둔 대역 응답을 가져가거나 호출 횟수를 바꾼다.
      공통 확장이 검사가 끝날 때 그 검사가 띄운 작업을 모두 join 한다([ADR-20261007 / background-tasks](ADR-20261007-background-tasks.md)).
      시간을 추측해 기다리지 않는다. 상한은 멈춘 작업을 잡는 데만 쓰고, 넘으면 남은 작업의 이름과 함께 그 검사를 실패로 둔다.
    - **대역 상태는 검사마다 비운다.** 공통 확장이 검사 전후에 `StubHermesRunsClient` 와 시험 시계를 되돌린다. Mockito mock 과 spy 는 Spring 이 검사마다 초기화한다.
    - **검사는 앞 검사가 남긴 데이터에 기대지 않는다.** 스키마가 검사 클래스마다 새로 만들어지지 않는다. 고정된 유일 값(에이전트 code 등)을 쓰는 검사는 지운 것을 먼저 내보내거나 값을 검사마다 새로 만든다.
    - **기반의 spy 는 모든 통합 검사에서 spy 다.** 정하지 않으면 실제 동작이지만, 그 빈의 메서드를 `verify(...)` 의 matcher 사이에서 부르면 Mockito 가 matcher 수를 잘못 센다. 값은 먼저 지역 변수로 받는다.
    - **기반에 대역을 더하면 모든 검사가 바뀐다.** 더할 때는 전체 검사로 확인한다.
- **적용 범위**: `backend/src/test` 의 Spring 통합 검사. MySQL 태그 검사의 기준 클래스는 이 결정 밖이다.
  기반이 mock 으로 바꾼 빈의 실제 구현이 필요한 검사(실제 HTTP 서버로 Hermes 사건 스트림을 읽는 `SkillViewStreamTest`)도 `@SpringBootTest` 로 따로 둔다. 쓰는 방법은 [`docs/backend/testing.md`](../backend/testing.md) 가 갖는다.
