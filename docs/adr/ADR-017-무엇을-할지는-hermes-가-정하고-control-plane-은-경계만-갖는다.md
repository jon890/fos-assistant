## ADR-017: 무엇을 할지는 Hermes 가 정하고 Control Plane 은 경계만 갖는다

- **status**: `accepted`
- Date: 2026-09-18
- [ADR-016](ADR-016-다중-에이전트-조율은-control-plane이-맡는다.md) 의 조율 주체를 바꾼다.
  경계에 대한 결정은 그대로 둔다.

### 결정

**Control Plane 은 에이전트가 무엇을 할 수 있는지를 정하고,
Hermes 는 그 범위 안에서 무엇을 할지를 정한다.**

| 누가 | 무엇을 갖나 |
| --- | --- |
| Control Plane | 사용자 확인, 에이전트 접근 권한, Memory 접근 권한, credential 경계, 에이전트 목록, 실행 기록, 부모와 뿌리 관계, 사용량과 비용, 실행 사건과 화면 |
| Hermes | 추론, 도구 사용 판단, Task 분해, 자식 생성, 병렬 실행, 중간 결과 해석, 결과 종합 |

**Control Plane 은 workflow engine 이 되지 않는다.**

다른 전문 에이전트를 부르는 것은 Control Plane 이 MCP 도구로 연다.
그 도구를 부를지 말지와 어느 에이전트를 부를지는 **Hermes 가 정한다.**

### 맥락

ADR-016 은 Task 분해와 에이전트 선택과 병렬 실행을 Control Plane 이 맡기로 했다.
그 결정으로 `ResearchAndBuildFlow` 하나를 만들어 기반이 서는 것을 확인했다.

| 확인한 것 | |
| --- | --- |
| 자식 실행이 부모와 같은 사용자의 것으로 남는다 | 확인 |
| 자식마다 Memory 를 다시 조립한다 | 확인 |
| 부모와 자식이 한 나무로 그려진다 | 확인 |
| 실행마다 사용량이 따로 기록된다 | 확인 |

**그 실험은 성공했고, 그것을 넓히는 것이 문제다.**

`CareerFlow` 와 `TravelFlow` 와 `InterviewFlow` 를 Java 코드로 더하기 시작하면
이 저장소가 workflow engine 이 된다.
Task 보드와 의존 그래프와 재시도를 만들게 되고,
그것은 Hermes 가 이미 갖고 발전시키는 것을 다시 만드는 일이다.

ADR-016 자신이 그 대가를 적어 두었다.

> Kanban이 이미 가진 Task 보드, scheduler와 재시도를 Control Plane에 새로 만들어야 한다.

### 두 종류의 위임을 나눈다

| 무엇 | 언제 | 누가 만드나 |
| --- | --- | --- |
| `delegate_task` | 같은 전문 에이전트 안에서 임시 일꾼이 필요할 때 | Hermes 가 자기 안에서 |
| `agent_delegate` | 다른 전문 에이전트를 불러야 할 때 | Control Plane 을 거쳐 |

앞은 Hermes 의 기능을 그대로 쓴다.
조사와 검토처럼 오래 남을 필요가 없는 자식이 여기 해당한다.

뒤는 profile 이 달라진다.
profile 마다 SOUL 과 스킬과 도구와 모델과 provider 와 credential 이 다르므로
**Control Plane 을 거치지 않으면 경계가 무너진다.**

### `agent_delegate` 가 하는 것

**Control Plane 은 어느 에이전트를 부를지 판단하지 않는다.**
프롬프트를 보고 낱말로 고르는 규칙을 두지 않는다.

Hermes Chief 가 `agent_code` 와 목표를 정해 부르고,
Control Plane 은 아래만 검사한다.

- 그 에이전트가 있는가
- 지금 요청자가 그것을 쓸 수 있는가
- credential 경계가 맞는가
- 동시 실행 한도 안인가
- Memory 접근 범위가 맞는가

그 뒤 **서버가 가진 바인딩에서** profile 을 꺼낸다.
모델의 출력과 요청 본문이 profile 이나 credential 을 정하지 못한다.
이 규칙은 ADR-016 에서 그대로 가져온다.

자식 실행은 부모의 Memory 문자열을 복사하지 않는다.
**원래 요청자를 기준으로 Memory 를 다시 조립한다.**

### 이 경로는 이미 돌고 있다

Control Plane 이 Hermes 에 MCP 도구를 여는 길은 새로 만드는 것이 아니다.
`memory_read` 가 그 경로이고 실제로 도는 것을 확인했다.
`agent_delegate` 는 같은 자리에 도구를 하나 더 두는 것이다.

profile 의 도구 허용 목록도 그 모양으로 이미 바뀌어 있다.

### 거절한 대안

- **Control Plane 이 Flow 를 계속 더한다.**
  흐름마다 Java 코드가 늘고, 새 조합을 쓰려면 배포해야 한다.
  Hermes 가 추론으로 정할 수 있는 것을 코드로 굳히는 것이다.
- **Hermes Kanban 으로 옮긴다.**
  Kanban 은 오래 걸리고 재시도가 필요하고 프로세스가 죽어도 남아야 하는 일에 맞는다.
  대화 한 번의 조율과는 쓰임이 다르다.
  **지금 우선순위가 아니다.** 그런 일이 실제로 필요해질 때 다시 본다.
- **Control Plane 이 낱말로 에이전트를 고른다.**
  규칙이 늘수록 맞지 않고, 무엇을 골랐는지 설명하지 못한다.
  Hermes 가 에이전트 목록과 설명을 보고 고르는 편이 낫다.

### 결과

얻는 것

- 새 에이전트 조합을 만드는 데 배포가 필요 없다. Chief 가 그때그때 정한다
- Hermes 가 delegation 을 발전시키면 그것이 그대로 우리 것이 된다
- 경계는 ADR-016 이 세운 자리에 그대로 있다
- 다른 profile 호출이 top-level 실행이므로 사용량이 실행마다 남는다

감당할 것

- **도구 호출은 비싸다.** 도구를 부르는 턴 하나가 그 시점 프롬프트 하나만큼 든다.
  Chief 가 여러 번 부르면 그만큼 곱이 쌓인다
- **재귀를 막아야 한다.** 부른 에이전트가 다시 부를 수 있다.
  `root_execution_id` 가 만드는 나무의 깊이로 Control Plane 이 막는다
- **동시 실행 한도를 함께 쓴다.** Chief 가 자식을 기다리는 동안 그 턴이 자리를 여럿 차지한다
- **`delegate_task` 자식의 Memory 상속을 실측해야 한다.**
  소스에서 `skip_memory=True` 로 만드는 것을 보았으나 실행으로 확인하지 못했다.
  **확인하지 않은 상속 동작에 사용자 privacy 를 맡기지 않는다**
- **자식 토큰이 부모 사용량에 들어온다고 가정하지 않는다.**
  v0.21.0 에서는 들어오지 않았다. 버전이 오를 때마다 다시 측정한다

### `ResearchAndBuildFlow` 의 자리

**참조 구현으로 유지하고 넓히지 않는다.**
기반이 서는 것을 보여 준 실험이고 그 역할은 끝났다.

새 흐름을 Java 로 더하지 않는다.
