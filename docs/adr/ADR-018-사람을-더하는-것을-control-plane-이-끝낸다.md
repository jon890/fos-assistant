# ADR-018. 사람을 더하는 것을 Control Plane 이 끝낸다

## 상태

Accepted

## 맥락

사람 하나를 더하려면 지금 셋을 해야 한다.

1. Google 동의 화면의 테스트 사용자에 주소를 더한다
2. 환경 변수 `ASSISTANT_ALLOWED_EMAILS` 에 주소를 더하고 웹을 다시 띄운다
3. 홈서버에 들어가 Hermes profile 을 만들고 key 파일을 놓은 뒤, 관리 화면에서 에이전트를 등록한다

세 번째가 문제다. **관리자가 홈서버에 들어갈 수 있어야 사람이 늘어난다.**
[`prd.md`](../prd.md) 는 「사람이 늘어도 같은 방식으로 는다」를 지키는 것으로 적었고,
「한 사람을 더하는 것이 관리자의 판단 하나로 끝나야 한다」고 썼다.
지금은 그렇지 않다.

순서도 묶여 있다. 에이전트를 자기만 보는 것으로 만들려면 주인이 있어야 하는데,
주인은 그 사람이 로그인하기 전에는 존재하지 않는다.
그래서 관리자가 두 번 나눠 들어와야 한다.

Hermes 를 HTTP 로만 부르는 것이 [ADR-001](ADR-001-hermes를-런타임으로-두고-core를-고치지-않는다.md) 의 전제다.
profile 을 만드는 것은 Hermes 컨테이너 안에서 명령을 돌리는 일로 알고 있었고,
Control Plane 이 그것을 할 길이 없다고 보았다.

**그 전제가 틀렸다는 것을 실측으로 확인했다.**
Hermes 대시보드에 profile 관리 API 가 있고, 기계용 인증 자리가 따로 열려 있다.
확인한 내용은 [`hermes-integration.md`](../hermes-integration.md) 의
「profile 을 HTTP 로 만드는 길」이 갖는다.

## 결정

**사람을 더하는 일을 Control Plane 이 끝까지 한다.**

관리자가 화면에서 이메일과 이름과 profile 이름을 적으면 Control Plane 이 셋을 이어서 한다.

1. 허용 목록에 넣는다
2. Hermes 대시보드를 HTTP 로 불러 profile 을 만든다
3. key 를 만들어 그 profile 의 `.env` 와 우리 key 디렉터리에 같이 쓴다

그 사람이 처음 로그인할 때 `app_user` 와 에이전트가 함께 생긴다.

이를 위해 넷을 바꾼다.

| 무엇 | 어떻게 |
| --- | --- |
| 로그인 허용 목록 | 환경 변수에서 데이터베이스 표로 옮긴다 |
| Hermes 대시보드 인증 | plugin 을 하나 붙여 경로 둘만 토큰으로 연다 |
| key 디렉터리 | Control Plane 이 쓸 수 있게 붙인다 |
| 에이전트 생성 시점 | 첫 로그인으로 옮긴다 |

### 여는 경로를 둘로 한정한다

plugin 이 `register_token_route` 로 여는 것은 `POST /api/profiles` 와 `PUT /api/env` 다.
그 함수는 경로 문자열이 정확히 같은지만 보므로, 등록하지 않은 경로는 열리지 않는다.
**profile 을 지우고 이름을 바꾸는 경로는 열지 않는다.**

다만 만들다 실패했을 때 되돌리려면 삭제가 필요하다.
그 경로는 **만든 직후에 그 이름만 등록하고 되돌린 뒤 거둔다.**
`register_token_route` 는 기동 뒤에도 부를 수 있다.

### `clone_from` 을 쓰지 않는다

`POST /api/profiles` 에 `clone_from` 을 주면 본뜬 profile 의 `API_SERVER_KEY` 까지 복사된다.
key 하나로 두 profile 이 열리는 것을 실측했다.
profile 을 사람마다 나누는 뜻이 사라지므로 이 경로에서는 쓰지 않는다.

## 버린 대안

### 홈서버에 provisioning 창구를 새로 둔다

Control Plane 이 부를 좁은 HTTP 창구를 하나 만들고 그것이 Hermes CLI 를 돌리는 안이다.
Hermes 에 이미 그 API 와 인증 자리가 있는 것을 확인하기 전에 세운 안이다.
컨테이너가 하나 늘고 우리가 그것을 계속 유지해야 한다.
**Hermes 가 이미 주는 것을 다시 만드는 일이라 버렸다.**

### 대시보드의 사람용 로그인 비밀값을 Control Plane 에 넘긴다

지금 대시보드에 걸린 인증은 번들 `basic` provider 이고, 그 세션 토큰은 상태를 두지 않는 서명 값이다.
그 비밀값을 받으면 Control Plane 이 세션을 스스로 만들어 plugin 없이 같은 API 를 부를 수 있다.
조사가 실제로 그 방법을 썼다.
**대시보드의 모든 API 가 함께 열려서 버렸다.** 경로를 좁힐 수 없다.

### docker socket 을 Control Plane 에 준다

컨테이너가 홈서버의 root 권한을 얻는다. 검토만 하고 버렸다.

### 지금 방식을 두고 스크립트 하나로 줄인다

사람이 하는 걸음을 하나로 묶는 안이다.
줄어들기는 하지만 홈서버에 들어가는 일이 남는다.
**「관리자의 판단 하나로 끝난다」를 만족하지 못해 버렸다.**

### 에이전트를 관리자가 더할 때 함께 만든다

주인 없는 에이전트를 만들어 두고 로그인할 때 주인을 채우는 안이다.
주인 없는 자기 전용 에이전트라는 상태가 생기고,
그 상태에서 실행이 들어오면 무엇을 해야 하는지 정해야 한다.
**상태를 늘리지 않으려고 버렸다.** 첫 로그인에 만들면 그 상태가 없다.

## 얻는 것

- 사람을 더하는 데 홈서버 접근이 필요 없다
- 관리자가 두 번 나눠 들어오지 않는다
- profile 이름과 key 파일 이름이 어긋날 자리가 사라진다. 한 곳에서 함께 만든다
- Hermes core 를 고치지 않는다. plugin hook 만 쓴다

## 감당할 것

### Control Plane 이 Hermes 를 고칠 수 있게 된다

지금까지 Control Plane 은 Hermes 에 실행을 시키고 결과를 읽기만 했다.
이제 profile 을 만든다. **Control Plane 이 뚫리면 Hermes 의 격리 단위를 만들 수 있다.**

여는 경로를 둘로 한정하는 것이 이 값을 줄이는 수단이다.
읽기와 삭제와 이름 변경은 열지 않는다.

### Control Plane 이 key 를 쓸 수 있게 된다

key 디렉터리가 읽기 전용이었다. 쓰기로 바뀐다.
그 컨테이너가 모든 profile 의 key 를 읽을 수 있다는 것은 지금도 같지만,
이제 새 key 를 놓을 수도 있다.

**데이터베이스에 비밀값을 넣지 않는다는 규칙은 지켜진다.** key 는 파일에만 있다.

### Hermes 를 올릴 때 plugin 이 깨질 수 있다

`register_token_route` 와 `register_dashboard_auth_provider` 를 v0.21.0 에서 확인했다.
공개된 확장 지점이지만 우리가 정하는 것이 아니다.
Hermes 를 올릴 때 이 둘을 확인 목록에 넣는다.

### 첫 로그인에 에이전트가 안 생길 수 있다

에이전트를 만들려면 Hermes 에서 모델과 provider 를 읽어야 한다.
그때 Hermes 가 답하지 않거나 provider 를 비워서 주면 **에이전트를 만들지 않는다.**

그 사람은 들어오지만 고를 에이전트가 없다.
**관리자가 기존 에이전트 등록 화면에서 손으로 만든다.**
그 사람의 `app_user` 가 이미 있어 주인을 지정할 수 있다.

읽지 못한 값을 기본값으로 메우지 않는 이유는 하나다.
틀린 provider 로 만들어진 에이전트는 실행할 때마다 실패하고 그 원인이 화면에 드러나지 않는다.
만들지 않으면 없다는 것이 바로 보인다.

다시 시도하는 것을 요청 경로에 두지 않는다.
로그인 판정이 매 요청 도는 자리라, 거기서 Hermes 를 부르면 모든 요청이 그 응답을 기다리게 된다.

### 허용 목록이 비면 아무도 들어오지 못한다

환경 변수는 배포마다 다시 주어졌다. 표는 그렇지 않다.
데이터베이스를 새로 만들면 들어갈 길이 없고, 그때는 표에 직접 행을 넣어야 한다.

옮길 때 지금 쓰는 주소를 한 번 넣는다.
**그 절차는 비공개 저장소가 소유한다.** 이 저장소는 공개라 주소를 적지 않는다.
