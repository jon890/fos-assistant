## ADR-20261009 / skill-package: 스킬은 zip 묶음으로도 올리고, 스크립트는 실행 공간이 있는 에이전트에만 받는다

- **status**: `accepted`
- Date: 2026-10-09

### 결정

에이전트를 관리하는 사람은 스킬 하나를 zip 묶음으로 올린다. 묶음에는 `SKILL.md` 와 참고 파일, `scripts/` 가 함께 든다.
저장 자리와 게시 순서는 [ADR-034](../../backend/docs/adr/ADR-034-올린-스킬은-control-plane-이-버전-디렉터리에-쓰고-hermes-는-읽기만-한다.md) 그대로다.

1. **받기와 검사·저장을 나눈다.**
   받기는 묶음의 형식(zip)을 풀어 경로와 바이트의 목록을 만든다. 디스크에 풀지 않고 메모리에서 읽으며 상한에서 멈춘다.
   검사·저장은 그 목록만 보고 경로 규칙, 글 파일, 비밀 요청, 실행 공간, 크기를 판정한 뒤 기존 저장 경로를 탄다.
   GitHub 공개 저장소 가져오기는 받기만 새로 만들고 검사·저장을 그대로 쓴다.
2. **미리보기와 올리기는 두 번의 요청이고 서버에 임시 상태를 두지 않는다.**
   화면은 같은 zip 을 두 번 보낸다. 미리보기는 저장하지 않고 결과와 지금 버전의 지문을 준다.
   올리기는 그 지문을 함께 보내고, 그사이 지금 버전이 바뀌었으면 거절한다. 같은 이름의 스킬을 덮어쓰는 확인이 이 지문이다.
3. **`scripts/` 가 든 스킬은 실행 공간에서 스크립트를 돌릴 수 있는 에이전트에만 받는다.**
   그 에이전트의 API 도구에 `terminal` 이 켜져 있고, 그 profile 이 실행 공간 정책에 등록돼 있고, 정책에 스킬 루트가 있어야 한다.
   앞의 것은 Control Plane 이 보고, 뒤의 둘은 게시를 `require_sandbox` 로 보내 대시보드 plugin 이 판정한다.
   판정은 저장하는 그 스킬에만 한다. 함께 실리는 다른 스킬은 보지 않는다.
4. **실행 공간에는 그 profile 의 스킬 디렉터리 전체를 Hermes 와 같은 경로에 읽기 전용으로 붙인다.**
   plugin 이 실행 공간 설정을 쓸 때 `<스킬 루트>/<profile>` 을 더한다. 버전 디렉터리 하나가 아니라 profile 디렉터리다.
5. **이전 버전은 스킬마다 하나를 버전 디렉터리 밖에 둔다.**
   이미 있는 스킬을 저장하면, 게시에 성공한 뒤 바뀌기 전의 스킬을 `<스킬 루트>/<profile>/.previous/<스킬>` 에 쓴다.
   「이전 버전으로」 는 그 스킬과 지금 스킬을 맞바꿔 저장한다. 한 번 더 누르면 다시 돌아온다.

### 대체된 부분

[ADR-034](../../backend/docs/adr/ADR-034-올린-스킬은-control-plane-이-버전-디렉터리에-쓰고-hermes-는-읽기만-한다.md) 의 「스크립트는 받지 않는다」 와 대안 기각의 「스크립트까지 받는다」 를 이 결정이 대체한다.
기각 당시에는 셸 도구가 Hermes 프로세스 안에서 돌았다.
지금은 [ADR-086](ADR-086-셸과-파일-도구는-사용자별-docker-실행-공간에서만-돈다.md) 에 따라 사용자별 docker 실행 공간에서 돌고, 기본 에이전트에 셸이 켜져 있다.

### 맥락

- 사람들이 가진 스킬은 Claude 용으로 만든 묶음이 많다. 화면 편집기로 파일을 하나씩 옮기는 일이 번거롭고 `scripts/` 는 옮길 길이 없었다.
- Hermes 의 docker 실행 공간은 `skills.external_dirs` 를 `/root/.hermes/external_skills/<n>` 에 붙인다. 이 마운트는 **컨테이너를 만들 때의 버전 경로**다.
  plugin 이 컨테이너 키를 셸 설정의 지문으로 정하고 스킬 경로는 지문에 없다. 스킬을 다시 올려도 같은 컨테이너가 옛 버전을 본다([`hermes/sandbox.md`](../hermes/sandbox.md) 의 「이름과 재사용」).
- `skill_view` 가 모델에게 알려 주는 스킬 디렉터리는 Hermes 쪽 경로다. 실행 공간의 `external_skills/<n>` 경로가 아니다. 모델이 그 경로로 스크립트를 부르면 실행 공간에서 찾지 못한다.
- 실행 공간 정책에 없는 profile 의 셸은 Hermes 프로세스에서 돈다(local). 거기서 올린 스크립트를 돌리면 다른 profile 의 `.env` 에 닿을 수 있다.
- Control Plane 은 profile 이 실행 공간 정책에 있는지 읽는 경로가 없다. plugin 이 `require_sandbox` 로 거절하는 길은 이미 있다.
- 버전 디렉터리는 profile 의 스킬 전체를 담고, 표식 있는 최근 3개만 남는다. 다른 스킬을 몇 번 저장하면 한 스킬의 이전 내용이 사라진다.

### 대안 기각

- **서버에 올린 묶음을 잠시 두고 확인 번호로 저장한다.** 임시 묶음의 수명과 정리, 다른 사람이 같은 번호로 저장하는 경우를 다뤄야 한다. 묶음 상한이 작아 두 번 보내는 비용이 작다.
- **실행 공간의 `external_skills/<n>` 마운트에 기댄다.** 위 두 까닭으로 다시 올린 스크립트가 보이지 않고, 모델이 받은 경로와 다르다.
- **스킬 경로를 컨테이너 키 지문에 넣어 게시마다 새 컨테이너를 만든다.** 저장할 때마다 `/root` 가 새것이 되어 설치한 패키지와 셸 이력이 사라지고, 옛 컨테이너가 쌓인다.
- **스크립트를 사용자의 `/workspace` 에 복사한다.** Control Plane 이 실행 공간 디렉터리에 쓸 길이 없고, 모델이 고칠 수 있어 화면에 보인 스크립트와 도는 스크립트가 달라진다.
- **스크립트 판정을 함께 실리는 모든 스킬에 한다.** 셸을 끈 에이전트는 스크립트 스킬이 하나라도 있으면 다른 스킬을 하나도 고치지 못한다. 셸이 꺼지면 스크립트는 돌지 않을 뿐 위험이 늘지 않는다.
- **이전 버전을 버전 디렉터리에서 찾는다.** 표식 있는 최근 3개만 남아 다른 스킬의 저장에 밀려 사라진다.
- **묶음 상한을 편집기와 다르게 둔다.** 묶음으로 올린 스킬을 편집기에서 고치면 저장이 거절된다. 파일 수, 파일 크기, 합계 상한은 편집기와 같다.

### 결과

- 얻는 것:
  - 가진 스킬을 그대로 올리고, 덮어쓰기 전에 바뀌는 파일을 본다
  - 실행 공간의 스크립트는 다시 올린 내용이 다음 호출부터 보이고, 모델이 받은 경로 그대로 돈다
  - GitHub 가져오기가 받기 하나만 더하면 된다
  - 잘못 올린 스킬을 한 번에 되돌린다
- 감당할 것:
  - 운영이 실행 공간 정책에 스킬 루트를 넣고 socket proxy 가 그 마운트를 허용해야 스크립트 스킬이 올라간다. 그 전에는 모든 에이전트에서 거절한다
  - 옛 plugin 은 스킬 게시의 `require_sandbox` 를 판정하지 않고 받는다. 판정을 가진 plugin 을 Control Plane 보다 먼저 배포한다
  - 실행 공간이 그 profile 의 모든 버전과 이전 버전을 읽는다. 같은 profile 의 것이라 새로 열리는 것은 없다
  - 스크립트를 실행 공간에서 돌린 결과는 에이전트의 다른 셸 명령과 같은 경계 안에 있다. 망과 자원 상한은 [ADR-086](ADR-086-셸과-파일-도구는-사용자별-docker-실행-공간에서만-돈다.md) 이 갖는다
  - 셸을 나중에 끄거나 profile 이 정책에서 빠져도 이미 올린 스크립트 스킬은 남는다. 셸이 꺼지면 돌지 않고, local 로 돌아가면 다른 셸 명령과 같은 위험이다
  - 운영이 정책에 `skill_root` 를 넣은 뒤에는 스킬 디렉터리가 있는 실행 공간 profile 마다 다음 셸 설정 쓰기(도구 저장, 기본 도구 적용, 커넥터 바인딩, scripts 스킬 게시)에서 컨테이너 키가 바뀐다. scripts 가 있는지는 보지 않는다. 그 profile 의 `/root` 가 한 번 새것이 되고 옛 컨테이너가 남는다
