## ADR-20261116 / run-steer: 답이 도는 중 입력창 글은 대기 줄에 먼저 두고 루트 실행에 steer 하며, 넣지 못한 글은 말풍선을 붙인 채 대기 줄로 되돌린다

- **status**: `accepted`
- Date: 2026-11-16
- **decision-type**: `architecture`
- **areas**: `security, data, operations`
- **현재 규칙의 원본**: 설계 [`docs/features/chat/design.md`](../features/chat/design.md), 스펙 [`docs/features/chat/spec.md`](../features/chat/spec.md)(사용자 확인 2026-11-16), 기능 파일 [`docs/features/chat.md`](../features/chat.md) 의 「대기열과 중지」
- [ADR-048](ADR-048-응답-중에-보낸-메시지는-control-plane-이-쌓아-두고-다음-turn-으로-합쳐-보낸다.md) 의 「적용 범위」 가 미룬 steer 를 그 대기열 위에 얹는다. ADR-048 의 나머지 결정은 그대로다

### 운영 결정 대체 (2026-11-21)

운영에서는 `assistant.chat.steer.enabled` 를 끈다. 답이 도는 동안 보낸 글은 [ADR-048](ADR-048-응답-중에-보낸-메시지는-control-plane-이-쌓아-두고-다음-turn-으로-합쳐-보낸다.md) 의 대기열에 두고 답이 끝나면 다음 차례로 보낸다. 방향을 바꾸려면 「중지」 를 누른 뒤 이어 보낸다. [대화의 「응답 중 대기열」](../features/chat.md#응답-중-대기열) 결정이 이 ADR 의 운영 활성화 결정을 대체한다. 아래 규칙은 설정을 다시 켰을 때 적용한다.

### 결정

**설정이 켜져 있으면 답이 도는 중 대화 주인이 입력창에 쓴 글을 Control Plane 이 대기 줄에 먼저 저장하고, 대기 줄이 비어 있을 때만 그 대화의 루트 실행에 Hermes `steer` 를 보낸다.**

| 항목 | 정한 것 |
| --- | --- |
| 받음 | 대기 글을 빼고 그 turn 의 답 위에 `USER` 말풍선 행을 「전달됨」 으로 한 트랜잭션에 저장한다 |
| 거절(409·400·500) | 대기 줄에 그대로 둔다. ADR-048 대로 다음 turn 으로 간다 |
| 모름(시간 초과·연결 실패) | 「전달됐는지 확인 못 함」 말풍선을 남기고 같은 글을 멈춘 대기 줄에 둔다 |
| 돌아온 글(`pending_steer`) | 말풍선을 「다음 차례로 넘어감」 으로 바꾸고 말풍선 번호를 붙인 대기 글로 줄 앞에 되돌린다. 다음 turn 은 새 말풍선을 만들지 않는다 |
| 중지·결과 모름 | 그 turn 의 말풍선을 모두 줄 앞에 되돌려 멈춘다. 상태는 「전달됐는지 확인 못 함」 이고, 중지한 결과의 `pending_steer` 와 맞는 글만 「전달 안 됨」 이다(2026-11-17 개정) |
| 대상 | 입력창의 글만. 사진, 스킬 커맨드, 맡김, 카드 답, 위임 결과, 알림 줄은 끼우지 않는다. 위임한 자식에는 보내지 않는다 |
| 끄기 | 서버 설정 하나. 기본은 꺼짐이고, 배포 뒤 운영 왕복을 확인하고 켠다 |

### 맥락

대기열(ADR-048)은 글을 잃지 않지만 turn 이 끝난 뒤에야 모델에 닿는다. 도구를 여러 번 부르는 긴 turn 에서 사용자가 조건을 바꾸려면 중지해야 했다.
Hermes `steer` 는 도는 실행의 다음 도구 묶음 뒤에 글을 넣는다. 그러나 `running` 일 때만 받고, 「모델이 읽었다」 는 사건을 주지 않으며, 넣지 못하고 끝나면 중지한 경우까지 `pending_steer` 로 돌려준다(처음 소스 조사로는 중지 때 버린다고 봤으나 운영 확인 2026-11-17 에서 돌려줬다, [`hermes/docs/hermes-contract.md`](../../hermes/docs/hermes-contract.md) 의 steer 절).
그래서 글은 Control Plane 이 끝까지 들고 있어야 한다.
steer 글은 원래 요청과 같은 사용자 권한 표식으로 모델에 들어간다. 사람이 쓰지 않은 글이 이 길로 가면 프롬프트 주입 통로가 된다.

### 대안 기각

- **대기열 없이 steer 만 쓴다**: 거절·돌아온 글·중지로 넣었는지 모르는 글을 받아 둘 자리가 없다.
- **돌아온 글을 따로 「보낼 말풍선」 목록에 둔다**: 다음 turn 을 정하는 자리가 `NextTurnDispatcher.tryNext` 밖에 하나 더 생긴다(ADR-048 의 「자리는 하나」). 재시작과 멈춤도 다시 만들어야 한다.
- **말풍선을 새 표에 둔다**: 테이블을 늘리지 않기로 했다(사용자 결정 2026-11-01). 이력·암호화·지우기를 다시 이어야 한다.
- **시간 초과를 거절로 본다**: Hermes 가 받았다면 같은 지시가 다음 turn 에서 또 실행된다(예: 주문).
- **대기 줄에 글이 있어도 끼운다**: 나중 글이 먼저 들어가 고침의 순서가 뒤집힌다.
- **자식 실행에도 넣는다**: Hermes API 에 경로가 없고 Hermes core 를 고치지 않는다.

### 결과

- 얻는 것
  - 중지하지 않고 도는 실행의 다음 단계를 바꾼다. 받지 못한 글은 지금 대기열과 같은 결과가 된다.
  - 다음 turn 을 정하는 자리, 재시작 확인, 멈춤이 ADR-048 그대로다.
- 감당할 것
  - 「전달됨」 은 Hermes 가 받아 둔 것이지 모델이 읽었다는 뜻이 아니다.
  - 중지나 결과를 모르는 끝에서는 이미 들어간 글도 되돌린다. 사람이 다시 보낼지 고른다. 중지한 결과가 돌려준 글은 「전달 안 됨」 으로 구분해 보인다.
  - Hermes 가 마지막 정리에서 슬롯을 비운 뒤 상태를 바꾸기 전에 받은 글은 사라질 수 있다. 운영 확인으로 본다.
  - 루트 run 과 turn 잠금이 같은 JVM 메모리에 있다. ADR-048 처럼 서버 한 대를 전제로 한다.
  - steer 말풍선이 낀 답은 다시 생성하지 않는다. 다시 생성을 없애면 이 제약도 사라진다.
- **확인 방법**: `SteerService` 시험과 대기열·중지 통합 시험, 배포 뒤 스펙의 「운영 확인 항목」
