## ADR-20261008: 매일 깨우기가 끝나면 동의한 사용자의 살펴보기 한 번에 가치 평가와 행동 정책을 한 번만 잇는다

- **status**: `accepted`
- Date: 2026-10-08

### 맥락

문제 찾기, 가치 평가, 행동 정책, 판단 피드백은 각각 만들어졌다([ADR-093](ADR-093-문제-찾기는-살펴보기-결과의-문제-후보로-받고-control-plane-이-근거와-중복을-결정적으로-검사한다.md), [ADR-20261007 / value-evaluation](ADR-20261007-value-evaluation.md), [ADR-20261007 / autonomy-policy](ADR-20261007-autonomy-policy.md), [ADR-20261007 / decision-feedback](ADR-20261007-decision-feedback.md)).
그러나 가치 평가와 행동 정책은 관리자 화면의 단추나 따로 부른 API 로만 돈다.
매일 깨우기([ADR-085](ADR-085-매일-깨우기는-예약-작업을-다시-쓰고-다섯-칸-보고를-지금-화면에-올린다.md))가 문제 후보를 남겨도 그 후보는 평가되지 않고 사용자에게 가지 않는다.
루프 전체가 실제 사용자에게 쓸모 있는지 보려면 사람이 부르지 않아도 한 번 이어져야 한다.

### 결정

**이음매는 `ProactiveLoopCoordinator` 하나다.**
매일 깨우기(`CheckTrigger.SCHEDULED`)로 돈 살펴보기가 끝나 점검 대화의 잠금을 푼 뒤, 기존 `ValueEvaluationService.evaluate` 와 `AutonomyPolicyService.decide` 를 차례로 부른다.
두 서비스의 검사, 저장, 실패 처리, 자동 실행은 지금 그대로다. 이음매는 언제 부를지와 그 시도의 기록만 갖는다.
새 workflow engine, 대기열, 재시도 스케줄러를 만들지 않는다.

**사용자가 에이전트마다 켜야 돈다. 설치 설정도 켜져 있어야 한다.**
설치 설정 `assistant.proactive-loop.enabled` 와 사용자와 에이전트마다의 설정 줄이 모두 켜져 있을 때만 돈다. 둘 다 기본은 꺼짐이다.
사용자는 끄거나 정한 시각까지 쉬게 할 수 있다. 읽기 전용 자동 실행은 지금처럼 `assistant.autonomy.execution-enabled` 와 사용자 동의가 따로 연다.

**원천 살펴보기 하나에 시도는 한 번이다.**
시도 줄 `proactive_loop_run` 의 원천 살펴보기 칸을 유일 제약으로 두고, 평가를 부르기 전에 저장한다.
기동할 때 끝나지 않은 시도는 실패로 닫고 다시 부르지 않는다. 자동 실행은 기존 실행 키가 한 번만 연다.
그래서 서버가 도중에 멈춰도 평가, 판정, 자동 실행, 알림이 두 번 나가지 않는다.

**매일 깨우기만 잇는다.** 단추로 연 살펴보기(`MANUAL`)와 자동 실행이 연 살펴보기(`AUTONOMY`)는 잇지 않는다.
자동 실행의 결과가 다시 자동 실행을 부르는 연쇄가 생기지 않는다.

**한 시도의 비용은 정해져 있다.**
평가 한 번(모델 호출 한 번)과 판정 한 번이고, 자동 실행은 판정당 많아야 하나이며 기존 살펴보기 상한 안에서 돈다.
사용자마다 하루 시도 수에 상한을 둔다. 모델이 실패하면 평가는 `FALLBACK` 이고 모든 판정은 `IGNORE` 다. 다른 모델로 다시 부르지 않는다.

**사용자에게 보이는 것은 `SURFACE` 와 `ASK_APPROVAL` 판정뿐이다.**
지금 화면 「내 차례」 카드의 항목으로 보이며 알림 줄(`notification`)은 만들지 않는다. `IGNORE` 는 아무것도 만들지 않는다.
항목의 「받아들임」 은 반응을 기록할 뿐이다. 할 일, 승인 줄, 쓰기 실행을 만들지 않는다.
`ASK_APPROVAL` 도 승인 카드를 만들지 않는다. 외부에 쓰는 일은 지금처럼 커넥터 도구 승인 경로만 거친다.

**반응은 판정 줄의 판단 피드백 사건으로 남긴다.**
보인 판정은 `autonomy_decision:<번호>` 에 `SURFACED` 를 남기고, 사용자의 단추와 숨기기, 미루기도 같은 열쇠로 남긴다.
그래서 export 의 결정 하나(`check:<번호>`)에서 후보, 평가, 판정과 규칙 버전, 반응, 실행 결과가 이어진다. 후보 글과 모델 설명은 복제하지 않는다.

### 버린 대안

- **매일 깨우기의 살펴보기 turn 안에서 평가와 판정을 부른다**: 점검 대화의 잠금을 쥔 채 모델을 다시 부른다. 자동 실행은 같은 점검 대화의 잠금이 필요해 시작하지 못한다.
- **평가와 판정을 예약 작업의 새 종류로 띄운다**: 발화, 한도, 복구를 다시 맞춰야 하고 원천 살펴보기와의 연결이 시각으로만 남는다.
- **설치 설정 하나로만 켠다**: 사용자가 자기 루프를 끄거나 쉬게 할 길이 없다.
- **`SURFACE` 를 알림 줄이나 점검 대화의 알림 줄로 보낸다**: 숨기기와 미루기, 반응을 받을 자리가 없고 조용한 시간 규칙을 다시 정해야 한다.
- **중단된 시도를 기동할 때 다시 부른다**: 모델 비용이 다시 들고, 판정이 이미 남았으면 같은 원천에서 판정이 두 번 생긴다.

### 감당할 것

- 살펴보기가 끝난 뒤 시도 줄을 저장하기 전에 서버가 멈추면 그 살펴보기는 잇지 않는다. 다음 날 깨우기가 새 원천이다.
- 시도 줄은 원천 살펴보기에 묶인다. 점검 대화를 지우면 살펴보기와 함께 지워진다.
- 하루 상한은 같은 사용자의 시도 줄을 잠그고 센다. 다른 사용자의 시도와는 견주지 않는다.
- 실제 provider 의 판단은 매번 다를 수 있다. 합성 평가와 섞이지 않게 시도 줄과 평가의 provider 기록으로 구분한다.
