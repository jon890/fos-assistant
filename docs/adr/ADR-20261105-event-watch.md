## ADR-20261105 / event-watch: 사건 감지는 Control Plane 이 실행 밖에서 플러그인의 목록을 식별자와 받은 시각, 라벨만 받아 보고, 새 항목이 있을 때만 읽기 경계의 살펴보기를 연다

- **status**: `accepted`
- Date: 2026-11-05
- 스펙은 [`docs/features/proactive/spec.md`](../features/proactive/spec.md)(사용자 확인 2026-11-05), 설계는 [`design.md`](../features/proactive/design.md) 가 갖는다.
- [ADR-080](ADR-080-먼저-살펴보기는-점검-대화의-turn-하나로-돌고-읽기-경계를-control-plane-이-강제한다.md) 의 읽기 경계와 [ADR-085](ADR-085-매일-깨우기는-예약-작업을-다시-쓰고-다섯-칸-보고를-지금-화면에-올린다.md) 의 깨우기 제한 위에 계기 하나를 더한다.
- **개정(2026-11-05, 사용자 결정)**: 사건 감지는 사용자의 메인 에이전트에서 돈다. 그래서 사건 실행은 켜 둔 toolset 으로 시작을 막지 않고, 아래 「결정」 의 사건 실행의 도구 판정으로 위험한 도구 호출만 막는다. 분야 지침 스킬도 보지 않는다. 처음 결정의 「셸·파일·코드 실행 도구가 켜진 에이전트는 격리 실행 공간 설정이 켜지기 전까지 사건 감지를 켜지 못한다」 는 이 개정이 대체한다

### 맥락

지금까지 사용자 메일을 읽는 길은 모델 실행 안의 플러그인 도구뿐이었다. 그 호출은 실행마다 Control Plane 이 판정하고, 모델이 받은 글은 `<external-data>` 로 감싼다.
새 메일이 왔는지 알려고 15분마다 모델을 깨우면 비용이 들고, 메일이 오는 즉시 깨우는 push 는 Control Plane 을 바깥에 열어야 한다.
그래서 모델 없이 새 메일의 존재만 확인하는 길이 필요하다. 이 길은 실행 밖에서 사용자 메일의 메타데이터를 읽는 새 신뢰 경계다.

### 결정

**목록 조회는 대시보드 plugin 의 `POST /api/connectors/<id>/events` 하나다.**

| 경계 | 정한 것 |
| --- | --- |
| 누가 부르나 | Control Plane 만. 서비스 토큰이 필요하고 그 경로는 `execute` 와 같은 profile 확인(관리 표식, 설치 기록)을 거친다 |
| 무엇을 부르나 | 플러그인이 `assistant.json` 의 `event_watch` 로 선언한 조회 도구 하나. `tools` 에 `READ` 로 선언한 도구여야 하고, 인자는 선언이 정하며 Control Plane 이 주는 값은 조회 시작 시각 하나다 |
| 무엇을 돌려주나 | 항목마다 식별자, 받은 시각, 라벨 셋. 제목, 보낸 사람, 요약, 본문은 응답과 로그에 싣지 않는다 |
| 누구의 값으로 | 요청한 profile 에 그 사용자가 설치한 연결의 값. Control Plane 은 켜진 바인딩의 에이전트 profile 만 보낸다(rule-47) |
| 언제 켜지나 | 사용자가 그 에이전트의 바인딩에서 켰고, 연결과 바인딩이 `READY` 이고, 조회 도구가 살펴보기 트리에서 승인 없이 불리는 도구(`READ`, 승인 `none`)일 때. 같은 연결에서는 바인딩 하나만 켠다 |

**새 항목이 있을 때만 계기 `EVENT` 의 살펴보기를 연다.**
그 살펴보기는 에이전트의 쓰기 허용과 상관없이 읽기 경계로 돈다(`writes_allowed = false`). 메일 내용은 모델이 붙은 플러그인의 읽기 도구로 읽고, 그 호출은 지금처럼 Control Plane 이 판정한다.
결과 블록의 「알릴 항목」 은 입력에 실린 식별자만 받는다. 알림 본문에는 개수만 둔다. 알림 테이블은 평문이라 메일 내용이 남지 않게 한다.

**상태는 바인딩 줄에 둔다.** 새 테이블을 만들지 않고, 확인마다 줄을 쌓지 않으며 마지막 결과만 덮어쓴다.

**사건 실행의 도구 판정(2026-11-05 개정).** Hermes 에는 우리가 쓸 수 있는 실행마다의 toolset 칸이 없고(RoomLink 전용 실행 정책은 `bot_room` 이 필요하고 `/v1/runs` 본문으로 줄 수 없다) `subagent_start` hook 은 자식 생성을 막지 못한다. 그래서 막는 자리는 도구 호출 하나다.

| 경계 | 정한 것 |
| --- | --- |
| 무엇을 묻나 | fos-ctx 의 `pre_tool_call` 이 안전 목록(`web`, `vision`, `todo`, `skills` 의 읽기 도구와 도구 찾기. 로컬 경로의 사진 읽기는 뺀다) 밖의 도구 호출마다 묻는다. 플러그인 도구, Control Plane MCP 도구, 첨부 원본 도구는 지금의 판정 길이 이미 살펴보기 경계를 건다 |
| 어디에 묻나 | Control Plane 의 `POST /internal/hermes/tool-guard`. profile 토큰으로 인증하고 루트 session, session, 도구 이름, 도구 호출 id 를 서명한다 |
| 무엇을 막나 | 자식 등록이나 루트에서 도는 실행으로 풀린 트리가 사건 살펴보기인 호출. 풀리지 않으면 점검 대화의 session 이거나 그 profile 에 사건 살펴보기가 도는 동안의 호출 |
| 판정을 받지 못하면 | 막는다. hook 안의 예외도 잡아 막는다. 옛 Control Plane 의 404 만 한 배포 동안 통과시킨다 |
| 판정 plugin 이 없으면 | 깨우지도 켜지도 않는다. 깨울 때마다 그 바인딩의 설치 상태가 판정 plugin(`tool_guard`)을 보이는지 읽는다 |

### 결과

- Control Plane 은 사용자 메일의 식별자와 받은 시각, 라벨을 15분마다 받는다. 그 값은 바인딩 줄의 상태(`event_watch_state`)에 겹침 구간만큼만 남고 로그에 싣지 않는다
- 플러그인 하나가 선언만 더하면 같은 틀로 원천이 늘어난다. 대시보드 plugin 과 Control Plane 은 서비스 이름을 모른다(rule-65)
- (2026-11-05 개정) 셸·파일·위임 도구가 켜진 메인 에이전트에서도 사건 감지를 켠다. 메일 본문의 숨은 지시가 그 도구를 부르면 호출이 거절된다. 그 대신 안전 목록 밖의 도구는 보통 대화에서도 호출마다 Control Plane 왕복이 하나 늘고, Control Plane 이 답하지 않으면 막힌다
- Hermes 를 올릴 때 내장 도구 목록이 바뀌면 계약 테스트(`hermes/tests/test_tool_guard_contract.py`)가 실패한다. 새 도구는 안전 목록에 넣지 않는 한 사건 실행에서 막힌다

### 감당하는 위험

- **메일 주입이 성공하면 다른 메일 내용이 `web` 도구로 밖에 샐 수 있다.** 사건 실행은 외부인이 보낸 메일이 깨우는 사람 없는 실행이다. 메일 본문의 숨은 지시가 모델을 속이면 메일 읽기 도구로 다른 메일을 읽고 `web` 도구의 주소에 실어 보낼 수 있다. 읽기 경계(ADR-080)도 `web` 을 허용하고, 격리 실행 공간은 밖으로 나가는 요청을 막지 않는다. 도구 판정은 `web` 을 안전 목록에 둔다
- 사용자가 이 위험을 감수하고 `web` 이 켜진 에이전트도 사건 감지를 켜게 했다(2026-11-05). 남은 완화는 입력의 메일 글을 `<external-data>` 로 감싸고 따르지 말라고 지시하는 것, 플러그인 쓰기 금지, 결과 블록이 입력의 식별자만 알릴 항목으로 받는 것이다
- 실행마다 `web` 을 끄는 길이 생기면 이 결정을 다시 본다. 도구 판정이 생겼으므로 `web` 을 안전 목록에서 빼는 것만으로 막을 수 있다. 그 결정은 사용자가 한다
- `execute_code` 안의 도구 호출은 hook 에 session 이 오지 않아 판정하지 못하고 통과한다. 사건 실행 트리에서는 그 `execute_code` 가 막혀 이 길이 열리지 않는다. 운영 이미지에서 실제로 그런지는 배포 뒤 실측한다
- Hermes 가 plugin 을 불러오지 못하거나 hook dispatcher 자체가 실패하면 호출이 판정 없이 나간다(fail-open, [`hermes-contract.md`](../../hermes/docs/hermes-contract.md) 의 「막히는 것과 통과하는 것」). plugin 이 막을 수 없는 Hermes core 의 동작이다. 설치 상태의 `tool_guard` 는 파일만 보므로 import 실패를 알지 못한다. 배포 뒤 hook 로그로 확인한다
- 보통 대화에서도 안전 목록 밖의 도구는 호출마다 Control Plane 에 묻고, Control Plane 이 답하지 않으면 막힌다(fail-closed). 사용자가 이 영향을 감수했다(2026-11-05)
- `web_extract` 와 `vision_analyze` 의 주소 요청은 Hermes 의 내부망 차단(`allow_private_urls` 꺼짐)에 기댄다. 켜져 있으면 사건 실행이 내부 서비스에 GET 할 수 있다

### 다음 단계

- fos-ctx 의 옛 Control Plane 404 통과(`tool_guard.py`)는 이 개정의 Control Plane 이 운영에 올라간 뒤의 다음 fos-ctx 변경에서 지운다

### 대안 기각

- **15분마다 모델을 깨운다**: 새 메일이 없는 대부분의 확인이 비용이 된다
- **Google Pub/Sub push 를 받는다**: Control Plane 을 바깥에 열어야 한다. 예약 작업 문서가 바깥에 여는 결정을 미뤘다
- **기존 `call` 경로로 조회 도구를 부른다**: `call` 은 인자 없는 확인 도구만 받고 결과 전체를 돌려준다. 제목과 요약이 Control Plane 에 온다
- **목록 조회가 제목까지 받아 Control Plane 이 알릴지 정한다**: 실행 밖 경로가 메일 내용을 갖게 된다. 알릴지는 모델이 실행 안에서 정한다
- **(개정) 위험 toolset 이 켜진 에이전트를 계속 막는다**: 메인 에이전트는 셸·파일·위임 도구를 켜 두므로 사건 감지를 쓸 수 없다(사용자 결정 2026-11-05)
- **(개정) 막을 도구 이름 목록을 둔다**: Hermes 를 올려 생긴 새 도구가 판정 없이 열린다. 안전 목록을 둔다
- **(개정) `subagent_start` hook 으로 자식 생성을 막는다**: Hermes 가 그 hook 의 반환값을 버린다
- **(개정) 사건 실행 트리의 자식 등록을 거절한다**: 등록이 없으면 판정이 state.db 의 자식 줄에만 기댄다. 등록을 남겨 판정에 쓴다
- **예약 작업(`task`, `task_run`)에 상태를 둔다**: 발화마다 `task_run` 줄이 생기고, 「같은 연결에 하나뿐」 과 도구 허용은 바인딩 단위라 따로 맞춰야 한다
