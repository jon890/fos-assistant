## ADR-20261101 / proactive-suggestion: 먼저 살펴보기는 기억 위의 읽기 전용 깨우기와 제안 카드로 줄이고, 저장은 새 테이블 없이 할 일의 제안 상태와 기존 반응 기록으로 한다

- **status**: `accepted`
- Date: 2026-11-01
- 2026-11-01 사용자 결정(테이블은 최대한 늘리지 않고 기존 테이블을 활용한다)에 따라 처음 조사가 권고한 새 테이블 `proactive_suggestion` 을 만들지 않고 `follow_up` 의 `PROPOSED` 줄을 제안으로 쓴다.

### 결정

**먼저 살펴보기는 네 걸음만 남긴다.**

| 걸음 | 누가 | 하는 일 |
| --- | --- | --- |
| 1 | Control Plane | 매일 깨우기가 그 에이전트가 받는 기억에서 마지막으로 성공한 깨우기가 시작한 뒤에 바뀐 항목과 그것에 이어진 항목을 꺼내 입력에 싣는다 |
| 2 | 모델 | 그 목표와 관련된 변화를 읽기 도구로만 살펴본다 |
| 3 | 모델, Control Plane | 챙길 것이 있으면 제안을 낸다. Control Plane 은 소유와 크기만 검사해 `follow_up` 의 `PROPOSED` 줄로 저장하고 지금 화면에 카드로 보인다 |
| 4 | 사용자, Control Plane | 사용자의 반응(받아들임, 숨김, 미루기, 무응답)을 반응 기록에 남긴다. 기억 정비 루프가 이것을 신호로 읽는다. 기억을 직접 고치지 않는다 |

**Control Plane 이 갖는 것은 바뀌지 않아야 하는 안전 경계뿐이다.**
권한(기억 접근, 연결 권한), 쓰기 차단, 승인 카드, 실행 상한과 예산, 실행과 발화의 기록이다.
무엇이 중요한지, 언제 알릴지, 어떻게 묶어 제안할지는 모델이 정한다.
목표인지 최근 일인지, 중요도, 위험, 확신 같은 판단의 분류는 컬럼이나 enum 으로 만들지 않는다. 모델 출력의 자유 필드에 둔다.

**깨우기는 읽기만 한다. 실제 쓰기는 승인 카드만 거친다.**
제안을 받아들였다는 반응은 승인이 아니다. 외부 쓰기는 지금처럼 `connector_action` 의 승인 카드와 그때의 권한 재검사로만 연다.
모델이 다음 살펴보기를 스스로 이어 시작하는 경로는 두지 않는다. 지금의 `EXECUTE` 자동 실행은 없앤다.

**기억에서 꺼내는 것은 번호와 제목뿐이다.**
후보는 그 실행의 Memory 문맥에 싣는 항목, 곧 항상 싣는 항목과 색인 항목과 같은 판정을 지난 것뿐이다. 요청자의 읽기 권한, 에이전트가 받는 collection 과 민감도, 승인, 대체되지 않음을 모두 지나야 한다.
이어진 항목도 이 후보 안에서만 고른다. 연결이 있어도 에이전트가 받지 못하는 항목, 남의 항목, 대체된 항목은 싣지 않는다.
색인 항목의 본문은 모델이 번호로 `memory_read` 를 불러 읽고, 그 도구가 같은 권한을 다시 본다. 항상 싣는 항목의 본문은 이미 문맥에 있다.

#### 저장 모델

| 개념 | 저장 | 바꾸는 것 |
| --- | --- | --- |
| 제안과 근거 | `follow_up` 의 `PROPOSED` 줄 | 컬럼만 더한다 |
| 반응(노출, 열기, 받아들임, 숨김, 미루기, 복원, 결과) | `decision_feedback_event` | 컬럼만 더한다 |
| 실행과 실패, 비용 | `agent_execution` | 그대로 쓴다 |
| 깨우기 설정과 발화 | `task`, `task_run` | 그대로 쓴다. 사용자별 설정을 `task` 로 옮긴다 |
| 받아들인 할 일 | `follow_up` 의 `OPEN` 줄 | 제안 줄이 그대로 바뀐다 |
| 쓰기 승인 | `connector_action` | 그대로 쓴다 |

**제안은 할 일의 `PROPOSED` 줄이다.** [ADR-073](ADR-073-할-일은-에이전트가-제안하고-사람이-받아들인-것만-챙긴다.md) 이 이미 할 일을 에이전트가 제안하고 사람이 받아들이는 것으로 정했다. 받아들이면 같은 줄이 `OPEN` 이 되고, 거절하면 `REJECTED` 가 된다.
이미 있는 컬럼(`user_id`, `conversation_id`, `proposed_by_execution_id`, `title`, `status`, `accepted_at`)을 그대로 쓰고, `follow_up` 에 아래 컬럼만 더한다.

| 컬럼 | 제약 | 목적 |
| --- | --- | --- |
| `detail_json`, `detail_key_id` | nullable. 사용자 단위 암호화 본문과 key 식별자 | 제안 글, 목표·출처 참조, 근거, 모델의 자유 출력. 옛 분류 원문은 `legacy` 자유 필드에 둔다. 사용자가 직접 더한 할 일은 비어 있다 |
| `dedupe_key` | nullable, 서버 계산, `(user_id, dedupe_key)` UNIQUE | 같은 실행의 같은 결과를 다시 받아도 제안이 하나다. 실행 번호와 출력 안의 항목 식별자로 만든다 |
| `expires_at` | nullable | 받아들이지 않은 제안이 지금 화면에서 빠지는 시각. 받아들인 할 일에는 쓰지 않는다 |

사용자는 실행 소유자에서 서버가 정하고 요청 본문이 정하지 못한다. 대화를 지우면 그 대화의 제안 줄과 본문을 함께 지운다.

서버는 참조가 그 사용자의 것인지와 허용 크기만 검사한다. 근거 문구의 가치를 매기지 않는다.
서로 다른 날의 같은 뜻 제안을 합칠지는 모델이 정한다. 모델이 정한 자유 topic 값만으로 전역 중복을 강제하지 않는다.

`decision_feedback_event` 에 더하는 컬럼이다.

| 컬럼 | 목적 |
| --- | --- |
| `card_key` nullable | 같은 항목이 다른 카드에 있을 때 숨김과 미루기의 범위를 나눈다 |
| `until_at` nullable | 미루기가 끝나는 시각 |
| `event_key` nullable, `(user_id, event_key)` UNIQUE | 서버가 검증한 요청 키나 노출 키로 재전송을 하나로 합친다 |

`source_check_id`, `autonomy_decision_id` 컬럼은 옛 테이블과 함께 없앤다. 반응 기록에 판단 분류 컬럼이나 본문을 넣지 않는다.
지표는 모델·프롬프트 버전별 수락률, 무반응 비율, 정정률이다. 분모는 그 버전으로 만든 제안의 처음 노출 수이고, 무응답은 사건으로 남기지 않고 관측 기간 뒤 계산한다.

#### 숨김과 미루기를 반응 기록으로 옮기는 조건

지금의 판단 피드백 기록은 커밋 뒤 따로 넣고 실패를 삼킨다. 그대로는 숨김과 미루기의 원장이 될 수 없다.
그래서 `attention_control` 은 아래를 모두 구현한 단계에서만 없앤다. 구현하지 못하면 그 테이블을 남긴다.

- 숨김, 미루기, 복원은 사용자 줄을 잠그는 짧은 트랜잭션에서 사건을 반드시 저장하고, 실패하면 조작 API 도 실패한다
  - 구현(순서 5): 사용자 줄을 잠그지 않고 짧은 트랜잭션 하나에서 마지막 제어 사건을 읽고 사건을 넣는다. 같은 요청 키는 `event_key` 유일 제약이 하나로 합치고, 현재값은 가장 큰 사건 번호의 제어 사건이라 동시에 들어와도 마지막 사건이 하나로 정해진다. 사용자 줄 잠금은 user 모듈에 잠금 읽기를 더해야 해서 쓰지 않았다
- 승인, 기억, 할 일의 관측 사건은 지금처럼 본체 동작을 막지 않는 경로로 둔다. 같은 테이블을 쓰되 쓰기 계약을 나눈다
- `(user_id, card_key, subject_key, id)` 인덱스로 마지막 숨김·미루기·복원 사건을 읽는다
- 살아 있는 대상의 마지막 제어 사건은 지표 보관 기간이 지나도 지우지 않는다

#### 옮기는 순서

PR 하나가 한 걸음이다. 테이블에 데이터가 있다는 까닭만으로 변환 없이 지우지 않는다. 분류 원문은 과거 데이터로 옮기되 그 enum 을 남길 근거로 쓰지 않는다.

| 순서 | 내용 | 끝났다는 증거 |
| ---: | --- | --- |
| 2 | 새 읽기 경로. 깨우기가 기억에서 바뀐 항목과 이어진 항목을 꺼낸다. 기존 분류 로직이 아닌 계약 테스트를 먼저 고정한다 | 기억·연결 권한, 쓰기 도구 차단, 예산 중단과 실패 기록, 재기동 중복 발화 방지, 제안 없는 실행의 테스트 |
| 3 | 할 일의 제안 컬럼과 반응 컬럼. 새 제안 경로를 기능 스위치 뒤에 두고 사용자별 설정을 `task` 로 옮긴다 | 같은 사용자·에이전트의 설정 하나, 공유 에이전트의 사용자별 설정 보존, 같은 응답 재전송은 제안 하나 |
| 4 | 옛 발견과 문제 후보를 할 일의 `PROPOSED` 줄로 옮긴다. 이미 있는 할 일 줄은 그대로 둔다 | 제안별 사용자·대화·실행 연결, 기존 카드 링크와 반응 연결, 열린 할 일 중복 없음, 대화 삭제 뒤 본문 없음 |
| 5 | 노출과 반응을 한 테이블로 쓰고 숨김·미루기 경로를 옮긴다. 옛 제어 현재값도 처음 제어 사건으로 옮긴다 | 카드별 제어 독립, 상태가 바뀐 뒤 다시 보임, 미루기 만료와 복원, 동시 조작과 재전송, 보관 기간 뒤 숨김 유지 |
| 6 | 새 화면과 기록 경로로 바꾼 뒤 가치 평가, 네 수준, 자동 실행 동의, 다시 살펴보기 루프를 없앤다 | 승인 없이 외부 쓰기가 열리지 않음, 사라진 API·DTO·enum 참조 없음, 옛 실행·실패 이력 보존 |
| 7 | 옛 읽기·쓰기가 없음을 확인하고 열 개 테이블을 지운다 | MySQL 마이그레이션 검사, 사용자·대화·에이전트 정리 계약, CI |

지우는 테이블은 `proactive_autonomy_decision`, `proactive_check`, `proactive_check_finding`, `proactive_check_problem`, `proactive_loop_run`, `proactive_loop_setting`, `proactive_value_evaluation`, `user_autonomy_preference`, `attention_control`, `attention_event` 다.
`proactive_check` 가 갖던 실행 상태는 `agent_execution` 과 `task_run` 이 갖고, 깨우기 결과의 보고 본문은 대화 메시지의 보관 정책을 따른다.

**그룹 본체 테이블은 테이블 수를 줄이려는 목적만으로 새로 만들지 않는다.** 그룹의 수명이나 설정 관리 요구가 생길 때 따로 정한다.

### 배경

지금의 먼저 살펴보기는 발견과 문제 후보를 고정 필드로 받고, 가치 평가의 축과 행동 정책의 네 수준을 거쳐 자동 실행까지 잇는다.
그 판단 층이 테이블 일곱 개와 동의 테이블, 지금 화면의 제어 테이블 둘을 만들었다. 모델이 좋아져도 판단이 그 구조 안에 묶여 결과가 나아지지 않는다.
사용자는 Control Plane 을 얇은 안전 경계로 두고, 좋아졌는지는 판단 단계가 아니라 결과 지표로 보기로 했다.

### 대안 기각

- **지금 구조를 유지하고 컬럼만 줄인다**: 가치 평가와 정책이 남으면 자동 실행 동의와 재평가 루프도 남아 테이블이 줄지 않는다. 판단을 구조에 묶지 않는다는 결정과 어긋난다.
- **제안을 새 테이블 `proactive_suggestion` 에 둔다**: 처음 조사의 권고였다. 받아들인 뒤의 완료와 기한이 제안과 다른 수명이라는 까닭이었지만, 할 일은 이미 `PROPOSED` 와 `REJECTED` 로 제안의 수명을 갖고 받아들이면 같은 줄이 `OPEN` 이 된다. 2026-11-01 사용자 결정에 따라 테이블을 늘리지 않는다. 무응답과 완료는 상태와 `expires_at` 으로 나뉜다.
- **반응을 제안 테이블의 컬럼으로 둔다**: 노출, 숨김, 복원이 여러 번 일어나 마지막 값만으로는 첫 반응과 재노출을 읽지 못한다. 기억과 승인의 반응도 이미 반응 기록에 있다.
- **`attention_control` 을 남긴다**: 기능 차이는 없고 테이블이 하나 더 남는다. 위 조건을 구현하지 못하는 단계에서만 이 대안으로 돌아간다.
- **그룹 본체 테이블을 만들어 그룹 설정을 옮긴다**: 테이블이 줄지 않는다. 지금 그룹은 사용자의 `group_id` 값뿐이라 수명을 관리할 요구가 없다.

### 결과

얻는 것:

- 새 테이블 없이 테이블 열 개가 사라진다
- 모델과 프롬프트를 바꾸면 같은 지표로 바로 비교할 수 있다
- 안전 경계가 판단 구조와 떨어져 모델을 바꿔도 경계 테스트가 그대로다

감당할 것:

- 옮기는 동안 옛 경로와 새 경로가 함께 산다. 순서 3 의 기능 스위치가 꺼져 있는 동안 화면은 옛 경로를 쓴다
- 받아들이지 않은 제안이 할 일 목록에 섞이지 않게, 할 일을 읽는 모든 곳이 `PROPOSED` 를 지금처럼 따로 다뤄야 한다
- 반응에서 현재 숨김을 구하는 쿼리는 현재값 테이블보다 비싸다. 순서 5 에서 인덱스와 비용을 잰다
- 무엇이 목표인지 Control Plane 이 모르므로, 기억에 목표가 연결로 이어져 있지 않으면 깨우기가 놓칠 수 있다. 연결 정비는 기억 정비 루프가 맡는다
