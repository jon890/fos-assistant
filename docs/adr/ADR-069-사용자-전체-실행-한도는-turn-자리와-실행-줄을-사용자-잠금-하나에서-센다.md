## ADR-069: 사용자 전체 실행 한도는 turn 자리와 실행 줄을 사용자 잠금 하나에서 센다

- **status**: `accepted`
- **결정**: Control Plane 이 Hermes 에 제출하는 실행을 사용자마다 센다. 한 사용자가 동시에 쥘 수 있는 자리는 `assistant.user-execution.max-running`(기본 4)이다.
  세는 기준은 인증된 사용자다. 실행 줄의 `user_id` 와 turn 을 연 사용자를 쓰고 요청 본문의 값은 보지 않는다.

  한 사용자가 쥔 자리는 아래 셋의 합이다.

  | 자리 | 무엇 | 어디서 센다 |
  | --- | --- | --- |
  | turn 자리 | 열린 대화 turn 하나에 하나. 대화 잠금을 잡을 때 얻고 풀 때 돌려준다 | 프로세스 메모리 |
  | 실행 줄 | `RUNNING` 인 실행 줄 가운데 대화 turn 의 루트 줄이 아닌 것. 위임 자식, 흐름 단계, 추천 질문, Memory 제안이다 | 데이터베이스 |
  | 원격 종료 확인 자리 | 실행 줄은 끝났는데 Hermes 에서 그 run 이 끝났는지 확인하지 못한 실행 하나에 하나 | 프로세스 메모리 |

  **세고 자리를 만드는 것은 사용자 잠금 하나 안에서 한다.**
  turn 자리를 얻을 때와 실행 줄을 만들 때 모두 같은 잠금 안에서 셋을 더해 판정하고, 통과하면 그 잠금 안에서 자리를 만든다.
  실행 줄은 그 잠금 안에서 커밋까지 끝낸다. 그래서 실행 줄을 만드는 쪽은 트랜잭션 밖에서 부른다.

  **포화되면 기다리지 않고 거절한다.** 대기열을 두지 않는다.
  사용자가 보낸 turn 은 `USER_BUSY`(409)로 거절한다. 위임 자식은 기존 `BUSY` 도구 결과로 모델에 돌려준다.
  추천 질문과 Memory 제안은 사용자 자리를 `assistant.user-execution.background-reserve`(기본 1)만큼 남길 수 있을 때만 돈다. 남기지 못하면 이번에는 건너뛴다.

  **Hermes 에서 끝났는지 모르는 run 은 자리를 계속 쥔다.**
  대기 시간을 넘기거나 상태 조회가 실패해 실행 줄을 먼저 끝낸 경우가 여기 해당한다.
  실행 줄의 상태 계약([ADR-011](ADR-011-실행은-시작할-때-기록하고-끝날-때-갱신한다.md))은 그대로 두고, 메모리의 원격 종료 확인 자리로 쥔다.
  Hermes 에 중지를 한 번 보내고, 실행 조회가 끝났다거나 그 run 을 모른다(404)고 답할 때 돌려준다.
  `assistant.user-execution.remote-end-max-wait` 를 넘기면 경고 로그를 남기고 돌려준다.
- **맥락**: 기존 한도는 대화 하나에 turn 하나, 루트 하나에 위임 자식 4개, 서버 전체에 위임 16개였다.
  한 사용자가 여러 대화를 열고 대화마다 루트당 한도 안에서 위임하면 그 합이 Hermes 의 공유 listener 자리를 모두 차지할 수 있다([`hermes/concurrency.md`](../hermes/concurrency.md) 의 「동시 실행 한도는 listener 단위다」).
  listener 에는 profile 단위의 한도가 없어, 다른 사용자의 turn 이 같은 자리를 두고 다투다 429 로 실패한다.
  흐름은 Chief 의 루트 줄이 `SUCCEEDED` 가 된 뒤 자식이 돌고, 대화 turn 은 질문을 저장한 뒤에야 루트 줄이 생긴다.
  실행 줄만 세면 두 틈에서 그 turn 이 쥔 자리가 0 으로 보인다.
- **대안 기각**:
  - **실행 줄만 센다.** 흐름의 Chief 와 자식 사이, turn 을 연 뒤 루트 줄이 생기기 전에 그 turn 이 세어지지 않는다.
    그 틈에 다른 turn 이 자리를 가져가면 이미 시작한 흐름이 중간에 실패한다.
    turn 자리는 대화 잠금과 수명이 같아, 이미 검사로 지키는 잠금 해제 경로에 반환을 붙일 수 있다.
  - **메모리 semaphore 하나로 센다.** 반환을 실행이 끝나는 모든 경로에 하나씩 붙여야 한다.
    시작 실패, 완료, 취소, 시간 초과, 기동 정리 가운데 하나라도 빠지면 자리가 새거나 두 번 돌아온다.
    실행 줄은 그 경로들이 이미 상태를 적는 곳이라, 줄을 세면 반환 경로를 따로 두지 않는다.
  - **대기열에 넣고 자리가 나면 돌린다.** 대기 크기와 대기 시간, 취소 계약을 함께 정해야 하고, 부모가 자리를 쥔 채 자식 자리를 기다리면 교착이 생긴다. 첫 단계는 거절로 충분하다.
  - **실행 줄을 원격 종료가 확인될 때까지 `RUNNING` 으로 둔다.** 사용자는 이미 시간 초과를 받았는데 사용량 화면은 도는 중으로 보이고, 기동 정리가 그 줄을 대화 turn 으로 다시 잡는다. 기록 계약을 바꾸는 범위가 이 결정보다 크다.
- **결과**:
  - 얻는 것:
    - 한 사용자가 여러 대화와 위임으로 쥘 수 있는 Hermes 자리가 `max-running` 을 넘지 않는다.
    - 부모가 자식 자리를 기다리지 않으므로 교착이 없다. 모델은 `BUSY` 를 받고 직접 하거나 실패를 처리한다.
    - 추천 질문과 Memory 제안이 사용자의 마지막 자리를 가져가 그 사용자의 turn 이 거절되는 일이 없다.
  - 감당할 것:
    - **Control Plane 한 대를 전제로 한다.** turn 자리, 원격 종료 확인 자리, 사용자 잠금이 모두 프로세스 메모리에 있다. 여러 대로 늘리면 이 셋을 데이터베이스 잠금이나 공유 저장소로 옮겨야 한다.
    - **원격 종료 확인 자리는 재기동하면 사라진다.** 그 실행 줄은 이미 끝나 있어 기동 정리([ADR-061](ADR-061-재기동-때-남은-실행은-hermes-에-물어-정하고-도는-실행에는-다시-붙는다.md))도 다시 보지 않는다. 그 run 이 Hermes 에서 끝날 때까지 한도가 그만큼 덜 센다.
    - Hermes 의 native 하위 에이전트와 cron 은 Control Plane 이 제출하지 않아 세지 못한다.
    - 이 한도는 Hermes 에 동시에 맡기는 실행 수의 상한이다. OS 격리나 CPU, 메모리, 비용의 상한이 아니다.
- **적용 범위**: 기존 대화 잠금, 루트당 위임 한도, 서버 전체 위임 한도는 그대로 둔다. 네 한도의 관계와 진입점 목록은 [`backend/execution-limit.md`](../backend/execution-limit.md) 가 갖는다.
