## ADR-005: 기존 개인 저장소의 스택을 그대로 쓴다

- Status: Accepted
- Date: 2026-09-17

### 맥락

`fos-accountbook-backend` 와 `fos-accountbook` 이 이미 가족 단위 서비스로 돌고 있다.
Spring Boot 4 와 Java 21, MySQL, Flyway, Next.js 16, NextAuth Google OAuth 를 쓴다.
배포는 `fos-home-infra` 가 서비스별 compose 와 nginx 로 맡는다.

새 스택을 고르면 배포와 운영 방식을 하나 더 익혀야 한다.

### 결정

같은 스택을 쓴다.
저장소는 하나로 두고 안에서 `backend/` 와 `web/` 으로 나눈다.

기존 저장소에서 쓰지만 이번에 빼는 것도 있다.

| 뺀 것 | 이유 |
| --- | --- |
| QueryDSL | 지금 질의가 단순해 Spring Data 로 충분하다 |
| p6spy | SQL 로그가 필요한 시점에 넣는다 |
| Caffeine | 캐시할 대상이 아직 없다 |
| Checkstyle | 설정을 옮기는 비용보다 얻는 것이 적다. 코드가 자리 잡으면 넣는다 |

새로 더한 것은 없다.
Redis, 메시지 큐, vector 데이터베이스는 쓰지 않는다.
Hermes 가 실행을 맡으므로 우리 쪽에 비동기 작업 큐가 필요하지 않다.
Runs API 자체가 제출과 조회로 나뉘어 있다.

### 거절한 대안

- 프런트와 백엔드를 저장소 둘로 나누는 방식은
  초기에 계약이 자주 바뀌어 두 저장소를 계속 맞춰야 하므로 지금은 쓰지 않는다.
  계약이 굳으면 그때 나눈다.
- Python 으로 백엔드를 만드는 방식은 Hermes 와 언어가 같다는 것 말고 이점이 없다.
  우리는 Hermes 를 HTTP 로만 쓰고, 운영과 익숙함은 Java 쪽이 앞선다.

### 결과

배포는 `fos-home-infra` 의 기존 방식을 그대로 따른다.
Spring Boot 4 가 Jackson 3 을 쓴다는 점은 이번에 확인했다.
`com.fasterxml.jackson` 대신 `tools.jackson` 을 쓴다.
