# ADR-091: 사진 첨부는 사용자별로 저장하고 실행 공간에는 그 사용자만 붙인다

- **status**: `accepted`
- **결정**: 첨부 경로를 `{root}/users/{사용자 디렉터리 키}/{대화 번호}/{첨부 번호}.{확장자}` 로 나눈다.
  사용자 디렉터리 키는 기존 실행 공간 주인 문자열 `u<사용자 번호>` 의 UTF-8 SHA-256 소문자 64자리다.
  사용자 번호를 파일 경로에 직접 적지 않으며, 사용자에게 키를 받거나 DB 에 새 칸을 만들지 않는다.
  **키는 디렉터리 이름일 뿐 권한이 아니다. 다른 사용자의 키를 맞혀도 그 디렉터리가 실행 공간에 붙지 않는다.**

  Control Plane 은 대화 소유권을 확인한 요청자의 번호로 첨부 행을 만든다.
  디스크 저장과 기존 파일 복사는 그 행의 `uploaded_by_user_id` 를 따른다.
  실행 공간은 Control Plane 이 도구 저장, 스킬 게시와 커넥터 설치에서 정한 `sandbox_owner` 를 따른다.
  `vision`, `image_gen`, `video_gen` 은 셸·파일 계열과 같은 Docker 설정을 적용하며 `PRIVATE` 만 허용한다.
  이미지 편집과 영상 생성도 원본 사진을 파일 경로로 읽기 때문이다.
  사진 도구가 켜진 동안도 그룹 공개나 주인 변경을 거절한다. local 사진 도구는 Hermes 호스트의 전체 첨부를 읽을 수 있기 때문이다.
  사진 첨부는 주인이 있는 `PRIVATE` 에이전트만 받고, 실행 요청자와 주인이 다르면 메시지와 실행을 만들기 전에 거절한다.
  따라서 사용자 소유의 격리된 profile 과 첨부 경로가 같은 사용자 키를 쓴다.
  주인 없는 에이전트의 `a<에이전트 번호>` 는 별도 빈 첨부 디렉터리를 가리키며 사용자 첨부를 함께 붙이지 않는다.
- **더해진 부분**: 2026-10-07 에 [ADR-20261007 / connector-owner-attachments](ADR-20261007-connector-owner-attachments.md) 가 이 경계를 커넥터까지 넓혔다. 사용자 첨부를 읽는다고 선언한 커넥터는 바인딩 주인의 첨부 디렉터리 하나만 받는다. 사용자 디렉터리 키와 디렉터리를 만드는 쪽은 바꾸지 않는다.

## 실행 공간에 붙이는 것

신뢰한 운영 정책에 `attachment_root` 와 `attachment_agent_root` 를 필수로 둔다.
첫 값은 Docker 호스트의 첨부 루트, 둘째는 Hermes 와 실행 컨테이너에서 사진을 보는 루트다.
Control Plane 의 `assistant.attachment.agent-root` 와 둘째 값이 같아야 한다.
plugin 은 두 루트에 `users/{SHA-256(sandbox_owner)}` 를 붙여 사용자 디렉터리 하나만 읽기 전용으로 붙인다.
요청 본문과 모델은 루트나 mount 목록을 정하지 못한다.

source와 target의 경로는 Hermes에서 모두 검증할 수 있어야 한다. 보이지 않는 source 루트는 409로 거절한다.
중간 경로까지 링크를 따라가지 않고 열고, 실제 경로가 허용 루트 아래의 그 사용자 디렉터리인지 확인한다.
처음 확인한 뒤 mount 문자열 생성 직전, 설정 저장 직전에 경로와 디렉터리 식별자를 다시 대조한다.
디렉터리가 없거나 검증에 실패하거나 검사 뒤 교체되면 409로 중단하며 기존 terminal 설정을 보존한다. 사진 커넥터 설치에도 적용한다.

## 사용자 디렉터리는 Control Plane 이 만든다

**Control Plane 은 `writeApiServer`, `putConnector`, `publish` 를 부르기 전에 `sandbox_owner` 의 `users/{SHA-256(sandbox_owner)}` 를 만든다.**
만들지 못하면 멈추는 호출은 이 셋이고, 실행 공간 설정을 쓰는 경로도 이 셋이다. 도구 저장은 늘 만들고, 커넥터 설치는 켤 때만, 스킬 게시는 도구 목록을 함께 쓸 때만 만든다.
커넥터를 에이전트에 붙이는 바인딩 설치(`bindConnector`)도 보내기 전에 같은 디렉터리를 만든다. 다만 최선 노력이라, 만들지 못해도 멈추지 않고 요청을 보낸다.
사용자 첨부를 읽는다고 선언한 커넥터면 대시보드가 디렉터리를 확인하지 못해 409 로 거절하므로 경계는 그대로다.
끄는 설치와 스킬 경로만 바꾸는 게시는 plugin 이 실행 공간을 다시 쓰지 않으므로 첨부 디렉터리 문제로 막지 않는다. 이미 있으면 그대로 둔다.
첨부 루트는 미리 있어야 한다. 없으면 mount 누락으로 보고 만들지 않는다.
루트와 `users`, 사용자 디렉터리가 심볼릭 링크가 아니어야 한다. 실제 경로는 루트의 실제 경로 아래 그 디렉터리와 같아야 한다.
루트보다 위쪽 경로는 운영 mount 가 책임진다.
어긋나면 Hermes 에 보내지 않고 Hermes 가 거절한 것과 같은 `AGENT_SANDBOX_UNAVAILABLE` 409 로 멈춘다.

이 방식은 Hermes 정책의 `attachment_root` 와 `attachment_agent_root` 가 Control Plane 의 `assistant.attachment.root` 와 같은 디렉터리라는 전제에 선다.
plugin 은 두 루트 모두에서 사용자 디렉터리를 확인하므로, 어느 한쪽이 다른 디렉터리이면 새 주인이 모두 409 가 된다.

**plugin 은 사용자 디렉터리를 만들지 않는다.** 존재와 링크 없음만 확인하고, 없으면 위와 같이 거절한다.

운영에서는 Hermes 에게 첨부 루트를 읽기 전용 mount 로만 보인다.
Hermes 와 Control Plane 이 같은 실행 계정으로 돌 수 있어, 파일 소유권으로는 Hermes 의 교체나 링크를 막지 못하기 때문이다.
그러면 plugin 은 디렉터리를 만들 수 없다(EROFS).
업로드와 복사 때만 디렉터리를 만들면, 사진을 한 번도 올리지 않은 주인의 profile 은 도구 저장과 커넥터 설치, 스킬 게시가 모두 409 가 된다.

공통·profile 별 `read_only_mounts` 는 첨부 원본 루트와 겹치는 원본을 받지 않는다.
첨부 대상 루트와 겹치는 대상도 받지 않아 사용자별 mount 를 가리거나 별칭으로 전체 루트를 여는 일을 막는다.
실행 공간 루트와의 겹침도 기존처럼 거절한다. 세부 검증과 설정 계약은 [Hermes 설치 문서](../../hermes/README.md)의 「셸 실행 공간」 이 갖는다.
새 첨부 정책이 없으면 셸·파일·사진 도구 설정을 거절한다. mount 가 바뀌면 설정 지문과 컨테이너 키가 바뀐다.
`vision`, `image_gen`, `video_gen` 을 켜는 profile 은 정책 등록도 필수다. 미등록 profile 은 사진 도구 저장과 사진 커넥터 설치를 거절한다.
새 profile 의 기본 도구에는 `vision` 을 넣지 않고, 주인 지정과 정책 등록 뒤에 켠다.
이미 떠 있는 옛 컨테이너를 안전하게 정리하고 재설정하는 일은 운영 저장소가 맡는다.

`delegate_task` 의 이미지 전달은 Docker 밖의 Hermes 호스트에서 파일을 읽는다.
기존 `fos-ctx` 의 `pre_tool_call` 에서 `images` 와 `tasks[].images` 의 로컬 경로를 막고 HTTP(S)·이미지 data URL 만 받는다.
이미지 없는 자식 실행은 유지한다. Hermes core 는 고치지 않는다.

## 기존 사진과 되돌리기

**첫 배포에서는 기존 사진을 복사하고 옛 경로를 남긴다.** `AttachmentBackfill` 이 기동할 때 첨부 행을 256개씩 읽고
삭제하지 않은 사진을 새 사용자 디렉터리에 복사한다. DB 내용, 첨부 번호와 대화 식별자는 바꾸지 않는다.
파일 시스템을 다루는 일이라 Flyway 에 넣지 않는다. DB 의 트랜잭션으로 디스크 복사까지 되돌릴 수 없기 때문이다.

1. 새 폴더 안의 임시 파일에 복사를 끝내고 최종 이름으로 교체한다. 부분 파일을 화면이나 에이전트에 내주지 않는다.
2. 두 사본이 이미 있으면 내용이 같을 때만 완료로 본다. 다르면 덮어쓰지 않고 실패를 알린다.
3. 읽기와 Hermes 입력 생성도 같은 복사를 수행한다. 기동 뒤 들어온 옛 파일이나 중단된 복사를 다시 처리한다.
4. 이전 기간의 신규 업로드도 두 경로에 쓴다. 옛 사본을 쓰지 못하면 신규 파일을 정리하고 업로드를 실패시킨다.
5. 사용자 삭제와 만료 정리는 두 사본을 함께 지운다. 지운 파일을 옛 경로에서 다시 복사하지 않는다.

옛 파일이 없으면 새 경로를 읽는다. 둘 다 없으면 기존처럼 410 으로 답한다.
파일 이름은 첨부 번호와 허용 MIME 의 확장자와 같아야 하며, 루트 아래 경로의 심볼릭 링크를 거절한다.
복사는 같은 Control Plane 프로세스의 파일 저장·읽기·삭제와 직렬화한다. 여러 인스턴스의 동시 쓰기는 지원하지 않는다.
복사 오류는 준비 완료를 막고 다음 기동에서 재시도한다. 사진 수에 비례한 디스크 읽기와 복사 비용이 든다.

**이전 버전으로 되돌리는 동안은 첨부 업로드를 중지하고 기존 사진 조회만 유지한다.**
쓰기를 멈추고 백업한 뒤 사용자별 사본을 확인한다. 신규 업로드에도 옛 사본이 있어 기존 화면은 이전 버전에서 읽힌다.
그러나 이전 Backend 는 `agent-root/{대화 번호}` 를 실행 입력에 쓰므로 새 버전의 mount 대상과 맞지 않는다.
이전 plugin 정책에서 profile 마다 그 사용자의 하위 폴더만 `agent-root` 에 붙인 뒤 이전 버전을 띄운다.
전체 첨부 루트는 계속 금지한다. 정상화 전에는 옛 경로에만 사진을 쓰는 이전 버전의 업로드를 열지 않는다.
`fos-ctx` 1.4.0 은 유지한다. 이전 묶음으로 커넥터를 재설치해 hook 을 되돌리지 않는다.
새 hook 을 유지하지 못하면 `delegation` 도 끈다. 옛 hook 은 자식의 로컬 이미지 전달을 막지 못한다.
이 절차의 정책 반영과 업로드 중지, 사본 확인은 운영 저장소가 맡는다.

**양쪽 저장은 이전 기간에만 쓴다.** `assistant.attachment.legacy-write-enabled` 의 기본값은 `true` 다.
다음 배포가 안정되고 옛 버전으로 되돌릴 필요가 없어진 뒤 `ASSISTANT_ATTACHMENT_LEGACY_WRITE_ENABLED=false` 로 끈다.
그 뒤 모든 살아 있는 첨부의 새 사본을 확인하고 백업한 다음 옛 대화 번호 폴더만 별도 작업으로 정리한다.
`users` 폴더는 정리하지 않는다. 이 단계 뒤 이전 버전으로 되돌리려면 역방향 복사가 필요하다.
이전 종료와 옛 사본 정리는 [후속 이슈 #221](https://github.com/jon890/fos-assistant/issues/221)로 관리하며,
실제 절차와 값은 `fos-home-infra` 가 갖는다.

API 완료 뒤 실제 Docker 생성까지는 plugin이 경로를 고정하지 못한다.
운영에서 첨부 루트를 Hermes 에 읽기 전용으로만 보여, Hermes 실행 계정이 첨부 루트와 사용자 디렉터리를 교체하거나 링크로 바꾸지 못하게 한다.
실제 생성 시점에는 운영 저장소의 Docker socket proxy가 컨테이너 생성 본문의 bind source를 검사한다.
중간 링크가 없고 realpath가 허용 첨부 루트 아래의 요청한 사용자 디렉터리인지 확인해야 한다.

## 범위와 남는 위험

- [ADR-020](ADR-020-사진은-공유-디렉터리에-두고-에이전트가-파일로-읽는다.md)의 공유 저장소를 사용자별 하위 디렉터리로 나눈다.
  사진을 파일로 넘기고 `vision_analyze` 로 읽는 방식, 화면 API 의 대화 소유권과 보관 기간은 유지한다.
- [ADR-086](ADR-086-셸과-파일-도구는-사용자별-docker-실행-공간에서만-돈다.md)의 전체 첨부 mount 위험을 격리된 profile 에서 제거한다.
  사진 도구가 없는 local profile 의 다른 도구와 기존 Hermes 예약 작업의 격리는 그대로 후속 작업이다.
- 결과물 저장소도 사용자 경계 없이 대화 번호로 나뉜다. 전체 결과물 루트를 붙이면 같은 누출이 생긴다.
  격리된 profile 은 결과물을 `artifact_write` 로 저장하며 전체 결과물 루트를 붙이지 않는다.
  결과물 저장 구조를 바꾸는 일은 이 변경에 넣지 않는다.
- SHA-256 은 사용자 번호를 직접 쓰지 않기 위한 이름 규칙이다. 비밀 키나 암호화 수단으로 설명하지 않는다.
  운영자가 다른 별칭으로 같은 첨부 저장소를 붙이거나, local 도구로 저장소 전체를 읽는 것까지 막지 못한다.
- 배포 전에 기존 그룹 공개 에이전트의 사진·이미지·영상 도구를 끄고 공통 첨부 mount 를 제거한 뒤 사용자별 정책을 반영한다.
  사진만 쓰는 에이전트와 사진을 받는 연결용 에이전트도 정책에 등록한다. 모든 대상 profile 의 설정과 커넥터 설치를 다시 쓰고
  실제 A/B 실행, vision 과 기존 대화 사진 조회를 왕복 확인해야 한다. 운영 반영과 확인은 `fos-home-infra` 가 맡는다.
  설정 재저장과 실제 왕복 검증이 끝나기 전에는 사진 첨부와 사진 도구 사용을 열지 않는다.

### 감당할 것

`delegate_task` 의 로컬 이미지 차단은 새 판 `fos-ctx` hook 이 켜져 있을 때만 보장한다.
기존 일반 profile 은 도구 저장만으로 plugin 파일이 갱신되지 않는다. 관리·수동 profile 모두 파일을 갱신하고
gateway 에서 다시 읽은 뒤 로컬 이미지 거절을 확인해야 한다. 커넥터 profile 은 재설치로 갱신한다.
이 확인 전에는 첨부와 해당 도구 사용을 열지 않는다. hook 이 꺼진 profile 의 호스트 파일 읽기는 막지 못한다.

| 파일을 바로 옮기고 옛 경로를 지운다 | 이전 버전으로 되돌렸을 때 기존 대화 사진을 읽지 못한다 |
| DB 사용자 번호를 경로에 그대로 쓴다 | 기존 주인 문자열로 안정된 키를 만들 수 있어 번호를 드러낼 필요가 없다 |
| 전체 루트를 붙이고 프롬프트로 다른 폴더 접근을 금지한다 | 셸과 파일 도구가 파일 시스템에서 다른 사용자 사진을 읽을 수 있다 |
| plugin 이 사용자 디렉터리를 만든다 | Hermes 가 첨부 루트에 쓸 수 있어야 한다. 같은 실행 계정이면 쓰기를 열 때 디렉터리 교체와 링크도 막지 못한다 |
| 업로드와 복사 때만 디렉터리를 만든다 | 사진을 올린 적 없는 주인의 도구 저장, 커넥터 설치, 스킬 게시가 409 가 된다 |
| 결과물과 sandbox 전체를 함께 재설계한다 | 첨부 누출의 수정 범위를 넘는다. 결과물의 MCP 소유권 검사를 먼저 활용한다 |
