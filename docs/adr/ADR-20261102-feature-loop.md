## ADR-20261102 / feature-loop: 기능 스펙은 기능 파일 옆 `docs/features/<id>/spec.md` 에 두고, Draft 의 독립 리뷰는 verify 로 한다

- **status**: `accepted`
- Date: 2026-11-02
- 개정 2026-11-03: 4절의 독립 verify 대상을 기능 루프 PR 과 위험 라벨이 붙은 PR 로 좁힌다. 제목의 「Draft 의 독립 리뷰는 verify 로 한다」 는 이 범위의 PR 에 한한다.
- [ADR-20261009 / feature-docs](ADR-20261009-feature-docs.md) 의 「`features/` 아래에 하위 디렉터리를 두지 않는다」 에 예외 하나를 더한다. 그 ADR 의 나머지는 그대로다.
- [ADR-20261009 / docs-per-module](ADR-20261009-docs-per-module.md) 의 예외 표에 기능 스펙 한 줄을 더한다.

### 결정

기능 단위 개발 루프(spec, planning, build-with-teams, verify, docs-consolidate)를 이 저장소에 들인다.
문서 자리와 리뷰 순서를 아래처럼 정한다.

**1. 스펙은 `docs/features/<id>/spec.md` 에 둔다.**

- `<id>` 는 기능 파일 이름 규칙(소문자 영문과 숫자, 하이픈)을 따른다.
- 같은 이름의 기능 파일 `docs/features/<id>.md` 가 있어야 한다. 스펙만 있는 기능은 두지 않는다.
- 그 디렉터리에는 `spec.md` 하나만 둔다. 스킬이 길어진 설계를 나누는 `design.md` 는 두지 않고 스펙의 「설계」 절에 쓴다.
- 그 밖의 `docs/features/` 아래 하위 디렉터리와 파일은 지금처럼 막는다.
- 기존 기능을 바꾸면 새 스펙을 만들지 않고 그 기능의 `spec.md` 를 이번 변경의 내용으로 새로 쓴다.

`test/unit/doc-files.test.ts` 가 이 자리를 지킨다.

**2. 기능 파일과 스펙은 갖는 것이 다르다.** 같은 내용을 두 곳에 쓰지 않는다.

| 문서 | 갖는 것 | 갖지 않는 것 |
| --- | --- | --- |
| 기능 파일 `docs/features/<id>.md` | 지금 동작하는 기능의 요구와 끝에서 끝까지의 흐름, `covers:` | 요구사항 ID 표, 인수 조건, 「미결정」 절 |
| 스펙 `docs/features/<id>/spec.md` | 합의한 변경의 요구사항 ID(`R1` 부터)와 관측할 인수 조건, 그 요구사항에 연결한 설계 | 기능 파일에 이미 있는 요구와 흐름의 사본, ADR 의 결정과 근거 |
| ADR | 되돌리기 어려운 결정과 근거 | 요구사항 ID 와 인수 조건 |

스펙 검사기(`spec` 스킬의 `check_feature.py`)는 「목표」, 「범위」, 「요구사항과 인수 조건」, 「설계」, 「미결정」 다섯 절을 요구한다.
그 절은 아래처럼 채워 기능 파일과 겹치지 않게 한다.

- 「목표」 와 「범위」 는 이번 변경이 무엇을 바꾸는지만 쓴다. 기능 전체의 설명은 기능 파일을 링크한다.
- 「요구사항과 인수 조건」 은 스펙에만 둔다. 계획서와 verify 는 `docs/features/<id>/spec.md#R1` 처럼 이 ID 를 가리킨다.
- 「설계」 는 요구사항 ID 마다 바꿀 API, 데이터, 실패 동작, 테스트를 쓴다. 결정의 근거는 ADR 을 링크하고, 코드가 가진 값은 [ADR-20261009 / docs-per-module](ADR-20261009-docs-per-module.md) 대로 옮겨 적지 않는다.
- 「미결정」 은 스펙에만 있고, 머지되는 스펙에서는 언제나 「없음」 이다. 아직 만들지 않은 것은 `docs/prd.md` 가 갖는다. 기능 파일에는 이 절을 두지 않는다.

구현이 머지되면 기능 파일의 「요구」 와 「흐름」 이 그 동작을 설명한다. docs-consolidate 가 같은 PR 에서 기능 파일을 구현에 맞춘다.
머지된 스펙은 마지막으로 구현한 변경의 기록이다. 스펙 머리에 「구현을 마친 변경의 기록이며 지금 동작은 기능 파일이 갖는다」 를 한 줄 둔다.
다음 변경은 `spec.md` 를 새로 쓰고 요구사항 ID 를 `R1` 부터 다시 매긴다. 이전 요구사항과 설계는 git 이력에서 찾는다. 계획서를 git 이력에서 찾는 것과 같다.
기능이 여러 PR 로 나뉘면 스펙에는 이번 PR 이 구현하는 요구사항만 상세화한다. 「설계만 먼저 머지하지 않는다」(`AGENTS.md` 「머지는 PR 로 한다」)를 지키기 위해서다.

**3. 공유 계약 자리 `docs/contracts/` 는 두지 않는다.**
docs-consolidate 는 채택한 공통 규칙을 「기존 계약 또는 `docs/contracts/<주제>.md`」 에 두라고 한다. 새 디렉터리는 기존 계약이 없을 때의 기본값이다.
이 저장소에는 기존 계약 자리가 있다. 여러 기능이 쓰는 계약은 그 계약의 기능 파일(`connector.md`, `connector-policy.md` 처럼)과 ADR 이 갖는다.
그래서 `docs/` 아래 하위 디렉터리 금지를 이 자리에는 풀지 않는다.

**4. Draft PR 의 독립 리뷰는 verify 다. 독립 verify 는 위험한 PR 만 받는다.**

독립 verify 의 가치는 모델 능력이 아니라 구현한 대화와 맥락이 분리된 데 있다(사용자 결정 2026-11-03). 그래서 그 분리가 값을 하는 PR 에만 받는다.

| PR | 검증 |
| --- | --- |
| 기능 루프를 쓴 PR(확인받은 스펙이 있다) | 독립 verify. 대화를 모르는 하위 에이전트가 한다 |
| 위험 라벨(`scripts/pr/pr-risk-labels.sh`)이 하나라도 붙은 PR | 독립 verify |
| 그 밖의 인수 조건이 있는 PR | 같은 세션 검증. 구현한 세션이 verify 절차(인수 조건 대조, 검사 재실행, diff 읽기)를 스스로 하고 PR 본문에 「같은 세션 검증」 이라고 적는다 |
| 인수 조건이 없는 PR(저장소 규칙만 바꾸는 PR 등) | 사람이나 코디네이터가 Draft 에서 diff 를 읽는다 |

순서는 이렇다.

1. 작성자가 Draft PR 을 연다.
2. Draft CI 가 통과하면 최신 main 을 merge 한다.
3. 위 표대로 검증한다. 독립 verify 는 인수 조건별 증거와 코드, 문서 검토를 받는다. 이것이 Draft 의 독립 리뷰이고 별도 리뷰 에이전트는 띄우지 않는다.
4. 검증을 통과해야 Ready 로 올린다.
5. Ready 뒤 GitHub 의 `claude-review` 가 한 번 더 본다. 그 지적은 한 번에 반영한다.

이 순서는 2026-10-15 에 정한 「Ready 뒤 `claude-review` 만 독립 리뷰로 둔다」 를 바꾼다.
위험 라벨은 정보용이라 머지 규칙은 바꾸지 않고, 독립 verify 를 받을 PR 을 가르는 데만 쓴다.
라벨이 붙은 경로는 스크립트가 갖는다. 위험한 경로가 라벨에서 빠져 있으면 스크립트에 규칙을 더한다.

**5. verify 뒤 코드가 바뀌면 바뀐 범위만 다시 본다.**
리뷰 반영이나 main 합치기로 코드가 바뀌어도 verify 전체를 다시 돌리지 않는다.
바뀐 범위의 개발 테스트와 CI 만 다시 통과시킨다. 하위 에이전트 코드 검토와 `/review` 는 다시 띄우지 않는다.

### 맥락

fos-skills 의 spec 스킬은 스펙을 `docs/features/<feature-id>/spec.md` 에 둔다.
이 저장소의 `doc-files.test.ts` 는 `docs/features/` 아래 하위 디렉터리를 막았고, 실패해야 하는 예로 `docs/features/x/y.md` 를 들었다.
스펙의 다섯 절은 기능 파일의 구성(요구, 흐름, `covers:`)과 달라 기능 파일 안에 넣을 수 없다. 스펙만 새 기능 파일로 만들면 `covers:` 가 없어 `feature-covers.test.ts` 가 실패한다.

리뷰 규칙도 세 곳이 서로 달랐다. `AGENTS.md` 는 Draft 독립 리뷰와 Ready 뒤 `claude-review` 를 둘 다 두었고, 코디네이터 쪽 규칙은 `claude-review` 하나만 두었다.
`claude-review` 는 diff 와 그 diff 가 건드리는 지침을 읽는다. 요구사항마다 실행 증거를 대조하는 리뷰는 verify 뿐이다.
또 스킬의 「코드가 바뀌면 verify 를 다시 거친다」 를 글자대로 따르면, worker 가 Draft CI 뒤 언제나 main 을 merge 하므로 모든 PR 이 verify 를 두 번 돈다.

### 대안 기각

- 스펙을 `tasks/<plan>/spec.md` 에 임시로 두고 구현 PR 에서 기능 파일과 ADR 로 옮긴다: 테스트를 바꾸지 않지만, 여러 PR 로 나뉜 기능은 다음 계획이 남은 요구사항을 새 스펙으로 다시 옮겨야 하고 요구사항 ID 가 PR 마다 사라진다.
- 스킬을 고쳐 스펙을 기능 파일의 한 절로 쓰게 한다: 이 저장소 구조에 가장 잘 맞지만 스킬 쪽 작업이 끝나야 쓸 수 있다.
- `claude-review` 만 독립 리뷰로 두고 verify 를 쓰지 않는다: 인수 조건을 실행 증거로 대조하는 리뷰가 없다.
- 모든 PR 에 독립 verify 를 받는다: 실측에서 독립 verify 는 구현 worker 가 설계 의도로 읽고 넘긴 결함(정리한 사용자의 옛 허락 줄이 남는 것, #671)을 찾았지만, 테스트만 지운 PR(#673)은 같은 세션 검증으로 충분했다. 위험이 낮은 PR 까지 받으면 시간과 토큰이 값어치보다 크다.
- 독립 verify 를 없애고 같은 세션 검증만 한다: 구현한 대화를 모르는 눈이 없어 위험한 PR 에서 설계 의도로 읽고 넘긴 결함을 못 잡는다.
- verify 뒤 코드가 바뀔 때마다 verify 전체를 다시 돈다: 리뷰를 한 번만 반영한다는 규칙과 부딪히고, main 합치기마다 같은 검토가 반복된다.

### 감당할 것

같은 기능의 문서가 기능 파일과 스펙 두 곳에 생긴다. 2의 표로 나누고, 스펙이 기능 파일의 요구를 다시 쓰면 리뷰에서 링크로 바꾼다.
스펙은 `doc-code-references.test.ts`, `feature-covers.test.ts`, 기능 파일 길이 알림의 대상이 아니다. 스펙은 구현과 같은 PR 에서 머지되고 그 뒤로는 기능 파일이 동작을 설명하므로, 이 검사들은 기능 파일만 본다.
독립 verify 를 받을 PR 이 verify 를 건너뛰고 Ready 로 올라가면 검증 없이 머지될 수 있다. 같은 세션 검증은 구현한 대화의 맹점을 공유하므로, 위험 라벨이 빠진 경로의 PR 은 독립 verify 를 놓친다. 이 순서는 worker 지시서와 이 ADR 이 함께 적는다.
