## ADR-012: Memory 는 사람이 승인한 것만 남는다

- **status**: `accepted`
- **결정**: Memory 항목은 에이전트가 제안하고 사람이 받아들여야 저장된다.
  범위가 `USER` 든 `FAMILY` 든 같다. 에이전트가 스스로 쓰는 경로를 두지 않는다.
  범위는 `USER` 와 `FAMILY` 둘뿐이고, 어느 쪽인지 정하지 않으면 등록이 거절된다.
  남길 것은 사람에 관한 사실로 한정한다. 작업 기록은 남기지 않는다.
  `career` profile 이 쓰던 Hermes 내장 memory 는 Control Plane 으로 옮기고 그 toolset 을 끈다.

### 맥락

[ADR-003](ADR-003-memory-권한은-주입으로-강제한다.md) 이
Memory 의 단일 소스를 Control Plane 으로 정하고
Hermes 내장 memory 조회 도구를 주지 않기로 했다.
제목 색인의 본문을 읽는 제한된 Control Plane MCP 도구는
[ADR-015](ADR-015-memory-는-층을-나눠-싣는다.md)가 그 결정을 보완한다.

그런데 실제 운영이 그것과 어긋나 있다.
`career` profile 은 `memory` toolset 이 켜져 있고
`memories/MEMORY.md` 10,192 바이트와 `USER.md` 586 바이트를 들고 있다.
`bifos` profile 은 `disabled_toolsets` 에 `memory` 가 있어 결정을 지킨다.
한쪽만 지키는 규칙은 지켜지지 않는 규칙이다.

무엇을 언제 Memory 로 만들 것인가는 그동안 정하지 못한 채였다.
사람이 화면에서 손으로만 적게 하면 쓰지 않게 되고,
에이전트가 대화에서 알아서 쌓으면 틀린 사실이 남아 이후 실행마다 계속 주입된다.

Hermes 가 이미 자동으로 쌓는 쪽을 택하고 있어 그 결과물을 볼 수 있었다.
`career` profile 의 `MEMORY.md` 가 39줄, 10,192 바이트다.
그 내용이 사람에 관한 사실이 아니라 지난 세션의 작업 기록이다.

```
- Short-Term Memory - 2026-06-11: ... 커밋/푸시 `9484996 fix(career-os): ...` 완료.
  [score=0.815 recalls=0 avg=0.620 source=memory/2026-06-11.md:3-6]
- 2026-06-14 Memory: 2026-06-14 Memory: Plan072 HTML report planning was started in a
  separate worktree/branch... Worktree: `<worktree 경로>/plan072-...`
```

커밋 해시와 worktree 경로와 plan 진행 상태가 남았고,
머리말이 두 번 붙거나 점수 메타데이터가 본문에 섞인 줄도 있다.
이 10,192 바이트가 「오늘 날씨 좋다」 같은 한 문장에도 매번 함께 실린다.

한편 우리에게는 Hermes 에 없는 조건이 하나 더 있다.
**`FAMILY` 항목은 다른 사용자의 실행에도 주입된다.**
한 사람의 에이전트가 잘못 판단한 한 줄이 다른 가족의 답을 함께 틀리게 만든다.
Hermes 의 내장 memory 는 profile 주인 한 사람의 것이라 이 위험이 없다.

### 대안 기각

- **사람이 화면에서 손으로만 적는다.**
  가장 안전하지만 쓰이지 않는다.
  작업 영역이 그렇게 만들어졌고 등록된 행이 0 인 채로 끝났다.
  에이전트가 남길 것을 찾아 물어 오는 길이 있어야 실제로 쌓인다.
- **전부 자동으로 쌓고 사후에 고친다.**
  Hermes 가 택한 쪽이고 손이 가장 덜 간다.
  위의 `MEMORY.md` 가 그 결과물이다. 아무도 정리하지 않은 채 남았고,
  정리하지 않으면 그 10,192 바이트가 계속 실린다.
- **범위마다 다르게 다룬다.**
  개인 항목만 자동으로 넣고 가족 공용은 승인받는 길이다.
  들어오는 길이 둘이 되어 화면과 규칙이 갈라지는데,
  개인 항목이라고 틀려도 되는 것은 아니다.
  주입된 문자열이 곧 에이전트가 아는 전부라, 틀린 한 줄이 계속 재사용된다.
- **에이전트별로 Memory 를 나눈다.**
  `career` 가 볼 것과 다른 에이전트가 볼 것이 다르다는 문제는 실재한다.
  다만 지금 에이전트가 둘뿐이고, 나누는 순간 화면과 주입 규칙이 함께 복잡해진다.
  주입한 양이 실제로 문제가 되는지를 `context_chars` 로 먼저 측정하고 그 숫자를 보고 정한다.
- **Hermes 내장 memory 를 그대로 쓴다.**
  내장 memory 는 profile 단위라 개인과 가족 공용을 나누지 못한다.
  가족 중 한 사람만 보아야 할 것과 함께 보아야 할 것이 같은 파일에 섞인다.

### 결과

얻는 것

- 저장된 모든 항목을 사람이 한 번은 본 것이 된다. 틀린 사실이 들어올 자리가 한 곳으로 좁혀진다.
- 개인과 가족 공용이 같은 표에서 범위로 갈린다.
  다른 사용자의 `USER` 항목은 주입 대상을 고르는 단계에서 빠지므로,
  Hermes 로 나가는 문자열에 애초에 들어가지 않는다.
- `career` 의 Memory 가 Control Plane 으로 모이면서 ADR-003 의 결정과 운영이 다시 맞는다.
  `memory` toolset 도구 정의 3,178 바이트도 함께 빠진다.

감당할 것

- 제안을 보여주고 받아들이는 화면이 필요하다. 저장만 하는 것보다 만들 것이 많다.
- 사람이 제안을 오래 방치하면 Memory 가 늘지 않는다. 손으로 적는 길과 같은 자리로 돌아간다.
- 항상 주입하는 항목이 늘어나면 실행마다 실리는 양도 늘어난다.
  제목 색인의 본문은 이미 Control Plane MCP 도구로 읽는다.
  항상 주입 층의 양을 판단하려고 실행마다 주입한 글자 수를 남긴다.
- `career` 의 `MEMORY.md` 를 옮기는 동안 그 에이전트가 알던 것을 잠깐 잃는다.
  옮긴 뒤 실제로 한 번 물어 확인한다.

### 적용 범위

**남길 것은 사람에 관한 사실이다.**
다음에도 쓰일 선호, 상황, 결정이 여기 해당한다.

작업 기록은 남기지 않는다.
커밋 해시, 파일 경로, 진행 상태, 어느 브랜치에서 무엇을 했는지가 그것이다.
그 기준을 제안을 만드는 프롬프트에 명시한다.
`MEMORY.md` 가 그 기준 없이 쌓여 작업 로그가 된 것이 근거다.

제안을 만드는 경로는 설정으로 끌 수 있게 두고 기본값을 꺼진 쪽으로 둔다.
이 경로가 대화마다 LLM 을 한 번 더 부르므로, 그 비용과 제안의 질을 재고 켠다.
