## ADR-012: Memory 는 사람이 승인한 것만 남는다

- **status**: `accepted`
- **결정**: Memory 항목은 에이전트가 제안하고 사람이 받아들여야 저장된다.
  에이전트가 스스로 쓰는 경로를 두지 않는다.
  범위는 `USER` 와 `FAMILY` 둘뿐이고, 어느 쪽인지 정하지 않으면 등록이 거절된다.
  `career` profile 이 쓰던 Hermes 내장 memory 는 Control Plane 으로 옮기고 그 toolset 을 끈다.

### 맥락

[ADR-003](ADR-003-memory-권한은-주입으로-강제한다.md) 이
Memory 의 단일 소스를 Control Plane 으로 정하고
에이전트에게 memory 조회 도구를 주지 않기로 했다.

그런데 실제 운영이 그것과 어긋나 있다.
`career` profile 은 `memory` toolset 이 켜져 있고
`memories/MEMORY.md` 10,192 바이트와 `USER.md` 586 바이트를 들고 있다.
`bifos` profile 은 `disabled_toolsets` 에 `memory` 가 있어 결정을 지킨다.
한쪽만 지키는 규칙은 지켜지지 않는 규칙이다.

무엇을 언제 Memory 로 만들 것인가는 그동안 정하지 못한 채였다.
사람이 화면에서 손으로만 적게 하면 쓰지 않게 되고,
에이전트가 대화에서 알아서 쌓으면 틀린 사실이 남아 이후 실행마다 계속 주입된다.
틀린 사실은 조용히 남는 것이 아니라 그 뒤의 모든 답을 함께 틀리게 만든다.

### 대안 기각

- **사람이 화면에서 손으로만 적는다.**
  가장 안전하지만 쓰이지 않는다.
  실측한 것이 있다. 작업 영역이 그렇게 만들어졌고 등록된 행이 0 이었다.
- **에이전트가 자동으로 쌓는다.**
  손이 가장 덜 가지만 틀린 사실을 사람이 발견할 자리가 없다.
  주입된 문자열이 곧 에이전트가 아는 전부이므로, 틀린 한 줄이 계속 재사용된다.
- **에이전트별로 Memory 를 나눈다.**
  `career` 가 볼 것과 다른 에이전트가 볼 것이 다르다는 문제는 실재한다.
  다만 지금 에이전트가 둘뿐이고, 나누는 순간 화면과 주입 규칙이 함께 복잡해진다.
  주입한 양이 실제로 문제가 되는지를 `context_chars` 로 먼저 재고 그 숫자를 보고 정한다.
- **Hermes 내장 memory 를 그대로 쓴다.**
  내장 memory 는 profile 단위라 개인과 가족 공용을 나누지 못한다.
  가족 중 한 사람만 보아야 할 것과 함께 보아야 할 것이 같은 파일에 섞인다.

### 결과

얻는 것

- 저장된 모든 항목을 사람이 한 번은 본 것이 된다. 틀린 사실이 들어올 자리가 한 곳으로 좁혀진다.
- 개인과 가족 공용이 같은 표에서 범위로 갈린다.
  다른 구성원의 `USER` 항목은 주입 대상을 고르는 단계에서 빠지므로,
  Hermes 로 나가는 문자열에 애초에 들어가지 않는다.
- `career` 의 Memory 가 Control Plane 으로 모이면서 ADR-003 의 결정과 운영이 다시 맞는다.
  `memory` toolset 도구 정의 3,178 바이트도 함께 빠진다.

감당할 것

- 제안을 보여주고 받아들이는 화면이 필요하다. 저장만 하는 것보다 만들 것이 많다.
- 사람이 제안을 오래 방치하면 Memory 가 늘지 않는다. 손으로 적는 길과 같은 자리로 돌아간다.
- 주입할 양이 실행마다 늘어난다.
  ADR-003 이 이미 「memory 가 많아지면 도구 방식으로 옮긴다」 고 적었다.
  그 시점을 숫자로 판단하려고 실행마다 주입한 글자 수를 남긴다.
- `career` 의 `MEMORY.md` 를 옮기는 동안 그 에이전트가 알던 것을 잠깐 잃는다.
  옮긴 뒤 실제로 한 번 물어 확인한다.
