## ADR-20261101 / artifact-vault: 사용자가 보관한 결과물은 chat_artifact 의 보관 사본 행에 암호화해 두고 대화와 따로 남긴다

- **status**: `accepted`
- Date: 2026-11-01
- 이슈 #530 의 2026-10-13 사용자 결정(앱 안의 사용자별 암호화 보관함, 보관 주인은 대화 요청자, 대화를 지워도 보관본 유지, 사용자당 5GiB)을 구현 범위로 옮긴다. 2026-11-01 사용자 결정(테이블은 최대한 늘리지 않고 기존 테이블을 쓴다)에 따라 새 테이블을 만들지 않는다.
- [ADR-027](ADR-027-에이전트가-만든-html-은-대화별-폴더에-두고-스크립트-없이-보인다.md) 의 「결과물은 대화와 함께 사라진다」 에 사용자가 고른 보관본이라는 예외를 더한다.

### 결정

**보관본은 `chat_artifact` 의 행이다.** `vault_user_id` 가 채워진 행이 보관 사본이고, `message_id` 는 비어 있다.
컬럼은 `vault_user_id`, `vault_key_id`, `vault_body`, `vault_fingerprint` 네 개를 더한다. 평문 바이트 수는 기존 `byte_size` 를 쓴다.

| 규칙 | 내용 |
| --- | --- |
| 주인 | 대화 요청자다. 보관은 대화 주인만 하고, 읽기와 지우기는 `vault_user_id` 인 사용자만 한다. 남의 번호와 없는 번호는 같은 `ARTIFACT_NOT_FOUND` 로 답한다. 에이전트 주인에게는 자동으로 보이지 않는다 |
| 암호화 | 본문은 주인의 사용자별 데이터 key 로 암호화해 `vault_body` 에만 둔다([ADR-20261008 / data-encryption](../../backend/docs/adr/ADR-20261008-data-encryption.md) 와 같은 경로). 암호화가 꺼져 있거나 key 를 쓸 수 없거나 태그가 맞지 않으면 평문으로 두지 않고 일부도 주지 않는다. 암호문의 자리는 주인, 대화 번호, 경로, 지문으로 묶어 다른 줄로 옮기면 풀리지 않는다 |
| 대상 | HTML 과 CSS 만 보관한다. 사진, 스타일, 프레임을 부르는 표지(`<img>`, `<link>`, `url()`, `@import` 등)가 있으면 거절한다. 사진이 빠진 HTML 을 완성본으로 두지 않으려는 보수적인 판정이고, 묶음 보관은 PR 2 가 맡는다. 파일 하나는 5MiB 까지다 |
| 중복 | 같은 사용자의 같은 대화, 경로, 본문 바이트는 한 건이다(`vault_fingerprint` 유일). 내용이 바뀌면 새 보관본이다. 지문은 사용자 사이에 비교하지 않는다 |
| 용량 | 사용자당 5GiB(`assistant.artifact-vault.user-quota-bytes`)다. 넘으면 새 보관만 `ARTIFACT_VAULT_FULL` 로 거절하고 자동 삭제하지 않는다. 확인과 저장은 사용자별 잠금 안의 한 트랜잭션이다. Control Plane 이 한 인스턴스라는 전제이며 늘면 데이터베이스 잠금으로 바꾼다 |
| 대화 삭제 | 대화를 지워 정리해도 보관 사본 행은 남는다. 정리는 `vault_user_id` 가 빈 행만 지운다. 원본 정리와 만료 표시 작업도 보관 사본 행을 건드리지 않는다 |
| 지우기 | 행이 곧 본문이라 행을 지우면 읽을 수 없고 재시작으로 되살아나지 않는다. 별도 파일이 없어 파일과 DB 가 어긋나는 일도 없다. 개별 파일 삭제를 사용자 key 삭제로 처리하지 않는다 |
| 읽기 | 본문 응답에 스크립트가 돌지 않는 머리글(`sandbox` CSP)과 `no-store` 를 붙인다. 화면은 같은 격리의 iframe 으로 미리 본다 |

### 대안과 기각

- 새 표 `artifact_vault_item` 과 암호화 파일 저장소: 사용자 결정(새 테이블 금지)과 맞지 않고 파일과 DB 가 어긋나는 복구 작업이 따른다. 5MiB 이하 텍스트라 DB 컬럼에 두는 비용이 작다.
- 기존 `chat_artifact` 행에 표시만 다는 방식: 대화 정리가 행을 지우고 CSS 는 행이 없으며 같은 경로의 덮어쓰기가 보관본을 바꾼다. 그래서 보관 시점의 사본을 별도 행으로 둔다.
- 기존 실행 공간(`/files`)에 복사: 실행 공간의 주인은 에이전트 주인이라 요청자의 개인 보관함이 되지 못하고, 셸이 전체를 읽는다.

### 결과와 남은 일

- 보관 사본은 `LONGTEXT` 컬럼에 암호문(base64url)으로 들어가므로 평문보다 약 4/3 커진다. 5MiB 한 파일은 약 7MB 다. 목록은 본문 컬럼을 읽지 않는다.
- 원본을 읽는 길은 기존 결과물 읽기(`ArtifactService.find`/`open`)와 같다. 경로 검사와 읽기 사이의 링크 경쟁은 [#359](https://github.com/jon890/fos-assistant/issues/359) 의 위험 수용을 그대로 따른다. 보관본을 읽는 길에는 파일 경로가 없다.
- 대화를 지울 때 「보관본도 함께 지우기」 선택지, 이미지가 든 묶음(PR 2), turn 완료 때 자동 보관과 지우기 이력(PR 3)은 이 결정에 들어 있지 않다. 자동 보관은 지운 보관본을 다시 만들지 못하게 하는 지우기 이력이 필요하다.
