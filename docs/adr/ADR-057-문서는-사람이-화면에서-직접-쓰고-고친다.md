## ADR-057: 문서는 사람이 화면에서 직접 쓰고 고친다

- **status**: `accepted`. 아직 구현 전이다.
- **결정**: Memory 의 `DOCUMENT` 는 사용자가 `/memory` 화면의 문서 폼에서 직접 쓰고 고친다.
  직접 쓴 문서는 곧 `ACCEPTED` 다. 다른 서비스와 에이전트가 문서를 쓰는 길은 두지 않는다.
  기존 개인 지식 저장소를 옮기는 일회성 이관도 주인이 화면에서 검토하고 올린다([ADR-058](ADR-058-기존-개인-지식-저장소는-주인이-검토한-묶음을-화면에서-올려-들여온다.md)).
  이번에 만드는 것은 `USER` 범위의 문서다. 주인만 쓰고 주인만 본다.
  고칠 때 화면이 읽은 판 번호를 함께 보내고, 그 사이에 판이 올랐으면 거절한다.
  문서는 Memory 목록 API 에 나오지 않는다. 문서 API 가 따로 낸다. 문서 목록은 본문을 싣지 않는다.
- **맥락**: Memory 는 사람이 승인한 것만 남는다([ADR-012](ADR-012-memory-는-사람이-승인한-것만-남는다.md)).
  `DOCUMENT` 는 스키마와 판정만 있고 만드는 길이 없었다([ADR-052](ADR-052-memory-는-collection-종류-꺼내는-방식-민감도-판-출처를-가진다.md)).
  웹의 JWT 는 Next.js 서버만 만들므로, 화면이 없으면 사람이 부를 수 있는 API 가 없다.
  지금 Memory 목록은 본문을 통째로 내고 화면이 그것을 그대로 그린다. 민감 문서의 본문이 그 목록에 실리면 화면을 열 때마다 복호화한 본문이 오간다.
- **대체된 부분**: 없다. [`code-architecture.md`](../code-architecture.md) 의 「Memory 에서 아직 만들지 않은 것」 에 적힌 「문서 편집 화면」 가운데 쓰기와 고치기만 만든다. 판 이력 화면과 collection 탭은 그대로 남는다.
- **대안 기각**:
  - 서비스 토큰으로 문서를 올리고 화면에서 승인한다: 이미 받아들인 문서를 고칠 때 「승인 전인 다음 판」 을 따로 저장해야 한다. 지금 표에는 한 항목에 지금 값 하나뿐이다. 사람이 직접 쓰면 그 상태가 필요 없다.
  - 화면 없이 관리 명령으로 넣는다: 민감 본문이 셸 이력과 명령 인자에 남는다. 그 명령을 적은 문서는 이 저장소에 둘 수 없다.
  - Memory 목록에 문서를 함께 낸다: 화면의 기존 수정은 본문과 항상 실을지만 보낸다. 그 길로 문서를 고치면 민감 문서를 항상 층으로 올리려는 요청이 생긴다. 목록과 수정 경로를 나눈다.
  - 제목도 고치게 한다: 지금 `Memory` 는 제목을 고치지 않는다. 판이 제목을 함께 남기므로 제목을 고치면 판의 뜻이 달라진다. 판 이력 화면과 함께 정한다.
  - 판 번호 없이 마지막에 쓴 것이 이긴다: 문서는 길고, 탭 두 개에서 고치면 앞의 수정이 조용히 사라진다. 다른 서비스가 판 번호를 기준으로 삼으므로 판이 뜻하지 않게 오르는 일도 막는다.
- **결과**:
  - 얻는 것: 사용자가 민감 문서를 직접 넣고 고친다. 승인 절차가 따로 필요 없다.
    민감 본문은 사용자가 그 문서를 열 때와 허가받은 서비스가 읽을 때만 복호화된다.
  - 감당할 것: 다른 곳에 있는 문서를 하나씩 옮길 때는 사람이 붙여 넣는다. 기존 개인 지식 저장소를 통째로 옮기는 일은 [ADR-058](ADR-058-기존-개인-지식-저장소는-주인이-검토한-묶음을-화면에서-올려-들여온다.md) 의 이관 절차가 맡는다.
    민감 문서와 민감 항목은 Memory 목록의 수정 경로로 고치지 못한다([ADR-055](ADR-055-민감-memory-본문은-저장할-때-암호화하고-key-는-환경-변수로-받는다.md)).
    문서의 판 이력을 보는 화면이 없다. 판은 쌓이지만 화면에서 보지 못한다.
    지운 문서의 본문은 판에 남는다. 민감 문서의 판은 암호문이다([ADR-055](ADR-055-민감-memory-본문은-저장할-때-암호화하고-key-는-환경-변수로-받는다.md)).
    그룹 공용 문서는 만들지 못한다.
- **적용 범위**:

  모두 웹의 JWT 로 부르고, 요청자가 주인인 `USER` 범위의 문서만 다룬다. 남의 문서와 없는 문서는 같은 404 `MEMORY_NOT_FOUND` 다.

  | 경로 | 하는 일 |
  | --- | --- |
  | `GET /api/v1/memory-documents` | 문서 목록. `{id, collection, documentKey, title, sensitive, revision, updatedAt}`. 본문이 없다 |
  | `GET /api/v1/memory-documents/{id}` | 문서 하나. 위의 칸에 `content` 를 더한다 |
  | `POST /api/v1/memory-documents` | `{collection, documentKey, title, content, sensitive}` 로 만든다. `ACCEPTED`, `DOCUMENT`, 꺼내는 방식은 `SEARCH`, 판은 1 이다 |
  | `PUT /api/v1/memory-documents/{id}` | `{content, sensitive, expectedRevision}` 로 고친다. 고치기 전의 값을 판으로 남기고 판 번호를 올린다 |
  | `DELETE /api/v1/memories/{id}` | 이미 있는 삭제 경로를 그대로 쓴다 |
  | `GET /api/v1/memory-collections` | 요청자의 그룹이 쓰는 collection 목록. `{key, displayName}`. 문서 폼과 서비스 토큰 발급이 고를 목록이다 |

  | 거절 | 언제 |
  | --- | --- |
  | 400 `VALIDATION_FAILED` | `documentKey` 가 소문자나 숫자로 시작하지 않는다, 소문자·숫자·하이픈 밖의 글자가 있다, 128자를 넘는다. `collection` 이 그 사용자의 그룹 목록에 없다. 본문이 12,000자를 넘는다 |
  | 409 `MEMORY_DOCUMENT_EXISTS` | 같은 collection 에 같은 `documentKey` 의 문서가 이미 있다 |
  | 409 `MEMORY_REVISION_CONFLICT` | `expectedRevision` 이 지금 판 번호와 다르다 |
  | 409 `MEMORY_ENCRYPTION_UNAVAILABLE` | 민감 문서인데 암호화 key 가 없다 |

  `GET /api/v1/memories` 는 종류가 `MEMORY` 인 줄만 낸다. `PATCH /api/v1/memories/{id}` 는 문서에 `MEMORY_NOT_FOUND` 로 답한다.

- **다음**: 판 이력 화면, collection 탭, 그룹 공용 문서, 제목 고치기는 화면을 넓힐 때 정한다.
