# ADR-087: 사진 첨부는 사용자별로 저장하고 실행 공간에는 그 사용자만 붙인다

- **status**: `accepted`
- **결정**: 첨부 경로를 `{root}/users/{사용자 디렉터리 키}/{대화 번호}/{첨부 번호}.{확장자}` 로 나눈다.
  사용자 디렉터리 키는 기존 실행 공간 주인 문자열 `u<사용자 번호>` 의 UTF-8 SHA-256 소문자 64자리다.
  사용자 번호를 파일 경로에 직접 적지 않으며, 사용자에게 키를 받거나 DB 에 새 칸을 만들지 않는다.
  **키는 디렉터리 이름일 뿐 권한이 아니다. 다른 사용자의 키를 맞혀도 그 디렉터리가 실행 공간에 붙지 않는다.**

  Control Plane 은 대화 소유권을 확인한 요청자의 번호로 첨부 행을 만든다.
  디스크 저장과 기존 파일 복사는 그 행의 `uploaded_by_user_id` 를 따른다.
  실행 공간은 Control Plane 이 도구 저장과 스킬 게시에서 정한 `sandbox_owner` 를 따른다.
  셸·파일 계열 도구가 켜진 에이전트는 `PRIVATE` 만 되고, 도구를 끄기 전에는 주인을 바꾸지 못하는 기존 규칙을 유지한다.
  따라서 사용자 소유의 격리된 profile 과 첨부 경로가 같은 사용자 키를 쓴다.
  주인 없는 에이전트의 `a<에이전트 번호>` 는 별도 빈 첨부 디렉터리를 가리키며 사용자 첨부를 함께 붙이지 않는다.

## 실행 공간에 붙이는 것

신뢰한 운영 정책에 `attachment_root` 와 `attachment_agent_root` 를 필수로 둔다.
첫 값은 Docker 호스트의 첨부 루트, 둘째는 Hermes 와 실행 컨테이너에서 사진을 보는 루트다.
Control Plane 의 `assistant.attachment.agent-root` 와 둘째 값이 같아야 한다.
plugin 은 두 루트에 `users/{SHA-256(sandbox_owner)}` 를 붙여 사용자 디렉터리 하나만 읽기 전용으로 붙인다.
요청 본문과 모델은 루트나 mount 목록을 정하지 못한다.

공통·profile 별 `read_only_mounts` 는 첨부 원본 루트와 겹치는 원본을 받지 않는다.
첨부 대상 루트와 겹치는 대상도 받지 않아 사용자별 mount 를 가리거나 별칭으로 전체 루트를 여는 일을 막는다.
실행 공간 루트와의 겹침도 기존처럼 거절한다. 세부 검증과 설정 계약은 [Hermes 설치 문서](../../hermes/README.md)의 「셸 실행 공간」 이 갖는다.
새 첨부 정책이 없으면 셸 도구 설정을 거절한다. mount 가 바뀌면 설정 지문과 컨테이너 키가 바뀐다.
이미 떠 있는 옛 컨테이너를 안전하게 정리하고 재설정하는 일은 운영 저장소가 맡는다.

## 기존 사진과 되돌리기

**첫 배포에서는 기존 사진을 복사하고 옛 경로를 남긴다.** `AttachmentBackfill` 이 기동할 때 첨부 행을 256개씩 읽고
삭제하지 않은 사진을 새 사용자 디렉터리에 복사한다. DB 내용, 첨부 번호와 대화 식별자는 바꾸지 않는다.
파일 시스템을 다루는 일이라 Flyway 에 넣지 않는다. DB 의 트랜잭션으로 디스크 복사까지 되돌릴 수 없기 때문이다.

1. 새 폴더 안의 임시 파일에 복사를 끝내고 최종 이름으로 교체한다. 부분 파일을 화면이나 에이전트에 내주지 않는다.
2. 두 사본이 이미 있으면 내용이 같을 때만 완료로 본다. 다르면 덮어쓰지 않고 실패를 알린다.
3. 읽기와 Hermes 입력 생성도 같은 복사를 수행한다. 기동 뒤 들어온 옛 파일이나 중단된 복사를 다시 처리한다.
4. 이전 기간의 신규 업로드도 두 경로에 쓴다. 옛 사본을 쓰지 못하면 신규 파일을 정리하고 업로드를 실패시킨다.
5. 사용자 삭제와 만료 정리는 두 사본을 함께 지운다. 지운 파일을 옛 경로에서 다시 복사하지 않는다.

옛 파일이 없으면 새 경로를 읽는다. 둘 다 없으면 기존처럼 410 으로 답한다.
파일 이름은 첨부 번호와 허용 MIME 의 확장자와 같아야 하며, 루트 아래 경로의 심볼릭 링크를 거절한다.
복사는 같은 Control Plane 프로세스의 파일 저장·읽기·삭제와 직렬화한다. 여러 인스턴스의 동시 쓰기는 지원하지 않는다.
복사 오류는 준비 완료를 막고 다음 기동에서 재시도한다. 사진 수에 비례한 디스크 읽기와 복사 비용이 든다.

이전 버전으로 되돌릴 때는 쓰기를 멈추고 백업한 뒤 이전 버전을 띄운다.
신규 업로드에도 옛 사본이 있어 파일을 역방향으로 옮기거나 DB 를 되돌릴 필요가 없다.
격리 설정은 유지하며 전체 첨부 루트를 다시 mount 하지 않는다. 옛 버전은 기동 전에 새 파일을 사용자 폴더에
복사하지 않으므로, 되돌린 뒤 새로 올린 사진의 실행 공간 조회에는 운영의 사용자 폴더 동기화가 필요하다.

**양쪽 저장은 이전 기간에만 쓴다.** `assistant.attachment.legacy-write-enabled` 의 기본값은 `true` 다.
다음 배포가 안정되고 옛 버전으로 되돌릴 필요가 없어진 뒤 `ASSISTANT_ATTACHMENT_LEGACY_WRITE_ENABLED=false` 로 끈다.
그 뒤 모든 살아 있는 첨부의 새 사본을 확인하고 백업한 다음 옛 대화 번호 폴더만 별도 작업으로 정리한다.
`users` 폴더는 정리하지 않는다. 이 단계 뒤 이전 버전으로 되돌리려면 역방향 복사가 필요하다.
이전 종료와 옛 사본 정리는 후속 이슈로 관리하며, 실제 절차와 값은 `fos-home-infra` 가 갖는다.

## 범위와 남는 위험

- [ADR-020](ADR-020-사진은-공유-디렉터리에-두고-에이전트가-파일로-읽는다.md)의 공유 저장소를 사용자별 하위 디렉터리로 나눈다.
  사진을 파일로 넘기고 `vision_analyze` 로 읽는 방식, 화면 API 의 대화 소유권과 보관 기간은 유지한다.
- [ADR-086](ADR-086-셸과-파일-도구는-사용자별-docker-실행-공간에서만-돈다.md)의 전체 첨부 mount 위험을 격리된 profile 에서 제거한다.
  유효한 정책에 등록하지 않은 local profile 과 기존 Hermes 예약 작업의 격리는 그대로 후속 작업이다.
- 결과물 저장소도 사용자 경계 없이 대화 번호로 나뉜다. 전체 결과물 루트를 붙이면 같은 누출이 생긴다.
  격리된 profile 은 결과물을 `artifact_write` 로 저장하며 전체 결과물 루트를 붙이지 않는다.
  결과물 저장 구조를 바꾸는 일은 이 변경에 넣지 않는다.
- SHA-256 은 사용자 번호를 직접 쓰지 않기 위한 이름 규칙이다. 비밀 키나 암호화 수단으로 설명하지 않는다.
  운영자가 다른 별칭으로 같은 첨부 저장소를 붙이거나, local 도구로 저장소 전체를 읽는 것까지 막지 못한다.
- 배포 전에 공통 첨부 mount 를 제거하고 사용자별 정책을 반영한다. 모든 대상 profile 의 설정을 다시 쓰고
  실제 A/B 실행, vision 과 기존 대화 사진 조회를 왕복 확인해야 한다. 운영 반영과 확인은 `fos-home-infra` 가 맡는다.

## 대안 기각

| 대안 | 기각한 까닭 |
| --- | --- |
| 파일을 바로 옮기고 옛 경로를 지운다 | 이전 버전으로 되돌렸을 때 기존 대화 사진을 읽지 못한다 |
| DB 사용자 번호를 경로에 그대로 쓴다 | 기존 주인 문자열로 안정된 키를 만들 수 있어 번호를 드러낼 필요가 없다 |
| 전체 루트를 붙이고 프롬프트로 다른 폴더 접근을 금지한다 | 셸과 파일 도구가 파일 시스템에서 다른 사용자 사진을 읽을 수 있다 |
| 결과물과 sandbox 전체를 함께 재설계한다 | 첨부 누출의 수정 범위를 넘는다. 결과물의 MCP 소유권 검사를 먼저 활용한다 |
