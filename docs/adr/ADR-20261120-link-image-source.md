## ADR-20261120 / link-image-source: 사용자가 보낸 링크의 사진은 Control Plane 이 대화에 있는지 확인하고 허용 목록 없이 공개 주소에서만 받는다

- **status**: `accepted`
- Date: 2026-11-20
- **decision-type**: `architecture`
- **areas**: `security`
- **현재 규칙의 원본**: 설계 [`docs/features/generated-image/design.md`](../features/generated-image/design.md) 의 「PR5」, 스펙 [`spec.md`](../features/generated-image/spec.md) 의 REQ20 부터 REQ23 까지, DECISION34 부터 DECISION38 까지, DECISION43 부터 DECISION46 까지(사용자 확인 2026-11-20), [`fos-ctx` README](../../hermes/plugins/fos-ctx/README.md) 의 「그림을 고칠 사진을 받는다」
- [ADR-20261120 / image-source](ADR-20261120-image-source.md) 의 받기 길에 가리킴 하나를 더한다. 그 ADR 의 「가리킴이 아닌 값(주소)은 막는다」 는 그대로다. 주소는 `link:` 가리킴으로만 온다

### 결정

**모델은 `image_generate` 의 바탕이나 참고에 `link:<사용자가 보낸 주소>` 를 적는다. Control Plane 이 그 주소가 origin 실행의 대화에서 요청자가 보낸 메시지에 있는지 확인한 뒤, 허용 주소 목록 없이 공개 IP 의 https 주소에서만 사진이나 페이지의 대표 사진을 받아 원본 바이트로 돌려준다. 받은 바이트는 저장하지 않는다.**

| 항목 | 정한 것 |
| --- | --- |
| 받을 수 있는 주소 | 요청자가 그 대화에 보낸 메시지에 있는 주소. 비서가 찾은 주소는 받지 않는다 |
| 내부망 차단 | 넘어가는 주소마다 이름을 풀어 모든 주소가 공개 IP 이고 금지 목록에 없는지 보고, 그 IP 에 고정해 연결한다. 공개 IP 판정은 `ArtifactSourceFetcher` 와 같다. 이름이 풀리지 않는 것과 막힌 것은 같은 응답이다 |
| 금지 목록 | 홈서버 자신에게 되돌아오는 호스트 이름과 IP 대역을 설정 값으로 받는다. 값은 운영 저장소가 갖는다. 비어 있으면 모든 링크를 막는다(개발과 테스트만 명시 설정으로 연다) |
| 허용 주소 목록 | 쓰지 않는다. 스티커 받기(`artifact_write`)의 목록은 그대로다 |
| 받는 것 | 사진 주소면 그 사진, 웹 페이지면 `og:image` 대표 사진 하나. 사진 네 형식, 20MiB. 응답 종류를 사진이 아닌 이름(예: `application/octet-stream`)으로 적었으면 머리 바이트로 네 형식인지 판정해 받는다. `text/html` 은 페이지로 읽는다 |
| 남기는 것 | 받은 바이트는 남기지 않는다. 그림 행에 쓴 링크 주소만 암호화해 남긴다 |

### 대체된 부분

「받을 수 있는 주소」 항목에서 비서가 찾은 주소를 받지 않는다는 부분은 [ADR-20261121 / found-link-image-source](ADR-20261121-found-link-image-source.md) 가 대체했다. 비서가 웹 검색과 페이지 읽기로 찾은 주소도 Control Plane 이 확인한 뒤 받는다. 나머지 항목은 그대로다.

### 맥락

Codex 와 비교한 그림은 상품 사진을 참고로 넣어 모양이 맞았고, 우리 비서는 상품 이름만 보고 모양을 지어냈다(스펙 「목표」).
쇼핑몰마다 사진 서버 주소가 달라, 허용 주소 목록을 쓰면 새 쇼핑몰마다 관리자가 목록을 고쳐야 한다(스펙 DECISION35).
바깥 주소를 서버가 여는 일은 내부망 요청 위조(SSRF)의 입구다. 모델은 페이지 글이나 검색 결과로 조종될 수 있어 모델이 고른 주소를 그대로 열면 안 된다.

### 대안 기각

- fos-ctx 가 Hermes 안에서 직접 받는다: 대화의 메시지를 모르는 쪽이라 「사용자가 보낸 주소인가」 를 판정하지 못한다. 내부망 차단도 두 벌이 된다.
- 모델이 고른 주소를 허용 목록으로만 막는다: 목록 관리가 관리자 일이 되고, 목록 안의 주소라도 사용자가 고르지 않은 상품을 쓸 수 있다.
- Hermes 가 주소를 그대로 받게 둔다(`image_generate` 는 주소를 받는다): 이미지 서비스나 Hermes 가 주소를 열어 내부망 차단과 대화 확인을 모두 건너뛴다. [ADR-20261120 / image-source](ADR-20261120-image-source.md) 가 주소를 막은 까닭과 같다.
- 받은 사진을 대화 첨부로 저장해 다시 쓴다: 남의 사진이 대화와 보관함에 쌓인다(스펙 DECISION36).

### 결과

- 얻는 것: 가족이 링크를 보내면 관리자 설정 없이 그 상품 사진을 그림에 쓴다. 판정이 Control Plane 한 곳에 있고 PR3 의 받기 길을 그대로 쓴다.
- 감당할 것: 사용자가 보낸 임의의 공개 주소를 서버가 연다. 내부망 판정, 금지 목록, IP 고정에 기대므로 그 코드를 바꿀 때 보안 테스트가 함께 지켜야 한다. 금지 목록이 비면 링크 받기가 모두 막히므로 운영 배포에서 값이 들어갔는지 확인한다. IP 를 근거로 요청을 믿는 내부 서비스가 없다는 전제도 운영 저장소에서 지킨다. 자동 요청을 막는 쇼핑몰은 쓸 수 없고 우회하지 않는다. 메시지 본문을 풀어 찾으므로 긴 대화에서 받기 한 번에 그 대화의 사용자 메시지를 모두 읽는다.
- 확인 방법: 받기 객체의 단위 테스트(내부망, 넘기기, 형식, 크기, 제한 시간)와 받기 경로의 통합 테스트(대화에 있는 주소만). 실제 쇼핑몰 링크로 그림 한 장을 만드는 왕복은 배포 뒤 운영에서 확인한다.
