## ADR-20261015 / financial-user-limits: 주문 상한은 운영 최대치 안에서 계좌 주인이 정하고, 에이전트는 올리기를 승인 카드로만 요청한다

- **status**: `accepted`
- Date: 2026-10-15
- [ADR-20261013 / financial-order-opening](ADR-20261013-financial-order-opening.md) 의 계좌 허용 목록과 통화별 상한 위에 선다. 그 ADR 의 「거절은 어느 검사에 걸렸는지 밝히지 않는다」 를 상한 거절에 한해 개정한다.
- 2026-10-16: 상한과 상한 변경을 두는 곳을 아래 「개정: 상한과 상한 변경을 본체의 컬럼에 둔다」 가 바꾼다.

### 맥락

개방 때 주문 상한은 운영 설정 다섯 값(`max-order-amount-krw`, `max-order-amount-usd`, `max-order-quantity`, `max-daily-amount-krw`, `max-daily-amount-usd`)뿐이었다.
바꾸려면 운영 값을 고치고 재기동해야 했고, 거절은 어느 검사에 걸렸는지 밝히지 않아 사용자는 왜 주문이 막혔는지 알 수 없었다.

소유자가 2026-10-15 에 다음을 정했다.

- 운영 설정의 상한은 최대치다. 실제로 적용하는 상한은 계좌 주인이 최대치 안에서 정한 값이고, 정하지 않았으면 최대치다.
- 사용자는 대화로 바꾼다. 낮추기는 바로 반영해도 되고, 올리기는 계좌 주인의 승인을 거쳐야 한다. 최대치를 넘는 값은 거절하고 최대치를 알린다.
- 「외부 서비스 연결」 화면에서도 지금 값과 오늘 쓴 금액을 보고 바꾼다. 화면에서 올리는 것은 계좌 주인의 직접 조작이라 승인 카드 없이 한 번 더 확인하고 반영한다.
- 에이전트가 승인 없이 상한을 올리는 경로는 하나도 없어야 한다. 외부 글에 숨은 지시에 속아 상한을 올리고 주문을 쌓지 않게 하기 위해서다.
- 상한에 걸린 주문은 어느 상한인지와 오늘 남은 한도를 에이전트와 화면에 알린다. 허용 계좌, key, scope 의 거절 이유는 지금처럼 감춘다.
- 주문 승인 카드에 오늘 남은 한도를 보인다.

정할 것이 넷이었다.

1. 사용자가 정한 상한을 어디에 어떤 단위로 둘까
2. 대화로 올리는 요청을 어떤 승인 흐름에 태울까
3. 하루 합계와 바뀐 상한이 어떻게 맞물릴까
4. 상한 변경 승인과 주문 승인이 겹칠 때 무엇으로 판정할까

### 결정

#### 사용자 단위로 상한 다섯 컬럼을 DB 에 둔다

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| (사용자, 계좌 순번) 단위로 둔다 | 연결 하나와 상한 하나가 맞는다 | 하루 합계는 사용자 단위다. 계좌 단위 상한과 맞추려면 합계를 계좌로 나눠야 하고, 그러면 운영 하루 최대치가 계좌 수만큼 늘어난다 |
| **사용자 단위로 둔다** | 하루 합계와 같은 단위다. 운영 최대치의 뜻이 바뀌지 않는다 | 한 사용자가 계좌 둘을 열면 두 계좌가 상한 하나를 함께 쓴다 |

둘째를 고른다. 한 계좌는 한 사용자에게만 열리므로 계좌 하나를 쓰는 지금은 두 선택지가 같다.

- `financial_order_limit` 테이블이 사용자마다 한 줄을 갖고, 운영 설정과 같은 다섯 컬럼을 둔다. 컬럼이 비었거나 줄이 없으면 그 컬럼은 최대치를 따른다. 2026-10-16 에 `app_user` 의 컬럼으로 옮겼다(아래 개정).
- 적용하는 값은 사용자 값과 최대치 가운데 작은 것이다. 운영자가 최대치를 낮추면 사용자 값이 더 커도 최대치가 이긴다.
- 0 은 그 종류의 주문을 받지 않는다는 뜻이다. 운영 설정의 0 과 같다.
- 비밀값이 아니므로 DB 에 둔다. 금액과 수량은 평문 `DECIMAL` 이다.

#### 대화로 올리는 요청은 승인 줄(`connector_action`)로 만든다

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| 상한 변경만의 요청 테이블과 카드, 승인 API 를 따로 만든다 | 커넥터 도구가 아닌 것을 커넥터 줄에 섞지 않는다 | 승인 카드, 알림과 그 해소, 만료, 대화로 결과 전하기를 다시 만든다 |
| **원고 저장처럼 Control Plane MCP 도구가 승인 줄을 만들고, 종류의 내용은 딸린 테이블에 둔다** | 카드, 알림 해소, 만료, 결과 전하기를 그대로 쓴다 | 승인 API 가 딸린 테이블을 보고 갈래를 나눠야 한다 |

둘째를 고른다.

- Control Plane MCP 에 `order_limit_read` 와 `order_limit_change` 를 둔다. 에이전트가 상한을 바꾸는 길은 `order_limit_change` 하나뿐이다.
- 낮추거나 같은 값은 바로 반영하고 줄을 만들지 않는다. 더 닫히는 쪽이라 승인이 없어도 주문이 늘지 않는다.
- 최대치를 넘는 값은 줄 없이 거절하고 최대치를 답에 싣는다.
- 그 사이의 올리기는 PENDING 승인 줄을 만들고 반영하지 않는다. 승인 줄은 부른 에이전트에 붙은 금융 연결의 줄이다. 위험도는 `WRITE`, 승인 방식은 `always` 라 상시 허락과 대화 허락을 받지 않는다.
- 요청한 종류와 값은 딸린 테이블 `financial_limit_change` 에 둔다. 승인 API 는 그 줄이 있으면 금융 주문 승인보다 먼저 상한 변경 승인으로 보낸다. 2026-10-16 에 승인 줄의 컬럼으로 옮겼다(아래 개정).
- 승인은 그 순간의 최대치로 다시 본다. 그 사이에 최대치가 내려가 넘게 되면 반영하지 않고 실패로 끝낸다.
- 살펴보기 트리(매일 깨우기 포함)는 이 도구를 부르지 못한다. MCP 가 살펴보기 트리의 도구 호출을 정해진 목록 밖이면 막기 때문이다. 일반 예약 작업은 부를 수 있지만 올리기는 승인 줄만 만든다.
- 화면의 변경은 브라우저 세션으로만 부르는 API 다. 에이전트는 이 API 를 부를 수 없다.

#### 하루 합계는 그대로 두고 바뀐 상한과 비교만 한다

- 오늘 쓴 금액은 지금처럼 KST 하루에 승인한 EXECUTING, SUCCEEDED, UNKNOWN 주문의 금액 합이다.
- 상한을 낮춰 오늘 쓴 금액이 새 하루 상한보다 커지면 남은 한도는 0 이다. 이미 승인한 주문은 되돌리지 않고, 새 주문은 다음 KST 하루까지 거절한다.
- 대기 중인 주문 카드는 승인할 때 그 순간의 상한으로 다시 판정한다.

#### 상한을 바꾸는 쪽도 사용자 행을 잠근다

- 금융 준비와 금융 승인은 이미 사용자 행(`app_user`)을 잠근 뒤 하루 합계와 상한을 본다.
- 상한을 바꾸는 세 경로(대화 낮추기, 상한 변경 승인, 화면 변경)도 같은 행을 잠그고 쓴다.
- 그래서 주문 판정과 상한 변경은 차례로 일어나고, 주문은 그 순간에 커밋된 상한으로 판정한다.

#### 상한 거절만 이유를 밝힌다

- 상한에 걸리면 어느 상한(한 건 금액, 한 건 수량, 하루 합계)인지와 그 상한 값, 통화, 오늘 남은 한도를 밝힌다. 사용자가 정한 값이라 감출 것이 없다.
- 준비 단계의 거절은 에이전트에게 가는 답에 이 내용을 싣고, `order_limit_change` 로 바꿀 수 있음을 안내한다.
- 승인 단계의 거절은 화면에 `FINANCIAL_LIMIT_EXCEEDED` 오류로 가고, 카드는 그 주문이 넘는 상한과 남은 한도를 보인다.
- 허용 계좌, key, scope, 모양이 틀린 주문, 가격 없는 수량 주문의 거절은 지금처럼 한 문장으로 감춘다.

### 결과

- 운영 최대치는 그대로 마지막 상한이다. 사용자가 무엇을 정해도 최대치를 넘지 못한다.
- 에이전트가 올리는 길은 승인 카드뿐이라, 외부 글에 속은 에이전트도 사람의 승인 없이는 상한을 올리지 못한다.
- 낮추기는 승인 없이 반영되므로, 외부 글에 속은 에이전트가 상한을 0 으로 낮춰 주문을 막을 수는 있다. 더 닫히는 쪽이라 감수한다.
- 상한 거절의 이유가 보이므로, 거절 응답으로 다른 사용자의 상한을 알아내는 일은 없다. 상한은 자기 주문에만 보인다.
- 한 사용자가 계좌 둘을 열면 상한 하나를 함께 쓴다. 계좌별 상한이 필요해지면 이 결정을 다시 연다.

### 개정: 상한과 상한 변경을 본체의 컬럼에 둔다

2026-10-16 에 소유자가 저장 위치를 다시 정했다. 사용자, 그룹, 에이전트에 1:1 로 붙는 단순한 값은 따로 테이블을 두지 않고 본체의 컬럼에 두기로 했기 때문이다. 기준은 [저장 모델의 「테이블을 추가하는 기준」](../../backend/docs/data-schema.md#테이블을-추가하는-기준)이 갖는다.
두 테이블 모두 그 경우였다. 상한은 사용자마다 한 줄인 현재값이고, 상한 변경은 승인 줄 하나에 한 줄인 고정 값이다.

| 무엇 | 전 | 후 |
| --- | --- | --- |
| 사용자가 정한 상한 | `financial_order_limit` 의 사용자당 한 줄 | `app_user` 의 DECIMAL(20,6) NULL 컬럼 다섯 개와 `limit_updated_at` |
| 상한 변경 요청 | 승인 줄에 딸린 `financial_limit_change` 의 한 줄 | `connector_action` 의 `limit_kind`, `limit_requested`, `limit_previous` |
| 상한 변경 승인으로 보낼지 | 딸린 줄이 있는가 | 도구 이름이 맞고 서버가 적은 `limit_kind` 가 있는가 |

- 상한의 뜻은 그대로다. NULL 은 운영 최대치를 따르고 0 은 주문을 막으며, 적용 값은 사용자 값과 최대치 가운데 작은 것이다.
- 상한 컬럼은 전용 `UPDATE` 로만 바꾸고, 읽기도 엔티티를 거치지 않는 전용 쿼리로 한다. `AppUser` 엔티티는 이 컬럼을 넣기와 고치기에서 뺀다. 이름 바꾸기처럼 먼저 읽어 둔 사용자를 나중에 저장하는 흐름이 상한을 옛 값으로 덮지 않게 하려는 것이다.
- 상한을 바꾸는 세 경로와 주문 판정이 `app_user` 행을 먼저 잠그는 순서는 그대로다. 바꾸는 쪽은 잠근 뒤 다섯 값을 다시 읽어 쓴다.
- 승인 줄의 세 컬럼은 안전 판정에 쓰는 고정 값이라 구조로 둔다. 종류와 요청 값은 암호화한 인자에도 있지만 이전 값은 인자에 없고, 승인 API 가 인자를 풀지 않고 갈래를 나눌 수 있어야 한다.
- 세 컬럼은 줄을 넣을 때 서버가 적고 바꾸지 않는다. 엔티티도 이 컬럼을 고치기에서 뺀다. 커넥터가 같은 이름의 도구를 선언해도 그 줄에는 이 컬럼이 없어 상한 변경 승인으로 가지 않는다.
- 승인은 지금처럼 그 순간의 최대치로 다시 본다.
- 두 테이블의 줄은 마이그레이션이 옮긴 뒤 테이블을 지운다. 컬럼을 더하는 파일, 줄을 옮기는 파일, 테이블을 지우는 파일로 나눈다.
