## ADR-072: 먼저 알리기의 기본값은 알리지 않음이고 Control Plane 기록에서 정한 신호만 화면 안에 올린다

- **status**: `accepted`
- **결정**: 사용자가 묻지 않았는데 무언가를 보이는 일을 **먼저 알리기**(surfacing)라 부른다.
  후보 하나마다 판정 셋 가운데 하나를 내고, **기본값은 `SUPPRESSED`** 다.

  | 판정 | 뜻 |
  | --- | --- |
  | `NOW` | 지금 볼 것. 사이드바 「지금 볼 것」 링크의 건수와 새 대화 화면의 「확인할 것 N건」 에 세고, 카드의 맨 위에 둔다 |
  | `LATER` | 지금 화면의 카드 안에는 보이지만 건수에 세지 않는다 |
  | `SUPPRESSED` | 보이지 않는다 |

  1. **후보는 Control Plane 이 직접 적은 기록과 할 일에서만 나온다.** 실행 줄, 승인 줄, Memory 제안, 할 일([ADR-073](ADR-073-할-일은-에이전트가-제안하고-사람이-받아들인-것만-챙긴다.md)), 결과 전달 상태(#162)다. 에이전트의 제안(Memory 제안과 할 일 제안)은 후보가 되지만 `NOW` 가 되지 못한다. 외부 서비스의 변화를 지켜보는 감시는 두지 않는다.
  2. **판정은 읽을 때 계산한다.** 지금 화면이나 건수를 읽는 요청이 원래 기록을 읽어 판정한다. 배경 작업, 일정 실행, 알림 대기열을 두지 않는다. 저장하는 것은 사용자의 숨기기와 미루기, 지표 사건뿐이다.
  3. **억제 신호를 먼저 본다.** 사용자가 숨긴 상태, 미룬 기한, 이미 해결된 상태, 원래 기록을 읽지 못한 경우, 오래된 경우 가운데 하나라도 맞으면 `SUPPRESSED` 다. 그다음 관련성 신호가 `NOW` 를 정하고, 나머지는 `LATER` 다.
  4. **같은 원래 기록은 한 번만 보인다.** 항목의 열쇠(`itemKey`)는 원래 기록 하나를 가리키고, 같은 대화의 실행 실패와 결과 전달 실패는 대화 하나로 묶는다. 숨기기는 그 항목의 상태 열쇠(`stateKey`)에 걸려, 새 실패처럼 상태가 바뀌면 다시 보인다.
  5. **판정에 확신도와 신선도를 붙인다.** 확신도는 `CONTROL_PLANE`(기록으로 정해진 것), `USER_CONFIRMED`(사람이 받아들인 것), `MODEL_INFERRED`(에이전트의 제안)다. `MODEL_INFERRED` 는 `NOW` 가 되지 못한다. 신선도는 판정할 때 원래 기록을 읽은 시각이고, 읽지 못한 source 는 추정하지 않고 「불러오지 못했다」 로 보인다.
  6. **항목마다 「왜 보였는가」 를 코드로 남긴다.** `trigger`, 맞은 신호의 목록, 출처의 `source` 와 `ref` 와 시각이다. 화면은 코드에 정해진 문구를 그린다. 모델이 쓴 글로 이유를 만들지 않는다.
  7. **먼저 알리기는 보이기만 한다.** 판정이 Hermes 실행, 커넥터 호출, Memory 쓰기를 시작하지 않는다. 카드의 단추는 이미 있는 동작으로 보낸다. 승인은 승인 API, 실패는 그 대화, 할 일은 할 일 API 다. 결과 전달 실패는 그 대화를 열고, 다시 전달은 그 대화의 「결과 다시 전달」([ADR-075](ADR-075-결과-전달은-묶음과-시도로-남기고-사용자가-저장된-결과만-다시-전달한다.md))이 한다. 모두 사용자가 누를 때만 돈다.
  8. **화면 안에서만 보인다.** 판정에 `channel` 칸을 두고 값은 `IN_APP` 하나다.

  trigger 와 신호의 표, 기준값, 지표는 [`backend/attention.md`](../backend/attention.md) 가 갖는다.
- **맥락**: #160 은 비서가 모든 변화를 요약하는 대신 지금 알아야 할 것만 골라 주의를 지키라고 했다.
  지금 화면 밖으로 알리는 길은 없다. 사용자가 무언가를 알게 되는 길은 대화 안의 알림 줄, 승인 카드, 기억 메뉴의 제안 건수뿐이다.
  실패한 실행은 사용량 목록 안에만 있고, 승인 대기는 그 대화를 열어야 보인다.
  #97 은 별도 workflow engine 을 만들지 않고 실행을 Hermes 에 맡긴다고 정했다.
  2026-10-04 에 사용자가 MVP 를 화면 안에서만 보이기로 정했다. 외부 채널은 나중에 더할 자리만 남긴다.
  같은 날 웹 알림([ADR-070](ADR-070-알림은-control-plane-의-notification-표가-원장이고-웹은-사용자-단위-SSE-로-받는다.md))과의 경계도 정했다. **웹 알림은 일어난 일의 사건 목록**이고 읽음 상태를 갖는다. **먼저 알리기와 지금 화면은 아직 남은 일**을 현재 상태에서 계산한 view 다.
  같은 승인 대기가 두 곳에 보이는 것은 받아들인다. 지금 화면에서 그 승인을 처리해도 알림의 읽음 상태는 바꾸지 않는다. 웹 알림도 원인의 상태를 따라 알림을 바꾸지 않는다.
- **대안 기각**:
  - **먼저 알리기의 판정 결과를 저장한다.** 「지금 남은 일인가」 는 원래 기록의 상태가 바뀌면 함께 바뀐다. 저장하면 상태가 바뀔 때마다 그 줄을 고치는 배경 경로와 다시 시도가 생겨 workflow engine 처럼 커진다. 읽을 때 계산하면 같은 결과를 낸다. 일어난 일 자체를 남기는 웹 알림(ADR-070)은 이 기각과 다르다. 그것은 사건이고 상태가 바뀌어도 고치지 않는다.
  - **무엇이 중요한지 모델에게 묻는다.** 화면을 열 때마다 실행 비용과 대기 시간이 붙고, 개인 기록을 모델에 더 보낸다. 같은 입력에 다른 판정이 나와 「왜」 를 설명하지 못한다.
  - **모든 변화를 보인다.** 사용자가 직접 걸러야 해 #160 의 목적과 반대다.
  - **외부 채널로도 보낸다.** 그 채널의 credential 을 둘 곳, 실을 내용의 민감도, 외부로 나가는 글의 승인(ADR-065)을 함께 정해야 한다. 사용자가 미뤘다.
- **결과**:
  - 얻는 것:
    - 같은 기록이면 같은 판정이 나오고, 그 근거가 코드로 남아 「왜 보였는가」 를 설명할 수 있다.
    - 판정을 바꿔도 지울 저장 상태가 없다. 기준값을 고치면 다음 요청부터 바뀐다.
    - 먼저 알리기가 실행을 시작하지 않으므로 사용자 실행 한도(ADR-069)와 승인 경로(ADR-050)를 건드리지 않는다.
  - 감당할 것:
    - 화면과 건수를 읽을 때마다 여러 표를 읽는다. 한 사용자의 최근 기록만 읽도록 기간과 개수에 상한을 둔다.
    - 화면을 열지 않으면 아무것도 알지 못한다. 급한 일을 놓칠 수 있다는 것을 받아들인다.
    - 집중 모드처럼 사용자가 알리기를 끄는 설정이 없다. 화면 밖으로 나가지 않으므로 미룬다.
    - `itemKey` 와 `stateKey` 를 source 마다 바꾸지 않아야 숨기기가 유지된다.
- **열린 질문**: 외부 채널(Discord, Web Push)을 더할 때 정할 셋이다.
  - credential 을 어디 두는가. 데이터베이스에 비밀값을 넣지 않는 원칙과 어떻게 맞추는가
  - 알림에 무엇을 싣는가. 제목만 실어도 개인 내용이 밖으로 나간다
  - 외부로 나가는 글을 사람이 매번 승인하는가. ADR-065 의 outbound 선언과 어떻게 맞추는가
- **적용 범위**: 할 일 자체의 저장과 제안은 [ADR-073](ADR-073-할-일은-에이전트가-제안하고-사람이-받아들인-것만-챙긴다.md), 판정을 그리는 화면은 [ADR-074](ADR-074-지금-화면은-원래-기록을-읽어-만든-view-이고-정해진-카드-넷만-그린다.md) 가 정한다.
  결과 전달 실패의 상태는 #162 가 저장하고, 이 판정은 그것을 읽기만 한다.
