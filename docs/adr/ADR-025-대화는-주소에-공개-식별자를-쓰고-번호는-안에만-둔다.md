## ADR-025: 대화는 주소에 공개 식별자를 쓰고 번호는 안에만 둔다

- **status**: `accepted`
- **결정**: 대화마다 UUID 공개 식별자 `public_id` 를 둔다. 화면 주소와 Control Plane API 는 대화를 이 식별자로만 주고받는다.
  대화 표의 번호(`id`)는 그대로 PK 이고 다른 표의 참조도 그대로다. 번호는 Control Plane 안에서만 쓴다.
  화면 주소는 `/c/{번호}` 에서 `/chat/{공개 식별자}` 로 바꾸고, 옛 주소는 주인에게만 새 주소로 넘겨 준다.

### 맥락

대화 주소가 `/c/120` 처럼 1씩 늘어나는 번호였다.
주인 확인은 모든 대화 경로에 있어서 번호를 바꿔 넣어도 남의 대화가 열리지는 않는다.
그래도 두 가지가 남는다.

- 경로를 더하다 주인 확인을 한 번 빠뜨리면, 번호를 하나씩 바꿔 넣는 것만으로 남의 대화가 열린다.
  맞힐 수 없는 식별자는 그 실수를 한 겹 더 막는다.
- 주소만 보고 대화가 몇 개인지, 얼마나 자주 만들어지는지 알 수 있다.
  이 화면을 공개하는 것을 검토하고 있어 주소를 나중에 바꾸는 비용이 계속 커진다.

### 대안 기각

- **PK 를 UUID 로 바꾼다.** 대화를 참조하는 표(`chat_message`, `agent_execution`, `chat_attachment`)의 외래 키를 모두 옮겨야 한다.
  UUID PK 는 인덱스가 커지고 넣는 순서가 흩어져 쓰기가 느려진다. 공개용 칸 하나로 같은 것을 얻는다.
- **번호를 그대로 두고 주인 확인만 믿는다.** 지금은 구멍이 없다. 그러나 앞으로 더할 경로 하나하나가 확인을 빠뜨리지 않아야 안전하다.
- **첨부, 실행, 메시지 번호도 바꾼다.** 이것들은 대화 안에서만 쓰이고 사용자가 링크로 주고받지 않는다.
  모두 주인 확인을 거친다. 바꾸는 비용에 비해 얻는 것이 적다.
- **옛 주소를 버린다.** 번호를 받는 경로가 완전히 사라진다.
  그러나 가족이 저장해 둔 링크가 모두 「없는 대화」 가 된다. 넘겨 주는 경로는 주인 확인을 거치므로 새로 드러나는 것이 없다.

### 결과

- 얻는 것: 주소로 대화를 맞히거나 셀 수 없다. 주인 확인을 빠뜨린 경로가 생겨도 식별자를 알아야 닿는다.
- 감당할 것:
  - 새 대화는 UUID v7 을 받는다. 시간 순서로 만들어져 v4 보다 인덱스에 부담이 적다. Hibernate 의 생성기를 쓰므로 새 의존성이 없다
  - 이미 있는 대화는 마이그레이션이 임의 값(v4)을 채운다. MySQL 에 v7 을 만드는 함수가 없고, 주소에 쓰는 데는 버전이 상관없다
  - Control Plane 의 대화 경로와 응답 칸이 모두 UUID 를 받는다. web 과 테스트가 함께 바뀐다
  - 옛 주소를 넘겨 주려고 번호로 대화를 찾는 경로가 하나 남는다. 주인만 답을 받는다. 옛 링크가 쓰이지 않게 되면 지운다
  - 사진이 놓이는 디렉터리 이름은 대화 번호 그대로다. 사람이 보지 않고 Hermes 만 파일 경로로 읽는다
