# 기억 전체 암호화와 민감 구분 제거

확인: 2026-11-03

구현을 마친 변경의 기록이며 지금 동작은 [기능 파일](../memory.md)이 갖는다.
이 스펙은 PR 세 개로 구현했다. PR1 은 REQ1 부터 REQ4, REQ6 부터 REQ8 이고, PR2 는 REQ5 의 코드와 화면, DECISION17 이다. REQ5 의 「칸이 없다」 는 PR2 배포를 확인한 뒤 칸을 지우는 PR3 이 채웠다(설계의 DECISION8, 「PR3: 옛 칸 삭제」).

## 목표

모든 기억의 제목과 본문을 DB 에 평문으로 두지 않는다. 그다음 「민감 기억」 구분을 없애, 주인은 자기 기억을 모두 화면에서 보고 고치고 에이전트는 받은 collection 의 기억을 쓴다.
지금은 일반 기억 23건이 평문이고, 민감 기억 28건은 암호화돼 있지만 민감 허용을 켠 에이전트가 없어 아무도 쓰지 못하고 주인도 볼 수 없다.

## 범위

이번 범위:

- `memory` 와 `memory_revision` 의 제목과 본문을 주인 key 로 암호화한다. `USER` 범위는 사용자별 데이터 key, `GROUP` 범위는 새로 둘 그룹별 데이터 key 다
- 이미 있는 평문 줄과, 민감 key 로 암호화한 28건을 새 key 로 다시 쓴다
- 암호화를 마친 뒤 민감도 칸, 에이전트의 민감 허용, 화면의 「민감한 내용이라 보이지 않아요」, 민감 항목 수정 거절을 없앤다
- 목록, 상세, 검색, 색인, 개인 사실 구역, 「참고한 기억」 이 앱 안에서 풀어 쓴다

범위 밖:

- 임베딩 벡터의 암호화. 벡터는 평문으로 둔다
- 기억 밖의 데이터(대화 제목, 예약 작업 등). [ADR-20261008 / data-encryption](../../../backend/docs/adr/ADR-20261008-data-encryption.md) 과 `backend/docs/data-schema.md` 의 「본문 칸과 운영 조회」 가 갖는다
- 기억 쓰임(usage) 스펙. 이 스펙이 머지된 뒤 그 스펙을 이어 쓴다
- 「민감해 보이는 글은 제안 카드로」 저장 규칙(바로 저장 조건 6, 7). 저장 정책이라 이번에 바꾸지 않는다
- Hermes 쪽 실행 기록(`state.db`)에 남는, 실행 때 실은 기억 글. Hermes 가 갖는 저장소라 이번 암호화 대상이 아니다

## 요구사항과 인수 조건

| ID | 요구사항 | 관측할 인수 조건 |
| --- | --- | --- |
| REQ1 | 기억의 제목과 본문은 DB 에 평문으로 남지 않는다 | 이관 뒤 운영에서 `memory`, `memory_revision` 의 제목과 본문이 모두 암호문 꼴이고, key id 칸이 빈 줄이 0건이다. 새로 저장하고 고친 줄도 같다 |
| REQ2 | `USER` 기억은 그 사용자의 데이터 key, `GROUP` 기억은 그 그룹의 데이터 key 로 암호화한다 | 다른 사용자나 다른 그룹의 key 로는 풀리지 않는다(테스트). 그룹 key 는 기존 key 테이블에 줄로 더하고 새 테이블을 만들지 않는다 |
| REQ3 | 민감 key 로 암호화한 28건을 잃지 않고 옮긴다 | 이관 전후 건수와 각 줄의 본문 해시가 같다. 옮긴 뒤 옛 민감 key 를 쓰는 줄이 0건이다 |
| REQ4 | 화면과 에이전트의 동작은 암호화 전과 같다 | 목록, 상세, 검색, 색인, 개인 사실 구역, 「참고한 기억」, `memory_search`, `memory_read` 의 기존 테스트가 통과하고, 기존 「Memory 회수 측정」 이 악화 금지 게이트를 통과한다 |
| REQ5 | 민감 구분이 없다 | 민감도 칸과 에이전트의 민감 허용 칸이 없다. `/memory` 와 제안 카드, 대화의 「기억했어요」 에 「민감한 내용이라 보이지 않아요」 가 없고, 주인은 28건을 보고 고친다. collection 허용은 그대로 에이전트가 받을 기억을 나눈다 |
| REQ6 | key 를 읽지 못하면 평문으로 내려 저장하지 않는다 | 운영(데이터 암호화 필수 설정)에서 key 를 읽지 못하면 저장과 수정은 거절되고, 목록은 실패하지 않고 그 줄만 「읽지 못함」 으로 보인다. 필수 설정이 꺼진 로컬과 개발 설치는 대화 메시지와 같이 평문 저장을 허용하고 경고를 남긴다 |
| REQ7 | 관리자 화면은 다른 사용자의 개인 기억 제목을 보이지 않는다 | 에이전트 상세의 「최근 변경」 과 정리 후보 화면에서 남의 `USER` 기억은 건수만 보인다 |
| REQ8 | 이관 실패가 남지 않는다 | 이관이 줄 하나라도 실패하면 그 줄 번호만 로그에 남기고 기동은 잇는다. 민감 구분 제거 PR 은 운영의 평문 줄과 옛 key 줄이 0건인 것을 확인한 뒤에만 연다 |

## 설계

요지만 적는다. 상세는 [`design.md`](design.md) 가 갖는다.

- 암호화 PR 은 배포 뒤 직전 이미지로 되돌리지 않는다. 직전 이미지는 암호문을 그대로 화면과 답에 낸다. 이관 직전에 DB 백업을 하나 떠 두고, 문제가 생기면 앞으로 고친다
- PR 은 둘 이상이다. 1) 그룹 key 와 기억 암호화, 이관(REQ1~REQ4, REQ6) 2) 민감 구분 제거(REQ5). 1 을 배포해 운영 건수를 확인한 뒤 2 를 연다
- 사용자별 데이터 key 는 대화 메시지가 쓰는 [ADR-20261008 / data-encryption](../../../backend/docs/adr/ADR-20261008-data-encryption.md) 의 key 다. 민감 본문의 환경 변수 key([ADR-055](../../../backend/docs/adr/archive/ADR-055-민감-memory-본문은-저장할-때-암호화하고-key-는-환경-변수로-받는다.md))는 이관 뒤 쓰지 않는다
- 검색은 지금도 후보를 SQL 로 읽고 점수를 앱에서 매긴다. 제목과 본문을 앱에서 풀어 점수를 매긴다. 운영 기억이 수십 건이라 속도 영향은 작고, 측정 게이트로 확인한다
- 근거: `docs/features/memory.md` 의 「범위와 조립」 가운데 「제목과 본문」 단락, 「기억 검색의 구현 계약」, 「개인 사실 구역」, `backend/docs/data-schema.md` 의 `memory`, `user_data_key`
