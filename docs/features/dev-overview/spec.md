# 웹에서 개발 문서와 로드맵을 보고, 관리자는 진행 보드까지 점검한다

확인: 2026-11-17

## 목표

사용자가 assistant 웹에서 이 저장소의 개발 문서와 앞으로 할 일(로드맵)을 읽고, 관리자는 지금 진행 중인 작업(진행 보드)까지 함께 보며 큰 그림을 점검한다.
문서와 로드맵은 모든 사용자의 일반 화면에, 진행 보드는 관리자 영역에 둔다(DECISION5).
설계 그림과 검토 문서를 미리보기 파일로 흩어 두지 않고 저장소 문서로 남겨, 다음 작업 전에 지금 구조와 방향을 다시 확인할 수 있게 한다.

원본은 저장소의 `docs/` 하나다. 웹은 배포된 커밋의 문서를 읽기 전용으로 보이고, 고칠 때는 지금처럼 PR 로 고친다(DECISION1).

## 범위

이 스펙은 PR 둘로 구현한다(DECISION7). 첫 PR 은 이 스펙의 설계와 PR1 구현을 함께 담는다.

| PR | 담는 것 | 요구사항 |
| --- | --- | --- |
| PR1 | 일반 화면의 「개발 문서」 화면, 문서를 웹 이미지에 담기, 문서 목록과 본문, mermaid 그림, 커밋 해시, `docs/prd.md` 의 「로드맵」 절과 그 표시 | REQ1, REQ2, REQ3, REQ4, REQ5, REQ6, REQ9 |
| PR2 | Control Plane 의 보드 받기 API 와 저장, 관리자 영역의 「진행 보드」 화면 | REQ7, REQ8 |

코디네이터 맥북에서 보드를 보내는 쪽(fos-skills 의 `orch`)은 이 저장소 밖의 별도 작업이다. PR2 가 배포된 뒤 그 작업이 붙어야 REQ7 을 운영에서 확인할 수 있다.

범위 밖:

- 웹에서 문서를 쓰거나 고치는 것. 고치기는 PR 로만 한다(DECISION1)
- GitHub Wiki, 공개 정적 사이트, DB 에 담는 위키(DECISION1)
- 운영 저장소(`fos-home-infra`)의 문서. 공개 저장소 규칙에 따라 이 화면에 넣지 않는다
- 웹에서 진행 보드를 고치는 것. 보드는 지금처럼 코디네이터가 고친다
- Agent Runtime 추상화 검토 그림을 이 PR 에서 옮기는 것. 자리만 정하고 옮기는 일은 Hermes 업그레이드 뒤 추상화 스펙 PR 이 한다(DECISION9)

## 요구사항과 인수 조건

| ID | 요구사항 | 관측할 인수 조건 |
| --- | --- | --- |
| REQ1 | 문서와 로드맵은 모든 사용자, 진행 보드는 관리자만 연다 | 로그인한 사용자는 역할과 상관없이 사이드바 「고급」 의 「개발 문서」 에서 문서와 로드맵 화면을 연다. `ADMIN` 은 관리자 영역의 메뉴에서 「진행 보드」 를 열고, 그 화면에서 「개발 문서」 로 가는 링크가 있다. `MEMBER` 역할 사용자에게는 「진행 보드」 메뉴가 없고 주소로 열면 첫 화면으로 돌아가며, 보드 API 는 그 사용자에게 보드를 내지 않는다(DECISION5, DECISION11) |
| REQ2 | 배포된 커밋의 문서를 읽기 전용으로 보인다 | 화면 위에 그 문서를 담은 커밋의 짧은 해시가 보이고, 누르면 GitHub 의 그 커밋으로 간다. 문서에 고치는 단추가 없다. 각 문서에 「GitHub 에서 보기」 링크가 있어 같은 커밋의 같은 파일로 간다 |
| REQ3 | 문서 목록을 정한 단위로 보인다 | DECISION4 의 묶음으로 목록이 보인다. 목록의 이름은 문서의 첫 제목(H1)이다. 찾기 칸에 글자를 넣으면 목록 이름이나 파일 이름에 그 글자가 든 줄만 남고, 기능의 스펙이나 설계만 맞으면 그 기능 줄이 펼쳐진 채 남는다(DECISION12) |
| REQ4 | 문서 본문을 Markdown 으로 그린다 | 표, 코드 블록, 제목이 그려진다. 문서 안의 HTML 은 실행되지 않는다(rule-57). 상대 링크가 목록에 있는 문서를 가리키면 이 화면 안의 그 문서로 가고, `#절` 이 있으면 그 절로 내려간다. 목록에 없는 파일(코드, `README.md`, 목록 밖 문서)을 가리키면 같은 커밋의 GitHub 파일이 새 탭으로 열린다. 저장소 밖 링크는 새 탭으로 간다(DECISION13) |
| REQ5 | mermaid 그림을 손그림과 노드 종류별 색으로 그린다 | 문서의 ` ```mermaid ` 블록이 그림으로 보인다. 블록에 `look` 설정이 없어도 손그림(`handDrawn`)으로 그리고, 블록이 정한 `classDef` 색이 보인다. 그림 문법이 틀리면 그 블록 자리에 원문과 「그림을 그리지 못했어요」 가 보이고 나머지 본문은 그대로 보인다. 화면이 어두운 테마여도 그림은 밝은 바탕 위에 `classDef` 색 그대로 그린다(DECISION16) |
| REQ6 | 로드맵을 보인다 | 「개발 문서」 를 열면 처음에 DECISION3 의 로드맵이 보이고 문서 목록은 옆에 있다. 로드맵은 원본 표를 Markdown 그대로 그리고, 줄 안의 링크는 REQ4 의 링크 규칙대로 하나씩 동작한다(DECISION14) |
| REQ7 | 진행 보드를 보인다 | 보드 항목이 받은 순서대로 보인다. 항목마다 제목, 상태 꼬리표, 단계 이름과 끝난 단계의 체크, 정할 것 제목, 연결 PR 이 보인다. 상태는 아는 값이면 우리말로, 모르는 값이면 원문으로 보인다. PR 번호는 GitHub 의 그 PR 로 가는 링크다. 보드를 받은 시각이 보이고, DECISION2 가 정한 길로 보드가 바뀌면 다음에 화면을 열 때 바뀐 내용이 보인다(DECISION15) |
| REQ8 | 보드가 없거나 오래됐을 때 | 받은 보드가 없으면 「아직 받은 진행 보드가 없어요」 가 보인다. 받은 지 DECISION6 의 기준보다 오래면 받은 시각 옆에 「오래됨」 이 붙는다. 보드를 읽지 못하면 「불러오지 못했어요」 와 다시 읽기가 보인다. 칸이 빠지거나 모양이 틀린 보드는 받을 때 거절되고 보낸 쪽이 오류를 받으며, 화면은 마지막으로 받은 보드를 그대로 보인다(DECISION17) |
| REQ9 | 화면에 운영 정보가 나오지 않는다 | 화면이 읽는 문서는 공개 저장소의 `docs/` 와 모듈 `docs/` 뿐이다. 진행 보드에서 화면으로 보내는 칸은 DECISION2 가 정한 칸뿐이다 |

## 도메인 규칙 변경

도메인 규칙 변경 없음: 개발 문서와 진행 보드를 보여 주는 화면이고 대화, 실행, 기억, 플러그인 규칙을 바꾸지 않는다.

## 배포 뒤 확인

- 관리자가 아닌 계정으로 「개발 문서」 를 열어 문서와 로드맵이 보이는지 본다
- 관리자 계정으로 「개발 문서」 를 열어 화면 위 커밋 해시가 배포한 커밋과 같은지 본다
- mermaid 그림이 든 문서 하나를 열어 손그림과 색으로 그려지는지 본다
- `MEMBER` 역할 계정으로 「진행 보드」 주소를 열면 첫 화면으로 돌아가는지 본다
- 진행 보드를 한 번 보낸 뒤 화면에 그 내용과 받은 시각이 보이는지 본다(보드 PR 이 배포된 뒤)
