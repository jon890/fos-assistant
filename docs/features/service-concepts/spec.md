# 서비스 개념: 에이전트가 우리 서비스의 말을 알아듣고 직접 처리한다

확인: 2026-11-20

## 목표

사용자가 대화에서 서비스의 기능을 평소 말로 부르면 에이전트가 알아듣고 가능한 한 직접 처리한다.
「이거 매일 아침 7시에 해 줘」, 「이거 할 일로 적어 둬」, 「그거 끝냈어」, 「그 기억 지워 줘」, 「구글 캘린더 연결해 줘」, 「더 좋은 모델로 해 줘」, 「블로그 비서로 바꿔 줘」 가 그 예다.
사용자가 직접 골라야 하는 것(모델 단계, 대화할 에이전트)과 사람이 눌러야 하는 것(계정 연결의 동의 화면)은 에이전트가 대신하지 않고 그 자리로 가는 길을 알린다.

이 문서에서 쓰는 두 낱말의 뜻은 이렇다.

- **할 일**: 「지금 볼 것」 화면(`/now`)의 「할 것」 목록에 보이는 한 줄이다. 사용자가 해야 하거나 끝나기를 기다리는 일이다. 코드는 `follow_up` 이다
- **모델 단계**: 입력창에서 고르는 단추(Instant 부터 Pro 까지)다. 답 하나에 쓸 모델의 등급을 정한다([`model-usage.md`](../model-usage.md))

지금은 아래와 같다(2026-11-20 main).

- 파일 공간: 매 실행 입력에 설명과 넣기 도구(`file_space_put`) 규칙이 있다([파일 공간 스펙](../workspace/spec.md) REQ7)
- 기억: `memory_remember` 를 받은 에이전트에게만 「기억」 지침이 있다. 에이전트는 기억 화면(`/memory`)을 모르고, 기억을 지우는 도구가 없다
- 할 일: `follow_up_propose` 가 제안(`PROPOSED`)만 만들고 사용자가 「지금 볼 것」 에서 받아들여야 챙긴다. 끝내는 도구가 없다
- 예약 작업, 외부 서비스 연결, 모델 단계, 에이전트 고르기: 실행 입력에 설명이 없고 에이전트가 쓸 도구도 없다. 「매일 아침 7시에 날씨 알려 줘」 라고 하면 에이전트는 예약 작업이 있는지 모른다

## 범위

이 스펙은 PR 넷으로 구현한다(DECISION15). 이 스펙을 처음 구현하는 PR 은 PR1 이고, 뒤의 PR 은 같은 스펙과 설계를 쓴다.

| PR | 담는 것 | 시작 조건 | 요구사항 |
| --- | --- | --- | --- |
| PR1 | 모든 개념의 짧은 목록, 직접 처리하지 않는 개념의 안내(모델 단계, 에이전트 바꾸기, 연결 화면 링크), 아직 도구가 없는 개념의 화면 안내, 실제 모델 평가 세트 | 없음 | REQ1-REQ6 |
| PR2 | 예약 작업 만들기·고치기·멈추기·다시 켜기, 지우기 승인 카드 | PR1 이 main 에 머지됐다 | REQ7-REQ10 |
| PR3 | 할 일 바로 만들기와 끝내기, 기억 지우기 승인 카드 | PR2 가 main 에 머지됐다 | REQ11-REQ14 |
| PR4 | 연결이 끝난 뒤 「이 에이전트에 붙이기」 승인 카드 | PR3 이 main 에 머지됐다 | REQ15-REQ16 |

REQ17, REQ18 은 PR 마다 그 PR 이 더한 도구에 적용한다.
뒤 PR 이 들어오기 전까지 그 개념은 REQ3 의 화면 안내로 동작한다. PR 이 들어오면 그 개념의 안내가 직접 처리로 바뀌고, 그 PR 이 평가 세트에 그 개념의 직접 처리 문장을 더한다.

**승인 카드**는 플러그인 쓰기에 쓰는 지금의 확인 카드와 같은 자리(대화 옆 패널, 입력창 위의 건수 한 줄)와 흐름이다([`connector-policy.md`](../connector-policy.md)). 사용자가 승인을 누르면 Control Plane 이 저장한 인자로 한 번 실행한다. 이 스펙의 카드에는 승인과 거절만 두고 「계속 허용」 단추는 두지 않는다. 승인한 뒤에는 그 대화에 결과를 알리는 알림 줄만 남기고 에이전트가 다시 답하지 않는다(DECISION21). 에이전트는 사용자에게 「승인 카드」 라고 부르고, 패널의 탭 이름은 이 문서의 할 일과 헷갈리므로 쓰지 않는다.

이 문서의 「지금 볼 것」 은 용어 표의 **지금 화면**(`/now`)의 화면 이름이다([화면 틀 스펙](../app-shell/spec.md) REQ1).

범위 밖은 아래와 같다.

- 에이전트가 모델 단계를 바꾸는 것(DECISION7)
- 에이전트가 대화의 에이전트를 바꾸거나, 다른 에이전트로 새 대화를 만들어 요청을 옮기는 것(DECISION8). 에이전트가 필요할 때 다른 에이전트에게 일을 맡기는 지금의 위임은 그대로다
- 사용량. 에이전트는 사용량을 답하지도 안내하지도 않는다. 사용자 화면의 사용량(`/usage`)을 없애는 일은 이 스펙 밖의 별도 작업이다(DECISION9)
- 에이전트가 계정 연결의 로그인·동의를 대신하는 것, 연결을 떼거나 해제하는 것(DECISION6)
- 에이전트가 기억을 새로 쓰는 규칙과 바로 저장 판정을 바꾸는 것. `memory_remember` 와 [`memory.md`](../memory.md) 의 「바로 저장 판정」 은 그대로다(DECISION5)
- 에이전트가 다른 사람의 예약 작업, 할 일, 기억, 연결을 다루는 것(DECISION13)
- 관리자만 바꾸는 설정(에이전트 도구, 그룹 모델 설정, 사용자 관리)을 에이전트가 바꾸는 것(DECISION13)
- 에이전트가 에이전트를 만들거나 고치거나 지우는 것

## 요구사항과 인수 조건

| ID | 요구사항 | 관측할 인수 조건 |
| --- | --- | --- |
| REQ1 | 대화의 매 실행 입력에 서비스 개념 목록이 있다(PR1). 개념마다 이름, 사용자가 부르는 말, 화면 주소를 한 줄로 적는다. 모델 단계와 에이전트 고르기는 화면이 아니라 입력창의 단추와 `@` 이므로 주소 없이 쓴다(DECISION19). 개념은 파일 공간, 예약 작업, 기억, 할 일과 「지금 볼 것」, 외부 서비스 연결, 모델 단계, 에이전트 고르기다. 사용량은 없다. 화면 이름과 자리는 [화면 틀 스펙](../app-shell/spec.md) 이 정한 것(사이드바의 「지금 볼 것」, 「예약 작업」, 「기억」, 「설정」 안의 「외부 서비스 연결」, 「파일 공간」)을 쓴다. 언제 어떻게 처리하는지의 자세한 규칙은 실행 입력이 아니라 그 도구의 설명에 둔다(DECISION11). 지금의 파일 공간 단락은 그대로 두고 목록에는 이름과 주소 한 줄만 더한다(DECISION20) | 가짜 Hermes 가 받은 대화 실행 입력에 일곱 개념의 이름이 있고 화면이 있는 다섯 개념의 주소가 있으며 「사용량」 이나 `/usage` 가 없다. 예약 작업의 실행, 먼저 살펴보기, 맡긴 실행의 입력에도 같은 목록이 있다. 파일 공간 스펙 REQ7 의 인수 조건이 그대로 통과한다 |
| REQ2 | 사용자가 모델 단계를 바꿔 달라고 하면(「더 좋은 모델로 해 줘」, 「빠르게 답해 줘」) 에이전트는 단계를 바꾸지 않고, 입력창의 모델 단계 단추에서 고르면 다음 답부터 그 단계로 답한다고 안내한다. 바꿨다고 말하지 않는다(PR1) | 실행 입력의 모델 단계 줄에 이 규칙이 있다. 에이전트가 모델 단계를 바꾸는 도구가 없다. 모델 단계는 대화로 평가하지 않는다(DECISION35) |
| REQ3 | 아직 직접 처리하는 도구가 없는 개념을 부탁받으면 에이전트는 했다고 말하지 않고, 그 화면으로 가는 링크를 붙여 거기서 하는 방법을 알린다(PR1). 링크는 서비스 안의 상대 주소(`/tasks/new`, `/now`, `/memory`, `/connections`)다. 도구가 생긴 개념은 REQ7 부터의 요구사항대로 직접 처리한다 | PR1 만 들어간 상태의 평가 세트에서 「매일 아침 7시에 날씨 알려 줘」 의 답에 `/tasks` 로 가는 링크가 있고 「만들었다」 가 없다 |
| REQ4 | 사용자가 다른 에이전트로 바꿔 달라고 하면(「블로그 비서로 바꿔 줘」) 에이전트는 대화의 에이전트를 바꾸지 않는다. 입력창의 `@` 로 그 에이전트를 불러 다음 메시지를 맡기거나 새 대화에서 고를 수 있다고 안내하고, 그 에이전트가 골라진 새 대화 링크(`/new?agent=<code>`)를 붙인다. 요청자가 쓸 수 있는 에이전트만 링크를 붙이고, 없는 이름이면 쓸 수 있는 에이전트의 이름을 알린다(PR1) | 평가 세트의 에이전트 바꾸기 문장에서 답에 그 에이전트의 `/new?agent=` 링크가 있다. 링크를 열면 새 대화 화면에 그 에이전트가 골라져 있다. 요청자가 쓸 수 없는 에이전트의 이름으로 물으면 링크가 없다 |
| REQ5 | 사용자가 외부 서비스를 연결해 달라고 하면(「구글 캘린더 연결해 줘」) 에이전트는 그 플러그인의 연결 화면(`/connections/{id}`)으로 가는 링크를 주고, 그 화면에서 계정을 연결하라고 안내한다. 지금 에이전트가 요청자가 주인인 비공개 에이전트면 링크에 `?agent=<지금 에이전트>` 를 붙여 연결 화면이 그 에이전트를 맨 앞에 두고 바로 붙일 수 있게 한다. 그 밖의 에이전트면 `?agent=` 없이 준다(DECISION22). 이미 연결돼 있으면 그렇다고 알린다. 그런 플러그인이 없으면 없다고 알리고 연결 화면 목록(`/connections`) 링크를 준다(PR1) | 평가 세트의 연결 문장에서 있는 플러그인은 그 `/connections/{id}` 링크가, 없는 서비스는 「없다」 와 `/connections` 링크가 답에 있다. 에이전트가 연결했다고 말하지 않는다 |
| REQ6 | 개념마다 사용자가 쓸 법한 문장 여러 개를 실제 모델로 돌려 에이전트가 알아듣는지 보는 평가 세트가 있다(PR1). 문항마다 통과 조건(부른 도구, 답에 있어야 할 링크, 답에 없어야 할 말)을 적고, 판정 규칙은 네트워크 없이 단위 테스트로 검사한다. 이 스펙의 지침이나 도구 설명을 고치는 PR 은 평가를 두 번 돌린다. 머지 전에 바뀌기 전 지침의 운영에서 돌린 기준선을 PR 본문에 남기고, 머지·배포 뒤 다시 돌린 결과를 기능 완료 증거와 PR 댓글에 남긴다. 운영에서 돌리는 일은 코디네이터나 사용자가 한다. 기준에 못 미치면 지침을 고치는 후속 PR 을 연다(DECISION33). 기존 답변 품질 평가(`test/model-eval/answer/`)의 틀을 쓸 수 있는지는 기술 설계가 정한다(DECISION14) | 평가 세트에 REQ1 의 개념마다 문장이 둘 이상 있다. 판정 규칙의 단위 테스트가 CI 에서 돈다. PR1 본문에 기준선의 문항별 통과 여부가 있고, 배포 뒤 결과가 기능 완료 증거에 있다 |
| REQ7 | 사용자가 예약 작업을 부탁하면 에이전트가 바로 만든다(PR2). 사용자가 말한 시각과 반복을 채우고, 지시문은 DECISION28 의 요소를 갖춰 대화 맥락으로 쓰며, 에이전트는 지금 대화의 에이전트, 시간대는 화면에서 새로 만들 때의 기본값(`Asia/Seoul`), 모델 단계는 비워 그 에이전트의 기본 단계로 돈다. 대화 방식은 부탁한 그 대화에 이어 쌓기다(DECISION29). 발화마다 결과가 그 대화에 이어 붙고, 사람이 그 대화에서 이야기하는 동안 발화가 오면 지금처럼 잠금을 기다린다. 나머지 칸(놓친 실행 처리, 알림)은 화면에서 새로 만들 때의 기본값이다(DECISION12). 반복 간격과 하루 발화 수는 화면과 같은 한도(최소 15분, 사용자당 24시간 48번)를 따르고, 넘으면 만들지 않고 까닭을 알린다(DECISION30). 작업의 주인은 그 대화를 연 사용자다. 만든 뒤 답에 작업 이름, 다음 실행 시각, 지시문 요약, 그 작업 화면(`/tasks/{id}`) 링크를 적는다. 시각이나 반복이 모호하면 만들지 않고 되묻는다. 맡긴 실행처럼 부탁한 대화가 없으면 매번 새 대화다 | 가짜 Hermes 가 만들기 도구를 부르면 요청자의 예약 작업 목록에 그 작업이 있고, 에이전트와 시각과 반복이 맞으며 모델 단계가 비어 있다. 도구 결과에 작업 화면 주소가 있다. 평가 세트에서 「매일 아침 7시에 날씨 알려 줘」 가 만들기 도구를 부르고 답에 `/tasks/` 링크가 있다. 대화에서 조건 감시나 브리핑을 부탁한 문항에서 만든 지시문에 조건, 확인 방법, 알릴 기준, 새것이 없으면 알리지 않는다는 말이 있다 |
| REQ8 | 사용자가 예약 작업을 고치거나 멈추거나 다시 켜 달라고 하면 에이전트가 바로 한다(PR2). 에이전트는 요청자의 예약 작업 목록을 읽어 대상을 찾는다. 대상이 둘 이상이면 되묻는다. 고치는 칸은 이름, 지시, 시각과 반복, 알림이다. 모델 단계, 에이전트, 시간대, 대화 방식은 고치지 않는다. 대상은 일반 예약 작업이고 에이전트의 「매일 깨우기」 는 다루지 않으며 그 에이전트 화면(`/agents/{code}`) 링크로 안내한다(DECISION23) | 가짜 Hermes 가 멈추기 도구를 부르면 그 작업이 멈춘 상태다. 같은 이름의 작업이 둘이면 도구가 후보를 돌려주고 바꾸지 않는다. 고치기 도구의 인자에 모델 단계, 에이전트, 시간대, 대화 방식이 없다. 매일 깨우기 작업은 목록에 나오지 않는다 |
| REQ9 | 사용자가 예약 작업을 지워 달라고 하면 에이전트는 지우기 승인 카드를 띄운다(PR2). 카드에 작업 이름과 다음 실행 시각이 보인다. 사용자가 승인하면 지우고(작업이 목록과 발화에서 빠지고 지난 대화와 실행 기록은 남는다) 그 대화에 지웠다는 알림 줄을 남긴다. 거절하거나 만료되면 작업은 그대로다. 에이전트는 카드를 띄운 뒤 지웠다고 말하지 않고 승인을 기다린다고 알린다 | 지우기 도구를 부르면 작업은 그대로이고 대화에 승인 카드가 있다. 승인하면 작업 목록에서 사라진다. 거절하면 그대로다 |
| REQ10 | 사람이 지켜보지 않는 실행(예약 작업의 실행, 먼저 살펴보기, 다른 에이전트에게 맡긴 실행)도 REQ7 부터 REQ9 를 사람이 보낸 실행과 같은 규칙으로 쓴다(PR2, DECISION10). 먼저 살펴보기(사건 살펴보기 포함)는 바로 바꾸는 도구(예약 작업 만들기·고치기·멈추기·다시 켜기, PR3 의 할 일 만들기·끝내기)를 관리자가 그 에이전트에 쓰기를 켠 경우에만 받고, 승인 카드만 띄우는 도구(지우기, 붙이기)는 늘 받는다(DECISION32). 맡긴 실행은 자기 대화가 없으므로, 만드는 작업의 에이전트는 그 실행을 하는 맡겨진 에이전트이고 승인 카드는 루트 실행의 대화에 뜬다(DECISION27). 승인 카드가 뜨면 지금의 승인 요청 알림이 사람을 부른다. 이 실행이 만들거나 고친 예약 작업은 대화 기록과 작업 화면에 남아 사용자가 볼 수 있다 | 쓰기를 켠 먼저 살펴보기 트리에서 만들기 도구를 부르면 작업이 생기고, 켜지 않은 에이전트의 살펴보기에서는 거절된다. 켜지 않은 살펴보기에서도 지우기 도구는 승인 카드를 띄운다. 예약 작업의 실행에서 지우기 도구를 부르면 그 대화에 승인 카드가 뜨고 승인 요청 알림이 온다 |
| REQ11 | 사용자가 할 일을 적어 달라고 하면 에이전트는 그 할 일을 바로 챙기는 상태(`OPEN`)로 만든다(PR3). 바로 만드는 것은 사용자가 그 대화에서 보낸 메시지가 시킨 것과, 예약 작업의 실행에서 사용자가 작업 지시문에 써 둔 것이다(DECISION5, DECISION16). 지시문이 시킨 할 일은 그 실행이 바깥 글을 읽었어도 바로 챙긴다(DECISION31). 에이전트가 스스로 판단한 할 일, 먼저 살펴보기와 맡긴 실행의 할 일, 바깥 글을 읽은 대화의 할 일은 지금처럼 제안(`PROPOSED`)이다. 만든 뒤 답에 「지금 볼 것」(`/now`) 링크를 붙인다 | 사람이 보낸 「할 일로 적어 줘」 에서 만든 할 일이 「지금 볼 것」 의 「할 것」 에 바로 보인다. 먼저 살펴보기 트리에서 같은 도구를 부르면 제안으로 남는다. 사람이 보낸 메시지의 대화가 바깥 글을 읽었으면 제안으로 남는다. 「메일 보고 할 일 있으면 적어 둬」 지시문의 예약 작업 실행이 메일을 읽고 만든 할 일은 바로 챙기는 상태다 |
| REQ12 | 사용자가 할 일을 끝냈다고 하면(「그거 끝냈어」) 에이전트가 그 할 일을 바로 끝낸다(PR3). 에이전트는 요청자의 열린 할 일을 읽어 대상을 찾고, 둘 이상이면 되묻는다. 끝낸 할 일은 화면에서 되돌리지 못하므로, 잘못 끝냈다고 하면 에이전트가 같은 제목과 기한으로 다시 적는다(DECISION34). 바로 끝내는 조건은 REQ11 의 바로 만드는 조건과 같다. 그 밖의 실행은 상태를 바꾸지 않고 답에서 사용자에게 끝났는지 묻는다. 끝내자는 새 카드는 만들지 않는다(DECISION24) | 사람이 보낸 「병원 예약 끝냈어」 에서 그 할 일이 끝난 상태가 되고 「할 것」 에서 빠진다. 같은 제목의 할 일이 둘이면 도구가 후보를 돌려주고 바꾸지 않는다 |
| REQ13 | 사용자가 기억을 지워 달라고 하면 에이전트는 지우기 승인 카드를 띄운다(PR3). 지우는 대상은 기억 화면의 「알고 있는 것」 과 「검토할 기억」 이고, 사람이 화면에서 쓰는 문서는 다루지 않는다(DECISION25). 카드에 그 기억의 내용이 보인다. 승인하면 지우고 다음 실행부터 그 기억이 실리지 않는다. 거절하거나 만료되면 그대로다. 개인 기억은 주인만, 그룹 기억은 `ADMIN` 만 승인할 수 있다는 지금 화면의 규칙을 그대로 따른다. 지울 수 없는 기억이면 카드 없이 까닭을 알린다 | 지우기 도구를 부르면 기억은 그대로이고 승인 카드가 있다. 승인하면 기억 화면에서 사라지고 다음 실행 입력에 없다. `MEMBER` 역할 사용자가 그룹 기억을 지워 달라고 하면 카드가 없고 까닭이 답에 있다 |
| REQ14 | 에이전트가 기억 화면(`/memory`)과 「지금 볼 것」(`/now`)이 무엇인지 알고, 기억을 고치거나 직접 보고 싶다는 말에는 그 화면 링크를 붙인다(PR3) | 평가 세트의 「내 기억 어디서 봐」 의 답에 `/memory` 링크가 있다 |
| REQ15 | 사용자가 이미 연결한 서비스를 지금 에이전트에 쓰게 해 달라고 하거나, REQ5 의 안내 뒤 연결을 마쳤다고 하면 에이전트는 「이 에이전트에 붙이기」 승인 카드를 띄운다(PR4). 카드에 서비스 이름과, 그 서비스에서 에이전트가 쓸 수 있게 되는 도구의 위험도별 수가 보인다(연결 카드와 같다). 승인하면 지금 화면의 「붙이기」 와 같게 붙이고, 지금 연결 화면처럼 언제 쓸 수 있는지(바로, 몇 분 안에, 관리자 확인 뒤)를 그 대화의 알림 줄로 알린다(DECISION26) | 연결이 준비된 상태에서 붙이기 도구를 부르면 바인딩이 없고 승인 카드가 있다. 승인하면 그 에이전트의 「이 에이전트가 쓰는 연결」 에 그 연결이 있다 |
| REQ16 | 붙이기 승인 카드는 요청자가 주인인 비공개 에이전트에만 띄운다(PR4). 그룹에 공개한 에이전트이거나 다른 사람의 에이전트, 연결이 아직 준비되지 않은 경우는 카드 없이 까닭과 할 수 있는 길(비공개 에이전트, 연결 화면 링크)을 알린다 | 그룹 공개 에이전트에서 부르면 카드가 없고 까닭이 도구 결과와 답에 있다. 연결이 준비되지 않았으면 `/connections/{id}` 링크가 답에 있다 |
| REQ17 | 이 스펙의 도구는 모두 요청자 자신의 데이터만 다룬다(PR2-PR4). 그룹에 공개한 다른 사람의 에이전트를 써도 예약 작업, 할 일, 기억은 요청자의 것이다. 다른 사람의 것을 가리키면 없는 것과 같은 결과를 준다 | 그룹 공개 에이전트로 만든 예약 작업과 할 일이 요청자의 목록에만 있다. 다른 사용자의 작업 번호로 멈추기를 부르면 없는 작업과 같은 결과다 |
| REQ18 | 도구가 실패하거나 승인 카드를 띄운 것뿐이면 에이전트는 했다고 말하지 않는다(PR2-PR4). 도구의 실패 결과는 못 한 사실과 까닭(권한 없음, 대상 없음, 대상이 여럿, 한도, 일시 장애)을 담고, 도구 설명은 실패했을 때 했다고 답하지 말고 까닭을 알리라고 정한다. 도구가 실패해도 실행은 실패로 끝나지 않는다 | 실패를 돌려주는 가짜 Hermes 시나리오에서 실행이 성공으로 끝나고 도구 결과에 까닭이 있다. 도구 설명에 이 규칙이 있다 |

실제 에이전트가 알아듣는지는 PR 마다 배포 뒤 운영에서 그 PR 의 대표 문장을 한 번씩 왕복시켜 확인한다. 절차는 운영 저장소가 갖는다.

## 도메인 규칙 변경

도메인 규칙 변경 없음: 이 저장소에는 여러 기능이 함께 참조하는 도메인 문서(RULE ID)가 없다. 바뀌는 현재 규칙 둘은 아래 「결정 기록 연결」 의 문서가 갖는다. 하나는 [`attention.md`](../attention.md) 의 「제안 도구」(에이전트가 만든 할 일은 제안)에 사용자가 직접 시킨 할 일은 바로 챙긴다는 예외를 더하는 것이다(DECISION5, DECISION16). 다른 하나는 [`mcp.md`](../mcp.md) 의 「Control Plane MCP」(먼저 살펴보기 트리는 받는 도구를 줄인다)에서 이 스펙의 새 도구를 받게 하는 것이다. 바로 바꾸는 도구는 쓰기를 켠 살펴보기에서만, 승인 카드 도구는 늘 받는다(DECISION10, DECISION32). `memory_remember` 를 받지 않는 규칙은 그대로다.
