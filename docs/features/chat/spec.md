# 답이 도는 중에 보낸 글을 도는 실행에 끼워 넣는다(steer)

확인: 2026-11-16

## 목표

에이전트가 도구를 여러 번 부르며 도는 중에 사용자가 입력창에 쓴 글이 그 실행의 다음 단계에 들어가, 중지하지 않고도 방향을 바꾼다.
검색·조사 중 조건 바꾸기(「2만원 이하로」, 「창가로」), 글쓰기 중 방향 바꾸기(「반말로」), 긴 작업 중 범위 줄이기, 잘못 가는 것 바로잡기(「그거 말고 위 것」)가 대상 장면이다(사용자 2026-11-16).

지금은 답이 도는 중에 보낸 글이 대기열에 쌓였다가 turn 이 끝난 뒤 다음 turn 이 된다([ADR-048](../../adr/ADR-048-응답-중에-보낸-메시지는-control-plane-이-쌓아-두고-다음-turn-으로-합쳐-보낸다.md), [`chat.md`](../chat.md) 의 「응답 중 대기열」).
이 변경은 대기열을 없애지 않고 그 위에 Hermes `POST /v1/runs/{run_id}/steer` 를 얹는다. 넣지 못한 글은 대기열이 받는다.

됐다고 볼 기준(사용자 2026-11-16): 다음 단계가 내 말을 따른다, 대기열과 헷갈리지 않는다, 휴대폰에서도 자연스럽다. 글을 잃지 않는 것은 저장소 원칙(`AGENTS.md`, ADR-048)이라 모든 요구사항의 바탕으로 둔다.

## 범위

한 PR 로 구현한다. 운영 코드 변경이 상한(`scripts/pr/pr-size.mjs`)을 넘으면 서버(PR1)와 화면(PR2) 둘로 나누고, 각 PR 이 그 단계의 설계와 구현을 함께 담는다(DECISION9).
기능은 서버 설정 하나로 켜고 끄며 기본은 꺼짐이다. 끈 채 머지하고 배포한 뒤 운영 왕복을 확인하고 켠다(DECISION8).

범위 밖:

- 중지했을 때 Hermes session 기록을 조회해 글이 들어갔는지 판정하기(DECISION2)
- 위임한 자식 실행에 글 넣기. Hermes API 에 경로가 없고 Hermes core 를 고치지 않는다(DECISION3)
- 사진, `/스킬` 커맨드, 맡김, 질문 카드 답, 넘기기 카드의 「다 했어요」 를 steer 로 보내기(DECISION4). 카드와 넘기기는 browser-cowork 스펙이 맡는다
- Memory 의 바로 저장 판정에 steer 글을 넣기([`memory.md`](../memory.md) 의 바로 저장 조건은 질문 메시지 하나만 본다)
- 위임 결과를 steer 로 넣기([ADR-040](../../../backend/docs/adr/ADR-040-위임-결과는-control-plane-이-부모-대화의-다음-turn-을-열어-전한다.md) 이 미룬 것)
- 사용자별로 켜고 끄기
- 다시 생성 기능 자체의 존폐. 사용자는 다시 생성이 꼭 필요한지 의문을 남겼고(2026-11-16) 따로 정한다. 다시 생성을 없애면 REQ7 의 제약도 사라진다

## 요구사항과 인수 조건

| ID | 요구사항 | 관측할 인수 조건 |
| --- | --- | --- |
| REQ1 | 설정을 켜면 답이 도는 중 입력창에서 보낸 글을 먼저 도는 실행에 끼워 넣는다 | 설정이 켜져 있고 그 대화의 루트 실행이 돌고 있으며(사람이 보낸 질문, 대기 글로 연 turn, 다시 생성, 위임 결과를 전하는 자동 turn 모두. 빼는 turn 은 DECISION26) 대기 칸(멈춘 줄 포함)이 비어 있을 때 입력창의 보내기(단추 하나, 휴대폰 같음)로 글만 보내면 Control Plane 이 그 글을 대기 줄에 먼저 저장한 뒤 그 루트 실행에 `steer` 를 보낸다. Hermes 가 받으면 그 글이 대기 칸에서 빠지고 그 turn 의 답 바로 위(질문 아래)에 사용자 말풍선으로 남으며 상태가 「전달됨」 이다. 말풍선 자리는 도는 동안과 끝난 뒤 같고 답을 쪼개지 않는다. 같은 turn 에 여러 번 보내면 받은 순서대로 그 자리에 쌓인다. 대기 칸에 글이 이미 있으면 새 글은 끼워 넣지 않고 지금처럼 대기 칸에 더해 순서대로 간다. 가짜 Hermes 에서 도구를 두 번 부르는 시나리오로 보내면 steer 요청 본문이 그 글이고 `run.steered` 사건 뒤 말풍선이 보인다. 같은 대화를 연 다른 창과 휴대폰에도 대화 단위 SSE 로 같은 말풍선과 상태가 보인다 |
| REQ2 | Hermes 가 받지 않았다고 답하면 지금 대기열로 가고, 받았는지 모르면 멈춰 둔다 | Hermes 가 409(`run_not_accepting_steer`, `steer_not_accepted`, 승인 대기·중지 중 포함), 400, 500 으로 거절하면 말풍선을 만들지 않고 글은 대기 칸에 남아 지금처럼 turn 이 끝난 뒤 다음 turn 으로 간다. 응답 없이 시간 초과되거나 연결이 끊기면 받았을 수 있으므로 말풍선을 「전달됐는지 확인 못 함」 으로 남기고 같은 글을 멈춘 대기 줄에 두어 REQ4 와 같이 사용자가 고른다. 어느 경우에도 자동으로 두 번 보내지 않는다 |
| REQ3 | 끼워 넣었지만 모델에 들어가지 못하고 돌아온 글은 바로 다음 차례로 간다 | turn 이 완료나 실패로 끝나며 종료 사건이나 조회 응답에 `pending_steer` 가 오면 그 글의 말풍선은 그 자리에 남고 상태가 「다음 차례로 넘어감」 으로 바뀐다. 이어서 그 글(과 그사이 대기 칸에 쌓인 다른 글)로 다음 turn 이 바로 열린다. 그 글의 사용자 말풍선은 대화에 하나뿐이다. `pending_steer` 없이 끝나면 말풍선은 「전달됨」 으로 남는다 |
| REQ4 | 끼워 넣은 뒤 중지하면 글을 멈춘 대기열로 되돌린다 | 「전달됨」 말풍선이 있는 turn 을 사용자가 중지하면 그 turn 에서 끼워 넣은 글의 말풍선 상태가 「전달됐는지 확인 못 함」 으로 바뀌고, 같은 글이 멈춘 대기 줄에 다시 들어가 지금 중지와 같이 「보내기」 와 「취소」 가 보인다. 사용자가 고르기 전에는 보내지 않는다. 그 turn 에서 끼워 넣은 글은 들어갔을 수 있는 것까지 모두 되돌린다. 「보내기」 를 누르면 새 말풍선을 만들지 않고 그 말풍선이 「다음 차례로 넘어감」 이 되어 다음 turn 으로 간다(REQ3 과 같다). 「취소」 를 누르면 글이 입력창으로 돌아가고 말풍선은 「전달됐는지 확인 못 함」 으로 기록에 남는다 |
| REQ5 | 위임이 도는 동안 보낸 글은 부모에 넣고 자식은 바꾸지 못한다고 알린다 | 루트 실행이 하위 에이전트를 위임해 자식이 도는 중에 보낸 글도 REQ1 대로 루트 실행에 넣는다. 그 말풍선 아래에 자식 종류에 맞는 안내 한 줄(DECISION19)이 보인다. 자식 실행에는 steer 를 보내지 않는다 |
| REQ6 | 사람이 입력창에 직접 쓴 글만 끼워 넣는다 | 대화 주인이 입력창에 쓴 글만 steer 한다. 사진을 붙인 글, `/이름` 스킬 커맨드, 맡김(다른 에이전트 지정), 질문 카드의 답, 넘기기 카드의 「다 했어요」, 위임 결과·알림 줄·도구 결과는 steer 를 부르지 않고 지금 경로(대기열이나 다음 turn)로 간다. 대상은 그 대화의 루트 실행 하나이고 실행 번호는 Control Plane 이 대화에서 찾으며 요청 본문이 정하지 못한다. 다른 사용자의 대화에는 보낼 수 없다(지금 대기열과 같은 소유 판정) |
| REQ7 | steer 말풍선이 낀 답은 다시 생성하지 않는다 | 질문과 답 사이에 steer 말풍선이 있는 답에는 다시 생성이 열리지 않는다(화면에 단추가 없고 API 도 거절한다). steer 말풍선이 없는 답의 다시 생성은 지금과 같다 |
| REQ8 | 설정을 끄면 지금과 똑같이 동작한다 | 서버 설정이 꺼져 있으면(기본값) 답이 도는 중 보낸 글은 모두 지금 대기열로 가고 Control Plane 은 `steer` 를 부르지 않는다. 기존 대기열·중지 테스트가 그대로 통과한다 |
| REQ9 | 계약 문서와 가짜 Hermes 가 steer 를 안다 | `hermes/docs/hermes-contract.md` 의 steer 절이 「Control Plane 이 부른다」 와 읽은 태그(v2026.9.24) 기준의 동작(받는 때, 넣는 두 때, `pending_steer`, 중지 시 버림, 위임 자식에 안 감)으로 고쳐지고, 가짜 Hermes 가 steer 경로와 `run.steered`, 종료 사건의 `pending_steer` 를 낸다. ADR-048 의 낡은 「흐름이 붙은 에이전트」 줄과 「steer 는 범위가 아니다」 가 이 변경에 맞게 고쳐진다 |
| REQ10 | 배포 뒤 운영 왕복을 확인하고 켠다 | 머지·배포 뒤 아래 「운영 확인 항목」 을 코디네이터가 운영에서 확인하고 결과 수치만 남긴 뒤 설정을 켠다. 하나라도 어긋나면 켜지 않고 스펙이나 설계로 돌아간다 |

### 운영 확인 항목

확인할 것만 적는다. 실행 방법은 `fos-home-infra` 가 갖는다.

1. 운영 Hermes 버전이 계약 문서가 읽은 태그와 같고 steer 경로가 열려 있다
2. 도구를 여러 번 부르는 실행에 steer 하면 200 과 `run.steered` 가 오고 다음 단계 답이 그 글을 따른다
3. 도구 없이 답만 쓰는 실행에 steer 하면 종료 사건과 조회 응답에 `pending_steer` 가 같은 글로 온다
4. 여러 번 steer 하면 줄바꿈으로 이어진 하나로 들어가거나 돌아온다
5. steer 뒤 중지하면 `run.cancelled` 에 `pending_steer` 가 없다
6. 중지 직후와 승인 대기 중 steer 는 409 `run_not_accepting_steer` 다
7. 위임 중 steer 는 자식이 끝난 뒤 부모에만 들어간다
8. 다른 profile 이나 key 로 steer 하면 404 다
9. 다음 turn 에서 이미 끼워 넣은 지시를 다시 실행하지 않는다
10. 운영 모델이 steer 표식을 프롬프트 주입으로 보고 거부하지 않고, 우리 instructions 와 부딪히지 않는다
11. 수 분 걸리는 도구(브라우저 채우기 등) 중 steer 가 반영되기까지 걸린 시간
12. 이번 turn 에서 도구를 부르기 전에 steer 한 글이 이번 질문보다 앞에 끼지 않는다
13. steer 뒤에도 prompt cache 읽기 토큰이 유지된다

| DECISION12 | 글 한 개의 길이와 개수 | 대기 줄의 상한(5개, 8000자)과 같다. 받은 글은 대기 줄에서 빠지므로 개수를 차지하지 않는다. 돌아오거나 되돌린 글(이미 말풍선이 있는 글)은 상한을 세지 않고 언제나 되돌린다 | 작성자 | 글은 대기 줄을 거쳐 가므로 같은 검사를 지난다. 이미 받아 보인 글을 상한 때문에 버리면 글을 잃는다(설계 DECISION9) |

| DECISION14 | Hermes 가 다시 떠 실행을 찾지 못할 때(404) | 받았던 글은 REQ4 와 같이 「전달됐는지 확인 못 함」 으로 두고 멈춘 대기열로 되돌린다 | 작성자 | gateway 가 다시 뜨면 실행 상태가 사라진다(`hermes-contract.md` 의 「실행 조회가 답하는 기간」). 들어갔는지 알 수 없는 점이 중지와 같다 |
| DECISION15 | 넘기기 카드와의 관계 | steer 는 turn 을 열지 않으므로 넘기기 카드를 닫지 않는다. 돌아온 글로 연 다음 turn 은 사람이 보낸 turn 과 같다 | 작성자 | 카드는 사람이 보낸 turn 이 시작될 때 닫힌다([ADR-20261111 / connector-handoff](../../adr/ADR-20261111-connector-handoff.md)). 대기 글로 연 turn 을 사람이 보낸 turn 으로 보는 것은 지금 대기열과 같다 |
| DECISION16 | 돌아온 글로 연 다음 turn 의 질문 말풍선 | 새 말풍선을 만들지 않는다. 돌아온 글은 앞 자리의 말풍선으로만 남고, 함께 간 다른 대기 글만 지금처럼 새 사용자 말풍선이 된다. 다른 대기 글이 없으면 그 turn 의 답이 돌아온 글 말풍선 뒤에 이어 보인다 | 작성자 | DECISION6 의 「같은 글이 두 번 보이지 않는다」 를 지키는 읽기가 이것 하나다 |
| DECISION17 | 끼워 넣기를 기다리는 글의 취소 | Hermes 응답을 기다리는 동안 그 대기 글의 「취소」 를 막는다. 응답이 오면 말풍선이나 대기 칸 한 곳에만 남는다 | 작성자 | 기다림은 요청 한 번의 짧은 시간이다. 취소를 받으면 입력창으로 돌아온 글과 모델에 들어간 글이 함께 생긴다 |
| DECISION18 | `pending_steer` 를 어느 말풍선에 맞추나 | 그 turn 에서 받은 글을 받은 순서로 이은 것의 뒤쪽이 `pending_steer` 와 글자로 같으면 그 글들만 「다음 차례로 넘어감」 이다. 맞는 묶음이 없으면 그 turn 의 「전달됨」 말풍선을 모두 「다음 차례로 넘어감」 으로 보낸다 | 작성자 | Hermes 는 받은 글을 줄바꿈으로 이어 하나로 돌려준다(`agent/interrupt_control.py`). 맞지 않을 때는 글을 잃지 않는 쪽으로 둔다. 맞추기 방법은 운영 확인 4 로 확인한다 |
| DECISION19 | 위임 안내를 붙이는 때와 글 | Control Plane 이 steer 를 받은 순간 그 turn 에 Hermes 안의 하위 에이전트가 돌면 「도우미가 하던 일은 바꾸지 못하고, 도우미가 끝난 뒤 반영돼요」, 그렇지 않고 그 대화에 `agent_delegate` 로 맡긴 실행이 돌면 「맡긴 도우미가 하던 일은 바꾸지 못해요」 를 붙인다. 말풍선과 함께 기록에 남아 새로 고침과 다른 창에서도 보인다 | 작성자 | 어느 쪽 자식이든 부모의 steer 를 받지 못한다(조사, `tools/delegate_tool_registry.py`). 맡긴 실행은 부모가 기다리지 않아(ADR-040) 글이 부모의 다음 단계에 곧바로 들어가므로 「끝난 뒤 반영」 은 하위 에이전트에만 맞다. 판정을 받은 순간 하나로 정해 창마다 달라지지 않게 한다 |
| DECISION20 | 말풍선 상태의 수명 | 상태는 그 말풍선에 저장되어 turn 이 끝난 뒤와 새로 고친 뒤에도 보인다 | 작성자 | 「다음 차례로 넘어감」 과 「전달됐는지 확인 못 함」 은 뒤에 대화를 읽을 때도 뜻이 있다 |
| DECISION21 | 흐름이 붙은 에이전트 | 따로 다루지 않는다. ADR-048 의 그 줄은 지운다 | 작성자 | 흐름 칸은 지워졌고(`V20261015151000__drop_agent_flow.sql`) 대기열의 받기 검사(`PendingMessageService.requireQueueable`)에도 없다 |
| DECISION22 | 중지로 되돌린 글의 「보내기」·「취소」 | 말풍선 하나로. 보내기면 그 말풍선이 「다음 차례로 넘어감」, 취소면 글은 입력창으로 돌아가고 말풍선은 「전달됐는지 확인 못 함」 으로 남는다. 그 turn 에서 끼워 넣은 글은 모두 되돌린다 | 사용자 2026-11-16 | 같은 글이 두 번 보이지 않고(DECISION6), 모델에 갔을 수 있는 글의 기록은 남는다. Hermes 는 어느 글이 들어갔는지 알려 주지 않는다 |
| DECISION23 | steer 요청이 시간 초과·연결 끊김으로 끝날 때 | 받았는지 모름으로 본다. 「전달됐는지 확인 못 함」 말풍선과 멈춘 대기 줄. 명시 거절(409·400·500)만 대기열로 | 사용자 2026-11-16 | 같은 지시(예: 주문)를 두 번 실행하는 쪽이 사람 손을 한 번 더 쓰게 하는 쪽보다 위험하다 |
| DECISION24 | 대기 칸에 글이 있을 때 새로 보낸 글 | 대기 칸(멈춘 줄 포함)이 비어 있을 때만 끼워 넣는다. 아니면 지금처럼 대기 칸에 더한다 | 사용자 2026-11-16 | 나중 글이 먼저 들어가 고침의 순서가 뒤집히지 않고, 멈춘 줄의 뜻(사람이 고를 때까지 보내지 않음)을 지킨다 |

## 도메인 규칙 변경

도메인 규칙 변경 없음: 실행 중 보낸 글을 다루는 규칙은 ADR-048 이 갖고, 이 변경은 그 ADR 의 「적용 범위」 가 미뤄 둔 steer 를 얹는다. 여러 기능이 참조하는 RULE ID 는 바뀌지 않는다.
