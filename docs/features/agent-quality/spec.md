# 에이전트 품질: 배포 뒤 자동 확인, 답 품질 채점, 피드백 루프

확인: 2026-11-21

처음 확인은 2026-11-20 이고, 2026-11-21 에 아래 고친 것과 함께 다시 확인받았다.

확인 뒤 2026-11-20 에 사용자 결정으로 고친 것: 배포 뒤 확인의 「예약 작업 만들기」 를 「예약 작업 발화」 로 바꿨다(DECISION3). 비서에게 예약 작업을 만드는 도구가 없어 늘 실패하기 때문이다.

2026-11-21 에 고친 것: 평가 문항을 사람 계정 대신 평가 전용 사용자로 돌리게 PR2 를 둘로 나누고 앞부분(PR2a)을 앞당겼다. REQ15 부터 REQ18 까지와 DECISION29 부터 DECISION41 까지를 더하고 REQ5, REQ6, REQ9, DECISION14 를 고쳤다. 사용자 요청은 「내 계정 활용해서 테스트를 진행하면서 평가용 계정을 별도로 분리해 줘」 다.

## 목표

기능을 바꾼 뒤 비서가 운영에서 실제로 동작하는지, 답 내용이 ChatGPT 만큼 좋은지를 사람이 직접 돌리지 않아도 알 수 있다(사용자 2026-11-20).
그룹의 사용자가 답에 남긴 반응을 모아 평가 문항을 늘리고, 관리자가 품질의 흐름을 한 화면에서 본다.

가장 먼저 잡을 품질 기준은 「답 내용이 ChatGPT 만큼 좋다」 다(사용자 2026-11-20). PR 순서는 운영 고장을 먼저 막도록 배포 뒤 확인부터 한다(DECISION1).

| REQ9 | 정기 평가는 주 1회 돌고 사람이 언제든 돌릴 수 있다(「지금 돌리기」 는 PR2a, 주 1회 실행은 PR2b) | 주 1회 정해진 때에 전체 실행이 사람 없이 돈다. 관리자는 품질 화면의 「지금 돌리기」 로 전체나 묶음과 모델 단계를 골라 돌린다. 결과에 쓴 모델 단계가 남는다(DECISION41). 정기 평가가 도는 동안 다른 정기 평가는 시작하지 않고 그 사실을 보인다. 예약 시각에 다른 정기 평가가 돌고 있으면 그 주 예약 실행은 건너뛴다. 배포 뒤 확인은 정기 평가와 상관없이 돈다(DECISION23). 우리 답이나 기준 답을 받지 못했거나 판정이 둘 이상 실패한 문항은 모델 판정이 「돌지 못함」 으로 남고 모델 점수에 넣지 않는다. 규칙 판정은 우리 답이 있으면 센다(DECISION24) |

| REQ11 | 그룹의 사용자 모두 답에 좋다·나쁘다를 누를 수 있다(PR3) | 사람이 보낸 질문(새 질문, 다시 생성, @ 맡김)의 답과 그 질문에서 이어진 위임 결과 답에 좋다·나쁘다 단추가 있고 휴대폰에서도 같다. 예약 작업과 먼저 살펴보기의 답에는 없다(DECISION22). 한 답에 하나만 고르고 바꾸거나 취소할 수 있다. 자기 대화의 답에만 누른다. 다시 생성한 답은 따로 누른다 |
| REQ12 | 나쁘다는 까닭과 문항 동의를 함께 받는다(PR3) | 나쁘다를 누르면 까닭(틀림, 오래된 정보, 출처 없음, 질문을 못 알아들음, 기타 글)을 고르고 「이 질문을 평가 문항으로 써도 된다」 를 고를 수 있다. 동의하면 답 바로 앞의 사용자 질문 한 줄이 미리 채워진 입력이 열리고, 본인이 앞 맥락을 보태 혼자서도 뜻이 통하게 고치고 개인 정보를 지운 뒤 보낸다. 첨부는 빠진다(DECISION28). 답 본문은 문항에 들지 않는다. 좋다는 까닭을 묻지 않는다 |
| REQ13 | 관리자는 반응의 수만 본다(PR3) | 품질 화면 셋째 칸에 주별 좋다·나쁘다 수, 나쁘다 까닭별 수, 사용자별 수가 보인다. 사용자별 수는 「사용자 1, 2」 처럼 이름을 가린다. 「기타」 까닭은 수만 세고 글은 보이지 않는다. 다른 사용자의 질문과 답 본문은 보이지 않는다(DECISION25) |
| REQ14 | 동의받은 질문은 문항 후보가 되고 관리자가 확정한다(PR3) | 품질 화면 넷째 칸에 본인이 다듬어 보낸 질문 글과 고른 까닭 항목 이름이 후보로 보이고, 보낸 사람은 가린다(DECISION25). 확정 문항은 모델 판정만 하고 규칙 기준의 분모에는 들지 않는다(DECISION26). 관리자가 묶음을 골라 확정하면 다음 정기 평가부터 그 문항이 돈다. 버리면 후보에서 사라진다. 본인이 설정의 「내가 보낸 평가 문항」 에서 그 문항을 빼면 후보와 확정 문항에서 질문 글이 지워진다. 반응을 바꾸거나 대화를 지워도 보낸 문항은 남는다(DECISION28) |
| REQ15 | 평가 문항은 평가 전용 사용자로만 돈다(PR2a) | 정기 평가의 모든 묶음과 기능 PR 의 배포 뒤 확인 문항이 사람의 토큰 없이 Control Plane 실행기 안에서 평가 전용 사용자의 새 대화로 돈다. 관리자가 관리자 API 나 품질 화면 「지금 돌리기」 로 전체나 묶음을 골라 시작하고, 문항별 통과·실패와 실패 까닭, 남겨 둔 실패 대화로 가는 길을 같은 API 와 화면에서 본다. 다른 사용자의 기억, 할 일, 예약 작업, 대화가 실행 전후로 바뀌지 않는다(DECISION29) |
| REQ16 | 문항은 여러 차례 대화와 승인 카드 처리를 표현한다(PR2a) | 문항이 차례마다 보낼 글과, 그 차례가 띄운 승인 카드를 「승인」, 「거절」, 「그대로 둠」 중 무엇으로 할지 적는다. 실행기가 평가 전용 사용자 권한으로 사람과 같은 승인 길로 카드를 누르고, 그 결과(예: 예약 작업이 지워졌는지, 기억이 지워졌는지)까지 판정한다. 카드 처리를 적지 않은 차례에 카드가 뜨면 「그대로 둠」 으로 보고 정리 때 거절한다. 배포 뒤 확인 기능(REQ1)은 지금처럼 카드가 뜨면 실패다(DECISION30) |
| REQ17 | 평가가 끝나면 그 실행이 만든 것을 비운다(PR2a) | 실행이 끝나면 그 실행이 평가 전용 사용자에게 만든 기억, 할 일, 예약 작업, 파일 공간 보관본을 문항의 통과·실패와 상관없이 지우고, 기다리는 승인 줄은 거절로 닫는다(승인 줄은 기록으로 남는다). 문항이 준비 때 넣은 기억을 고쳤으면 되돌린다. 대화와 그 결과물은 통과한 문항이면 바로, 실패한 문항과 답변 품질의 사람 비교 문항이면 30일 뒤 지운다(DECISION16, DECISION38). 실행을 시작할 때 지난 실행이 끊겨 남긴 것도 같은 기준으로 지운다. 준비 때 넣은 기억은 남긴다. 실행이 끝난 뒤 평가 전용 사용자에게 발화할 예약 작업이 남지 않는다(DECISION31) |
| REQ18 | 기능 PR 의 배포 뒤 대화 확인은 기능 묶음 문항으로 한다(PR2a) | 사용자에게 보이는 대화 동작을 바꾼 기능 PR 은 자기 기능 묶음 파일에 문항을 더한다. 배포 뒤 코디네이터가 「지금 돌리기」 로 그 묶음을 평가 전용 사용자로 돌린 결과를 기능 완료 증거에 남긴다. 그 뒤로는 주 1회 정기 평가에서 돌고, 배포 때 자동으로 돌지 않는다(DECISION39). 사람 계정으로 대화 확인을 하지 않는다. 묶음 문항으로 할 수 없는 확인(사람이 직접 계정을 연결해야 하는 플러그인 등)만 사람 계정으로 하고 그 까닭을 PR 본문에 적는다. 루트 `AGENTS.md` 의 「Hermes 연동을 바꿨으면 배포 뒤 왕복시켜 본다」 와 서비스 개념 스펙의 평가 운영(REQ6, DECISION33)을 이 규칙으로 고친다(DECISION32) |

### 배포 뒤 확인 기능

기능마다 1문항이다(DECISION3). 문항 글과 통과 규칙은 설계가 정한다.

| 기능 | 통과로 보는 것(규칙) |
| --- | --- |
| 검색과 출처 | `web_search` 사건이 남고 답 끝 「출처」 에 링크가 있다 |
| 위임 | 자식 실행이 생겨 성공하고 결과가 부모 대화에 전해진다 |
| 내 파일 넣기 | 평가 전용 사용자의 파일 공간에 그 파일이 생긴다 |
| 그림 만들기 | 답에 만든 그림이 붙는다 |
| 기억 읽기 | 미리 넣어 둔 평가용 기억의 내용이 답에 든다 |
| 예약 작업 발화 | 실행기가 평가 전용 사용자의 예약 작업을 「지금」 으로 하나 만들어 발화시키고, 그 turn 이 성공으로 끝난다 |
| 원본 사진 조회 | 앞 메시지에 올린 사진의 심은 글자가 답에 든다 |
| 도구 찾기 | 도구 이름을 적지 않은 질문에서 Control Plane 도구(예약 작업 목록)를 찾아 불러 실패 없이 끝낸다(DECISION43) |

평가 비서가 Control Plane 도구를 받지 못한 채 돌아 실패한 기능과 문항은 품질 실패가 아니라 「환경 오류」 로 따로 보인다(DECISION44).

| DECISION41 | 「지금 돌리기」 의 모델 단계 | 화면과 API 에서 모델 단계를 고른다. 고르지 않으면 평가 사용자에게 걸리는 기본 단계(사용자 기본, 없으면 그룹 기본)다. 결과에 쓴 단계를 적고, 직전 실행과의 비교와 하락 판정은 같은 단계의 실행끼리만 한다. 주 1회 실행은 기본 단계로 돈다 | 사용자 2026-11-21(주 1회의 단계는 작성자) | 단계별 품질을 비교할 수 있다. 다른 단계끼리 비교하면 하락이 단계 차이에 섞인다. 주 1회는 실제 사용자가 받는 기본 단계를 본다 |
| DECISION42 | ChatGPT 예약 작업 비교 묶음 | 사용자의 ChatGPT 예약 작업 가운데 결과가 매번 나오는 유형 4개(가격 비교, 채용 동향, 생활 팁, 기술 동향)의 지시문을 「ChatGPT 예약 작업 비교」 묶음으로 넣는다. 같은 시각에 우리 비서로 돌리고 ChatGPT 의 그 회 결과를 기준 답으로 나란히 채점한다. 개인 정보는 가상 프로필로 바꿔 문항에 넣고 원문은 공개 저장소에 넣지 않는다. 묶음은 PR2b 가 모델 채점과 함께 만든다. 런타임 비교 스펙도 이 묶음을 쓴다 | 사용자 2026-11-21(PR 자리는 작성자) | 실제로 쓰던 지시문이라 「ChatGPT 만큼 좋다」 를 실제 쓰임으로 잰다. 나란히 채점은 PR2b 의 판정 profile 이 있어야 돌아 PR2b 에 둔다. 조건 감시형과 비공개 맥락이 필요한 작업은 한 번 실행으로 채점할 출력이 없거나 공개 저장소에 둘 수 없어 뺐다 |
| DECISION43 | 도구를 찾지 못하는 회귀를 배포 뒤 확인이 잡는 방법 | 도구 이름을 적지 않은 「도구 찾기」 기능을 더한다. 예약 작업 목록을 묻고 `task_list` 가 실패 없이 끝나면 통과다 | 코디네이터 2026-11-24 | 다른 기능 문항은 도구 이름을 글에 적어, 모델이 지연 도구 이름 목록을 받지 못해도 그 이름으로 바로 불러 통과한다. 2026-11-24 묶음 평가에서 Control Plane 도구를 하나도 못 부른 회귀를 배포 뒤 확인이 놓쳤다. 목록 읽기는 만드는 것이 없어 비울 것도 없다 |
| DECISION44 | 평가 비서가 Control Plane 도구를 받지 못한 채 돈 실패 | 기능과 문항의 까닭을 「환경 오류」 로 바꾸고 결과에 따로 표시한다. 묶음 평가는 그 뒤 남은 문항을 보내지 않고 같은 까닭으로 적는다. 통과한 것은 그대로 둔다 | 코디네이터 2026-11-24 | 2026-11-24 같은 커밋을 두 번 배포하며 Control Plane 이 다시 떠 평가 profile 의 MCP 연결이 8분 쉬었고, 그 사이 돈 묶음 평가가 품질 하락처럼 보였다. 품질 실패와 섞이면 회귀를 쫓는 시간이 헛든다 |
