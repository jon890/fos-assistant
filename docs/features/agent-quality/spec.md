# 에이전트 품질: 배포 뒤 자동 확인, 답 품질 채점, 피드백 루프

확인: 2026-11-20

확인 뒤 2026-11-20 에 사용자 결정으로 고친 것: 배포 뒤 확인의 「예약 작업 만들기」 를 「예약 작업 발화」 로 바꿨다(DECISION3). 비서에게 예약 작업을 만드는 도구가 없어 늘 실패하기 때문이다.

## 목표

기능을 바꾼 뒤 비서가 운영에서 실제로 동작하는지, 답 내용이 ChatGPT 만큼 좋은지를 사람이 직접 돌리지 않아도 알 수 있다(사용자 2026-11-20).
그룹의 사용자가 답에 남긴 반응을 모아 평가 문항을 늘리고, 관리자가 품질의 흐름을 한 화면에서 본다.

가장 먼저 잡을 품질 기준은 「답 내용이 ChatGPT 만큼 좋다」 다(사용자 2026-11-20). PR 순서는 운영 고장을 먼저 막도록 배포 뒤 확인부터 한다(DECISION1).

## 범위

세 단계를 한 스펙에 두고 아래 순서로 PR 을 나눈다(DECISION1). PR 마다 그 단계의 설계와 구현을 함께 담는다. 한 단계가 운영 코드 상한(`scripts/pr/pr-size.mjs`)을 넘으면 그 단계 안에서 PR 을 더 나눈다.

| PR | 담는 것 | 요구사항 |
| --- | --- | --- |
| PR1 | 배포 뒤 기능별 자동 확인, 평가 전용 사용자, 실패 알림, 품질 화면의 배포 뒤 확인 칸 | REQ1~REQ4 |
| PR2 | 정기 평가 틀(기능별 묶음), 기준 답과 모델 채점, 답변 품질 20문항 옮기기, 주 1회 실행, 점수 하락 알림, 품질 화면의 정기 평가 칸과 「지금 돌리기」 | REQ5~REQ10 |
| PR3 | 답의 좋다·나쁘다 단추, 나쁘다의 까닭과 문항 동의, 문항 후보 확정, 품질 화면의 반응 칸과 문항 후보 칸 | REQ11~REQ14 |

범위 밖:

- 배포 실패 때 자동으로 이전 버전으로 되돌리기. 알림만 하고 되돌리기는 사람이 한다(DECISION4)
- 점수가 떨어졌을 때 다음 배포 막기(DECISION9)
- 블로그 사진, 서비스 개념, 기억 요약 평가를 정기 평가로 옮기기. 각 스펙이 같은 묶음 형식으로 붙인다(DECISION12)
- 관리자 화면 전체 재편. 관리자 영역 재편 스펙이 갖고, 품질 화면은 그 스펙의 「살펴보기」 묶음 두 번째 자리에 둔다
- 배포 파이프라인 쪽 작업(확인을 부르는 것, 파이프라인 알림). `fos-home-infra` 에 요청으로 넘긴다
- 정기 평가의 문항 수 상한. 두지 않는다(DECISION8)
- 비서가 예약 작업을 직접 만드는지 확인하기. 지금 비서에게 예약 작업을 만드는 도구가 없다. 서비스 개념 스펙의 PR2(비서가 예약 작업을 직접 만들기)가 들어오면 그때 「예약 작업 만들기」 확인을 더한다(DECISION3)
- 사용자 ChatGPT 계정으로 기준 답을 받는 것. 처음 사람 비교 대조에서 참고로만 쓴다(DECISION6)

## 요구사항과 인수 조건

| ID | 요구사항 | 관측할 인수 조건 |
| --- | --- | --- |
| REQ1 | 배포가 끝나면 기능별 확인이 사람 없이 돈다(PR1) | 배포 파이프라인이 Control Plane 에 확인 시작을 요청하면 평가 전용 사용자로 아래 「배포 뒤 확인 기능」 의 문항이 기능마다 새 대화에서 운영 Control Plane, Hermes, 모델을 그대로 거쳐 돈다. 결과는 기능마다 통과·실패와 실패 까닭 한 줄이고, 규칙(도구 사건, 만들어진 파일·기억·예약, 답의 출처)으로 정한다. 답 내용을 채점하지 않는다. 통과한 기능의 대화와 만든 파일·기억·예약은 바로 지우고, 실패한 기능의 것은 30일 남긴다(DECISION19). 기능마다 10분을 넘으면 그 기능만 「시간 초과」 실패다 |
| REQ2 | 평가 전용 사용자는 실제 사용자 데이터를 건드리지 않는다(PR1) | 확인과 정기 평가는 평가 전용 사용자의 에이전트와 데이터만 쓴다. 다른 사용자의 기억, 파일, 예약 작업, 대화가 확인 전후로 바뀌지 않는다. 평가 전용 사용자는 관리자 영역에만 평가용으로 보이고, 일반 화면(사용자 목록, 에이전트 고르기, 멘션)과 반응·사용량 집계에서 빠진다. 사용량 화면에는 「평가」 한 줄로 따로 보인다(DECISION27) |
| REQ3 | 확인이 실패하면 알린다(PR1) | 기능 하나라도 실패하면(시간 초과 포함) 관리자에게 앱 안 알림이 간다. 알림은 실패한 기능 이름과 품질 화면으로 가는 길을 담는다. 배포 파이프라인은 확인 결과(통과, 실패)를 받아 자기 알림으로 보낸다. 앱이 응답하지 않으면 파이프라인이 실패로 본다. 되돌리기는 하지 않는다 |
| REQ4 | 품질 화면에 배포 뒤 확인 기록이 보인다(PR1) | `/admin/quality` 의 첫 칸에 배포마다 시각, 기능별 통과·실패, 실패 까닭, 걸린 시간이 최근 순으로 보인다. 실패 줄에서 남겨 둔 그 평가 대화로 들어갈 수 있다. 「다시 확인」 단추로 같은 확인을 다시 돌린다. 관리자만 들어온다. 휴대폰에서도 읽힌다 |
| REQ5 | 정기 평가는 기능별 묶음으로 나뉘고 골라 돌릴 수 있다(PR2) | 평가 문항은 묶음(예: 답변 품질)에 속한다. 전체 실행과 묶음을 골라 돌리는 실행이 모두 된다. 새 묶음은 문항 파일을 더해 만들고 실행기를 고치지 않는다. 문항 수 상한은 없다 |
| REQ6 | 답변 품질 20문항이 정기 평가의 첫 묶음이다(PR2) | 지금 `test/model-eval/answer/` 의 문항과 규칙 판정(출처 링크, 링크 열림, 날짜)이 정기 평가의 「답변 품질」 묶음으로 돌고 같은 숫자를 낸다. 옮긴 뒤 옛 스크립트는 지운다 |
| REQ7 | 답 내용을 기준 답과 나란히 모델이 채점한다(PR2) | 문항마다 같은 실행 안에서 같은 질문을 OpenAI 내장 검색을 켠 평가 전용 profile 로 물어 기준 답을 받고, 판정 전용 profile 이 우리 답과 기준 답을 나란히 보고 「비슷하다」 나 「모자라다」 와 까닭 한 줄을 낸다. 「비슷하다」 는 우리 답이 기준 답보다 사실, 내용, 최신성에서 모자라지 않다(같거나 낫다)는 뜻이고 출처는 판정 모델이 보지 않는다(DECISION20). 판정은 세 번 해 다수결로 정하고, 둘 이상 성공해 같은 답이 나오면 판정한다(DECISION24). 기준 답과 판정은 구독 경로로 부르고 API key 를 쓰지 않는다. 규칙 판정은 그대로 함께 낸다 |
| REQ8 | 모델 채점을 사람 비교로 보정한다(PR2) | 처음 두 번의 정기 평가에서 사용자가 사람 비교 8문항을 ChatGPT 와 나란히 본 결과를 적을 자리가 있고, 품질 화면에 모델 판정과 사람 판정이 맞은 누적 비율이 보인다. 누적 비율이 80% 이상이 될 때까지 모든 실행의 모델 점수에 「보정 전」 이 붙는다. 판정 지시나 판정 모델을 바꾸면 다시 「보정 전」 으로 돌아가 한 번 더 대조한다(DECISION21) |
| REQ9 | 정기 평가는 주 1회 돌고 사람이 언제든 돌릴 수 있다(PR2) | 주 1회 정해진 때에 전체 실행이 사람 없이 돈다. 관리자는 품질 화면의 「지금 돌리기」 로 전체나 묶음을 골라 돌린다. 정기 평가가 도는 동안 다른 정기 평가는 시작하지 않고 그 사실을 보인다. 예약 시각에 다른 정기 평가가 돌고 있으면 그 주 예약 실행은 건너뛴다. 배포 뒤 확인은 정기 평가와 상관없이 돈다(DECISION23). 우리 답이나 기준 답을 받지 못했거나 판정이 둘 이상 실패한 문항은 모델 판정이 「돌지 못함」 으로 남고 모델 점수에 넣지 않는다. 규칙 판정은 우리 답이 있으면 센다(DECISION24) |
| REQ10 | 점수가 떨어지면 알린다(PR2) | 실행이 끝나면 묶음마다 「비슷하다」 수, 규칙 판정 수, 문항 수, 모델 호출 수, 걸린 시간, 직전 실행과의 차이가 품질 화면 둘째 칸에 남는다. 규칙 기준(출처가 붙은 문항 비율, 열린 링크 비율, 날짜 문항) 아래이거나, 직전 실행과 양쪽 모두 판정된 같은 문항끼리 비교해 「비슷하다」 가 2문항 이상 줄면 관리자에게 앱 안 알림이 간다. 규칙 기준은 [`answer-quality/spec.md`](../answer-quality/spec.md) DECISION10 의 「17 중 15」 를 비율(15/17)로 바꾼 값과 링크 90% 다(DECISION20). 배포를 막지 않는다 |
| REQ11 | 그룹의 사용자 모두 답에 좋다·나쁘다를 누를 수 있다(PR3) | 사람이 보낸 질문(새 질문, 다시 생성, @ 맡김)의 답과 그 질문에서 이어진 위임 결과 답에 좋다·나쁘다 단추가 있고 휴대폰에서도 같다. 예약 작업과 먼저 살펴보기의 답에는 없다(DECISION22). 한 답에 하나만 고르고 바꾸거나 취소할 수 있다. 자기 대화의 답에만 누른다. 다시 생성한 답은 따로 누른다 |
| REQ12 | 나쁘다는 까닭과 문항 동의를 함께 받는다(PR3) | 나쁘다를 누르면 까닭(틀림, 오래된 정보, 출처 없음, 질문을 못 알아들음, 기타 글)을 고르고 「이 질문을 평가 문항으로 써도 된다」 를 고를 수 있다. 동의하면 답 바로 앞의 사용자 질문 한 줄이 미리 채워진 입력이 열리고, 본인이 앞 맥락을 보태 혼자서도 뜻이 통하게 고치고 개인 정보를 지운 뒤 보낸다. 첨부는 빠진다(DECISION28). 답 본문은 문항에 들지 않는다. 좋다는 까닭을 묻지 않는다 |
| REQ13 | 관리자는 반응의 수만 본다(PR3) | 품질 화면 셋째 칸에 주별 좋다·나쁘다 수, 나쁘다 까닭별 수, 사용자별 수가 보인다. 사용자별 수는 「사용자 1, 2」 처럼 이름을 가린다. 「기타」 까닭은 수만 세고 글은 보이지 않는다. 다른 사용자의 질문과 답 본문은 보이지 않는다(DECISION25) |
| REQ14 | 동의받은 질문은 문항 후보가 되고 관리자가 확정한다(PR3) | 품질 화면 넷째 칸에 본인이 다듬어 보낸 질문 글과 고른 까닭 항목 이름이 후보로 보이고, 보낸 사람은 가린다(DECISION25). 확정 문항은 모델 판정만 하고 규칙 기준의 분모에는 들지 않는다(DECISION26). 관리자가 묶음을 골라 확정하면 다음 정기 평가부터 그 문항이 돈다. 버리면 후보에서 사라진다. 본인이 설정의 「내가 보낸 평가 문항」 에서 그 문항을 빼면 후보와 확정 문항에서 질문 글이 지워진다. 반응을 바꾸거나 대화를 지워도 보낸 문항은 남는다(DECISION28) |

### 배포 뒤 확인 기능

기능마다 1문항이다(DECISION3). 문항 글과 통과 규칙은 설계가 정한다.

| 기능 | 통과로 보는 것(규칙) |
| --- | --- |
| 검색과 출처 | `web_search` 사건이 남고 답 끝 「출처」 에 링크가 있다 |
| 위임 | 자식 실행이 생겨 성공하고 결과가 부모 대화에 전해진다 |
| 내 파일 넣기 | 평가 전용 사용자의 파일 공간에 그 파일이 생긴다 |
| 그림 만들기 | 답에 만든 그림이 붙는다 |
| 기억 읽기 | 미리 넣어 둔 평가용 기억의 내용이 답에 든다 |
| 예약 작업 발화 | 실행기가 평가 전용 사용자의 예약 작업을 「지금」 으로 하나 만들어 발화시키고, 그 turn 이 성공으로 끝난다 |
