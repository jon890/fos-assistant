# 비서가 찾은 사진: 상품 이름만 말해도 비서가 사진을 찾아 그림에 참고한다

확인: 2026-11-21

## 목표

사용자가 「GGRN 양말 신은 아이 그려 줘」 처럼 상품이나 사물, 장소의 이름만 말해도 비서가 웹에서 그 사진을 찾아 그림의 참고 그림으로 넣고, 실제 모양이 맞는 그림을 한 번에 만든다.

지금은 사용자가 이 대화에 보낸 링크의 사진만 받는다([그림 스펙](../generated-image/spec.md) 의 REQ21, DECISION34).
비서가 검색이나 페이지 읽기로 찾은 주소는 서버가 거절해, 「웹검색으로 너가 찾아서 적용해줘」 라고 해도 비서는 상품 설명만으로 비슷하게 그렸다(2026-11-20 GGRN 양말 대화).
사용자가 링크를 직접 보낸 뒤에야 상품 사진이 참고로 들어갔다.

## 범위

이 스펙은 [그림 스펙](../generated-image/spec.md) 위에 받는 길 하나를 더한다. 올린 사진과 만든 그림을 쓰는 길은 그대로다. 사용자가 보낸 링크의 길은 받지 못했을 때 비서가 대신 찾는 것만 달라진다(DECISION23).

PR 둘로 구현한다(DECISION15). 이 스펙을 처음 구현하는 PR 은 PR1 이다.

| PR | 담는 것 | 시작 조건 | 요구사항 |
| --- | --- | --- | --- |
| PR1 | 비서가 찾은 주소를 서버가 확인하고 받기, 찾은 주소를 참고로 쓰라는 지침. 「찾아서 그려 줘」 가 이때부터 된다 | 없음 | REQ2, REQ3, REQ8, REQ9 |
| PR2 | 이름만 말해도 찾기, 사진 고르기와 다시 시도, 사람과 캐릭터 규칙, 답의 출처 줄과 화면의 「비서가 찾음」 표시 | PR1 이 main 에 머지됐다 | REQ1, REQ4, REQ5, REQ6, REQ7, REQ10 |

범위 밖:

- 실존 인물의 얼굴, 로고, 캐릭터를 찾아 참고하기(DECISION2)
- 찾은 사진 여러 장을 사용자에게 보이고 골라 달라고 묻는 화면(DECISION3)
- 사진에 얼굴이 있는지 서버가 판별해 막기. 비서가 받는 지침으로만 다룬다(DECISION7)
- 사람이 없는 실행(예약 작업, 먼저 살펴보기)에서 그림 만들기. 그림 스펙 REQ14 그대로다
- 받은 사진을 대화나 보관함에 남기기. 그림 스펙 REQ23 그대로다
- 찾은 사진을 답 안에 그림으로 보이기. 링크로만 보인다(DECISION11)
- 저작권 안내 글(DECISION14)
- 브라우저 도구나 터미널로 연 페이지의 주소를 받기(DECISION18)
- 자동 요청을 막는 쇼핑몰을 우회해 받기

## 요구사항과 인수 조건

인수 조건은 가짜 Hermes 와 가짜 웹 페이지, 테스트용 그림 파일로 확인한다.
실제 상품을 찾아 그리는 왕복은 배포 뒤 운영에서 코디네이터가 확인한다(REQ9).

| ID | 요구사항 | 관측할 인수 조건 |
| --- | --- | --- |
| REQ1 | 사용자가 특정 상품(양말, 신발, 옷), 사물, 장소나 건물을 이름으로 말하며 그림을 부탁하면, 「찾아서」 라고 하지 않아도 비서가 웹에서 그 사진을 찾아 참고 그림으로 넣는다. 사용자가 그 대상의 사진이나 링크를 이미 보냈으면 그것을 쓰고 따로 찾지 않는다. 「고양이」, 「바닷가」 처럼 특정 대상이 아닌 것은 찾지 않는다 | 비서가 받는 지침에 이 규칙이 있다. 가짜 Hermes 가 검색해 찾은 가짜 상품 페이지를 참고로 가리킨 실행에서 이미지 도구가 그 페이지의 대표 사진을 입력으로 받고, 답에 새 그림이 보인다 |
| REQ2 | 서버는 비서가 가리킨 주소가 비서가 실제로 찾은 주소일 때만 받는다. 실제로 찾은 주소는 요청자의 이 대화에서 비서가 답을 만들며 돌린 웹 검색과 페이지 읽기의 결과에 글자 그대로 나온 페이지 주소와 사진 주소다. 비서가 맡긴 에이전트가 찾은 것과 앞 답에서 찾은 것도 포함한다(DECISION4, DECISION5). 비서가 지어냈거나 고친 주소, 비서가 읽기 도구에 스스로 적어 넣었을 뿐 결과에는 나오지 않은 주소(DECISION25), 다른 대화나 다른 사용자의 실행이 찾은 주소는 받지 않는다. 같은 주소로 보는 범위는 DECISION19 가 정한다 | 검색과 읽기 결과에 없던 주소, 결과의 주소에서 글자를 바꾼 주소, 비서가 읽기 도구에 적어 넣기만 한 주소, 다른 대화의 실행이 찾은 주소를 가리키면 이미지 도구에 사진이 전달되지 않고 비서가 쓸 수 없다고 답한다 |
| REQ3 | 찾은 주소도 사용자가 보낸 링크와 같은 안전 검사로 받는다. 공개 https 주소만 받고, 내부망 주소와 금지 목록, 넘어가는 주소마다의 재검사, 사진 네 형식, 20MB 상한, 제한 시간이 같다(그림 스펙 REQ21, DECISION35, DECISION37, DECISION44, DECISION45) | 찾은 결과에 나온 주소라도 내부망 주소, 사진이 아닌 주소, 20MB 를 넘는 사진이면 이미지 도구에 사진이 전달되지 않는다 |
| REQ4 | 사진이 여러 장이면 비서가 부탁에 가장 맞는 것을 골라 확인을 묻지 않고 바로 그린다 | 찾은 사진을 쓴 실행에서 사용자에게 고르라는 질문 없이 그림이 만들어진다 |
| REQ5 | 비서는 찾은 사진을 참고해 그린 답에 어떤 사진을 참고했는지 출처 링크와 함께 적는다. 「그림 지시문 보기」 의 「참고한 링크」 에도 그 주소가 보이고, 비서가 찾은 링크라는 표시가 붙는다. 사용자가 보낸 링크에는 그 표시가 없다 | 찾은 사진을 쓴 그림의 답 글에 참고한 사진의 링크가 있고, 「그림 지시문 보기」 를 펼치면 그 주소가 「비서가 찾음」 표시와 함께 보인다. 사용자가 보낸 링크로 만든 그림에는 표시가 없다 |
| REQ6 | 고른 사진을 받지 못하면 비서가 다른 사진을 골라 다시 시도한다. 그림 한 장에 다른 사진 3장까지다(DECISION13). 사용자가 보낸 링크의 사진을 받지 못했을 때도 같은 상품을 찾아 시도하고, 보낸 링크 대신 찾은 사진을 썼다고 답에 적는다(DECISION23). 쓸 만한 사진을 찾지 못했거나 상한까지 모두 받지 못하면, 또는 대상 여럿 가운데 하나라도 사진이 없으면(DECISION24) 그림을 만들지 않고, 사진을 찾지 못했다는 것과 사진을 직접 올리거나 링크를 보내는 방법을 답한다. 사용자가 그 뒤에 설명만으로 그리라고 하면 그린다(DECISION21) | 첫 사진이 열리지 않고 둘째 사진이 열리는 실행에서 둘째 사진으로 그림이 만들어진다. 모든 사진이 열리지 않는 실행에서는 그림 파일이 생기지 않고 비서가 찾지 못했다고 답하며 실행은 실패로 끝나지 않는다 |
| REQ7 | 비서는 실존 인물의 얼굴, 로고, 캐릭터를 참고하려고 사진을 찾지 않는다. 캐릭터나 로고가 든 상품은 실제로 파는 상품이면 찾는다(DECISION26). 그런 부탁을 받으면 사진을 찾아 참고하지 못한다고 알리고, 사용자가 사진을 직접 올리거나 링크를 보내는 길을 알린다. 상품 사진은 사람이 없는 것을 먼저 고른다. 사람이 찍힌 사진밖에 없으면 그 사진을 쓰되, 그림 지시문에 참고 사진에서 상품의 모양과 색만 쓰고 사진 속 사람의 얼굴과 생김새는 쓰지 않는다고 적는다 | 비서가 받는 지침에 이 규칙이 있다. 가짜 Hermes 가 사람이 찍힌 상품 사진을 참고로 넘긴 실행의 지시문에 상품만 따온다는 줄이 있다 |
| REQ8 | 찾은 사진을 쓴 그림 뒤에 같은 인물의 다음 장면을 그릴 때도 그 사진을 다시 참고로 넣는다(그림 스펙 REQ25). 다시 받지 못하면 그림 스펙 DECISION52 와 같이 앞 그림만 참고로 그리고 알린다 | 찾은 사진을 쓴 그림 뒤에 다음 장면을 부탁하면 이미지 도구가 앞 그림과 그 사진을 참고로 받는다 |
| REQ9 | PR1 배포 뒤 운영에서 실제 상품을 찾아 그리는 왕복이 한 번에 된다 | 코디네이터가 운영에서 「GGRN 양말 신은 아이 그려 줘. 사진은 웹에서 찾아서 적용해 줘」 를 링크 없이 보내면 답에 그림이 보이고, 「그림 지시문 보기」 의 참고한 링크에 비서가 찾은 주소가 있으며, 그림의 양말 모양이 그 사진과 맞는다 |
| REQ10 | PR2 배포 뒤 운영에서 상품 이름만 말해 그리는 왕복이 한 번에 된다 | 코디네이터가 운영에서 「GGRN 양말 신은 아이 그려 줘」 만 보내면 REQ9 와 같은 결과에 더해 답 글에 참고한 사진의 링크가 있고 참고한 링크에 「비서가 찾음」 표시가 보인다 |

| DECISION15 | PR 나눔 | 둘로 나눈다. PR1 은 찾은 주소를 받는 길과 그 주소를 쓰라는 지침, PR2 는 나머지 지침과 화면 표시다 | 작성자(위임) | 사용자가 2026-11-21 에 권장안으로 진행하라고 맡겼다. 서버가 바깥 주소를 여는 범위를 넓히는 코드를 따로 리뷰하고, 받는 길이 운영에서 되는지 본 뒤 지침을 다듬는다 |
| DECISION16 | 찾은 주소 기록의 수명 | 대화와 함께 두고 대화를 지우면 함께 지운다. 기록이 지워진 주소는 다시 검색해야 쓴다 | 작성자 | 실행 기록과 그림 행이 이미 따르는 규칙이다. 대화가 없어지면 그 주소를 다시 받을 까닭이 없다 |
| DECISION17 | 받지 못한 까닭의 표시 | 사용자가 보낸 링크와 같은 까닭 글을 쓴다(열 수 없는 주소, 사진을 찾지 못함, 너무 큼, 열지 못함). 비서가 찾지 않은 주소는 대화에 없는 링크와 같은 응답이다 | 작성자 | 그림 스펙 REQ21 과 같은 길이라 까닭을 따로 만들지 않는다 |
| DECISION18 | 서버가 결과를 보는 도구 | 웹 검색(`web_search`)과 페이지 읽기(`web_extract`) 둘이다. 브라우저 도구나 터미널로 연 페이지의 주소는 받지 않는다 | 작성자 | 비서의 답 지침이 출처로 인정하는 도구가 이 둘이다([`answer-quality.md`](../answer-quality.md) 의 「지침」). 브라우저 도구는 profile 틀에서 꺼져 있다. 결과를 서버가 볼 수 없는 검색 서비스로 바꾸면 이 기능이 멈추므로 「위험과 대응」 에 적는다 |
| DECISION19 | 결과의 주소와 같은 주소로 보는 범위 | 그림 스펙 DECISION43 의 범위에 더해, 결과에 적힌 주소의 HTML 엔티티(`&amp;`)를 푼 주소, `//` 로 시작하는 주소를 https 로 푼 주소, 상대 주소를 그 결과의 페이지 주소로 푼 주소를 같은 주소로 본다. 그 밖에 비서가 글자를 붙이거나 바꾼 주소는 찾은 주소가 아니다 | 작성자 | 페이지 본문의 사진 주소는 이런 꼴로 자주 나온다. 셋 다 서버가 결과만으로 정해진 대로 계산하는 변환이라 비서가 지어낸 글자가 들어가지 않는다. 링크 받기가 대표 사진 주소를 푸는 방식과 같다 |
| DECISION20 | 사용자가 보낸 페이지 안의 다른 사진 | 비서가 그 페이지를 읽어 본문에 나온 사진 주소는 찾은 주소다. 대표 사진이 부탁과 다른 색이거나 묶음 사진이면 그 사진을 고를 수 있고 「비서가 찾음」 표시가 붙는다. 사용자가 보낸 주소 자체를 가리키면 지금처럼 대표 사진 하나이고 표시가 없다 | 작성자 | DECISION4 와 DECISION5 를 그대로 적용한 것이다. 표시는 누가 그 주소를 골랐는지를 나타낸다 |
| DECISION21 | 사진을 찾지 못한 뒤 사용자가 설명만으로 그리라고 할 때 | 그린다. DECISION6 은 비서가 스스로 고르는 기본 동작만 막는다 | 작성자 | 사용자가 모양이 다를 수 있음을 알고 고른 것이다. 막으면 상품 이름을 빼고 다시 부탁해야 한다 |
| DECISION22 | 한 대상에 쓰는 찾은 사진의 장수 | 대상 하나에 가장 맞는 한 장을 기본으로 한다. 앞과 옆처럼 모양을 알려면 더 필요할 때만 더 넣는다 | 작성자 | 받는 사진마다 실패할 수 있고 기다리는 시간이 는다. 장수 상한은 DECISION12 그대로다 |
| DECISION23 | 사용자가 보낸 링크의 사진을 받지 못했을 때 | 비서가 같은 상품을 찾아 다른 판매처의 사진으로 그리고, 보낸 링크 대신 찾은 사진을 썼다고 답에 적는다. 찾지 못하면 REQ6 과 같다. 그림 스펙 REQ21 의 「그림을 만들지 않고 알린다」 는 찾을 수 없는 대상(DECISION2 밖)과 끝내 찾지 못한 때에 남는다 | 작성자(위임) | 사용자가 2026-11-21 에 권장안으로 진행하라고 맡겼다. 쇼핑몰 차단이 잦고, 어떤 사진을 썼는지 보여 틀리면 바로 안다 |
| DECISION24 | 대상 여럿 가운데 일부만 사진을 찾았을 때 | 하나라도 없으면 그림을 만들지 않고 어느 대상의 사진을 찾지 못했는지 알린다 | 작성자(위임) | 사용자가 2026-11-21 에 권장안으로 진행하라고 맡겼다. DECISION6 과 그림 스펙 DECISION32 와 같은 기준이다 |
| DECISION25 | 비서가 스스로 주소를 적어 읽은 페이지 | 찾은 주소가 아니다. 검색 결과에 나온 주소와, 읽은 페이지의 본문에 나온 주소만 받는다. 비서가 읽기 도구에 적어 넣은 주소는 검색 결과나 다른 페이지의 본문에도 나왔을 때만 받는다 | 작성자(위임) | 사용자가 2026-11-21 에 권장안으로 진행하라고 맡겼다. 받는 범위를 남이 쓴 결과에 실제로 있던 주소로 묶어야 서버가 확인하는 뜻이 있다. 검색을 한 번 거치면 같은 일이 된다 |
| DECISION26 | 캐릭터나 로고가 든 상품 | 실제로 파는 상품이면 찾아서 참고한다. 캐릭터 자체나 로고만 그려 달라는 부탁은 찾지 않는다 | 작성자(위임) | 사용자가 2026-11-21 에 권장안으로 진행하라고 맡겼다. 사용자가 그 상품 링크를 보내면 지금도 같은 그림이 나온다 |
| DECISION27 | 비서가 찾은 상품 페이지의 대표 사진 | DECISION18의 읽기 도구에 상품 페이지 전용 경로를 더한다. Hermes 플러그인이 원본 HTML에서 사진 후보를 뽑아 서버에 넘긴다. 서버는 페이지를 다시 열지 않고 JSON-LD의 `Product.image`, 사이트 공통 사진을 뺀 `og:image`, 본문의 가장 큰 상품 사진 순으로 골라 받는다. 페이지와 사진 주소의 대화 확인과 사진 받기 안전 검사는 모두 거친다 | 사용자 2026-11-21 | 「서버가 사진 고르기」를 선택했고, 기본 `web_extract`가 마크다운만 반환하는 것을 확인한 뒤 원본 HTML을 받을 플러그인 경로를 추가하기로 했다 |

## 위험과 대응

서버가 여는 바깥 주소의 범위가 「사용자가 보낸 링크」 에서 「비서가 읽은 웹 결과에 나온 주소」 로 넓어진다. 웹 페이지의 글은 남이 쓴 것이라 비서를 조종하려는 글이 섞일 수 있다.

| 위험 | 대응 | 남는 것 |
| --- | --- | --- |
| 페이지의 글이 비서에게 내부망 주소나 홈서버 자신을 열게 시킨다 | 찾은 주소도 사용자가 보낸 링크와 같은 검사로 받는다(REQ3). 내부망 주소와 금지 목록, 넘어가는 주소마다의 재검사가 같다 | 그 검사 코드에 기댄다. 바꿀 때 보안 테스트가 함께 지킨다 |
| 페이지의 글이 비서에게 대화 내용을 주소에 붙여 바깥으로 보내게 시킨다 | 결과에 글자 그대로 나온 주소만 받는다(REQ2). 비서가 글자를 붙이거나 바꾼 주소, 비서가 읽기 도구에 적어 넣기만 한 주소는 거절한다(DECISION25) | 이 기능으로 새로 생기는 길은 없다. 페이지 읽기 도구는 지금도 비서가 고른 공개 주소를 열며, 그것은 이 스펙이 바꾸지 않는다 |
| 나쁜 페이지가 본문에 심어 둔 주소가 참고 사진으로 쓰인다. 범위가 대화 전체라 한 번 읽은 페이지의 주소는 그 대화가 끝날 때까지 쓰일 수 있다(DECISION4) | 받는 것은 공개 주소의 사진 네 형식뿐이고 받은 바이트는 이미지 서비스에만 넘긴 뒤 지운다. 어떤 주소를 참고했는지 답과 「그림 지시문 보기」 에 「비서가 찾음」 표시와 함께 보인다(REQ5). 사람이 없는 실행에서는 그림을 만들지 않는다(DECISION9) | 엉뚱하거나 불쾌한 사진이 참고로 들어가 그림이 이상해질 수 있다. 사용자가 출처 링크를 보고 알아차리고 다시 부탁한다. 그 주소의 서버는 우리 서버가 사진을 받아 갔다는 사실을 안다 |
| 비서가 다른 사용자나 다른 대화에서 찾은 주소를 가리킨다 | 요청자의 그 대화에서 찾은 주소만 받는다(REQ2). 대화에 없는 주소와 같은 응답이라 있는지 없는지도 드러나지 않는다 | 없음 |
| 찾은 사진이 남의 저작물이다 | 받은 사진을 남기지 않고(DECISION9) 출처 링크를 보인다(REQ5). 안내 글은 두지 않는다(DECISION14) | 그림이 원본과 비슷할 수 있다. 밖에 올릴지는 사용자가 판단한다 |
| 검색 서비스를 결과가 서버에 보이지 않는 것(OpenAI 내장 검색)으로 바꾼다 | 지금 설정은 Hermes 의 도구로 도는 검색이라 결과가 보인다([`answer-quality.md`](../answer-quality.md) 의 「검색 서비스」) | 검색 서비스를 바꾸면 검색 결과의 주소는 받지 못하고 페이지 읽기 결과의 주소만 남는다. 바꾸기 전에 이 기능을 다시 확인한다 |
