## 책임과 경계

| 모듈 | 맡는 것 |
| --- | --- |
| `hermes/plugins/fos-ctx` | 결과 hook 에서 `web_search` 와 `web_extract` 의 결과 글을 읽어 주소 후보를 뽑고, 서명한 호출 맥락과 함께 Control Plane 에 보낸다. 결과 글은 바꾸지 않는다. 보내지 못해도 도구 결과는 그대로 간다 |
| `backend` 의 `mcp` | 새 경로로 후보를 받아 origin 실행의 대화를 정하고 `chat.conversation` 에 맡긴다. 받기 경로는 사용자 메시지에 없는 링크를 `chat.conversation` 에 다시 묻는다 |
| `backend` 의 `chat.conversation` | 후보를 정해진 꼴로 바꿔 해시를 대화 행에 남기고, 가리킨 주소가 그 해시에 있는지 답한다. 같은 주소로 보는 규칙은 사용자 메시지의 링크 판정과 한 벌이다 |
| `backend` 의 `chat.artifact` | 그림 규칙의 주소 줄을 고친다. 받기는 바뀌지 않는다 |
| `web` | PR2 에서 「비서가 찾음」 표시를 그린다 |

**주소를 뽑는 쪽이 fos-ctx 인 까닭.** Control Plane 이 받는 도구 사건의 결과는 500자로 잘린다([`hermes-contract.md`](../../../hermes/docs/hermes-contract.md) 의 「붙은 플러그인 서버의 도구 사건」). 결과 전체를 보는 곳은 Hermes 안의 결과 hook 뿐이다.
fos-ctx 는 후보를 뽑기만 하고, 같은 주소인지와 받아도 되는지는 Control Plane 이 정한다.

## 인터페이스와 데이터

### fos-ctx 가 뽑는 후보

결과 hook(`transform_tool_result`)이 도구 이름이 `web_search` 나 `web_extract` 이고 결과가 JSON 글이며 session 과 `tool_call_id` 가 있을 때만 돈다. `execute_code` 안에서 돈 호출은 `tool_call_id` 가 없어 알리지 않는다.
결과의 모양은 [`hermes-contract.md`](../../../hermes/docs/hermes-contract.md) 의 「웹 도구의 결과」 가 갖는다.

| 도구 | 후보 |
| --- | --- |
| `web_search` | `success` 가 참일 때 `data.web[]` 항목의 `url`, `title`, `description` 에서 찾은 `http://`, `https://` 주소. 기준 주소는 없다. 실패 응답의 `error` 글은 남이 쓴 결과가 아니라 읽지 않는다 |
| `web_extract` | 결과 항목마다 `content` 에서 찾은 절대 주소, 마크다운 링크와 사진의 대상(`](대상)`), `src` 와 `href` 속성 값. 기준 주소는 그 항목의 `url` 이다. 항목의 `url` 자체는 후보가 아니다(스펙 DECISION25). `error` 가 있는 항목은 읽지 않는다 |

- 절대 주소는 공백과 `<>"'`, 역슬래시 앞에서 끊고, 끝의 문장 부호와 짝이 맞지 않는 닫는 괄호를 뗀다
- 절대 주소 뒤에 한글 조사처럼 주소에 쓸 수 없는 글자가 바로 붙었으면 그 앞까지 자른 꼴과 붙은 꼴을 둘 다 후보로 낸다
- 후보 하나는 2,048자까지, 한 호출은 2,000개까지다. 넘는 것은 보내지 않는다. 같은 후보는 한 번만 보낸다. 다듬기 전에 4,096자를 넘는 덩어리는 버린다
- 알리는 주소는 받기 경로처럼 플러그인 정책 주소(`guard_url`)의 마지막 조각을 바꿔 만든다. 새 환경 값이 없다
- 제한 시간은 5초다. 실패와 옛 Control Plane 의 거절(이 경로를 모르는 서버는 인증 거절로 답한다), 그 밖의 오류는 로그에 종류만 남기고 넘어간다. hook 은 늘 None 을 돌려줘 결과 글을 바꾸지 않는다

### 알리는 경로

`POST /internal/hermes/found-links`. 인증은 `/mcp` 와 같은 profile 토큰이고, 본문의 `_fos_ctx` 는 도구 이름 `found_links` 로 서명한 호출 맥락이다.

```json
{"_fos_ctx": {}, "pages": [{"base": "https://shop.example.com/goods/1", "links": ["/img/a.jpg", "https://cdn.example.com/b.png"]}], "typed": ["https://shop.example.com/goods/1"]}
```

| 응답 | 뜻 |
| --- | --- |
| 204 | 남겼다. 대화가 없는 실행이면 남기지 않고 같은 응답이다 |
| 400 `VALIDATION_FAILED` | `pages` 나 `typed` 의 모양이 틀리거나 상한(후보 2,000개, 페이지 200개, 적어 넣은 주소 50개, 기준 주소 2,048자)을 넘는다 |
| 403 `MCP_CALL_CONTEXT_INVALID` | 본문이 객체가 아니거나 서명이나 origin 실행이 맞지 않는다 |

새 경로는 profile 토큰으로 인증하는 경로 목록 세 곳(`AgentTokenAuthenticationFilter`, `ControlPlaneJwtFilter`, `SecurityConfig`)에 더한다.

origin 판정은 받기 경로와 같다(`McpCallerResolver`). 요청 본문이 사용자나 대화를 정하지 못한다. 비서가 맡긴 에이전트의 실행도 origin 이 같은 대화면 그 대화에 남는다(스펙 DECISION4).

### 같은 주소로 보는 규칙

`ConversationLinks` 의 주소 비교를 값 객체 `LinkTarget`(`chat.conversation.application.dto`)으로 꺼내 두 판정이 함께 쓴다. 비교 글은 punycode 소문자 호스트와, 퍼센트 인코딩을 푼 경로와 쿼리다. 조각과 scheme 은 뺀다(그림 스펙 DECISION43).

후보 하나에서 아래 꼴을 모두 만들어 각각 남긴다(스펙 DECISION19).

| 꼴 | 만드는 법 |
| --- | --- |
| 적힌 그대로 | 절대 주소면 그대로 |
| 엔티티를 푼 꼴 | `&amp;`, `&#38;`, `&#x26;` 을 `&` 로 바꾼다 |
| `//` 로 시작 | 앞에 `https:` 를 붙인다 |
| 상대 주소 | 기준 주소가 http(s) 절대 주소일 때 그 주소로 푼다. 기준이 없으면 버린다 |

후보에서 만든 꼴 가운데 하나라도 비교 글이 그 페이지의 기준 주소나 그 호출의 `typed`(비서가 `web_extract` 에 적어 넣은 주소)와 정확히 같으면 그 후보의 꼴을 모두 남기지 않는다. 꼴마다 따로 빼면 본문이 자기 주소를 `&amp;` 로 되풀이했을 때 적힌 꼴이 남는다. 읽기 서비스에 따라 결과 항목의 주소가 넘어간 뒤의 최종 주소일 수 있어 적어 넣은 주소를 따로 받는다. `typed` 가 없는 옛 fos-ctx 의 알리기는 기준 주소만 뺀다. 페이지가 자기 주소를 본문에 되풀이한 것만으로 비서가 적어 넣은 주소가 찾은 주소가 되지 않게 한다(스펙 DECISION25). 본문에 적힌 다른 주소는 글자가 비슷해도 본문에 나온 주소라 남긴다.

상대 주소는 `java.net.URI` 로 푼다. `?` 로 시작하는 후보만 기준 주소의 경로에 직접 붙인다(`java.net.URI` 가 이 꼴을 표준과 다르게 푼다). `chat.artifact.infra` 의 받기 객체를 참조하지 않는다. 한 호출 안에서 같은 해시는 한 번만 남긴다.

### 저장

`conversation` 에 칸 하나를 더한다. 새 표를 만들지 않는다(사용자 결정 2026-11-01). 정확한 스키마는 [`data-schema.md`](../../../backend/docs/data-schema.md) 의 「대화 표」 가 갖는다.

| 칸 | 내용 |
| --- | --- |
| `found_link_hashes` | 비교 글의 SHA-256 앞 16바이트를 16진수 32자로 적어 이어 붙인 글. 구분 문자가 없다. `MEDIUMTEXT`, 비어 있으면 NULL |

- **주소가 아니라 해시를 둔다.** 판정에는 「있었는가」 만 필요하다. 검색한 주소의 원문을 대화마다 쌓지 않고, 암호화할 것도 없다
- 더하기는 `UPDATE` 한 문장이다. 지금 값 뒤에 새 해시를 붙이고 뒤에서 640,000자(해시 20,000개)만 남긴다. 한 실행의 도구 결과 여럿이 동시에 와도 읽고 쓰는 사이에 서로를 덮지 않는다. 오래된 해시가 먼저 밀려난다. 지운 대화(`deleted_at` 이 있는)에는 더하지 않는다
- 받기 판정을 통과한 해시는 같은 문장으로 뒤에 다시 붙인다. 그림에 쓴 링크가 뒤에 읽은 페이지들에 밀려나 다음 장면에서 빠지는 일을 줄인다
- 있는지는 글을 32자씩 잘라 비교한다. 구분 문자가 없어 글 전체에서 찾으면 두 해시의 경계에 걸친 일치가 생긴다
- 대화 엔티티에는 이 칸을 두지 않고 전용 조회와 전용 `UPDATE` 로만 읽고 쓴다. 대화 행을 고치는 다른 저장이 이 칸을 옛 값으로 덮지 않고, 대화를 읽을 때마다 이 칸을 함께 읽지 않는다. 테스트 스키마는 엔티티에서 만들어지므로 기억 벡터 칸처럼 테스트용 SQL(`hibernate.hbm2ddl.import_files`)로 칸을 더한다
- 앞선 호출이 이미 남긴 해시를 다시 보내도 빼지 않는다. 판정은 있는지만 본다
- **대화를 지울 때 이 칸을 비운다(스펙 DECISION16).** 대화 행은 지우지 않고 `deleted_at` 만 적으므로, 대기 메시지를 비우는 같은 자리에서 NULL 로 바꾼다

### 받기 경로의 판정

`ImageSourceService` 의 `link:` 분기가 차례로 본다.

1. 요청자가 그 대화에 보낸 메시지에 있는 주소인가(지금 그대로). 맞으면 사용자가 보낸 링크다
2. 아니면 그 대화의 `found_link_hashes` 에 가리킨 주소의 해시가 있는가. 맞으면 비서가 찾은 링크다. 가리킨 글에 엔티티(`&amp;` 등)가 있으면 엔티티를 푼 글을 먼저 보고, 없으면 가리킨 글 그대로를 본다. 맞은 쪽의 글로 받을 주소를 만든다
3. 둘 다 아니면 `IMAGE_SOURCE_UNKNOWN` 이다

받을 주소의 꼴(`https://`, 소문자 punycode 호스트, 퍼센트 인코딩)과 길이 상한, 그 뒤의 받기와 오류 코드는 사용자가 보낸 링크와 같다.
그래서 비서가 `&amp;` 가 든 꼴 그대로 가리켜도 푼 주소로 받고, 그림 행에 남는 주소도 푼 꼴이라 다음 장면에서 다시 받을 때 통과한다(REQ8).
상대 주소와 `//` 로 시작하는 주소는 푼 꼴의 해시만 남는다. 비서가 그 꼴 그대로 적으면 맞지 않으므로 그림 규칙이 완전한 주소로 적게 시킨다.

### 그림 규칙과 막는 글

PR1 은 `IMAGE_RULES` 의 「검색이나 페이지에서 찾은 주소는 쓰지 않는다」 를 아래 뜻으로 바꾼다. 줄 수를 세는 머리 문장도 함께 고친다.

- 웹 검색과 페이지 읽기 결과에 나온 페이지 주소나 사진 주소의 사진을 참고로 쓸 때도 `link:<결과에 나온 주소 그대로>` 로 적는다. 주소를 고치거나 지어내지 않는다. 스스로 적어 넣어 읽은 주소는 쓰지 못한다. 결과에 `/` 나 `//` 로 시작하는 꼴로 나온 사진 주소는 그 페이지의 주소를 기준으로 완전한 `https://` 주소로 적는다

fos-ctx 의 막는 글 두 개(`NOT_REFERENCE`, `UNKNOWN`)에서 「사용자가 보낸 주소」 를 「사용자가 보낸 주소나 검색·읽기 결과에 나온 주소」 로 넓힌다.

PR2 가 나머지 줄을 더한다. 줄 수를 세는 머리 문장도 함께 고친다. 글자 그대로의 글은 `IMAGE_RULES` 가 갖는다.

| 줄 | 뜻 |
| --- | --- |
| 이름만 말해도 찾기(REQ1) | 특정 상품, 사물, 장소나 건물을 이름으로 말하며 그림을 부탁하면 「찾아서」 가 없어도 `web_search` 로 사진을 찾아 참고로 넣는다. 그 대상의 사진이나 링크가 이미 있으면 찾지 않는다. 특정 대상이 아닌 것은 찾지 않는다 |
| 찾지 않는 대상과 사람이 찍힌 사진(REQ7) | 실존 인물의 얼굴, 로고, 캐릭터 자체는 찾지 않고 직접 올리거나 링크를 보내는 길을 알린다. 그것이 든 상품은 파는 상품이면 찾는다. 사람이 없는 사진을 먼저 고르고, 사람이 찍힌 사진만 있으면 지시문에 상품의 모양과 색만 쓰고 사진 속 사람은 쓰지 않는다는 줄을 적는다 |
| 고르기(REQ4) | 부탁에 가장 맞는 사진을 골라 묻지 않고 그린다. 대상 하나에 한 장이 기본이다(스펙 DECISION22) |
| 다시 시도(REQ6) | 받지 못하면 결과의 다른 사진으로 3장까지 더 시도한다. 사용자가 보낸 링크가 열리지 않으면 같은 상품을 찾아 시도하고 그렇게 했다고 적는다. 끝내 없거나 대상 하나라도 없으면 그리지 않고 직접 올리거나 링크를 보내는 길을 알린다. 그 뒤 설명만으로 그려 달라면 그린다 |
| 출처 줄(REQ5) | 찾은 사진을 참고한 답에 참고한 사진의 페이지 링크를 적는다 |
| 검색 도구를 직접 부르기(REQ1) | 사진을 찾을 때는 `web_search` 와 `web_extract` 를 직접 부른다. `execute_code` 안에서 부른 검색과 읽기의 결과 주소는 쓰지 못한다 |

마지막 줄(쓸 수 없는 결과를 받으면 그림 없이 까닭을 답한다)에는 「다음 장면이 아닌데 찾은 사진이나 보낸 링크의 사진을 받지 못했으면 다시 시도 줄을 따른다」 는 예외를 더한다. 다음 장면에서 다시 넣은 링크만 막히면 지금처럼 다음 장면 줄(앞 그림만 참고)이 먼저다(스펙 REQ8).
fos-ctx 의 링크 까닭 글(`LINK_REASONS`) 넷은 다음 방법을 「결과의 다른 사진으로 바꿔 다시 부르고, 없으면 그리지 않고 알린다」 로 바꾼다. 열 수 없는 주소(`IMAGE_SOURCE_LINK_BLOCKED`)도 바로 알리지 않고 다시 시도로 바꾼다. 찾은 주소 가운데 하나가 금지 목록에 걸려도 다른 판매처의 사진으로 될 수 있다. 대화에 없는 주소(`UNKNOWN`)의 다음 방법에는 「스스로 적은 상품 페이지 주소나 `execute_code` 안에서 얻은 주소였으면 `web_search` 나 `web_extract` 를 직접 불러 그 페이지를 읽고 본문의 사진 주소로 다시 부른다」 를 더한다. PR1 배포 뒤 운영에서 비서가 `execute_code` 안의 검색으로 얻은 썸네일 주소와 스스로 적은 상품 페이지 주소를 넣었다가 두 번 거절되고, 거절 뒤 페이지를 읽고도 다시 그리지 않은 일이 있었다.
`execute_code` 안의 결과 주소는 받지 않는다. 그 결과는 비서가 쓴 코드의 출력이라 비서가 지어낸 글자가 섞일 수 있어 스펙 DECISION25 의 뜻이 없어진다. 스펙 DECISION18 이 받는 도구를 둘로 정했으므로 지침으로 두 도구를 직접 쓰게 한다.
알리기가 실패하거나 알릴 맥락이 없으면 경고 로그로 남긴다. PR1 은 debug 로 남겨 운영에서 원인을 볼 수 없었다.
몇 장째인지는 fos-ctx 가 세지 않고 그림 규칙의 상한을 비서가 지킨다. 호출마다 따로 도는 hook 이 그림 한 장의 시도를 묶을 길이 없다.

### 「비서가 찾음」 표시(PR2)

받기 경로가 2번으로 통과한 응답에 머리 `X-Image-Source-Found: 1` 을 더한다. 1번으로 통과한 사용자가 보낸 링크에는 머리가 없다. PR1 은 이 머리를 내지 않았다.

fos-ctx 는 받은 링크와 함께 이 머리를 호출마다 기억하고, 그림 올리기의 meta 에 `found_links` 를 넣는다.

| 칸 | 내용 |
| --- | --- |
| `found_links` | `source_links` 가운데 비서가 찾은 주소. `source_links` 의 순서를 따른다. 없으면 칸을 넣지 않는다 |

- 서명은 `found_links` 가 있을 때만 아홉째 줄로 그 주소를 줄바꿈으로 이은 글의 SHA-256 을 더한다. 없으면 지금 일곱 줄이나 여덟 줄 그대로다
- Control Plane 은 `found_links` 의 항목이 모두 `source_links` 에 있어야 받는다. 하나라도 없으면 서명이 틀린 올리기와 같이 거절한다
- 옛 Control Plane 은 머리를 내지 않으므로 새 fos-ctx 가 `found_links` 를 넣지 않는다. 옛 fos-ctx 는 머리를 읽지 않으므로 새 Control Plane 이 표시 없는 그림으로 남긴다. 어느 순서로 배포해도 그림 올리기가 막히지 않는다. 예외는 Control Plane 을 되돌리는 순간에 사진은 새 서버에서 받고 그림은 옛 서버에 올린 호출 하나다. 그 그림은 서명이 맞지 않아 남지 않는다

**그림 행에 남기는 자리.** `chat_artifact` 에 칸 하나를 더한다. 새 표를 만들지 않는다.

| 칸 | 내용 |
| --- | --- |
| `generation_found_link_flags` | `generation_source_links` 의 링크마다 비서가 찾은 것이면 `1`, 사용자가 보낸 것이면 `0` 을 같은 순서로 이은 글. 찾은 링크가 없으면 NULL. `VARCHAR(16)` 이다. 그림 올리기의 링크 상한(16개)과 묶여 있어 상한을 올리면 칸도 넓힌다 |

- 링크 원문을 다시 두지 않는다. 링크는 이미 봉해 두었고 표시는 「누가 골랐는가」 만 알면 된다. 그래서 이 칸은 암호화하지 않는다
- 표시와 링크의 수가 다르면(옛 행이나 깨진 행) 표시를 모두 없는 것으로 읽는다. 표시가 틀리게 붙느니 붙지 않는 쪽을 고른다

**메시지 응답의 모양.** 그림 결과물의 `sourceLinks` 옆에 `foundSourceLinks`(그 가운데 비서가 찾은 주소, 같은 순서)를 더한다. 옛 화면은 이 칸을 읽지 않고, 새 화면은 옛 응답에 이 칸이 없으면 표시를 붙이지 않는다.
화면의 「참고한 링크」 는 `foundSourceLinks` 에 든 링크 옆에 「비서가 찾음」 을 붙인다.

**같은 주소가 두 길로 통과할 때.** 받기 판정이 1번을 먼저 보므로, 사용자가 보낸 주소를 비서가 결과에서 다시 찾았어도 표시가 없다. 사용자가 보낸 페이지를 읽어 본문에서 고른 다른 사진 주소는 2번으로 통과해 표시가 붙는다(스펙 DECISION20).
다음 장면에서 그림 행의 참고 링크를 다시 넣으면 받기 판정을 다시 거치므로 표시도 같은 규칙으로 다시 정해진다.

### 상품 페이지에서 대표 사진 고르기

`web_extract`의 기본 경로는 마크다운만 넘기므로 `fos-ctx`가 상품 사진용 읽기 도구 `product_page_read`를 자기 toolset `fos-product-page`에 등록한다. 이 toolset은 웹 검색(`web`)이 켜진 profile에서만 켜진다([Hermes 계약](../../../hermes/docs/hermes-contract.md)의 「plugin toolset 이름」). 그림 지침은 검색 결과가 상품 페이지일 때 이 도구로 한 번 읽은 뒤 같은 페이지 주소를 가리키게 한다. 원본 HTML을 받는 데 Hermes가 사용하는 무료 Firecrawl 읽기 경로를 이용한다. 공개 웹 주소와 Hermes 웹사이트 정책을 요청 전과 제공자가 알려준 최종 주소에 적용한다. 유료 경로로 넘어가지 않는다. 페이지 원문은 모델이나 Control Plane에 보내지 않는다.

플러그인은 읽은 HTML에서 `Product.image`, `og:image`, 본문의 `img`와 `srcset`을 뽑고 HTML에 크기가 적혔으면 함께 알린다. 본문 그림 가운데 `width`·`height` 속성이나 `srcset` 크기의 한 변이 200px 보다 작은 것과, 파일 이름이나 `alt` 가 배지, 아이콘, 로고, 스프라이트인 것은 후보에 넣지 않는다. 기존 `found-links` 요청의 페이지 항목에 `requested`와 `images`를 선택 칸으로 보낸다. 사진 후보는 기존 `links`에도 담는다. 알리기와 받기의 대화는 서명한 origin 실행에서 얻는다. 읽기 요청과 최종 페이지의 주소는 별도로 발견한 기록이 있을 때 쓸 수 있다.

Control Plane은 대화 행에 사진 후보 해시와 상품 사진을 위해 페이지를 읽었다는 표시를 남긴다. 대화별 페이지 주소와 사진 후보의 연결은 메모리에서 잠시 유지한다. 후보가 메모리에서 사라졌거나 읽은 페이지에 쓸 후보가 없으면 다시 읽기 전까지 그 페이지로 사진을 받지 않는다. 사진을 받은 뒤 주소 해시에 직접 사진으로 받는 표시를 붙인다. 다음 장면에서 그 주소가 웹 페이지를 반환하면 사진을 찾지 못한 것으로 처리한다.

서버는 페이지 주소가 기존 대화 해시와 맞을 때 그 페이지의 사진 후보를 읽는다. 후보는 구조화 상품 사진, Open Graph 사진, 본문 사진 순이다. Open Graph 사진에 사이트 공통 파일 이름이나 경로가 쓰였거나 같은 대화의 다른 상품 페이지에서 같은 사이트의 같은 사진을 대표로 알렸으면 건너뛴다. 본문 사진은 알려진 크기가 200×200 이상인 것만 크기가 큰 순으로 고르고, 크기가 같으면 본문 순이다. 작거나 크기를 모르는 본문 그림은 배지나 아이콘일 수 있어 자동으로 고르지 않는다. 고를 사진이 없으면 사진을 찾지 못한 것으로 답해 비서가 다른 출처를 찾게 한다. 선택한 사진의 해시까지 대화에서 확인하고 기존 전송의 주소, 이동, 크기, 형식 검사를 거쳐 사진만 받는다. 사진 주소가 또 HTML을 돌려주면 실패로 처리한다. 답에는 상품 페이지를 출처로 쓸 수 있고, 그림의 참고 링크에는 실제로 받은 사진 주소가 남는다.

배포가 섞여 있을 때와 상품 사진 전용으로 읽지 않은 페이지는 기존 받기 경로를 이용한다. 사용자 메시지에서 보낸 페이지는 기존 대표 사진 받기를 이용한다.

## 실패와 일관성

| 무엇 | 어떻게 되나 |
| --- | --- |
| 새 fos-ctx 에 옛 Control Plane | 알리는 경로를 모르는 서버가 인증 거절로 답한다. fos-ctx 가 넘어가고 도구 결과는 그대로다. 찾은 주소는 지금처럼 막힌다 |
| 옛 fos-ctx 에 새 Control Plane | 알리는 호출이 없어 해시가 비어 있다. 찾은 주소는 `IMAGE_SOURCE_UNKNOWN` 이다. 그림 규칙은 찾은 주소를 쓰라고 하므로 비서가 막히는 호출을 한 번 한다. 그래서 fos-ctx 를 먼저 배포한다 |
| 알리기가 실패하거나 늦는다 | 그 결과의 주소는 남지 않아 `link:` 가 막힌다. 결과 hook 은 결과가 모델에게 가기 전에 돌므로, 성공한 알리기는 비서가 그 주소를 쓰기 전에 끝난다 |
| 해시 20,000개를 넘긴 대화 | 오래된 주소부터 다시 검색해야 쓴다. 이미 그림에 쓴 링크도 밀려나면 다음 장면에서 그림 스펙 DECISION52 대로 앞 그림만 참고한다 |
| 해시가 우연히 겹친다 | 128비트라 일어나지 않는다고 본다. 겹쳐도 받는 것은 같은 안전 검사를 거친 공개 주소의 사진이다 |
| 검색 서비스를 답을 LLM 이 쓰는 것으로 바꾼다 | 결과 글이 비서의 질의에 든 주소를 되풀이할 수 있어 스펙 DECISION25 가 약해진다. 지금 설정은 검색 결과 목록을 그대로 주는 서비스다. 바꾸기 전에 이 기능을 다시 확인한다 |
| 검색 서비스가 OpenAI 내장 검색이다 | 검색이 Hermes 의 도구로 돌지 않아 결과 hook 이 불리지 않는다. 페이지 읽기 결과의 주소만 남는다(스펙 「위험과 대응」) |

마이그레이션은 칸을 더하기만 한다. 배포 순서는 fos-ctx 가 먼저다.

| --- | --- | --- | --- | --- |
| DECISION1 | 찾은 주소를 누가 아는가 | fos-ctx 의 결과 hook 이 뽑아 Control Plane 에 알린다 | 작성자 | Control Plane 의 도구 사건은 500자로 잘려 주소가 빠진다. 결과 전체는 hook 만 본다 |
| DECISION2 | 어디에 남기나 | `conversation` 의 새 칸에 해시로 | 작성자 | 범위가 대화 전체(스펙 DECISION4)이고 대화와 함께 지워져야 한다(스펙 DECISION16). 새 표를 만들지 않는다. 주소 원문은 판정에 필요 없다 |
| DECISION3 | 동시에 오는 알리기 | 한 문장의 `UPDATE` 로 이어 붙인다 | 작성자 | 한 실행이 검색과 읽기를 나란히 돌린다. 읽고 고쳐 쓰면 서로를 덮는다 |
| DECISION4 | 대화마다의 상한 | 해시 20,000개, 넘으면 오래된 것부터 버린다 | 작성자 | 페이지 하나가 15,000자 안에서 내는 주소는 많아야 수백 개다. 검색과 읽기 백여 번을 담고 칸은 640KB 에서 멈춘다 |
| DECISION5 | 같은 주소 판정을 어디에 두나 | `chat.conversation` 에서 사용자 메시지 판정과 같은 값 객체로 | 작성자 | 두 판정이 어긋나면 한쪽에서만 통과하는 주소가 생긴다 |
| DECISION6 | 자기 주소를 되풀이한 본문 | 기준 주소와 정확히 같은 후보는 남기지 않는다 | 작성자 | 스펙 DECISION25 를 지키려면 페이지가 자기 주소를 적어 둔 것만으로 통과하면 안 된다 |
| DECISION7 | PR1 에서 「비서가 찾음」 을 남기나 | 남기지 않는다. PR2 가 응답 머리와 그림 행의 자리를 더한다 | 작성자 | 스펙 DECISION15 의 나눔이다. PR1 의 그림은 참고한 링크가 표시 없이 보인다 |
| DECISION8 | 「비서가 찾음」 을 그림 행 어디에 두나 | 링크마다 `0`, `1` 을 이은 새 칸 `generation_found_link_flags`. 암호화하지 않는다 | 작성자 | 링크 글에 표지를 섞으면 칸의 뜻이 바뀌고 다음 장면에 넣는 링크를 읽는 곳마다 표지를 벗겨야 한다. 찾은 주소 목록을 따로 봉하면 같은 주소를 두 번 둔다. 누가 골랐는지는 비밀이 아니다 |
| DECISION9 | 응답의 모양 | `sourceLinks` 는 그대로 두고 `foundSourceLinks` 를 더한다 | 작성자 | `sourceLinks` 를 객체 배열로 바꾸면 옛 화면이 깨진다. 더한 칸은 옛 화면이 읽지 않는다 |
