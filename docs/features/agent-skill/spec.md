# 플러그인이 낸 에이전트용 스킬을 붙이기와 함께 설치

확인: 2026-11-20

변경: 2026-11-20 설계 검토 뒤 DECISION7 을 바꾸고 DECISION16, DECISION17 을 더했다(사용자 답). REQ3, REQ4, REQ6, REQ9 가 그에 맞춰 바뀌었다.

## 목표

플러그인을 에이전트에 붙이면, 그 플러그인이 일반 에이전트용으로 낸 스킬도 그 에이전트에 함께 설치된다.
사용자가 같은 스킬의 줄인 사본을 화면에서 따로 올리지 않아도 된다. 예를 들어 fos-career 의 공고 추천(`position-recommender`)과 읽을거리 수집(`study-collection`)을 커리어 에이전트의 assistant 웹 대화에서 부를 수 있다.

## 지금 동작

- 붙이기는 `plugin.json` 의 `skills` 디렉터리(없으면 `./skills`)에 있는 스킬을 그 profile 의 `skills/` 로 복사한다. `SKILL.md`, `references/`, `templates/` 만 복사한다(`hermes/plugins/dashboard-profile-api/connector_skills.py`, [플러그인 연결](../connector.md) 의 「바인딩 설치」).
  fos-career 는 이 칸이 `connector-skills/` 를 가리키고, Claude Code 전용 스킬은 `skills/` 에 둔다. 일반 에이전트용 디렉터리 `agent-skills/` 는 비어 있다(fos-agents `career-os/docs/adr/ADR-139`, `ADR-141`).
- 실행 공간에는 assistant 가 profile 의 비밀값을 넘기지 않는다(`sandbox.py` 의 `_sandbox_terminal`, [ADR-086](../../adr/ADR-086-셸과-파일-도구는-사용자별-docker-실행-공간에서만-돈다.md)).
  운영 정책은 profile 마다 비밀이 아닌 경로와 URL 의 `env`, 읽기 전용 마운트, 망을 줄 수 있다([`hermes/README.md`](../../../hermes/README.md) 의 「셸 실행 공간」).
  운영은 커리어 역할 profile 의 실행 공간에만 플러그인 폴더, `CLAUDE_PLUGIN_ROOT` 같은 env, token 파일, 커리어 Backend 로 가는 망을 준다. 그 셸이 token 을 읽을 수 있다는 위험은 ADR-086 의 「감당할 것」 에 적혀 있다.
- 플러그인 스킬은 스킬마다 파일 20개, 파일마다 10만 자까지이고 설명 길이 한도는 없다(`connector_schema.py`).
- Hermes 는 스킬 본문의 `${CLAUDE_PLUGIN_ROOT}` 를 바꾸지 않는다. 본문의 `bun --no-env-file "${CLAUDE_PLUGIN_ROOT}/dist/career-local.js"` 는 셸이 실행 공간의 env 로 푼다.
- 커리어 에이전트는 첫 사용자가 주인인 비공개 에이전트이고, fos-career 가 붙이기로 붙어 있다(운영 확인 2026-11-20).

## 범위

이번 범위: 플러그인 manifest 의 에이전트용 스킬 칸, 그 스킬의 설치 조건 판정, 붙이기·다시 설치·떼기에서의 설치와 제거, 붙이기 결과에 빠진 스킬과 까닭 전달, 에이전트 화면의 안내.

범위 밖:
- 원티드·LinkedIn 반영 도구. fos-agents 쪽 별도 스펙이 맡는다.
- fos-agents 의 `agent-skills/` 비서용 사본과 manifest 칸 채우기. 이 스펙이 머지된 뒤 따로 맡긴다.
- 운영 정책을 받지 않은 profile(사용자 기본 profile 등)에서 실행기를 돌리는 것. assistant 는 비밀값과 실행기를 셸에 넘기는 새 경로를 만들지 않는다(DECISION2).
- 스킬의 `scripts/` 복사. 실행기는 운영이 붙인 플러그인 폴더에서 부른다.
- 입력창 `/` 목록에 플러그인 스킬을 보이는 것. 지금처럼 이름을 직접 입력하면 부를 수 있다(agent-skill.md 「스킬 커맨드」).

## 요구사항과 인수 조건

PR1 은 REQ1 부터 REQ7 까지, PR2 는 REQ8 과 REQ9 다(DECISION6).

| ID | 요구사항 | 관측할 인수 조건 |
| --- | --- | --- |
| REQ1 | 플러그인의 `assistant.json` 이 에이전트용 스킬 디렉터리와, 스킬마다 실행 공간에 요구하는 env 이름을 선언할 수 있다 | 칸을 둔 플러그인의 카탈로그 항목에 에이전트용 스킬 이름과 요구 env 이름이 나온다. 칸이 없는 플러그인의 카탈로그와 붙이기는 지금과 같다. 에이전트용 스킬이 앞머리 비밀 요청 칸, 링크, 한도 초과, 같은 플러그인의 다른 스킬과 이름 겹침 가운데 하나라도 있으면 그 플러그인은 카탈로그에서 빠진다. 요구 env 이름이 운영 정책 `env` 의 허용 목록 밖이면 같다 |
| REQ2 | 붙이면 요구 env 가 없는 에이전트용 스킬은 늘 그 에이전트에 설치된다 | 붙인 profile 의 `skills/` 에 그 스킬의 `SKILL.md`, `references/`, `templates/` 가 있고 Hermes 스킬 목록에 보인다. 처음 설치하면 켜져 있고, 관리자가 꺼 둔 스킬은 다시 설치해도 꺼진 채다 |
| REQ3 | 요구 env 가 있는 에이전트용 스킬은 셸 조건을 모두 채운 에이전트에만 설치된다. 조건은 API 도구에 `terminal` 이 켜져 있고, 그 에이전트의 셸 설정이 실행 공간(docker)이고, 셸 설정이 넘기는 env 에 선언한 이름이 모두 있는 것이다. 셸 설정은 도구를 저장할 때 운영 정책으로 쓰인 값이다 | 조건을 채운 profile 에는 설치된다. 하나라도 빠진 profile 은 붙이기가 성공하고 MCP 도구와 다른 스킬은 설치되며, 그 스킬만 없다. 붙이기 응답에 빠진 스킬 이름과, 해당하는 까닭(터미널 꺼짐, 실행 공간 미등록, env 없음, 이름 겹침)이 모두 있다. 「바뀐 것 없음」 응답에도 같은 목록이 있다 |
| REQ4 | 셸 조건이나 manifest 가 붙인 뒤에 바뀌면 에이전트용 스킬을 자동으로 맞춘다. 설치 상태 판정이 지금 조건으로 「깔려야 하는데 없음」 과 「빠져야 하는데 있음」 을 어긋남으로 보고, 정의 어긋남 점검이 다시 설치한다 | 터미널을 켜거나, 셸 설정에 env 가 들어오거나, 새 버전이 스킬을 더하면 다음 점검 주기 뒤 그 스킬이 깔린다. 반대 경우는 지워진다. 바뀐 파일은 덮어쓴다. 다른 플러그인과 올린 스킬은 그대로다. 조건이 바뀌지 않으면 점검이 다시 설치를 보내지 않는다 |
| REQ5 | 떼면 그 플러그인이 설치한 에이전트용 스킬을 지운다 | 뗀 뒤 그 profile 의 `skills/` 와 Hermes 스킬 목록에 그 스킬이 없다 |
| REQ6 | 처음 붙일 때 에이전트용 스킬 이름이 그 profile 의 다른 스킬과 겹치면 붙이지 않는다. 셸 조건 때문에 설치하지 않을 스킬도 이름을 본다. 붙인 뒤 생긴 겹침(올린 스킬, 모델이 만든 스킬)은 다시 설치에서 그 에이전트용 스킬만 빼고 까닭 「이름 겹침」 으로 낸다 | 처음 붙이기는 `SKILL_NAME_TAKEN` 이고 아무 파일도 바뀌지 않는다. 다시 설치는 성공하고 바인딩은 그대로 쓸 수 있으며, 겹친 스킬은 깔리지 않고 올린 스킬이 가려지지 않는다. 플러그인 스킬(`plugin.json` 의 `skills`)의 겹침은 지금 규칙대로 그 바인딩을 `PENDING` 으로 둔다 |
| REQ7 | assistant 는 실행 공간에 비밀값을 넘기는 경로를 새로 만들지 않는다 | 셸 설정(`_sandbox_terminal`)이 넘기는 env 와 마운트는 이 기능 전후로 같다. 붙이기가 profile `.env`, 정책, 마운트를 바꾸지 않는다 |
| REQ8 | Control Plane 은 붙이기와 다시 설치 응답의 빠진 스킬과 까닭을 바인딩에 남기고 에이전트 연결 목록 응답에 낸다 | 조건을 못 채운 붙이기 뒤 연결 목록 응답의 그 바인딩에 빠진 스킬 이름과 까닭이 있다. 조건을 채우고 다시 설치하면 비어 있다. 성공한 설치 응답만 기록을 바꾸고, 설치가 실패하면 옛 기록을 둔다. 이 칸을 모르는 옛 대시보드 plugin 의 응답이면 빈 목록이다 |
| REQ9 | 에이전트 상세의 「이 에이전트가 쓰는 연결」 절이 빠진 스킬과 고치는 방법을 안내한다 | 빠진 스킬이 있는 바인딩 아래에 스킬 이름과 문구가 보인다. 까닭에 이름 겹침이 있으면 「같은 이름의 스킬이 이미 있어요. 그 스킬의 이름을 바꾸거나 지우면 함께 설치돼요」, 실행 공간 미등록이나 env 없음이 있으면 「이 에이전트에는 이 스킬을 돌릴 실행 환경이 없어요. 관리자에게 문의해 주세요」, 터미널 꺼짐만 있으면 「터미널을 켜면 잠시 뒤 함께 설치돼요」 를 보인다. 여러 문구가 해당하면 이 순서로 모두 보인다. 절은 지금처럼 주인에게만 보인다 |

운영 확인은 fos-agents 가 `agent-skills/` 사본과 manifest 칸을 낸 뒤에 한다. 커리어 에이전트에 fos-career 를 다시 설치하고, `/position-recommender` 를 직접 입력해 실행기를 한 번 왕복시킨다(AGENTS.md 「Hermes 연동을 바꿨으면 배포 뒤 왕복시켜 본다」). 확인 절차는 `fos-home-infra` 가 갖는다.

| DECISION17 | env 를 받았다는 판정 기준 | 그 에이전트의 셸 설정이 실제로 넘기는 env. 운영 정책 파일은 보지 않는다 | 사용자 2026-11-20(설계 검토 뒤) | 깔린 스킬이 늘 돌 수 있다. 정책을 바꾼 뒤 도구 저장이나 운영 일괄 반영 전에는 셸 설정이 옛 값이다 |
| DECISION15 | 스킬만 바뀐 다시 설치의 반영 상태 | 지금처럼 `reload_pending` 이고 잠시 「붙이는 중」 이다 | 작성자 | 스킬이나 이름 대응만 바꾼 설치는 `reload_pending` 을 답하는 지금 규칙이다(`connector_binding.py`). DECISION3 과 같다 |
