# Agent Runtime 을 바꿔 끼울 수 있게 하고 OpenClaw 와 ZeroClaw 를 붙여 Hermes 와 비교하기

확인: 2026-11-21

## 목표

관리자가 에이전트의 Agent Runtime 을 Hermes 에서 OpenClaw 나 ZeroClaw 로 바꿔 같은 질문을 돌려 보고, 답 품질과 동작을 숫자로 비교할 수 있다.

Hermes 는 그대로 운영한다. 이 기능은 Hermes 를 내리지 않고, 교체할지는 비교 결과를 보고 다음 스펙에서 정한다(DECISION2).
가족에게는 아무것도 달라지지 않는다. 런타임은 관리자만 바꾸는 내부 설정이다(DECISION5).

사용자 원문은 이렇다.

- 2026-11-20: 런타임 추상화 스펙을 시작하고, 새 런타임의 모델은 API key 가 아니라 ChatGPT 구독 로그인으로 쓴다
- 2026-11-21: 「최대한 열린 개방형 제품으로 우리는 개발하고, 쉽게 갈아탈 수 있는 환경을 구축하자」
- 2026-11-21: 「내부적으로만 변경하고. 품질을 테스트해 보고 싶음. 다른 하네스는 어떤 원칙을 가지고 개발했는지, 더 일상생활 비서에 적합한 하네스인지 궁금함」
- 2026-11-21: 「hermes 와 같은 더 다른 하네스 없을까? 일상용 비서로 사용할 만한 에이전트 하네스가 필요한데」

배경은 둘이다.
Control Plane 은 Hermes 하나에 맞춰져 있다. backend 운영 코드 파일 1482개 가운데 379개가 Hermes 를 이름으로 가리킨다(2026-11-21).
Hermes 는 마이너 버전마다 계약이 크게 바뀌고([Hermes 버전 올리기](../hermes-upgrade.md)), API server 세션에서는 비동기 위임 결과가 부모 대화에 전달되지 않아 Control Plane 이 hook 과 자동 turn 으로 메우고 있다([ADR-20261117 / native-delegation-wake](../../adr/ADR-20261117-native-delegation-wake.md)). 지금 사용자에게는 위임 결과가 전달된다.

OpenClaw 와 ZeroClaw 는 Hermes 처럼 개인 비서용으로 만든 열린 하네스다. 메신저 연동, 기억, 예약, 도구 플러그인을 갖추고 자기 머신에서 돈다.
Control Plane 이 지금 Hermes 에 기대는 곳, 후보 런타임 조사(「일상생활 비서용 하네스 후보」), 하네스 설계 원칙 비교는 [기능 파일](../runtime-abstraction.md)이 갖는다.

## 범위

**갈아타기 쉬운 경계를 Agent Client Protocol(ACP) 구현 하나로 만든다(DECISION3).**
ACP 는 편집기가 에이전트를 부리려고 만든 공개 프로토콜이고 OpenClaw, ZeroClaw, goose, Hermes 가 이 프로토콜로 뜬다.
Control Plane 이 ACP 로 말하는 구현을 하나 가지면, 런타임을 더할 때 그 런타임을 띄우는 명령과 설정만 더하면 된다.

들어가는 것은 이렇다.

- 실행 경계를 런타임에 묶이지 않는 port 로 정리한다. Hermes 의 동작은 바뀌지 않는다
- ACP 구현과 그 위의 OpenClaw, ZeroClaw
- 관리자만 바꾸는 에이전트별 런타임 설정
- 새 런타임에서 도는 실행: 지침과 기억 주입, 웹 검색, 사진 입력, 중지, 대화 이어 가기. 대화 turn 뿐 아니라 그 에이전트의 예약 작업 turn 같은 나머지 실행도 같은 런타임으로 간다(DECISION20)
- 새 런타임이 Control Plane 도구(기억 읽기, 예약 작업 등)를 요청자 권한으로 부르기
- 승인 카드
- 위임: 새 런타임의 비서가 맡기는 것과 새 런타임의 에이전트가 맡는 것
- 비교 결과: 평가 숫자, 왕복 확인 결과, 하네스 설계 원칙 비교

범위 밖은 이렇다.

- Hermes 를 내리거나 기본 런타임을 바꾸는 일. 다음 스펙에서 정한다
- 가족 사용자에게 새 런타임을 여는 일, 사용자가 런타임을 고르는 화면. 가족의 에이전트와 그룹 공개 에이전트는 런타임을 바꿀 수 없다(DECISION18)
- Hermes core 변경, 새 테이블
- 답이 나오는 중에 보낸 글을 그 turn 에 끼워 넣기. 새 런타임에서는 다음 turn 으로 넘긴다(DECISION3)
- Hermes 에 설치하는 플러그인 도구(쇼핑 등), 스킬 게시, toolset 설정을 새 런타임으로 옮기는 일. 새 런타임의 에이전트에서는 쓰지 못한다(DECISION9)
- profile, 플러그인, 스킬, toolset, gateway 를 부르는 나머지 port 를 런타임 중립으로 바꾸는 일(DECISION8)
- 런타임이 스스로 가진 하위 에이전트 기능. 끈다(DECISION17)
- 런타임 로그인 화면과 로그인 절차. 절차는 운영 저장소가 갖는다(DECISION6)
- ACP 를 거치지 않는 런타임 전용 구현. 구독 로그인, 지침 넣기, Control Plane 도구 붙이기, 웹 검색 가운데 ACP 로 되지 않는 것이 있으면 설계 단계에서 사용자에게 다시 묻는다(DECISION3)
- 새 런타임이 스스로 가진 기억, 예약, 메신저 채널, 스킬을 쓰는 일. 끄거나 쓰지 않는다(DECISION17)
- Codex, OpenCode 같은 코딩 에이전트와 nanobot 같은 다른 후보를 붙이는 일(DECISION3)
- 평가 문항을 만드는 일. 예약 작업 비교 묶음은 평가 계정 스펙이 만든다(DECISION4)

비서 중심 대화 스펙(`docs/features/assistant-hub/`, 2026-11-21 진행 중)은 사용자가 에이전트를 고르는 자리를 없앤다. 이 스펙은 고르는 자리를 만들지 않고, 위임은 그 스펙이 정한 「비서가 전문 에이전트를 부른다」 흐름을 그대로 쓴다.

## 요구사항과 인수 조건

PR 나눔은 DECISION7 이다. 표의 (PR n) 은 그 요구가 들어가는 PR 이다.
「새 런타임」 은 OpenClaw 와 ZeroClaw 다. 첫째로 붙이는 것이 OpenClaw, 둘째가 ZeroClaw 다. 「왕복 확인」 은 배포한 뒤 실제 실행을 한 번 돌려 본 결과를 말한다.

| ID | 요구사항 | 관측할 인수 조건 |
| --- | --- | --- |
| REQ1 | 실행 경계가 런타임에 묶이지 않는다(PR1) | 실행 port 를 부르는 모든 곳(대화 turn, 예약 작업 turn, 중지, 재기동 복구, 위임, 대화 삭제, 추천 질문, 대화방 요약, 사용량 정리)이 쓰는 port 에 Hermes 의 주소, profile 이름, Hermes 사건 이름이 없다. Hermes 구현으로 지금의 backend 테스트가 그대로 통과하고, 배포 뒤 Hermes 대화 한 번의 왕복 확인이 전과 같다 |
| REQ2 | 하네스 설계 원칙 비교가 문서로 남는다(PR1) | [기능 파일](../runtime-abstraction.md)의 「하네스 설계 원칙 비교」 에 Hermes, OpenClaw, ZeroClaw 의 지침 구조, 도구 호출, 기억과 맥락, 다시 시도와 실패 처리, 하위 에이전트, 안전 장치, 일상생활 비서에 맞는지가 있고 읽은 날짜와 「확인 못 함」 이 표시돼 있다 |
| REQ3 | 관리자만 에이전트의 런타임을 바꾼다(PR2) | 관리자 화면의 에이전트 설정에서 런타임을 Hermes, OpenClaw, ZeroClaw 가운데 고른다. 고를 수 있는 에이전트는 관리자 자신과 평가 계정이 주인인 비공개 에이전트뿐이고, 다른 사용자의 에이전트와 그룹 공개 에이전트에서는 거부된다(DECISION18). 새 에이전트와 지금 있는 에이전트는 모두 Hermes 다. `MEMBER` 역할이 런타임을 바꾸려 하면 거부되고 값이 그대로다. 가족이 보는 화면과 그 화면이 받는 응답에 런타임이 나오지 않는다 |
| REQ4 | 새 런타임으로 대화 turn 이 돈다(PR2) | 런타임이 OpenClaw 인 에이전트에 메시지를 보내면 답이 흐르며 나타나고, 실행 기록에 런타임, 실제로 돈 모델, 토큰 수가 남는다. 런타임이 토큰을 어림값으로만 알려 주면 그 값을 남기고 비교 표에 「어림값」 이라고 표시한다. 대화의 모델 고르기는 새 런타임의 에이전트에서 보이지 않는다(DECISION12). 같은 대화의 다음 turn 이 앞 turn 의 내용을 알고 답한다. Control Plane 을 다시 띄운 뒤의 동작은 DECISION21 을 따른다. 그때 돌던 turn 은 실패로 기록되고, 다음 메시지는 런타임이 세션을 다시 불러오면 앞 내용을 알고 답하며, 불러오지 못하면 새 세션으로 돌고 대화에 「앞 내용을 이어받지 못했다」 는 알림 줄이 남는다. 예약 작업 turn 도 같은 런타임으로 돈다(DECISION20) |
| REQ5 | 지침과 기억이 새 런타임 실행에도 들어간다(PR2) | 공통 답변 지침과 요약 구역이 새 런타임의 실행 입력에 들어간다. 테스트가 런타임에 보낸 입력에서 둘을 확인하고, 왕복 확인에서 요약 구역에 있는 사실을 물으면 그 사실로 답한다. 답이 형식을 얼마나 지키는지는 인수 조건이 아니라 평가 표의 숫자다(DECISION4). 다른 사용자의 기억은 들어가지 않는다 |
| REQ6 | 새 런타임의 turn 을 중지한다(PR2) | 답이 나오는 중에 중지를 누르면 답이 멈추고 실행이 취소로 기록된다. 그 대화에 다음 메시지를 보낼 수 있다 |
| REQ7 | 답 중에 보낸 글은 다음 turn 으로 간다(PR2) | 새 런타임의 답이 나오는 중에 보낸 메시지는 그 turn 에 끼지 않고, turn 이 끝난 뒤 다음 turn 으로 합쳐 보내진다([ADR-048](../../adr/ADR-048-응답-중에-보낸-메시지는-control-plane-이-쌓아-두고-다음-turn-으로-합쳐-보낸다.md)) |
| REQ8 | 새 런타임이 웹 검색으로 답한다(PR2) | 최신 정보 질문에 새 런타임이 웹 검색 도구를 불러 그 결과로 답한다. 출처 링크가 붙는 비율은 인수 조건이 아니라 평가 표의 숫자다(DECISION4). 런타임이 검색어를 사건으로 알려 주면 답이 나오는 동안 검색 중임이 보이고, 알려 주지 않으면 그 표시 없이 답만 나온다 |
| REQ9 | 사진을 붙인 메시지를 처리한다(PR2) | 런타임이 이미지 입력을 받는다고 알리면 사진이 함께 전달돼 사진 내용을 답한다. 받지 못하는 런타임이면 실행이 실패로 기록되고 대화에 「이 에이전트는 사진을 받지 못한다」 는 안내가 남는다. 이것은 새 런타임의 에이전트에만 생기는 새 동작이다. 사진 단추를 보일지 정하는 지금 규칙(비공개이고 주인이 있는 에이전트)과 Hermes 에이전트의 동작은 그대로다 |
| REQ10 | 새 런타임의 명령 실행과 파일 쓰기는 승인을 받아야 돈다(PR2, PR4) | 새 런타임은 명령 실행, 파일 쓰기, 작업 디렉터리 밖의 파일 읽기를 늘 묻도록 설정하고, 그렇게 설정하지 못하는 런타임이면 그 도구를 끈다. PR2 와 PR3 에서는 새 런타임이 이 권한을 물으면 자동으로 거절되고, 그 turn 은 그 도구 없이 이어지거나 못 한다는 답으로 끝난다. 실행 기록에 거절한 요청이 남는다. PR4 부터는 요청마다 승인 카드가 뜨고 카드에 돌릴 명령이나 쓸 파일이 보인다. turn 은 카드의 답을 기다리고, 카드에는 이번만 승인, 「이 대화에서 계속 허용」, 거절이 있다. 이번만 승인하면 그 한 번만 돌고, 거절하거나 실행 한도까지 답하지 않으면 돌지 않는다. 「이 대화에서 계속 허용」 을 누르면 같은 대화에서 같은 종류(명령 실행, 파일 쓰기, 작업 디렉터리 밖 읽기)의 요청은 다시 묻지 않고 돈다. 다른 종류의 요청과 다른 대화에서는 다시 묻는다(DECISION19). 권한을 묻지 않고 돌리는 설정은 새 런타임에서 꺼 둔다 |
| REQ11 | 사용자마다 런타임이 격리된다(PR2) | 한 사용자의 에이전트가 쓰는 런타임 세션과 작업 디렉터리를 다른 사용자의 실행이 읽지 못한다. 테스트가 두 사용자의 실행이 서로 다른 격리 단위로 가는 것을 확인한다 |
| REQ12 | 새 런타임이 실패하면 기록하고 알린다(PR2) | 런타임 프로세스가 죽었거나 로그인이 만료됐거나 Hermes 실행과 같은 한도까지 끝나지 않으면 실행이 실패로 기록되고 대화에 실패 안내가 남는다. 프로세스가 살아 있으면 사건이 한동안 없어도 그 한도까지 기다린다. Hermes 로 자동으로 바꿔 돌리지 않는다. 다음 메시지를 보내면 런타임을 다시 띄워 돈다 |
| REQ13 | ZeroClaw 를 같은 구현에 붙이고 1차 숫자를 낸다(PR3) | ZeroClaw 가 REQ4 부터 REQ12 까지를 같은 ACP 구현으로 만족한다. 런타임마다 다른 코드가 띄우는 명령과 설정에 그치는지, 그 밖에 무엇을 고쳐야 했는지가 기능 파일에 적혀 있다. 답변 평가 20문항을 Hermes, OpenClaw, ZeroClaw 로 같은 날 돌린 표(출처 링크가 붙은 문항 수, 열리는 링크 비율, 형식을 어긴 문항 수, 걸린 시간, 토큰)가 기능 파일에 있다 |
| REQ14 | 새 런타임이 Control Plane 도구를 요청자 권한으로 부른다(PR4) | 새 런타임의 에이전트는 Hermes 에서 받던 Control Plane 도구(기억, 예약 작업, 에이전트 목록과 위임, 첨부 보기 등)를 그대로 받는다. Hermes 에 설치하는 플러그인 도구는 받지 않는다(DECISION9). 새 런타임의 실행이 기억 읽기와 예약 작업 도구를 부르면 그 실행의 요청자 것만 읽고 만든다. 다른 사용자의 실행 맥락이나 맥락 없는 호출은 거부된다. 도구 호출 기록에 어느 실행이 불렀는지 남는다 |
| REQ15 | 승인 카드가 새 런타임에서도 뜬다(PR4) | 승인이 필요한 Control Plane 도구(예: 예약 작업 지우기)를 새 런타임이 부르면 지금과 같은 승인 카드가 뜨고, 승인하면 실행되고 거절하면 실행되지 않는다. 런타임이 스스로 권한을 물을 때의 카드는 REQ10 을 따른다 |
| REQ16 | 위임이 런타임을 넘어 이어진다(PR5) | 새 런타임의 비서가 Hermes 의 전문 에이전트에게 맡기면 결과가 부모 대화에 돌아와 비서의 다음 답이 열린다. Hermes 의 비서가 새 런타임의 전문 에이전트에게 맡겨도 같다. 맡기는 쪽과 맡는 쪽이 모두 새 런타임이어도 같다 |
| REQ17 | 최종 비교 결과가 문서로 남는다(PR5) | 기능 파일에 세 가지가 있다. 같은 평가 세트를 Hermes, OpenClaw, ZeroClaw 로 같은 날 돌린 표(REQ13 의 칸과 같다). 평가 계정 스펙의 예약 작업 비교 묶음이 그때 있으면 함께 돌리고, 없으면 「묶음이 생긴 뒤 돌린다」 고 적는다. REQ2 의 하네스 설계 원칙 비교. 새 런타임마다 중지, 대화 이어 가기, 기억 도구, 승인 카드, 위임 결과 전달을 왕복 확인한 결과(된다, 안 된다, 안 되면 그 까닭). 통과 기준은 두지 않는다(DECISION4) |

Hermes 내장 memory 도구는 주지 않는다」(AGENTS.md)와 같은 경계다. 하네스의 기억을 켜면 Control Plane 이 모르는 곳에 사용자 사실이 남고, 하네스마다 기억 방식이 달라 실행 루프의 차이를 볼 수 없다 |
| DECISION18 | 런타임을 바꿀 수 있는 에이전트 | 관리자 자신과 평가 계정이 주인인 비공개 에이전트만 바꿀 수 있다. 다른 사용자의 에이전트와 그룹 공개 에이전트는 거부한다. 평가 계정을 알아보는 방법은 평가 계정 스펙을 따른다 | 사용자 2026-11-21 | 「가족에게는 아무것도 달라지지 않는다」 와 DECISION5 를 지키려면 가족이 답을 받는 에이전트의 런타임이 바뀌면 안 된다 |
| DECISION19 | 런타임이 묻는 권한의 승인 카드 동작 | turn 이 카드의 답을 기다린다. 실행 한도까지 답이 없으면 거절로 본다. 카드에는 이번만 승인, 「이 대화에서 계속 허용」, 거절이 있다. 계속 허용하면 같은 대화 안에서 같은 종류(명령 실행, 파일 쓰기, 작업 디렉터리 밖 읽기)의 요청을 다시 묻지 않고, 대화를 벗어나면 허용이 사라진다. 이 셋은 런타임이 늘 묻도록 설정하고, 그렇게 설정하지 못하면 그 도구를 끈다 | 사용자 2026-11-21 | ACP 의 권한 요청은 도는 turn 안에서 답을 기다리는 방식이라 지금의 Control Plane 도구 카드(호출을 막고 turn 을 끝낸 뒤 승인하면 저장한 인자로 실행)와 다르다. 명령마다 누르면 여러 명령을 잇는 작업이 번거로워 대화 단위의 허용을 둔다. ZeroClaw 의 기본 수준은 위험이 낮다고 본 명령을 묻지 않고 돌리므로 늘 묻게 설정한다 |
| DECISION20 | 대화 turn 밖의 실행 | 에이전트의 모든 실행(대화 turn, 예약 작업 turn, 위임받은 실행, 추천 질문, 대화방 요약)이 그 에이전트의 런타임으로 간다 | 작성자 | 예약 작업 비교 묶음(DECISION4)을 세 런타임으로 돌리려면 예약 turn 이 새 런타임에서 돌아야 한다. 실행 종류마다 런타임이 다르면 비교가 흐려진다 |
| DECISION21 | Control Plane 을 다시 띄웠을 때의 새 런타임 | 그때 돌던 새 런타임의 turn 은 실패로 기록한다. 다음 메시지에서 런타임에 세션을 다시 불러오게 하고, 불러오지 못하면 새 세션으로 돌리며 대화에 알림 줄을 남긴다. 런타임마다 어느 쪽이었는지를 왕복 확인 결과에 적는다 | 작성자 | ACP 연결이 끊기면 런타임 프로세스의 turn 을 이어받을 표준이 없다. OpenClaw 의 ACP 연결은 세션 다시 불러오기를 일부만 지원한다고 문서에 적혀 있어 되는지를 인수 조건으로 고정하지 않는다 |

## 도메인 규칙 변경

도메인 규칙 변경 없음: `docs/domain/` 이 없다. 「실행할 profile 은 요청자의 바인딩에서만 꺼낸다」, 「Memory 접근 권한은 Control Plane 이 정한다」, 「실행 기록은 실패해도 남긴다」(AGENTS.md)는 새 런타임에도 그대로 지킨다. 셸과 파일 도구의 경계([ADR-086](../../adr/ADR-086-셸과-파일-도구는-사용자별-docker-실행-공간에서만-돈다.md))는 Hermes 에서 그대로다. 새 런타임에서는 DECISION10 이 정한 대로 승인받은 명령이 런타임이 도는 곳에서 돈다.

## 위험

- **승인한 명령은 런타임이 도는 곳에서 돈다.** Hermes 의 셸과 파일 도구는 사용자별 Docker 실행 공간에서만 돌지만([ADR-086](../../adr/ADR-086-셸과-파일-도구는-사용자별-docker-실행-공간에서만-돈다.md)), 새 런타임이 승인받아 돌리는 명령은 그 런타임 프로세스가 있는 곳에서 돈다. 그곳에는 런타임의 로그인 파일과 그 사용자의 세션이 있다. 줄이는 방법은 셋이다. 사용자마다 런타임 프로세스와 디렉터리를 따로 둔다(DECISION16). 승인을 받는다(DECISION10). 「이 대화에서 계속 허용」 을 누른 대화에서는 같은 종류의 명령이 묻지 않고 돈다(DECISION19). 새 런타임을 쓰는 사람을 관리자로 묶는다(DECISION5). 런타임을 어디에 어떤 권한으로 띄우는지는 technical-design 과 운영 저장소가 정한다
- **문서로만 확인한 것이 많다.** 구독 로그인, 지침 넣기, Control Plane 도구 붙이기, 웹 검색이 ACP 로 되는지는 실제로 띄워 보기 전이다. OpenClaw 의 ACP 연결은 세션마다 넘기는 MCP 서버를 받지 않는다고 문서에 적혀 있다([기능 파일](../runtime-abstraction.md)). 안 되는 것이 나오면 설계 단계에서 사용자에게 다시 묻는다(DECISION3)
