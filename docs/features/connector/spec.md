# 커넥터 보관 파일 암호화

확인: 2026-11-03

## 목표

커넥터 토큰 같은 비밀값을 서버에 한 곳, 암호화된 보관 파일에만 둔다. 에이전트 profile `.env` 에 평문 사본을 만들지 않아 서버 디스크에 커넥터 비밀값의 평문이 남지 않게 한다.
실행 중인 플러그인 프로세스의 격리 수준은 지금과 같다. 같은 계정으로 도는 플러그인은 key 와 다른 보관 파일을 읽을 수 있고, 이는 지금 다른 profile 의 `.env` 를 읽을 수 있는 것과 같다.

## 범위

이번 범위: 대시보드 plugin 의 커넥터 보관 파일을 별도 key 로 암호화해 쓰고 읽는다. 커넥터 MCP 서버는 우리 plugin 의 실행기로 띄워, 실행기가 띄우는 순간 보관 파일을 풀어 그 프로세스 환경에만 값을 넘긴다. 배포 때 남은 평문 파일을 암호화하고, 이미 붙은 바인딩의 `.env` 사본을 지우고 실행기 방식으로 다시 설치한다.

범위 밖: Hermes core 가 직접 읽는 profile `.env` 값(`API_SERVER_KEY` 등). 원격(HTTP) 플러그인의 비밀값(DECISION8, 예외로 `.env` 에 둔다). 사용자 브라우저 중계 주소의 접근 표식(DECISION11, 다음 스펙). Hermes core 는 고치지 않는다. Control Plane 은 바뀌지 않는다.

함께 고칠 문서: `docs/privacy.md` 의 평문 보관 서술, `docs/features/connector.md`, `hermes/docs/hermes-contract.md` 의 운영 값 표.

## 요구사항과 인수 조건

| ID | 요구사항 | 관측할 인수 조건 |
| --- | --- | --- |
| REQ1 | 보관 파일을 암호문으로 쓴다 | key 가 있으면 PUT 과 배포 때 이관 뒤 파일이 v2 이고 파일 글에 칸 값이 없다. 도구 호출(`connector_run.py`), 바인딩 설치의 .env 복사(`connector_install.py`), Control Plane 의 연결 확인이 원래 값을 받는다. 바인딩 설치는 원격 플러그인만 `.env` 에 쓴다 |
| REQ2 | 파일을 다른 연결로 옮기면 열리지 않는다 | 다른 연결 이름으로 복사한 파일은 읽기 실패, 예외와 로그에 값이 없다 |
| REQ3 | 배포 때 남은 평문 파일과 옛 key 파일을 한 번에 활성 key 로 다시 쓴다 | 대시보드 기동마다 이관이 돌고, 기동 로그에 v1 파일 수와 옛 key 파일 수가 남는다. 배포 뒤 둘 다 0 이다. 운영 확인 절차는 `fos-home-infra` 가 갖는다 |
| REQ4 | 운영은 key 가 필수다 | 「key 필수」 를 켜고 key 가 없거나 모양이 틀리면 보관 파일 PUT 이 503 이고, 그 연결은 「외부 서비스 연결」 화면에 실패로 남는다. 이미 있는 연결의 도구 호출은 동작한다. 끄면 평문으로 쓰고 경고를 남긴다 |
| REQ6 | 로컬(stdio) 커넥터 비밀값을 profile `.env` 에 쓰지 않는다 | 바인딩 설치 뒤 그 profile 의 `.env` 와 `config.yaml` 에 커넥터 칸 값이 없고, `config.yaml` 에는 실행기와 보관 파일 id 만 있다. 아래가 모두 원래 값을 받는다: Hermes 가 띄운 MCP 서버, 대시보드 직접 실행(`connector_run.py`, 소유 기록의 보관 파일로 읽음), 실행 가드 scope 검사(`connector_prepare.py`), 스냅샷(`connector_snapshot.py`). 서버 정의 비교(`_server_matches`)는 실행기 정의와 옛 정의를 모두 알아보고, 바인딩을 떼면 실행기 정의와 남은 사본을 지운다. `PUT /api/env` 는 플러그인 칸 key 를 거절한다. 보관 파일을 풀지 못하면 그 MCP 서버만 뜨지 않고 로그에 값이 없다 |
| REQ8 | 연결 토큰을 바꾸면 붙인 바인딩이 재시작 대기가 된다 | 보관 파일 PUT 뒤 그 연결을 붙인 바인딩의 반영 확인이 `restart_required` 다. 재시작 뒤 MCP 서버가 새 값을 받는다 |
| REQ7 | 이미 붙은 로컬 바인딩을 배포 때 실행기 방식으로 다시 설치하고 `.env` 사본을 지운다 | 기동 이관 뒤 보관 파일을 풀 수 있는 바인딩의 사본이 0개이고 도구 호출이 동작한다. 풀지 못한 바인딩은 옛 방식과 사본을 남기고, 기동 로그에 남은 사본 수가 남는다. 이관 뒤 gateway 재시작이 필요하다고 답한다 |
| REQ5 | key 를 잃거나 이전 이미지로 되돌리면 연결을 다시 등록한다 | 이 저장소 문서에는 「분실·되돌림 때 다시 등록」 과 「Control Plane KEK 와 다른 key」 만 적고, key 사본 위치는 `fos-home-infra` 에만 둔다 |

## 설계

설계는 [`design.md`](design.md) 가 갖는다. 2026-10-08 에 세웠던 옛 계획(git 이력)에서 암호 방식(AES-256-GCM), AAD `connector-vault:<vault>:<connector>`, v2 파일 모양, key 파일 모양만 따른다. 이관 시점, key 없음 처리, 테스트 기대값은 이 스펙의 결정대로 다시 썼다.
이 스펙은 PR 둘로 구현한다. PR1 은 REQ1 부터 REQ5 이고(REQ1 의 「바인딩 설치는 원격 플러그인만 `.env` 에 쓴다」 는 PR2), PR2 는 REQ6, REQ7, REQ8 이다.

| DECISION2 | key 분실 | 연결 다시 등록, key 사본은 홈서버 별도 보관 위치에 하나 | 사용자 2026-11-03 | 대화 KEK 와 같은 운영 절차 |
| DECISION3 | 기존 평문 파일 | 배포 때 한 번에 암호화 | 사용자 2026-11-03 | 평문이 남는 기간을 없앤다 |
| DECISION4 | key 없는 설치 | 운영은 새 「key 필수」 환경 변수로 가른다. 필수인데 key 가 없거나 모양이 틀리면 보관 파일 저장만 거절하고, 이미 있는 연결의 읽기와 도구 호출은 그대로 둔다. 개발은 평문 허용과 경고 | 사용자 2026-11-03 | 기억 암호화 REQ6 과 같은 방식 |

| DECISION7 | key 회전 | 기동 때 이관이 옛 key 로 암호화한 파일도 활성 key 로 다시 쓴다. 기동 로그에 옛 key 파일 수를 남긴다 | 사용자 2026-11-03 | 옛 key 를 지워도 되는 때를 관측할 수 있다 |
