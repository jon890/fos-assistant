# 사건 감지형 살펴보기: 새 메일을 에이전트가 스스로 살펴보고 알린다

확인: 2026-11-05

REQ2 의 확인 지점과 REQ5 의 알릴 메일 문구는 기술 설계 뒤 사용자 동의로 고쳤다(2026-11-05).
REQ9, REQ10 과 REQ13 은 사건 감지를 사용자의 메인 에이전트에서 돌리고 분야 지침 스킬을 빼기로 한 사용자 결정으로 고쳤다(2026-11-05, DECISION25~27).

## 목표

사용자가 단추를 누르거나 정한 시각을 기다리지 않아도, 붙인 서비스에 새 사건(첫 버전은 Gmail 새 메일)이 생기면 에이전트가 알맞은 때 스스로 살펴보고, 알릴 것만 알림과 지금 화면으로 알린다.

## 범위

이번 범위(첫 버전, Gmail):

- 대시보드 plugin 에 「사건 감지용 메일 목록 조회」 경로를 새로 만든다. Control Plane 이 모델 없이 그 경로로 마지막 확인 뒤의 새 메일 목록(식별자, 받은 시각, 라벨)만 받는다. 본문과 제목은 이 경로로 받지 않는다
- 15분마다 그 선행 검사를 돌린다. Gmail 의 프로모션·소셜 분류는 검색식으로 뺀다
- 새 메일이 있을 때만 에이전트가 점검 대화에서 살펴보기 한 번을 돈다. 계기는 새 값 「사건」 이다
- 에이전트가 알릴 것으로 고른 메일이 있으면 실행마다 알림 한 건과 지금 화면 제안 카드를 낸다
- 하루 실행 횟수 상한, 조용한 시간의 알림 미루기, 연결 실패 알림
- 에이전트 상세의 먼저 살펴보기 절에서 Gmail 사건 감지를 켜고 끈다

범위 밖:

- 가계부 새 지출, 토스 체결·경고, 커리어 새 공고·자료. 이 틀을 써 본 뒤 원천마다 뒤 PR 로 더한다
- 메일이 오는 즉시 깨우는 push(Google Pub/Sub). Control Plane 을 바깥에 열지 않는다
- 사용자가 정하는 제외 규칙(보낸 사람, 검색식, 기억). 첫 버전은 Gmail 분류만 쓴다
- 플러그인 쓰기(답장 초안, 라벨 변경, 보내기)와 위임(`delegation`) 도구
- 지금 단추와 매일 깨우기의 동작. 그대로 둔다
- 사건 감지 전용 에이전트. 사건 감지는 사용자의 메인 에이전트에서 돈다(DECISION25)

## 요구사항과 인수 조건

| ID | 요구사항 | 관측할 인수 조건 |
| --- | --- | --- |
| REQ1 | 새 메일 확인은 모델 없이 15분마다 돈다 | 사건 감지를 켠 바인딩마다 15분 간격으로 목록 조회가 한 번 돌고, 새 메일이 없으면 모델 실행 줄과 살펴보기 줄이 생기지 않는다. 확인마다 행을 쌓지 않고 마지막 확인 시각과 결과(새 메일 수, 건너뜀 사유)만 덮어쓴다. 모델 없이 끝난 확인은 하루 발화 상한에서 빠진다 |
| REQ2 | 같은 메일로 두 번 깨우지 않는다 | 마지막 확인 지점(결과를 다 쓴 마지막 조회를 시작한 Control Plane 시각. 보낸 사람이 쓰는 메일의 받은 시각은 쓰지 않는다)과 겹치는 구간의 메일 식별자를 기존 테이블의 컬럼에 둔다. 조회는 지점보다 조금 앞부터 겹쳐 받고 식별자로 중복을 뺀다. 서버를 다시 띄운 테스트에서 같은 메일로 두 번 깨우지 않고 늦게 도착한 메일도 놓치지 않는다. 새 테이블을 만들지 않는다 |
| REQ3 | 광고 분류 메일은 깨우지 않는다 | 프로모션·소셜 분류 메일만 새로 왔으면 에이전트를 깨우지 않는다 |
| REQ4 | 새 메일이 있으면 에이전트가 점검 대화에서 살펴본다 | 계기가 「사건」 인 살펴보기 줄이 생기고, 실행 입력에 새 메일 식별자 목록이 실린다. 에이전트는 허용된 메일 읽기 도구로 내용을 읽고, 모델이 받은 글은 `<external-data>` 로 감싼다. 기존 읽기 경계와 도구 조건 검사를 받는다 |
| REQ5 | 알릴 것이 있으면 실행마다 알림 한 건을 낸다 | 결과 블록의 `findings` 가운데 「새로 알릴 것」 으로 남은 것의 `topicKey` 가 알릴 메일 식별자이고, Control Plane 은 입력에 실린 식별자만 센다. 하나 이상이면 새 종류의 알림 한 건(「새 메일 N건 중 M건 확인 필요」 처럼 개수만, 메일 제목 없음)이 생기고 누르면 점검 대화로 간다. 점검 대화의 답에 고른 메일 목록과 이유, Gmail 원문 링크가 있다. 할 일 제안은 지금 상한(열린 제안 3개)을 따른다. 알릴 것이 없으면 알림이 없다 |
| REQ6 | 조용한 시간에는 살펴보되 알림은 아침에 한 건으로 보낸다 | 사용자 시간대(켤 때 저장, 기본 Asia/Seoul)의 22시~07시에 생긴 알림은 미뤄 두었다가 07시 뒤 첫 확인에서 「밤사이 N건」 알림 한 건으로 낸다 |
| REQ7 | 하루 실행 횟수 상한이 있다 | 바인딩마다 하루 사건 실행 수가 상한에 닿으면 그날은 깨우지 않고 확인 지점을 옮기지 않는다. 다음 날 첫 확인에서 쌓인 메일을 함께 본다. 에이전트 상세에 「오늘 상한 도달」 이 보인다 |
| REQ8 | 플러그인 쓰기는 하지 않는다 | 사건 실행은 에이전트의 쓰기 허용과 상관없이 읽기 경계로 돈다. 플러그인 쓰기 도구를 부르면 거절된다. 할 일 제안(`follow_up_propose`)은 받는다 |
| REQ9 | 사건 실행 동안 위험한 도구 호출만 막는다 | 루트가 사건 살펴보기 turn 인 실행 트리에서 안전 목록(`web`, `vision`, `todo`, `skills` 의 읽기 도구와 도구 찾기) 밖의 내장 도구, 붙지 않은 MCP 서버의 도구, 다른 plugin 의 도구를 부르면 거절된다. 위임(`delegate_task`), 셸·프로세스, 파일 읽기와 쓰기, 코드 실행(`execute_code`), 원격 연결(`manage_connections`), 로컬 경로의 사진 읽기가 여기 든다. 같은 에이전트의 보통 대화에서는 그 도구가 그대로 돈다. 판정을 받지 못하면(Control Plane 이 답하지 않음, hook 예외, 풀리지 않는 session) 막는다. 예외는 셋이다. 코드 실행 안의 호출은 그 코드를 연 `execute_code` 가 판정을 받아 묻지 않는다. 판정 경로가 없는 옛 Control Plane 의 404 는 한 배포 동안 통과시킨다. Hermes 가 plugin 을 불러오지 못하거나 hook dispatcher 가 실패하면 plugin 이 막을 수 없다. 켜 둔 toolset 때문에 사건 감지를 켜지 못하거나 깨우지 않는 일은 없다. 판정 plugin 이 그 profile 에 없거나 옛 버전이면 켜지도 깨우지도 않고 화면이 까닭을 보인다 |
| REQ10 | 사용자가 켜고 끈다 | 기본은 꺼짐이다. Gmail 연결이 붙어 있고 그 바인딩에서 메일 검색 도구가 허용돼 있어야 켤 수 있다. 같은 Gmail 연결에 사건 감지를 켠 에이전트는 하나뿐이다. 분야 지침 스킬과 켜 둔 toolset 은 켜기 조건이 아니라서, 사용자의 메인 에이전트(셸·파일·위임 도구가 켜진 에이전트 포함)에서 켤 수 있다 |
| REQ11 | 연결 실패를 알린다 | 목록 조회가 연속으로 정해진 횟수 실패하면 확인 지점을 그대로 둔 채 「Gmail 다시 연결 필요」 알림을 한 번 내고, 에이전트 상세에 상태를 보인다. 시도는 계속하고, 성공하면 상태가 풀린다 |
| REQ12 | 점검 대화가 바쁘면 다음 확인으로 넘긴다 | 사용자나 대화에 도는 turn 이 있으면 확인 지점을 옮기지 않고 다음 15분에 다시 본다. 읽지 않은 보고가 있어도 건너뛰지 않는다. 사용자가 점검 대화를 지웠으면 다음 사건 실행이 새로 만든다 |
| REQ13 | 살펴보기는 분야 지침 스킬 없이 돈다 | 단추 살펴보기, 매일 깨우기, 사건 실행 모두 `proactive-check` 스킬이 없어도 시작 전 점검이 막지 않고, 화면에 스킬 까닭 문구가 없다. 실행 입력은 스킬을 읽으라고 하지 않는다. 모든 살펴보기의 지시에 공통 지침(맥락을 보고 조사할 것을 고르고 없으면 `NOTHING_NEW`, 원문을 열어 확인한 것만 사실, 문제 후보는 목표나 맥락과 이어지고 이번 발견이 근거일 때만)이 실린다 |

## 설계

기술 설계는 [design.md](design.md) 가 갖는다. 아래는 스펙을 확인할 때 합의한 방향이다.


- 목록 조회 경로는 실행 밖에서 사용자 메일의 메타데이터를 읽는 새 신뢰 경계다. 기술 설계에서 인증, 받는 칸(식별자, 받은 시각, 라벨), 바인딩과 도구 허용 확인을 정하고 독립 검토를 받는다
- 마지막 확인 지점, 실패 횟수, 하루 실행 수, 미룬 알림, 시간대는 기존 테이블(예약 작업이나 바인딩 줄)의 컬럼에 둔다. 정확한 자리는 기술 설계가 정한다
- 실행은 기존 살펴보기 경로(`ProactiveCheckService`, 점검 대화)를 다시 쓰고 계기 값과 결과 블록의 「알릴 메일」 칸만 더한다
- 알림은 `notification` 에 새 종류를 더한다(`docs/features/attention.md` 의 알림 종류 표도 고친다). 지금 화면은 기존 제안 카드를 쓴다
- 사건 실행이 잦으면 점검 대화의 session 교체(14회)가 빨라진다. 기술 설계에서 영향만 적는다
