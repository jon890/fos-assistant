# 먼저 살펴보기의 발견·문제 후보 테이블 정리

확인: 2026-11-05

## 목표

먼저 살펴보기의 발견(`proactive_check_finding`)과 문제 후보(`proactive_check_problem`) 테이블을 없애 운영 테이블을 41개에서 39개로 줄인다. 제안과 반응은 할 일의 제안 줄(`follow_up`) 한 곳에서만 다룬다.

## 범위

이번 범위:

- 살펴보기 결과 블록의 발견과 문제 후보를 저장하지 않는다. 답과 보고를 그리는 데만 쓴다
- 다음 살펴보기 입력의 「최근에 알린 발견」 과 「받아들인 문제 후보」 를 그 점검 대화의 최근 제안 줄(상태와 반응 포함)로 바꾼다
- 점검 대화의 발견 반응 단추와 그 API, 「관심 없음」 주제를 정해진 기간 자동으로 내리던 판정을 없앤다
- 옛 발견·문제 후보를 제안 줄로 옮기던 기동 이관(`LegacySuggestionBackfill`)은 PR2 까지 남겨, DROP 직전 기동에서 마지막으로 돌린 뒤 PR2 에서 지운다
- 이미 알린 발견과 받아들인 문제 후보의 되풀이 판정은 저장된 보고(`proactive_check.report_json`)와 제안 줄에서 주제 키와 출처를 읽어 유지한다
- 결과 저장 스위치(`proactive-suggestion.enabled`)를 지운다
- 옛 `AUTONOMY` 계기의 살펴보기 줄과 그 값을 지운다
- `proactive_check` 에서 읽는 곳이 없는 칸, `decision_feedback_event.source_check_id`, 호출 없는 조회를 지운다
- 두 테이블을 DROP 한다

범위 밖:

- `proactive_check` 테이블 자체. 살펴보기 한 번의 상태, 쓰기 허용 경계, 보고, 읽지 않은 보고 표시를 그대로 갖는다
- 매일 깨우기 일정과 보고 카드 화면
- 제안 줄(`follow_up`)의 구조와 지금 화면의 제안 카드

## 요구사항과 인수 조건

| ID | 요구사항 | 관측할 인수 조건 |
| --- | --- | --- |
| REQ1 | 살펴보기가 발견과 문제 후보를 따로 저장하지 않는다 | 살펴보기를 돌린 뒤 결과 블록의 발견과 문제 후보가 답과 보고에 그려지고, 제안은 지금처럼 제안 줄로 생긴다. 두 테이블을 쓰는 코드와 엔티티가 없다 |
| REQ2 | 다음 살펴보기 입력이 제안 줄과 보고로 최근 맥락을 받는다 | 실행 입력에 그 점검 대화의 최근 제안 줄(제목, 상태, 마지막 반응. 거절한 줄 포함, 만료한 줄 제외)과 최근 보고의 발견 주제가 실린다. 모델이 쓴 글은 `<external-data>` 로 감싼다. 실리는 개수와 기간의 상한이 있다 |
| REQ7 | 이미 알린 소식의 되풀이 판정이 그대로다 | 같은 주제 키나 출처의 발견만 다시 나온 살펴보기는 지금처럼 「새로 알릴 것 없음」 으로 조용히 끝나고, 다음 매일 깨우기가 `UNREAD_REPORT` 로 막히지 않는다. 받아들인 문제 후보의 중복도 같은 기간 안에서 걸러진다. 기존 판정 테스트를 보고 기반으로 옮겨 통과한다 |
| REQ3 | 점검 대화의 발견 반응 단추가 없다 | 점검 대화 답 아래에 발견 반응 단추가 보이지 않고, 그 API 가 없다(404). 지금 화면의 제안 카드 반응은 그대로 동작한다 |
| REQ4 | 보고의 읽지 않음 표시와 매일 깨우기 건너뛰기는 그대로다 | 읽지 않은 보고가 있으면 매일 깨우기가 건너뛰고(`UNREAD_REPORT`), 보고를 열면 표시가 지워진다. 기존 테스트가 통과한다 |
| REQ5 | 두 테이블과 쓰지 않는 칸이 운영에서 사라진다 | PR2 배포 뒤 운영에 두 테이블, `decision_feedback_event.source_check_id`, 읽는 곳 없는 `proactive_check` 칸이 없고, 계기가 `AUTONOMY` 인 살펴보기 줄이 0행이다. 운영 확인 절차는 `fos-home-infra` 가 갖는다 |
| REQ6 | 옛 기록 정리는 사용자에게 보인 적 있는 데이터를 잃지 않는다 | DROP 직전 기동 이관의 로그가 실패 0건이고, 옮기지 않은 줄은 지운 대화의 발견과 같은 제목의 할 일이 이미 열려 있던 발견뿐이다. 보인 적 없는 참고 발견과 버린 후보, 위 두 경우만 사라진다 |

## 설계

PR 두 개로 나눈다.
PR1 은 읽기와 쓰기를 끊는다. 결과 저장, 입력 조립, 반응 단추와 API, 기동 이관, 쓰지 않는 칸과 조회를 지우고, 입력을 제안 줄로 바꾼다.
PR2 는 PR1 배포를 확인한 뒤 두 테이블과 칸을 DROP 한다(테이블 줄이기의 DROP 순서와 같다).
ADR-081, ADR-093, ADR-20261008 / check-finding-reaction, ADR-20261101 / proactive-suggestion 을 개정하거나 대체한다.
함께 고칠 것: `docs/features/proactive.md` 의 발견 반응, 되풀이 판정, 반응 사건 절, `backend/docs/data-schema.md`, 정리 분류(purge 정의와 fixture), 웹 브라우저 테스트와 E2E 시나리오의 살펴보기 사례. 보고를 보일 때 발견마다 남기던 `SURFACED` 사건도 사라진다.
칸별 쓰는 곳과 읽는 곳의 조사는 기술 설계에서 다시 확인한다.
