# 네이버 쇼핑: 에이전트가 상품을 찾아 주문서까지 채우고, 결제는 사람이 한다

확인: 2026-11-10

## 목표

사용자가 대화에서 「이 상품을 네이버에서 사 줘」 라고 하면, 에이전트가 「내 브라우저」 로 네이버 쇼핑에서 상품을 찾아 보이고, 사용자가 고른 상품을 승인 뒤 네이버 주문서까지 채운다.
결제(네이버페이 비밀번호와 인증)는 사람이 「내 브라우저」 화면에서 직접 한다. 에이전트는 결제 단추를 누르지 않는다.

이 기능이 함께 정하는 공통 기반이 둘 있다. 뒤의 다른 구매·예매 기능(코레일 KTX 예매 등)도 같은 기반을 쓴다.

- **화면 넘기기**: 실행 중에 로그인, 캡차, 기기 인증, 결제처럼 사람이 해야 하는 단계를 만나면 멈추고 사람에게 「내 브라우저」 화면을 넘긴 뒤, 사람이 마치면 이어 간다
- **구매 상한과 결제 직전 금액 재확인**: 사용자가 정한 상한을 넘는 주문서는 채우지 않고, 주문서의 최종 금액을 승인한 금액과 다시 견준 뒤에만 화면을 넘긴다

## 요구사항과 인수 조건

인수 조건은 가짜 네이버 화면(테스트용 HTML)과 가짜 중계 위에서 확인한다. 실제 네이버 계정과 운영 브라우저로 확인하는 절차는 플러그인 기능 파일(`docs/features/naver-shopping.md`)이 갖고 사용자가 직접 돈다. PR 마다 그 PR 의 도구만큼 절차를 더한다.

| ID | 요구사항 | 관측할 인수 조건 |
| --- | --- | --- |
| REQ1 | 네이버 쇼핑 플러그인을 연결하고 에이전트에 붙인다 | 카탈로그에 `naver-shopping` 이 오르고, 사용자가 넣는 칸이 없다. 연결 확인 도구가 「내 브라우저」 에 닿는지와 네이버 로그인 쿠키가 있는지 보고, 쿠키가 없으면 로그인 필요로 실패한다. 연결 화면의 「내 브라우저에서 로그인」 이 네이버 로그인 화면을 연다. 어느 에이전트에나 붙일 수 있다 |
| REQ2 | 상품을 검색한다 | 검색 도구가 검색어 하나로 네이버 쇼핑 검색 결과의 첫 페이지 하나만 읽어 상품마다 이름, 가격, 판매처, 상품 주소, 네이버페이로 바로 살 수 있는지를 돌려준다. 다음 페이지를 읽는 인자가 없다. 검색은 새 탭에서 하고 끝나면 그 탭만 닫는다. 결과는 대화에만 남고 서버에 저장하지 않는다 |
| REQ3 | 상품 상세를 읽는다 | 상세 도구가 검색이 준 상품 주소 하나로 상품 화면을 열어 이름, 판매처, 판매 가격, 옵션(이름, 추가 금액, 품절), 배송비, 네이버페이로 바로 살 수 있는지를 읽는다. 가격비교 묶음 주소면 묶음 화면을 열어 네이버페이 판매처 목록(판매처, 가격, 배송비, 상품 주소)을 돌려주고, 에이전트는 그중 하나의 주소로 상세를 다시 읽는다(DECISION28). 스마트스토어·브랜드스토어·가격비교 묶음이 아닌 주소는 화면을 열지 않고 「바로 살 수 없는 상품」 으로 링크만 돌려준다. 장바구니·구매 단추를 누르지 않는다 |
| REQ4 | 사람이 해야 하는 화면을 만나면 우회하지 않고 멈춘다 | 검색이나 상세 읽기 중 로그인, 캡차, 기기 인증 화면을 만나면 아무것도 누르거나 입력하지 않고 그 종류(`login`, `captcha`, `device_check`)를 담은 선언된 오류로 끝난다. 에이전트는 「내 브라우저」 에서 풀어 달라고 안내한다. PR2 뒤에는 이 오류가 화면 넘기기 카드가 된다(REQ7) |
| REQ5 | 도구가 Hermes 도구 검색에 영어 키워드로 걸린다 | 쇼핑 도구마다 이름과 설명 첫 문장에 영어 동작·대상 낱말(예: search, product, naver, shopping)이 있다. 플러그인 선언 검사가 영어 키워드가 없는 도구 선언, 그리고 다른 플러그인과 겹치는 도구 이름을 실패로 잡는다. 검사가 실제로 잡는지는 일부러 틀린 선언 사본으로 확인한다 |
| REQ6 | 검색과 상세 읽기는 사람이 연 대화에서만 돈다 | 먼저 살펴보기, 매일 깨우기, 예약 작업의 실행이 쇼핑 도구를 부르면 거절된다. 사람이 연 대화 안의 흐름(사람이 친 메시지, 「다 했어요」 단추 메시지, 승인 결과를 전하는 자동 turn, 그 대화의 위임 자식 실행)은 부를 수 있다(DECISION32) |
| REQ7 | 화면 넘기기 카드를 띄운다 | 플러그인이 「사람이 해야 함」 으로 끝나면 그 대화에 카드가 뜬다. 카드는 무엇을 해야 하는지(로그인, 캡차, 기기 인증, 결제)와 「내 브라우저 열기」, 「다 했어요」 단추를 보인다. 「내 브라우저 열기」 는 그 작업 탭을 연 「내 브라우저」 화면으로 간다. 같은 때 알림 단추에 알림 한 건이 생기고 누르면 그 대화로 간다. 실행은 멈춰 기다리지 않고 turn 을 마친다 |
| REQ8 | 「다 했어요」 로 이어 간다 | 「다 했어요」 를 누르면 사람이 마쳤다는 다음 메시지가 그 대화로 가고 에이전트가 멈춘 단계부터 다시 부른다. 카드를 누르지 않고 입력창에 답해도 이어 간다. 카드와 알림은 이어 간 뒤 사라지거나 읽음이 된다. 다시 불렀는데 아직 같은 화면이면 카드가 다시 뜬다 |
| REQ9 | 구매 상한을 정한다 | 상한은 한 건(상품 금액과 배송비를 더한 예상 합계)과 KST 하루에 승인한 합계 둘이고 원화다. 사용자가 「외부 서비스 연결」 화면에서 정하며 기본은 0 이다. 운영 최대치는 없다(DECISION31). 0 이면 주문서 준비가 「상한을 정해 주세요」 로 거절된다. 에이전트는 상한을 바꾸지 못한다. 새 테이블을 만들지 않는다 |
| REQ10 | 주문서 준비는 매번 승인 카드를 거친다 | 에이전트가 상품 하나, 옵션, 수량으로 주문서 준비를 부르면 플러그인이 상품 화면을 다시 읽어 서버가 만든 요약으로 카드가 뜬다. 카드는 상품명, 판매처, 옵션, 수량, 상품 금액, 배송비, 예상 합계, 오늘 남은 구매 한도, 상품 링크를 보이고 배송지와 결제 수단은 싣지 않는다. 배송비는 무료 조건을 반영한 기본 배송비이고 카드에 「지역 추가 배송비 별도」 를 적는다(DECISION29). 「승인하고 묻지 않기」 와 「이 대화에서 계속 허용」 이 없다. 예상 합계가 한 건 상한이나 오늘 남은 한도를 넘으면 카드를 만들지 않고 걸린 상한을 알린다. 승인하는 순간에도 그때의 상한과 오늘 합계로 다시 보고, 넘으면 주문서를 채우지 않고 거절한다(DECISION30) |
| REQ11 | 승인하면 주문서까지 채우고 결제 단추는 누르지 않는다 | 승인 뒤 플러그인이 새 탭에서 상품 화면을 열어 옵션과 수량을 고르고 「구매하기」 로 주문서까지 간다. 장바구니에 담지 않는다. 결제 단추를 누르는 코드 경로가 없다. 같은 승인으로 주문서를 두 번 열지 않는다. 결과를 모르면 다시 보내지 않고 그 승인을 끝낸 뒤, 「내 브라우저」 에 열린 탭을 확인해 달라는 화면 넘기기 카드(REQ7)를 띄운다(DECISION33) |
| REQ12 | 결제 직전에 금액을 다시 본다 | 주문서의 최종 결제 금액이 승인한 예상 합계보다 1원이라도 크거나 상한을 넘으면 화면을 넘기지 않고 그 금액을 알린다. 같거나 작으면 결제 화면 넘기기 카드(REQ7)를 띄운다 |
| REQ13 | 주문서 준비는 사람이 연 대화에서만 시작한다 | 먼저 살펴보기, 매일 깨우기, 예약 작업의 실행이 주문서 준비를 부르면 카드 없이 거절된다. 허용하는 흐름은 REQ6 과 같다(DECISION32) |
| REQ14 | 결제 뒤 주문을 확인한다 | 결제 화면 넘기기 뒤 「다 했어요」 로 이어 가면 에이전트가 네이버 주문 내역에서 그 상품의 주문이 생겼는지와 결제 금액을 읽어 알린다. 없으면 결제가 확인되지 않았다고 알린다. 취소·반품 도구는 없다 |

| DECISION9 | 구매 상한 | 한 건과 KST 하루에 승인한 합계, 원화, 기본 0. 0 이면 주문서를 채우지 않는다 | 사용자 2026-11-10 | 사용자가 직접 정해야 열린다. 토스 주문 상한([ADR-20261015 / financial-user-limits](../../adr/ADR-20261015-financial-user-limits.md))과 같은 틀이다 |
| DECISION10 | 결제 직전 금액이 다를 때 | 승인한 예상 합계보다 크거나 상한을 넘으면 멈춘다. 같거나 작으면 넘긴다 | 사용자 2026-11-10 | 승인보다 많이 내는 일만 막고, 할인은 사람을 다시 부르지 않는다 |
| DECISION11 | 화면 넘기기의 알림과 이어 가기 | 대화 카드와 웹 안 알림, 「다 했어요」 단추가 다음 메시지를 보내 이어 간다. 실행은 멈춰 기다리지 않는다 | 사용자 2026-11-10 | 기다리는 실행이 없어 시간 제한과 동시 실행 한도를 잡지 않는다. 묻는 카드([ADR-026](../../adr/ADR-026-에이전트가-물을-것은-답-끝의-태그로-두고-화면이-카드로-그린다.md))와 같은 틀이다. 웹 푸시는 아직 없다 |
| DECISION12 | 쓸 에이전트 | 어느 에이전트에나 붙인다. 도구 이름과 설명 첫 문장에 영어 키워드를 넣고 선언 검사가 지킨다 | 사용자 2026-11-10 | Hermes 도구 검색이 한국어를 색인하지 않는다. 도구 수가 적다 |
| DECISION13 | 쇼핑 도구를 부를 수 있는 실행 | 사람이 연 대화의 turn 만. 먼저 살펴보기, 매일 깨우기, 예약 작업은 검색·상세·주문서 준비를 모두 부르지 못한다 | 사용자 2026-11-10 | 답은 「주문서 준비는 대화에서만, 살펴보기·예약 작업은 검색과 상세만」 이었으나 DECISION6 의 「반복·예약 검색은 하지 않는다」 와 겹쳐 더 좁은 쪽으로 맞췄다. 스펙 확인에서 사용자가 이 맞춤을 확인한다 |
| DECISION14 | 주문 확인과 취소 | 확인만. 결제 뒤 주문 내역을 읽어 알린다. 취소·반품은 사람이 네이버에서 한다 | 사용자 2026-11-10 | 돈을 되돌리는 쓰기는 사람에게 둔다 |
| DECISION15 | 상한을 바꾸는 길 | 「외부 서비스 연결」 화면에서 사용자가 직접 바꾼다. 에이전트가 상한을 바꾸는 도구는 두지 않는다 | 작성자 | 토스의 대화 경로(`order_limit_change`)는 올리기에 승인 카드가 하나 더 든다. 첫 버전에 필요한 길은 화면 하나다. 스펙 확인에서 사용자가 확인한다 |
| DECISION16 | 검색 결과의 수 | 검색 결과 첫 페이지의 상품을 40개까지 돌려준다(DECISION19) | 작성자 | 네이버 쇼핑 검색의 기본 한 페이지가 40개다 |
| DECISION17 | 하루 합계에 드는 것 | 그날(KST) 승인한 주문서 준비의 예상 합계. 결제했는지와 상관없이 센다. 결제 화면을 넘기지 못한 승인(주문서를 못 채움, 결제 직전 재확인에서 멈춤)은 빼고, 결과를 모르는 승인은 센다(DECISION30) | 작성자 | 결제는 사람이 네이버에서 해 Control Plane 이 알 수 없다. 승인을 세면 넘치지 않는 쪽이다. 토스의 하루 합계와 같은 기준이다 |
| DECISION18 | 검색 결과의 「네이버페이로 바로 살 수 있는지」 | 결과 카드에 보이는 네이버페이 표시로 `yes` 로 두고, 표시가 없으면 `unknown` 이다. 확정은 상세 읽기가 한다 | 작성자 | 검색 화면만으로는 확정할 수 없다(DECISION6). 짐작한 값을 확정처럼 보이지 않는다 |
| DECISION19 | 검색 결과를 읽는 범위 | 첫 페이지에 처음 실린 상품을 40개까지 읽는다. 아래로 내려 더 실리는 상품은 읽지 않아 40개보다 적을 수 있다. 광고 상품도 40개 안에 세고 광고라고 표시한다 | 작성자 | 기술 설계에서 고쳤다(design.md DECISION9). 내려서 실리는 상품은 페이지의 처음 데이터에 없다. 다음 페이지로 넘어가지 않는다 |
| DECISION20 | 사람에게 넘길 때의 탭 | 사람이 해야 하는 화면에서 멈추면 그 탭을 닫지 않고 남긴다. 정상으로 끝난 읽기만 탭을 닫는다 | 작성자 | 화면 넘기기(DECISION11)는 사람이 그 탭에서 바로 풀어야 뜻이 있다 |
| DECISION21 | 상품 금액 | 화면의 판매가(즉시할인 반영)에 옵션 추가 금액을 더하고 수량을 곱한다. 쿠폰과 포인트는 넣지 않는다 | 작성자 | 사람이 상품 화면에서 보는 값이다. 쿠폰은 주문서에서 붙어 금액을 줄이므로 DECISION10 에 걸리지 않는다 |
| DECISION22 | 결제 직전에 견주는 금액 | 주문서 화면의 최종 결제 금액(쿠폰·포인트를 뺀 뒤 실제로 낼 값) | 작성자 | 사람이 실제로 내는 금액이 승인보다 크지 않은지가 DECISION10 의 뜻이다 |
| DECISION23 | 결제 직전의 상한 | 그 순간의 상한과, 이 주문을 뺀 오늘 합계로 다시 본다. 승인 뒤에 낮춘 상한에도 걸린다 | 작성자 | 토스가 실행 직전(claim)에 같은 방식으로 다시 판정한다 |
| DECISION24 | 입력창 답으로 이어 가기 | 카드를 띄운 뒤 그 대화에 오는 다음 메시지는 무엇이든 새 turn 을 연다. 카드는 사람이 보낸 다음 turn 이 시작되면 닫힌다(2026-11-12 사용자 결정: 담당의 결과를 전하는 자동 turn 은 닫지 않는다). 다시 부를지는 에이전트가 메시지를 읽고 정한다 | 작성자 | 묻는 카드(ADR-026)와 같다. 카드는 입력을 대신 보내는 단추일 뿐이다 |
| DECISION25 | 결제 넘기기 카드의 내용 | 해야 할 일, 단추 둘에 더해 확인한 최종 결제 금액과 승인한 예상 합계를 함께 보인다 | 작성자 | 결제 직전 재확인의 결과를 사람이 결제 화면 앞에서 본다 |
| DECISION26 | 연결 확인의 로그인 판정 | 네이버 블로그 플러그인처럼 네이버 로그인 쿠키가 있는지만 본다. 만료된 쿠키는 다음 도구가 로그인 화면을 만나 화면 넘기기(REQ4, REQ7)로 드러난다 | 작성자 | 네이버 블로그 `session_status` 와 같은 기준이다. 확인 때 화면을 열지 않는다 |
| DECISION27 | 주문 확인에서 맞추는 주문 | 결제 화면을 넘긴 시각 뒤에 생긴 주문 가운데 상품과 결제 금액이 맞는 것만 「확인됐다」 고 알린다 | 작성자 | 예전에 산 같은 상품을 잘못 보고하지 않는다 |
| DECISION28 | 가격비교 묶음 상품 | 묶음 안의 네이버페이 판매처로 들어간다. 상세 도구가 판매처 목록을 돌려주고 에이전트가 하나의 상품 주소로 다시 읽는다 | 사용자 2026-11-10 | 사람이 실제로 사는 길과 같고, 검색 결과를 버리지 않는다 |
| DECISION29 | 승인 카드의 배송비 | 무료 조건을 반영한 기본 배송비. 지역 추가 배송비는 넣지 않고 카드에 「지역 추가 배송비 별도」 를 적는다 | 사용자 2026-11-10 | 카드 금액이 대부분의 실제 금액과 같고, 지역 추가는 결제 직전 재확인이 잡아 사람이 본다 |
| DECISION30 | 승인 때 다시 판정과 하루 합계 | 승인하는 순간 그때의 상한과 오늘 합계로 다시 본다. 결제 화면을 넘기지 못한 승인은 하루 합계에서 빼고, 결과를 모르는 승인은 센다 | 사용자 2026-11-10 | 결제 화면까지 간 것만 한도를 쓰고, 모르는 것은 넘치지 않는 쪽으로 센다 |
| DECISION31 | 운영 최대치 | 두지 않는다. 사용자 상한만 있다 | 사용자 2026-11-10 | 결제가 사람 손에 있어 이중 잠금의 이득이 작고, 기본 0 이 이미 닫힌 상태다 |
| DECISION32 | 사람이 연 대화의 흐름 | 사람이 친 메시지, 「다 했어요」 단추 메시지, 승인 결과를 전하는 자동 turn, 그 대화의 위임 자식 실행을 모두 허용한다. 막는 것은 먼저 살펴보기, 매일 깨우기, 예약 작업의 실행이다 | 사용자 2026-11-10 | 사람이 그 자리에서 보는 대화라는 경계를 지키면서 흐름이 끊기지 않는다 |
