## ADR-061: 재기동 때 남은 실행은 Hermes 에 물어 정하고 도는 실행에는 다시 붙는다

- **status**: `accepted`
- **결정**: Control Plane 이 다시 뜰 때 `RUNNING` 으로 남은 실행 줄을 곧바로 실패로 적지 않는다.
  `hermes_run_id` 가 있는 줄은 `GET /v1/runs/{run_id}` 로 Hermes 에 묻고 그 답으로 정한다.

  | Hermes 의 답 | 실행 줄 |
  | --- | --- |
  | 끝났다(`completed`, `failed`, `cancelled`, `error`, `interrupted`) | 그 상태와 답과 사용량을 보통 turn 과 같은 기록 경로로 적는다 |
  | 아직 돈다 | `RUNNING` 으로 두고 끝날 때까지 다시 묻는다. 끝나면 위와 같이 적는다 |
  | 404 | `FAILED`, `error_code` 는 `REMOTE_RUN_LOST` |
  | 닿지 못했다(연결 실패, 5xx, 429) | `RUNNING` 으로 두고 다시 묻는다 |
  | `hermes_run_id` 가 없다 | 묻지 않고 `FAILED`, `error_code` 는 `ORPHANED` |

  **도는 실행에는 다시 붙는다.** 대화 turn 과 `agent_delegate` 로 맡긴 실행이 여기 해당한다.
  흐름으로 도는 turn 과 그 자식에는 붙지 않는다. Hermes 에 중지를 보내고 끝난 상태와 사용량만 적는다.
  흐름의 단계 순서와 합치기는 프로세스 메모리에만 있어 이어 갈 수 없다.

  **기다리는 시간에는 상한이 있다.** `assistant.restart-reconcile.max-wait` 이고 기본값은 `hermes.run-timeout` 과 같다.
  넘으면 Hermes 에 중지를 보내고 `FAILED` 로 적는다.
  그때까지 한 번이라도 Hermes 의 답을 받았으면 `RECONCILE_TIMEOUT`, 한 번도 받지 못했으면 `RECONCILE_UNREACHABLE` 이다.

  **대화 turn 을 다시 정하는 동안 그 대화의 turn 잠금을 잡는다.**
  웹 서버가 요청을 받기 전에 잡고, 그 실행 줄을 적은 뒤에 푼다.
  새 표와 새 칸은 두지 않는다. 남은 실행의 목록은 `RUNNING` 인 실행 줄이다.
- **맥락**: 기동 정리는 `RUNNING` 줄을 모두 `FAILED`(`ORPHANED`) 로 바꿨다.
  Hermes 는 별도 프로세스라 Control Plane 이 내려가도 실행을 계속한다.
  배포는 Control Plane 만 다시 띄운다. 그래서 배포할 때마다 도는 실행의 답과 사용량을 잃었고,
  끝난 위임이 실패로 부모 대화에 전해졌다.
  Hermes v0.21.5 는 끝난 실행의 상태와 답과 사용량을 종료 뒤 1시간 동안 실행 조회로 돌려준다([`hermes/docs/hermes-contract.md`](../../../hermes/docs/hermes-contract.md) 의 「실행 조회가 답하는 기간」).
  다시 뜨는 데 걸리는 시간이 그보다 훨씬 짧으므로 조회만으로 회수할 수 있다.
  이 결정은 [ADR-011](ADR-011-실행은-시작할-때-기록하고-끝날-때-갱신한다.md) 의 「기동할 때 `RUNNING` 으로 남아 있는 줄을 `FAILED` 로 정리한다」 를 대체한다. ADR-011 의 나머지는 그대로다.
- **대체된 부분**: 없다.
- **대안 기각**:
  - 도는 실행을 기동 때 모두 중지한다: 구현이 가장 작다. 그러나 배포할 때마다 긴 실행과 위임이 끊긴다. 이 결정이 풀려던 문제가 그대로 남는다.
  - 붙어 있는 동안 답 조각도 다시 흘린다: Hermes 의 사건 스트림은 구독하기 전의 조각을 다시 주지 않는다. 앞부분이 빠진 답이 흐른다. 화면은 「답을 만드는 중」 을 보이고 끝난 답을 이력에서 읽는다.
  - 흐름 turn 에도 붙는다: 어느 단계까지 갔는지와 자식의 답을 저장하지 않는다. 그것을 저장하려면 흐름 상태를 담을 표가 필요하다. 흐름을 이어 가는 일은 이 결정에서 넓히지 않는다.
  - 다시 정할 실행을 표에 따로 적는다: 실행 줄의 `status` 와 `hermes_run_id` 로 같은 목록이 나온다. 표를 두면 두 곳이 어긋날 수 있다.
  - 404 를 일시 실패로 보고 다시 묻는다: Hermes 는 모르는 run 에 404 를 낸다. gateway 가 다시 떴거나 종료 뒤 1시간이 지난 것이고, 다시 물어도 답이 바뀌지 않는다.
  - 제출할 때 `Idempotency-Key` 를 보내 run 번호가 붙기 전에 끊긴 실행도 찾는다: Hermes 가 그 key 로 실행 상태를 디스크에 남긴다. 실행 줄에 key 를 담을 칸과 제출 경로 변경이 필요하다. run 번호 없이 끊기는 구간은 제출 호출 한 번의 길이라 따로 정한다.
- **결과**:
  - 얻는 것: 배포로 Control Plane 만 다시 떠도 도는 대화 turn 과 위임이 끝까지 가고, 답과 사용량과 비용이 남는다. 끝난 위임은 실제 결과로 부모 대화에 전해진다. 다시 정하는 동안 그 대화에 새 turn 이 열리지 않아 같은 Hermes session 에 두 turn 이 겹치지 않는다.
  - 감당할 것:
    - 다시 붙은 turn 은 답 조각과 도구 사건을 흘리지 않는다. 그 실행의 작업 과정에는 끊기기 전의 사건과 끝 사건만 남는다.
    - 다시 붙어 끝난 대화 turn 은 Memory 제안과 추천 질문 갱신을 돌리지 않는다. 둘은 turn 을 돌린 프로세스가 끝에 하는 부가 실행이다.
    - Hermes 가 오래 닿지 않으면 그 대화는 상한까지 잠긴다. 그동안 보낸 글은 대기 메시지로 쌓인다.
    - 상한은 기동마다 새로 센다. 상한 안에 여러 번 다시 뜨면 한 실행을 상한보다 오래 기다린다.
    - 다시 붙은 위임 실행은 서버 전체 동시 위임 한도의 자리를 차지하지 않는다. 루트당 한도는 실행 줄로 세므로 그대로다.
    - Control Plane 이 한 대라는 전제를 그대로 쓴다. 여러 대면 다른 인스턴스가 돌리는 실행에 붙는다.
- **적용 범위**: 기동할 때 한 번 시작한다. 도는 Control Plane 이 Hermes 와 끊겼을 때의 처리는 바꾸지 않는다.
