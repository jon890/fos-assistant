## ADR-034: 올린 스킬은 Control Plane 이 버전 디렉터리에 쓰고 Hermes 는 읽기만 한다

- **status**: `accepted`
- **결정**: 에이전트를 관리하는 사람([ADR-033](ADR-033-사용자가-에이전트를-만들고-공개해도-만든-사람이-관리한다.md))이 화면에서 스킬을 올리고 고치고 지운다. 승인 절차는 없다.
  스킬은 `SKILL.md` 와 참고용 텍스트 파일(`references/`, `templates/`)만 받는다. 스크립트는 받지 않는다.
  Control Plane 이 공유 디렉터리의 **profile 별 새 버전 디렉터리**에 그 profile 의 올린 스킬 전체를 쓰고, 그 profile 의 `skills.external_dirs` 를 새 버전으로 바꿔 게시한다.
  Hermes 컨테이너는 그 디렉터리를 **읽기 전용**으로 본다. 스킬 본문은 데이터베이스에 두지 않는다.
  스킬을 올린 에이전트는 `skills` toolset 이 켜져 있어야 한다.
  누가 어느 실행에서 어느 스킬을 썼는지는 Control Plane 이 실행 줄에 딸린 표로 남긴다.
- **맥락**:
  - Hermes 가 스킬을 붙이는 정식 설정은 `skills.external_dirs` 다. 대시보드 `POST /api/skills` 는 `SKILL.md` 하나만 만들고, 이미 색인을 계산한 gateway 는 재시작 전까지 새 스킬을 보지 못한다. 반면 `external_dirs` 에 새 경로를 더하면 같은 프로세스의 다음 색인에 나타난다. 근거는 [`hermes/tools-and-skills.md`](../../../docs/hermes/tools-and-skills.md) 의 「스킬 파일과 색인 적용 시점」 이다.
  - 대시보드에는 스킬을 지우는 경로가 없다.
  - `skills` toolset 에는 `skill_manage` 가 함께 들어 있어, 쓰기 가능한 외부 스킬은 모델이 고칠 수 있다.
  - 에이전트와 profile 은 하나씩 짝이다(`agent.hermes_profile` 이 유일하다). 에이전트에 올린다는 것은 그 profile 에 붙인다는 것이다.
  - 결과물 파일은 이미 같은 틀을 쓴다. Control Plane 이 쓰는 디렉터리를 Hermes 컨테이너도 마운트해 본다([ADR-028](ADR-028-결과물은-사용자의-대화-폴더에-mcp-도구로-쓴다.md)).
  - 「Hermes 가 관리할 것은 Hermes 에 두고 필요한 것만 동기화한다」는 원칙이 있다. 스킬은 Hermes 가 읽는 자리에만 있고 Control Plane 은 쓰기와 권한만 맡는다.
- **대안 기각**:
  - **대시보드 API 로 profile 안에 쓴다.** 참고 파일을 쓰는 HTTP 경로가 확인되지 않았고, 새 스킬이 재시작 전까지 보이지 않으며, 지우는 경로가 없다.
  - **본문을 데이터베이스에 두고 Hermes 로 동기화한다.** 정본이 둘이 되어 어긋날 수 있다. 페르소나도 같은 이유로 Hermes 에만 둔다([ADR-019](ADR-019-페르소나는-hermes-가-갖고-control-plane-은-화면만-준다.md)).
  - **스크립트까지 받는다.** 실행하려면 terminal 이나 code_execution 이 필요하고 둘은 `ADMIN` 등급이며 비공개 전용이다. 쓸 수 있는 에이전트가 적은데 검사할 것은 많다.
  - **Hermes 가 쓸 수 있게 마운트한다.** 모델이 `skill_manage` 로 올린 스킬을 바꾸면 화면이 보인 것과 실제로 도는 것이 달라진다.
  - **같은 디렉터리 안에서 파일을 바로 바꾼다.** 쓰는 도중의 반쯤 바뀐 스킬을 실행이 읽을 수 있다. 새 디렉터리를 다 쓴 뒤 설정 한 번으로 바꾸면 실행은 옛 버전 아니면 새 버전 하나만 본다.
- **결과**:
  - 얻는 것:
    - 올리고 고친 스킬이 다음 실행부터 확실히 쓰인다. 재시작이 필요 없다
    - 되돌리기는 설정을 옛 버전 디렉터리로 돌리는 것이고, 지우기도 우리 손에 있다
    - 화면에 보이는 스킬과 도는 스킬이 같다
    - 지금 어느 버전이 게시됐는지는 게시에 성공한 버전 디렉터리의 표식 파일로 안다. 데이터베이스에 두지 않는다. Hermes 설정을 읽는 경로는 열지 않는다(`GET /api/config` 가 비밀값까지 펼쳐 돌려준다)
  - 감당할 것:
    - 운영에 공유 디렉터리 마운트가 하나 늘고, 대시보드 플러그인이 `skills.external_dirs` 도 받아야 한다
    - 스킬 하나를 고쳐도 그 profile 의 올린 스킬 전체를 새 디렉터리에 다시 쓴다. 텍스트 파일 상한 안이라 크기는 작다. 옛 버전은 몇 개만 남기고 지운다
    - 같은 에이전트의 저장은 한 번에 하나씩 돈다. 뒤에 저장한 것이 남는다
    - Hermes 기본 스킬과 같은 이름은 거절한다. profile 로컬 스킬이 같은 이름이면 외부 스킬보다 먼저 선택되기 때문이다
    - 새 스킬의 설명은 60자까지이고 에이전트마다 올린 스킬 수에 한도가 있다(아래 「저장할 수 있는 스킬은 Hermes 가 제대로 고를 수 있는 스킬이다」)
    - 모델이 스스로 `skill_view` 로 읽은 스킬은 실행 사건에 스킬 이름이 실려 올 때만 이력에 남는다
    - **모델이 `skill_manage` 로 같은 이름의 로컬 스킬을 만들면 올린 스킬이 가려진다.** 로컬 스킬이 외부 스킬보다 먼저 선택되기 때문이다. 읽기 전용 마운트로는 막지 못해 서명 plugin 의 `pre_tool_call` 이 `skill_manage` 를 막는다. 모델에게도 실행 입력의 단락으로 쓰지 말라고 알린다(아래 「모델에게 `skill_manage` 를 쓰지 말라고 알린다」). 대화로 스킬을 만드는 길은 그래서 지금 없다
    - `SKILL.md` 앞머리의 `name` 은 디렉터리 이름과 같아야 한다. Hermes 목록은 앞머리 이름을 쓴다

### 호출 이력을 누가 보나

| 누구 | 보는 것 |
| --- | --- |
| 에이전트를 관리하는 사람 | 스킬별 호출 수와 마지막 호출 시각. 누가 어느 대화에서 불렀는지는 보지 않는다 |
| 각 사용자 | 자기 대화에서 부른 호출과 그 대화 |

가족용 에이전트에서 다른 가족의 대화가 어디 있는지 드러나지 않게 한다.

### 저장할 수 있는 스킬은 Hermes 가 제대로 고를 수 있는 스킬이다

화면에서 저장에 성공한 스킬은 Hermes 색인에서 설명이 잘리지 않아야 한다.
Hermes 는 색인에 설명을 60자까지만 싣고, 넘으면 57자에 `...` 을 붙인다.
잘린 설명으로는 모델이 그 스킬을 언제 써야 할지 알지 못한다.
그래서 저장 규칙을 Hermes 가 새 스킬을 만들 때의 검사와 맞춘다.

| 규칙 | 언제 보나 | 어기면 |
| --- | --- | --- |
| 앞머리 `description` 은 60자까지 | 새 스킬을 만들 때만. 이미 올린 스킬을 고칠 때는 보지 않는다 | `VALIDATION_FAILED` |
| 앞머리 `description` 은 1024자까지 | 저장할 때마다 | `VALIDATION_FAILED` |
| 앞머리 뒤에 공백이 아닌 본문이 있다 | 저장할 때마다 | `VALIDATION_FAILED` |
| 에이전트 하나에 올린 스킬은 설정 `assistant.skill.max-per-agent` 개까지. 기본 30 | 새 스킬을 만들 때만. 에이전트 행 잠금 안에서 센다 | `VALIDATION_FAILED` |

- 글자 수는 Hermes 와 같게 code point 로 센다. 60자는 앞뒤 공백과 앞뒤 따옴표를 뺀 뒤 세고, 1024자는 앞뒤를 빼지 않고 센다.
- 60자는 Hermes 의 상수를 읽지 않고 Control Plane 이 같은 값을 따로 갖는다. Hermes 를 올리며 값이 바뀌면 함께 고친다.
- 이미 올린 스킬은 설명이 60자를 넘어도 고칠 수 있다. Hermes 도 고칠 때는 60자를 보지 않는다.
- 개수는 우리가 올린 스킬만 센다. Hermes 기본 스킬과 모델이 만든 로컬 스킬은 세지 않는다. 표식 없이 남은 더 새 버전의 이름도 올린 스킬로 센다.
- 개수 한도는 색인이 커지는 것을 막는다. 스킬 하나가 API 호출 한 번의 입력에 20~45 토큰을 더하고, 많아지면 모델이 고를 스킬을 잘못 고른다.

### 모델에게 `skill_manage` 를 쓰지 말라고 알린다

Hermes 의 스킬 색인 안내문은 「스킬에 문제가 있으면 `skill_manage` 로 고쳐라」,
「어려운 작업 뒤에는 스킬로 저장하자고 제안하라」 를 조건 없이 싣는다.
우리 환경에서는 서명 plugin 이 `skill_manage` 를 막으므로 안내와 실제 권한이 어긋난다.

Hermes v0.21.5 에는 `skill_view` 를 두고 `skill_manage` 만 도구 목록에서 빼는 설정이 없다.
`agent.disabled_toolsets` 는 toolset 단위라 `skills` 를 빼면 `skill_view` 와 색인까지 사라진다.
plugin 이 남의 도구를 등록 해제하려면 운영자의 `allow_tool_override` 가 필요하고, 전역 plugin 의 해제는 같은 프로세스의 모든 profile 에 걸린다.
`skill_manage` 를 빼도 색인 안내문의 `skill_manage` 문장은 남는다.
근거는 [`hermes/skills.md`](../../../docs/hermes/skills.md) 의 「`skill_manage` 만 빼는 설정」 이다.

그래서 두 겹으로 막는다.

- Control Plane 이 매 실행 입력 앞에 붙이는 단락에 「이 환경의 스킬은 사용자가 관리 화면에서 관리한다. `skill_manage` 로 만들거나 고치지 않는다. 고칠 점이 보이면 사용자에게 알린다」 를 넣는다.
- 서명 plugin 의 `skill_manage` 차단은 그대로 둔다. 안내를 무시한 호출도 실패한다.

### Hermes 를 올릴 때 이름 충돌을 본다

올릴 때는 Hermes 기본 스킬과 같은 이름을 거절한다.
그 뒤 Hermes 를 올려 같은 이름의 번들 스킬이나 로컬 스킬이 생기면, 화면에는 올린 스킬이 보이는데 Hermes 는 다른 스킬을 쓴다.
로컬 스킬이 외부 디렉터리 스킬보다 먼저 선택되기 때문이다.

그래서 Hermes 업그레이드와 배포 확인에 「각 profile 의 올린 스킬 이름과 Hermes 가 더 앞서 고르는 스킬 이름이 겹치지 않는다」 는 검사를 둔다.
겹치면 배포를 멈춘다. 검사는 운영 절차라 `fos-home-infra` 가 소유한다.
