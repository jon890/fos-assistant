## ADR-20261009 / agent-purge: 지운 에이전트는 7일 뒤 정리 작업이 행을 지우고, 설정과 권한은 함께 지우되 대화와 실행과 승인 이력은 남긴다

- **status**: `accepted`
- Date: 2026-10-09
- **대체된 부분**: [ADR-033](ADR-033-사용자가-에이전트를-만들고-공개해도-만든-사람이-관리한다.md) 이 기각한 「지우면 에이전트 행도 지운다」 를 7일 뒤에 한해 뒤집는다.
  [ADR-20261008 / agent-memory-grants-admin](../../../docs/adr/ADR-20261008-agent-memory-grants-admin.md) 의 「기록은 지우지 않는다」 는 에이전트 행이 남아 있는 동안만 지킨다.

### 결정

**사용자가 에이전트를 지우면 지금처럼 `agent.deleted_at` 을 적는다.
정리 작업이 매분 지운 지 `assistant.agents.purge-after`(7일)가 지난 에이전트를 찾아 행을 실제로 지운다.**

| 표 | 정리할 때 |
| --- | --- |
| `agent_memory_collection`, `agent_memory_collection_change` | 지운다. 에이전트의 설정과 그 변경 기록이다 |
| `agent_toolset_request` | 지운다. 에이전트의 권한 요청이다 |
| `agent_connector_binding` | 지운다. 에이전트를 지울 때 이미 떼서 보통 없다 |
| `proactive_loop_setting` | 지운다. FK 의 `ON DELETE CASCADE` 를 기다리지 않고 직접 지운다 |
| `proactive_check` | 지운다. 발견, 문제, 평가, 자율 판정 표는 FK 가 함께 지우거나 비운다. 비용은 `agent_execution` 에 남는다 |
| `connector_connection.agent_id` | 비운다. 바인딩이 생긴 뒤로 쓰지 않는 칸이다. 연결은 사용자의 것이라 남긴다 |
| `connector_action.agent_id` | 비운다. 외부 서비스에 무엇을 쓰려 했고 누가 승인했는지의 이력이고, 남은 대화의 승인 카드가 이 줄을 읽는다 |
| `conversation`, `agent_execution`, `task` | 그대로 둔다. FK 가 없고, 읽는 경로가 에이전트 행이 없어도 「지운 에이전트」 로 그린다 |

| 상황 | 동작 |
| --- | --- |
| 그 에이전트에 사용자가 지웠지만 아직 정리되지 않은 대화가 있다(`deleted_at` 있음, `purged_at` 없음) | 미룬다. 대화 정리가 에이전트 행의 주소와 profile 로 Hermes session 을 지운다 |
| `profile_managed` 가 참이다 | 행을 지우기 전에 profile 거두기(MCP 토큰 폐기, 대시보드 profile 삭제, key 파일 삭제)와 스킬 디렉터리 지우기를 한 번 더 한다. 지울 때 이미 거뒀으면 대시보드의 404 와 없는 파일을 끝난 것으로 본다 |
| `profile_managed` 가 거짓이다 | Hermes 를 부르지 않는다. 운영에서 만든 profile 이다 |
| profile 거두기가 실패했다 | 행을 지우지 않는다. 기다리는 간격을 1분부터 한 시간까지 두 배씩 늘리며 다시 한다. 다섯 번 잇달아 실패하면 error 로그를 남긴다 |
| 이 결정 앞에 지운 에이전트 | 같은 정리 대상이다. 배포한 뒤 첫 차례가 지운 순서대로 지운다 |

한 차례는 지운 순서대로 20개까지 본다. 로그에는 에이전트 번호와 결과 수만 적는다.
데이터베이스 쪽은 에이전트 행을 쓰기 잠금으로 잡고 한 트랜잭션으로 지운다. 대화의 대기 여부도 그 트랜잭션 안에서 다시 본다.

### 맥락

에이전트를 지우면 `deleted_at` 만 적혀 행과 딸린 설정이 남았다.
[ADR-033](ADR-033-사용자가-에이전트를-만들고-공개해도-만든-사람이-관리한다.md) 은 대화, 실행, 사용량이 `agent_id` 로 이름을 읽는다는 이유로 행을 남겼다.
그 뒤 운영에서 에이전트 행이 없는 대화가 나와, 대화와 실행과 사용량을 읽는 경로가 행이 없어도 「지운 에이전트」 로 그리게 고쳐졌다.
행을 남겨야 할 이유가 없어졌고, 지운 에이전트의 Memory 허용과 도구 요청과 살펴보기 기록이 쓰이지 않은 채 쌓였다.
2026-10-09 에 운영에서 지운 에이전트는 4개였고, 그 Hermes profile 은 모두 이미 없었다.

### 대안 기각

- **지울 때 곧바로 행까지 지운다**: 지운 직후에는 늦게 끝난 실행, 자식 사용량 재조회, 지운 대화의 정리가 아직 그 에이전트의 주소를 읽는다. 7일이면 모두 끝난다.
- **그 에이전트의 대화도 함께 지운다**: 지울 때 화면이 「지난 대화는 읽을 수 있어요」 라고 약속한다.
- **`connector_action` 줄도 지운다**: 외부 서비스에 쓴 것의 승인 이력이 사라지고, 남은 대화의 승인 카드가 깨진다.
- **딸린 표의 FK 를 `ON DELETE CASCADE` 로 바꾼다**: 이미 적용한 표마다 마이그레이션이 늘고, 무엇이 함께 지워지는지가 코드가 아니라 스키마에 흩어진다.
- **실패 횟수를 표에 적는다**: [ADR-20261008 / conversation-purge](ADR-20261008-conversation-purge.md) 와 같은 까닭으로 메모리에 둔다.

### 결과

- 얻는 것: 지운 에이전트의 설정과 권한, 살펴보기 기록이 7일 뒤 사라진다. 사용량 합계와 대화는 그대로다.
- 감당할 것:
  - **에이전트 행이 지워진 뒤 그 에이전트의 대화를 사용자가 지우면 Hermes session 은 지우지 못한다.** 대화 정리가 주소를 몰라 경고 로그만 남긴다.
    관리형 profile 은 이미 session 과 함께 지워졌으므로 영향이 없다. 운영에서 만든 profile 만 session 이 남고, 그 정리는 운영이 한다.
  - 정리 작업이 대기 여부를 본 뒤 그 사이 사용자가 대화를 지우는 경합도 같은 결과다. 둘 다 드물다.
  - 대기는 그 에이전트가 주인인 대화(`conversation.agent_id`)만 본다. 그 에이전트가 다른 에이전트 대화의 위임 자식으로 돌았고 그 대화가 아직 정리되지 않았으면, 자식 session 도 같은 까닭으로 남을 수 있다. 관리형 profile 은 영향이 없다.
  - 기다리는 에이전트는 기다리는 간격에 넣지 않아 매 차례 후보 자리를 차지한다. 대화 정리를 기다리는 에이전트가 한 차례 상한(20개)을 넘으면 그 뒤 후보가 밀린다. 지금 규모에서는 일어나지 않는다.
  - **`code` 와 `hermes_profile` 이 다시 쓰일 수 있다.** 유일 검사가 에이전트 표만 본다. 사용자가 만든 에이전트의 두 값은 무작위 10자라 다시 뽑힐 일은 없다고 본다.
    관리자가 같은 profile 이름으로 에이전트를 다시 등록하는 것은 의도한 재사용이다. 사람을 더할 때는 대시보드가 이미 있는 profile 을 거절한다.
  - 에이전트 이름은 유일 제약이 없어 지금도 다시 쓴다. 이 결정과 관계없다.
  - `agent.id` 는 MySQL 8 이 자동 증가 값을 저장하므로 다시 쓰이지 않는다. 에이전트 번호로 만든 실행 공간 디렉터리는 남는다.
  - 기억 출처, 사용량 합계, 내 스킬 사용 목록은 행이 없는 에이전트를 「지운 에이전트」 로 보인다.
  - 정리 작업이 기다리는 간격은 메모리에만 있다. 재기동하면 실패하던 에이전트를 곧바로 다시 시도한다.
