## ADR-20261008 / data-encryption: 사용자 본문은 서버 KEK 로 감싼 사용자별 데이터 key 로 저장할 때 암호화하고, 대화 메시지부터 적용한다

- **status**: `accepted`
- Date: 2026-10-08
- [ADR-055](ADR-055-민감-memory-본문은-저장할-때-암호화하고-key-는-환경-변수로-받는다.md) 의 암호문 모양(`v1.<IV>.<암호문과 태그>`)과 AES-256-GCM 을 그대로 쓴다.
  ADR-055 의 민감 Memory 암호화는 이 결정이 바꾸지 않는다. 같은 key 구조로 옮기는 일은 다음 단계에서 정한다.

### 결정

**KEK(마스터 key) → 사용자별 데이터 key(DEK) → 본문 칸의 세 층으로 암호화한다. 이번에는 `chat_message.content` 에 적용한다.**

| 층 | 무엇 | 어디 |
| --- | --- | --- |
| KEK | 데이터 key 를 감싸는 AES-256 key. id 를 붙인 목록이다 | 서버 파일. 경로와 활성 id 는 운영 설정이 준다. 데이터베이스와 백업에 넣지 않는다 |
| DEK | 사용자마다 하나인 AES-256 key. 처음 암호화할 때 만든다 | `user_data_key` 에 KEK 로 감싸 둔다. 원문은 메모리에만 있다 |
| 본문 | 그 사용자의 DEK 로 암호화한 칸 | 원래 칸에 암호문을 쓰고 옆 칸(`content_key_id`)에 DEK 번호를 적는다. 옆 칸이 비면 평문이다 |

**KEK 는 제공자 인터페이스(`KeyEncryptionKeys`) 뒤에 둔다.** 열린 동작은 감싸기와 풀기뿐이고 KEK 원문은 밖으로 나가지 않는다.
첫 구현은 파일 제공자(`FileKeyEncryptionKeys`)다. 클라우드 KMS 제공자는 만들지 않았지만 같은 두 동작으로 들어온다.
KMS 로 바꾸면 KEK 가 서버 밖에 있고 풀 때마다 서버 밖에 기록이 남는다.

**메시지의 AAD 는 `chat_message:<메시지 번호>:conversation:<대화 번호>:user:<대화 주인>` 이다.**
메시지 번호는 줄을 넣은 뒤에야 생긴다. 그래서 본문을 빈 글로 넣고 같은 트랜잭션에서 암호문으로 고친다. 데이터베이스에 평문이 한 번도 쓰이지 않는다.
DEK 를 감싸는 AAD 는 `user_data_key:user:<사용자 번호>` 다.

| 상황 | 동작 |
| --- | --- |
| KEK 설정이 비어 있다 | 기동한다. 새 메시지를 평문으로 저장하고 기동 때 경고를 남긴다 |
| KEK 설정이 비어 있고 `required` 가 참이다 | 기동하지 않는다. 운영은 이 값을 켠다 |
| KEK 파일의 모양이 틀렸다, 활성 id 가 파일에 없다, 경로와 활성 id 가운데 하나만 있다 | 기동하지 않는다 |
| 사용자의 첫 메시지 | DEK 를 새 트랜잭션에서 만든다. 같은 사용자의 첫 저장 둘이 겹치면 한쪽이 유일 제약에 걸리고, 새 트랜잭션에서 다시 읽어 같은 DEK 를 쓴다 |
| 본문을 풀지 못한다(KEK 나 DEK 가 없다, DEK 의 주인이 대화 주인과 다르다, 태그가 맞지 않는다) | 본문 대신 「읽을 수 없는 메시지입니다.」 를 낸다. 메시지 번호와 대화 번호, DEK 번호만 경고 로그에 남긴다. 요청은 실패하지 않는다. 풀지 못한 DEK 는 1분 동안 다시 읽지 않고 경고도 한 번만 남긴다 |
| 데이터베이스에 닿지 못해 DEK 나 대화 주인을 읽지 못한다 | 요청이 실패한다. 일시적인 장애를 「읽을 수 없음」 으로 기억하지 않는다 |
| 데이터베이스에서 암호문을 다른 줄로 옮기거나 `conversation.user_id` 를 바꿨다 | AAD 가 달라 풀리지 않는다. 대화 주인은 30초 동안 메모리에 두므로 늦어도 30초 뒤부터 드러난다 |
| KEK 를 바꾼다 | 파일에 새 key 를 더하고 활성 id 를 바꿔 기동한다. 기동 작업이 옛 KEK 로 감싼 DEK 줄만 다시 감싼다. 본문은 다시 쓰지 않는다. 남은 줄이 없다는 로그를 본 뒤 옛 key 를 파일에서 뺀다 |
| 옛 KEK 를 다시 감싸기 전에 파일에서 뺐다 | 그 DEK 의 주인 본문을 읽지 못한다. 기동 때 줄 수를 경고한다 |
| 이 결정 앞의 평문 메시지 | 평문으로 읽는다. 옮겨 적는 배치는 다음 단계에서 만든다 |

푼 DEK 는 메모리에 10분, 최대 1,000개 둔다. 설정으로 바꾼다.
메시지는 읽을 때 풀지 않는다. 읽어 온 엔티티에 복호화 도구만 붙이고, 본문을 처음 꺼낼 때 푼다.

### 위협 모델

| 막는 것 | 까닭 |
| --- | --- |
| 데이터베이스 dump 와 백업의 유출 | 본문은 암호문이고 DEK 는 KEK 로 감싸 있다. KEK 는 데이터베이스와 백업에 없다 |
| 데이터베이스만 조회하는 사람. 운영자의 SELECT 도구도 포함한다 | 같다. 본문 칸에서 볼 수 있는 것은 길이와 시각, 대화 번호 같은 메타데이터다 |
| 데이터베이스 디스크 파일만 복사한 사람 | 같다 |
| 데이터베이스를 고쳐 남의 암호문을 자기 대화로 옮긴 사람 | AAD 가 메시지 번호와 대화와 주인을 묶어 풀리지 않는다 |

| 못 막는 것 | 까닭 |
| --- | --- |
| **KEK 와 데이터베이스를 모두 가진 사람** | KEK 로 DEK 를 풀고 DEK 로 본문을 푼다 |
| 서버 파일을 읽을 수 있는 root 운영자 | KEK 가 같은 서버의 파일이다. KMS 로 바꾸면 풀 때마다 서버 밖에 기록이 남지만, 그래도 서버를 쥔 사람은 실행 중인 Control Plane 의 메모리에서 푼 key 를 읽을 수 있다 |
| 코드를 바꿔 배포하는 운영자 | 바꾼 코드가 푼 본문을 어디로든 보낼 수 있다 |
| 모델 공급자 | 대화는 모델 공급자에게 평문으로 간다 |
| Hermes 의 저장 | profile 의 `state.db` 의 session 과 메시지, `memories/`, 첨부와 결과물 파일, 커넥터 출력 파일은 평문이다. 이 결정은 Control Plane 데이터베이스만 다룬다 |
| 메시지 밖의 칸 | 대화 제목, 실행 답 본문, 도구 사건, 승인 기록, 할 일, 알림 같은 칸은 아직 평문이다. 다음 단계에서 같은 구조로 옮긴다 |

### 맥락

친구들이 실제로 쓰기 시작한다. 대화와 등록한 비밀값이 데이터베이스와 서버 파일에 평문으로 있다.
운영자가 고른 방향은 서버 key 기반의 저장 시 암호화와 보완 넷(실제 삭제, 보관 파일 암호화, 운영 접근 통제, 안내 페이지)이다.
사용자 비밀 기반 암호화는 이번에 만들지 않고 얹을 자리만 둔다.

지금 암호화는 민감 Memory 본문 하나뿐이다([ADR-055](ADR-055-민감-memory-본문은-저장할-때-암호화하고-key-는-환경-변수로-받는다.md)).
그 방식은 key 하나로 칸을 바로 암호화하고 key 가 없으면 저장을 거절한다. 대화에 그대로 쓰면 key 없는 설치에서 대화가 막히고, 사용자 한 명의 본문만 지울 길이 없다.

메시지 본문으로 검색하거나 정렬하는 질의는 없다(`content` 를 쓰는 JPQL 과 네이티브 질의가 없다). 그래서 칸을 암호문으로 바꿔도 질의가 깨지지 않는다.

### 대안 기각

- **사용자 비밀 기반 암호화(비공개 모드)**: 사용자만 아는 비밀로 DEK 를 한 번 더 감싸면 운영자도 읽지 못한다.
  그러나 예약 작업과 위임 결과 전달처럼 사용자가 없을 때 Control Plane 이 대화를 이어 써야 한다. 비밀을 잃으면 본문을 되찾을 길이 없다.
  Hermes 의 `state.db` 와 모델 공급자에게 가는 글은 그대로 평문이라 얻는 것이 작다.
  자리는 열어 둔다. DEK 를 감싸는 층이 따로 있으므로, 사용자 비밀로 감싼 DEK 를 더하는 것은 본문 형식을 바꾸지 않는다.
- **TEE 와 confidential computing**: 홈서버 하드웨어가 지원하지 않는다. Hermes 와 모델 공급자의 평문은 그대로다.
- **데이터베이스의 저장 암호화(MySQL keyring, 디스크 암호화)**: 디스크 파일 복사는 막지만 SELECT 하는 사람과 논리 dump 는 막지 못한다. 시험은 H2 라 같은 동작을 확인할 수 없다.
- **KEK 하나로 칸을 바로 암호화한다(ADR-055 방식)**: 코드가 가장 적다. 그러나 사용자 한 명의 본문만 지울 수 없고(crypto-shredding), KEK 를 바꾸면 모든 본문을 다시 써야 한다.
- **KEK 를 환경 변수로 받는다(ADR-055 방식)**: 환경 변수는 `docker inspect` 와 프로세스 환경에 보이고 compose 파일과 함께 백업되기 쉽다. 파일은 권한과 마운트로 백업에서 뺄 수 있다.
- **key 가 없으면 메시지 저장을 거절한다**: key 없는 설치에서 대화가 막힌다. 운영은 `required` 로 같은 효과를 얻는다.
- **JPA 변환기(`AttributeConverter`)로 칸을 바꾼다**: 변환기는 줄 번호와 대화와 주인을 보지 못해 AAD 를 만들 수 없다. 암호문을 다른 줄로 옮겨도 열린다.
- **읽어 올 때 바로 푼다**: Hibernate 가 줄을 읽는 도중에 대화 주인을 묻는 질의가 나가고, 본문을 쓰지 않는 목록도 복호화 비용을 낸다.
- **암호문에 key id 를 넣고 옆 칸을 두지 않는다**: 사용자가 보낸 글이 암호문 모양이면 평문과 구분할 수 없다. 옆 칸이 있어야 평문 줄을 질의로 센다.

### 결과

- 얻는 것:
  - 데이터베이스와 백업만으로는 새 메시지 본문을 읽지 못한다.
  - KEK 교체는 사용자 수만큼의 DEK 줄만 다시 감싼다.
  - 사용자의 DEK 줄을 지우면 그 사용자의 암호문을 누구도 풀지 못한다. 탈퇴 흐름이 생기면 이 길로 지운다.
  - 다른 칸은 같은 `TextCipher` 로 옮긴다. 칸마다 옆 칸과 AAD 만 정한다.
- 감당할 것:
  - **KEK 를 잃으면 암호화한 본문을 되찾을 수 없다.** KEK 의 백업은 데이터베이스 백업과 다른 자리에 둔다. 운영 저장소 `fos-home-infra` 가 맡는다.
  - 본문을 내는 곳은 모두 `ChatMessage.content()` 를 거친다. `storedContent()` 는 암호문을 낸다.
    JPQL 이나 네이티브 질의로 `content` 칸을 직접 읽으면 암호문이 나간다. 틀려도 평문이 새지 않는 쪽으로 틀린다.
  - 새 메시지는 넣고 고치는 쓰기 두 번이다.
  - 풀지 못한 메시지의 본문을 읽는 다른 자리(추천 질문, 살펴보기 결과 읽기 같은 곳)도 「읽을 수 없는 메시지입니다.」 를 본문으로 받는다.
  - DEK 를 바꾸는 길은 없다. DEK 가 새어 나가면 그 사용자의 본문을 새 DEK 로 다시 써야 한다.
  - **이 결정 앞의 판으로 되돌리지 않는다.** 옛 코드는 `content_key_id` 를 몰라 암호문을 본문으로 낸다.
  - 대화 주인을 30초 동안 메모리에 둔다. 그 사이에 데이터베이스에서 바꾼 주인은 바로 드러나지 않는다.
  - DEK 를 처음 만들거나 메모리에서 비운 뒤 다시 읽을 때는 대화 줄을 잠근 트랜잭션이 연결 하나를 더 쓴다. 연결 풀(기본 10개)보다 많은 저장이 한꺼번에 처음 key 를 찾으면 연결을 기다린다. 사용자 수가 적어 지금은 받아들인다.
  - DEK 줄을 지우는 흐름을 만들 때는 메모리의 DEK 도 함께 비운다. 그러지 않으면 수명(10분) 동안 지운 key 로 새 본문을 암호화해 그 본문을 영영 풀지 못한다.

### 적용 범위

| 무엇 | 값 |
| --- | --- |
| 알고리즘 | `AES/GCM/NoPadding`, key 256비트, IV 12바이트를 매번 새로 뽑는다, 태그 128비트. KEK 의 DEK 감싸기도 같다 |
| 칸에 적는 모양 | `v1.<IV>.<암호문과 태그>`. 두 조각은 채움 문자 없는 base64url 이다 |
| 설정 `assistant.data-encryption.kek-file` | KEK 목록 파일. 한 줄에 `<id>:<base64 32바이트>`. 빈 줄과 `#` 줄은 건너뛴다. 환경 변수 `ASSISTANT_DATA_ENCRYPTION_KEK_FILE` |
| 설정 `assistant.data-encryption.active-kek-id` | 새 DEK 를 감쌀 KEK. 환경 변수 `ASSISTANT_DATA_ENCRYPTION_ACTIVE_KEK_ID` |
| 설정 `assistant.data-encryption.required` | 참이면 KEK 가 없을 때 기동하지 않는다. 환경 변수 `ASSISTANT_DATA_ENCRYPTION_REQUIRED` |
| 설정 `dek-cache-ttl`, `dek-cache-max-entries` | 푼 DEK 를 메모리에 두는 시간과 개수. 기본 10분과 1,000개 |
| KEK 파일 권한 | 소유자 말고도 읽을 수 있으면 기동 때 경고한다 |
