## ADR-090: 한 번에 받는 경로도 Hermes 사건 스트림을 열어 도구 사건을 남긴다

- **status**: `accepted`
- Date: 2026-10-06
- [ADR-013](ADR-013-실행-사건은-우리-모델로-정규화해-저장한다.md) 이 사건을 스트림에서 옮겨 적는 경로에 한 번에 받는 경로를 더한다. `docs/flow.md` 와 `web/docs/flow.md` 가 적었던 「한 번에 받는 경로에는 도구 사건이 오지 않는다」 를 바꾼다. 도구 내용을 가리는 규칙([ADR-047](ADR-047-도구-내용은-비밀값과-UUID를-가린-뒤-중계하고-저장한다.md), [ADR-083](../../../docs/adr/ADR-083-커넥터는-사용자가-한-번-연결하고-자기-에이전트에-여럿-붙여-그-에이전트가-도구를-직접-부른다.md))은 그대로다.

### 결정

**`POST /api/v1/chat/messages` 도 Hermes 의 사건 스트림(`GET /v1/runs/{run_id}/events`)을 열어 도구와 하위 에이전트 사건을 `execution_event` 에 남긴다.**

| 항목 | 정한 것 |
| --- | --- |
| 스트림을 여는 경로 | 스트리밍 경로와 한 번에 받는 경로 모두. 흐름(`Flow`)의 단계 실행은 지금처럼 열지 않는다 |
| 화면으로 흘리는 것 | 한 번에 받는 경로는 흘릴 곳이 없다. 사건은 실행 기록에만 쌓는다 |
| 가리는 범위 | 두 경로가 같다. 옛 커넥터 에이전트는 모든 도구, 다른 에이전트는 붙은 커넥터 서버의 도구 내용을 통째로 가린다. 비밀값과 식별자는 늘 가린다 |
| `first_delta_at` | 한 번에 받는 경로는 계속 비운다. 첫 반응 시간 통계는 사용자가 조각을 받는 경로만 센다 |
| 스트림을 기다리는 시간 | 한 번에 받는 경로는 `hermes.run-timeout` 까지만 기다린다. 넘으면 스트림을 닫고 결과 조회로 넘어간다. 그 조회가 다시 `hermes.run-timeout` 까지 기다리므로 이 경로의 요청이 Hermes 를 기다리는 시간은 늘어도 `hermes.run-timeout` 의 두 배까지다. 스트리밍 경로는 지금처럼 스트림이 닫힐 때까지 기다린다 |
| 스트림을 읽지 못할 때 | 경고만 남기고 답과 `RUN_STARTED`, `RUN_COMPLETED` 는 그대로 남긴다. 한 번에 받는 경로의 답은 실행 결과 조회로 받으므로 스트림이 끊겨도 답이 사라지지 않는다 |
| 스킬 사용 기록 | 한 번에 받는 경로에서도 `skill_view` 시작 사건이 오면 스트리밍 경로와 같이 `MODEL` 이력이 남는다 |

### 맥락

2026-10-06 에 가계부 커넥터를 에이전트에 붙이고 Hermes 에서 `mcp__accountbook__summarize_expenses` 가 실행된 것을 확인했다. 그런데 그 실행(`POST /chat/messages` 로 보냈다)의 `execution_event` 에는 `RUN_STARTED` 와 `RUN_COMPLETED` 두 줄뿐이었다.

원인은 붙은 커넥터가 아니라 경로였다.
같은 에이전트가 같은 도구 목록으로 돈 실행이라도 한 번에 받는 경로는 Control Plane 이 사건 스트림을 열지 않아 `terminal` 이나 `tool_search` 같은 도구도 남지 않았다.
그 에이전트의 profile 에서 한 번에 받는 경로로 돈 실행 26건이 모두 도구 사건 0건이었다. 같은 시각 화면(스트리밍 경로)에서 돈 다른 profile 의 실행은 도구 사건이 남았다.
스트리밍 경로의 붙은 서버 도구는 이미 도구 이름과 걸린 시간, 실패 여부만 남고 내용은 가려진다.

ADR-013 은 사건을 스트림에서 옮겨 적는다고 정했다. 한 번에 받는 경로에 도구 사건이 없는 것은 흐름 문서가 「그것이 맞다」 고 적었다.
그때는 한 번에 받는 경로가 화면의 폴백이라 사용자가 보는 일이 드물다고 보았다.
지금은 이 경로로 직접 메시지를 보내 실행을 확인하는 일이 있다.
관리자가 그 실행의 「작업 과정」 을 열면 어떤 도구를 불렀는지가 비어 있어, 실행이 도구를 실제로 불렀는지 알 수 없다.

### 대안 기각

- **한 번에 받는 경로의 도구 사건이 없는 것을 그대로 둔다.** 운영 확인이 Hermes 로그에 기댄다. Hermes 로그는 Control Plane 의 실행 줄과 이어지지 않는다.
- **실행이 끝난 뒤 Hermes 에 도구 호출 목록을 조회한다.** 실행 조회(`GET /v1/runs/{run_id}`)는 상태와 답과 사용량만 주고 도구 호출 목록이 없다.
- **한 번에 받는 경로를 없애고 스트리밍만 둔다.** 이 경로를 쓰는 화면 폴백과 직접 보내는 호출이 깨진다.
- **스트림을 열되 `first_delta_at` 도 적는다.** 사용자가 조각을 받지 않는 경로의 시각이 첫 반응 시간 통계에 섞인다.

### 결과

- 얻는 것:
  - 어느 경로로 돈 실행이든 도구 호출이 같은 모양으로 남는다. 붙은 커넥터의 도구 호출도 이름과 걸린 시간, 실패 여부가 남는다.
  - 한 번에 받는 경로로 돈 답에도 「작업 과정」 블록이 붙는다.
- 감당할 것:
  - 한 번에 받는 경로가 Hermes 에 연결을 하나 더 연다. 요청 스레드가 스트림이 닫히기를 기다리는 것은 스트리밍 경로와 같되, `hermes.run-timeout` 에서 끊는다.
  - 한 번에 받는 요청의 최대 대기가 `hermes.run-timeout` 의 두 배가 된다.
  - 흐름(`Flow`)의 단계 실행은 이 결정 밖이다. 도구 사건이 남지 않는다.
  - 한 번에 받는 경로의 실행 줄마다 사건 줄이 늘어난다.
  - 스트림이 열리지 않는 실행은 여전히 도구 사건 없이 남는다. 이때 Control Plane 로그에 경고가 남는다.
