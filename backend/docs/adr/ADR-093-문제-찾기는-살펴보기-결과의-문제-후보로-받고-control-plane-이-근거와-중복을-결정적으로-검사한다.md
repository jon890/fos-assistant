## ADR-093: 문제 찾기는 살펴보기 결과의 문제 후보로 받고 Control Plane 이 근거와 중복을 결정적으로 검사한다

- **status**: `accepted`
- **결정**: 먼저 살펴보기가 찾은 발견에서 「이 사용자가 풀 가치가 있는 문제」 를 뽑는 일(문제 찾기, #213)은 새 실행이나 새 모델 호출로 만들지 않는다.
  [ADR-081](ADR-081-살펴보기-결과는-답-끝의-구조화-블록으로-받고-control-plane-이-검사해-그린다.md)의 결과 블록을 버전 3으로 넓혀,
  살펴보기 turn 이 발견과 함께 `problemCandidates` 배열에 문제 후보를 3개까지 낸다.
  칸과 상한은 [`docs/features/proactive.md`](../../../docs/features/proactive.md) 의 「문제 후보」 가 갖는다.

  **관찰과 문제와 행동을 칸으로 나눈다.** 관찰은 같은 블록의 발견이고 후보는 그 발견의 `topicKey` 를 `evidence` 로 가리킨다.
  문제는 `problem`, 그 문제가 닿는 사용자의 목표나 맥락은 `relatedGoal`, 다음 행동이나 조사는 `proposedAction` 이다.
  해결했을 때의 기대 효과 가설(`expectedBenefit`), 모델의 확신(`confidence`), 행동이 밖에 남길 영향의 힌트(`sideEffect`, `risk`)를 함께 받는다.
  신선도는 모델에게 받지 않는다. Control Plane 이 근거 발견의 확인 시각 가운데 가장 이른 것을 적는다.

  **열린 추론은 모델이, 검사는 Control Plane 이 한다.** `ProblemJudgement` 가 후보마다 `ACCEPTED` 와 `DROPPED` 를 정하고 처음 걸린 까닭 하나를 남긴다.

  | 까닭 | 걸리는 때 | 지키는 원칙 |
  | --- | --- | --- |
  | `INCOMPLETE` | 문제 키, 문제, 행동, 기대 효과가 비었거나 정해진 값 밖이다 | 계약 검사 |
  | `NO_GOAL` | `relatedGoal` 이 비었다 | 새 데이터만으로 문제를 만들지 않는다 |
  | `NO_EVIDENCE` | 같은 블록에서 원문과 확인 시각과 신선도 검사를 통과한 발견을 하나도 가리키지 않는다 | 근거 없는 문제를 만들지 않는다 |
  | `DUPLICATE` | 같은 블록에 같은 문제 키가 앞에 있거나, 같은 점검 대화의 `digest-window` 안에 받아들인 같은 문제 키가 있고 `changeSinceLast` 가 없다 | 같은 관찰에서 같은 문제를 다시 만들지 않는다 |
  | `EXISTING_FOLLOW_UP` | 행동 글이 그 사용자의 `PROPOSED` 나 `OPEN` 할 일과 같은 `title_key` 다 | 이미 챙기는 일을 다시 만들지 않는다 |

  **문제 찾기는 우선순위와 권한을 정하지 않는다.** 점수, 순서, 실행 여부, 승인 필요 여부를 후보에 두지 않는다.
  `sideEffect` 와 `confidence` 는 다음 단계가 읽는 힌트일 뿐이며 커넥터 판정([ADR-080](../../../docs/adr/ADR-080-먼저-살펴보기는-점검-대화의-turn-하나로-돌고-읽기-경계를-control-plane-이-강제한다.md), [ADR-082](../../../docs/adr/ADR-082-먼저-살펴보기의-쓰기-도구는-관리자가-에이전트마다-켜고-커넥터-쓰기는-승인-카드로-보낸다.md))을 바꾸지 않는다.
  가치 판단은 #214, 자율 수준은 #215 가 맡는다.

  **후보는 대화에 그리지 않는다.** 대화와 보고는 지금처럼 발견과 할 일 후보 문장을 그린다.
  후보를 사용자에게 올릴지는 다음 단계가 정한다. 「문제가 있다」 와 「지금 알린다」 를 나누기 위해서다.

  **후보 0개는 정상이다.** 버전 1과 2의 블록, 후보가 없는 버전 3 블록, 발견이 없는 결과는 모두 후보 0개다.
  발견이 없으면 가리킬 근거가 없으므로 후보를 검사하지도 남기지도 않는다. 예약 실행의 침묵 경로([ADR-085](../../../docs/adr/ADR-085-매일-깨우기는-예약-작업을-다시-쓰고-다섯-칸-보고를-지금-화면에-올린다.md))는 바뀌지 않는다.

  **후보는 `proactive_check_problem` 에 남긴다.** 받아들인 것과 버린 것을 모두 남기고, 근거는 발견의 주제 키, 원문 주소, 확인 시각만 참조로 둔다.
  원문 본문과 커넥터 응답은 복제하지 않는다. 다음 살펴보기 입력에는 최근에 받아들인 후보의 문제 키와 문제를 `<external-data>` 로 감싸 싣는다.
- **맥락**: #219 로드맵의 Proactive Decision 1/5 다. #166 의 매일 깨우기가 발견, 다섯 칸 보고, 할 일 제안까지 이었지만,
  「무엇이 바뀌었나」 와 「그래서 사용자가 풀 문제가 무엇인가」 가 한 문장(`next`, `followUpCandidates`)에 섞여 있었다.
  #214 가 후보 여러 개를 견주려면 근거와 목표와 행동이 나뉜 후보가 필요하다.
  살펴보기 turn 은 이미 Memory 와 커리어 문서와 웹 근거를 읽은 상태라, 같은 turn 이 후보를 내면 모델 호출이 늘지 않는다.
- **대안 기각**:
  - 발견을 읽어 후보를 만드는 별도 모델 호출을 둔다. 깨우기마다 모델 호출이 늘고, 그 호출은 살펴보기 turn 이 읽은 맥락을 다시 실어야 한다.
  - Control Plane 이 규칙으로 후보를 만든다. 무엇이 사용자의 문제인지는 열린 추론이라 규칙으로 정하지 못한다.
  - 기존 `followUpCandidates` 문장을 후보로 쓴다. 근거와 목표가 없어 근거 검사와 중복 판정을 할 수 없다.
  - 후보를 대화에 바로 그린다. 우선순위 없이 모든 후보가 사용자에게 보여 #160 의 억제 원칙과 부딪친다.
  - 실행 비용 칸을 둔다. 비용은 후보끼리 견줄 때 쓰는 축이라 #214 가 정한다.
- **결과**:
  - 얻는 것: #214 가 근거와 목표와 행동이 나뉜 후보를 DB 에서 읽는다. 근거 없는 후보와 반복 후보는 모델이 무엇을 쓰든 버려진다.
    버린 후보와 그 까닭이 남아 #217 이 문제 찾기의 품질을 측정할 수 있다.
  - 감당할 것: 후보는 분야 스킬이 버전 3 블록을 내야 생긴다. 스킬을 고치기 전에는 늘 0개다.
    `EXISTING_FOLLOW_UP` 은 행동 글을 정규화한 `title_key` 가 정확히 같을 때만 걸린다. 같은 일을 다른 말로 적으면 걸리지 않으므로, 중복의 주된 방어는 분야 스킬이 정하는 문제 키다.
    `relatedGoal` 은 모델이 쓴 글이라 Control Plane 이 그 목표가 실제로 있는지 확인하지 못한다. 목표를 데이터로 두는 단계가 오면 목표 참조로 바꾼다.
    문제 키가 같으면 근거가 달라도 `changeSinceLast` 없이는 버려진다. 같은 문제를 새 근거로 다시 올리려면 스킬이 달라진 점을 적어야 한다.
- **적용 범위**: 결과 블록 버전 3의 `problemCandidates`, 그 검사와 저장, 다음 살펴보기 입력이다.
  우선순위, 자율 수준, 사용자 반응 기록은 다루지 않는다. 표는 [`backend/docs/data-schema.md`](../data-schema.md) 가 갖는다.
