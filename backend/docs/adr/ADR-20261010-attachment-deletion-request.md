## ADR-20261010 / attachment-deletion-request: 첨부 삭제 요청을 파일 작업 전에 커밋한다

- **Date**: 2026-10-10
- **status**: `accepted`
- **결정**: 최초 삭제 요청을 파일 작업 전에 커밋하여 접근을 차단한다. 실제 삭제 완료 시각은 원본과 사본을 지운 뒤 별도 트랜잭션에서 기록한다.
- **맥락**: 파일 삭제가 실패하거나 완료 기록 전에 종료돼도 접근이 다시 열려서는 안 된다. 파일과 DB를 하나의 트랜잭션으로 함께 되돌릴 수 없다.
- **대안 기각**: 파일을 먼저 지우면 실패 동안 접근이 열린다. 요청만으로 완료 시각을 기록하면 삭제 실패를 성공으로 표시한다. 메모리 차단은 재시작에서 사라진다.
- **결과**: 요청은 실패와 재시작에도 유지하며 기존 cleaner가 멱등 재시도한다. 데이터 주인의 사용자, 대화, 첨부 순으로 잠그고 대상별 새 트랜잭션으로 정리한다. purge도 session과 파일 작업 전, 최종 DB 삭제 전에 같은 진입점을 거친다. writer의 단독 호출을 막는다.
- **적용 범위**: 첨부의 영속 차단과 파일 정리다. 관찰 저장과 요청 매핑은 후속 구현이다. [기능 계약](../../../docs/features/attachment.md#삭제-요청과-접근-차단)과 [저장 모델](../data-schema.md#첨부-삭제-요청)이 자세한 의미를 갖는다.
