## ADR-20261009 / native-image-input: 사진마다 줄인 사본 파일을 원본 옆에 두고, 이번 메시지의 사진은 그 사본을 실행 입력에 직접 싣는다

- **status**: `accepted`
- Date: 2026-10-09
- [ADR-020](ADR-020-사진은-공유-디렉터리에-두고-에이전트가-파일로-읽는다.md) 의 「대화 본문에 사진을 실을 수 없다」 를 바꾼다.
  사진을 공유 디렉터리에 두고 실행 공간에 붙이는 것([ADR-091](../../../docs/adr/ADR-091-사진-첨부는-사용자별로-저장하고-실행-공간에는-그-사용자만-붙인다.md))은 그대로다.
- 2026-10-10 개정: 자체 합계 화소 상한을 제거한다. data URL 바이트 예산에 드는 가장 큰 해상도를 쓰며, 바이트가 충분하면 장수와 무관하게 사본을 그대로 싣는다. 20MB 업로드와 원본 자동 재조회는 별도 요구 격차로 검토한다([사진 첨부 기능 문서](../../../docs/features/attachment.md)의 「이미지 이해 품질의 남은 격차」).
- 2026-10-09 개정: 고정 10장 상한을 화소 예산과 크기 단계로 바꾸고, 한 번에 보낼 수 있는 30장을 모두 입력에 싣는다. 이번 메시지의 사진은 `vision_analyze` 로 보게 하지 않는다. 사진을 서명한 공개 주소로 넘기는 방식은 검토하고 접었다(「대안 기각」)

### 결정

**사진마다 긴 변 1600px JPEG 사본 파일을 원본 옆에 두고, 보내는 메시지의 사진은 그 사본을 `POST /v1/runs` 의 `input` 에 이미지 파트로 싣는다.**
바이트 예산을 넘을 때만 모든 사진을 같은 크기 단계로 줄여 한 입력에 싣는다. 한 번에 보낼 수 있는 장수(30장)는 모두 실리는 장수로 정한다. 이번 메시지의 사진은 `vision_analyze` 로 보게 하지 않는다.
원본은 지금처럼 실행 공간의 사용자 폴더에 두고, 실행 입력의 파일 목록도 그대로 적는다.
편집, 업로드처럼 원본이 필요한 도구는 원본을 쓴다.

| 무엇 | 어떻게 |
| --- | --- |
| 싣는 모양 | `input` 을 user 메시지 하나의 목록으로 보낸다. `content` 는 글 파트(지금의 입력 전체), 그 뒤로 사진마다 「N번째 사진」 글 파트와 `image_url` 파트(`data:image/jpeg;base64,...`)를 잇는다 |
| 사진이 없을 때 | `input` 을 지금처럼 문자열로 보낸다. 사진 없는 실행의 요청은 바뀌지 않는다 |
| 사본 | 긴 변 1600px 이하, JPEG 품질 0.85, EXIF 회전 반영, 투명 배경은 흰색으로 채운다. 작은 사진은 키우지 않는다 |
| 사본 파일 | 원본과 같은 폴더의 `{첨부 번호}.small.jpg`. 올릴 때 만든다. 이 결정 전에 올린 사진처럼 사본이 없으면 보낼 때 만든다. 만들지 못해도 올리기와 실행은 실패하지 않는다 |
| 사본을 지우는 때 | 원본과 함께 지운다. 사용자 삭제, 보관 기간 정리, 대화 정리가 모두 같은 파일 저장소의 지우기를 지난다 |
| 한 턴에 싣는 양 | data URL 합계 7MiB 안에서 긴 변 1600, 1280, 1024, 768px 단계를 큰 것부터 시도하고, 모두 담을 수 있는 가장 큰 단계로 싣는다. 합계 화소 상한은 두지 않는다. 768px에서도 바이트 예산을 넘으면 JPEG 품질을 0.6, 0.4, 0.3으로 낮춘다. 그래도 넘으면 앞에서부터 예산까지 싣는다 |
| 줄인 단계 | 1600px 단계는 사본 파일을 그대로 싣는다. 더 작은 단계와 낮춘 품질은 보낼 때 사본을 메모리에서 다시 줄여 싣고 파일로 남기지 않는다. 원본 파일은 바꾸지 않는다. 작은 사진은 키우지 않는다 |
| 한 번에 보낼 수 있는 장수 | 30장이다. 화면과 Control Plane 이 같은 값으로 막는다. 30장은 768px, 품질 0.3 이면 정사각형의 완전한 잡음 사진이어도 7MB 안에 들어 모두 실린다. 예외는 업로드가 몰려 보낼 때의 대기 합계 15초 안에 디코딩 차례를 얻지 못한 사진이다. 그 사진은 싣지 못한 사진으로 안내한다. 넘게 고르면 화면이 나눠 보내 달라고 알린다 |
| 싣지 못한 사진 | 사본을 만들지 못한 사진(JDK 가 읽지 못하는 WebP, 6천만 화소 초과, 디코딩 실패)과 다시 줄이지 못한 사진이다. 지시문은 이 사진을 도구로 읽게 하지 않고, 사용자에게 볼 수 없었다고 알리고 다시 보내 달라고 하게 한다(WebP 처럼 읽지 못하는 형식이면 JPEG 나 PNG 로 바꿔 달라고 한다). 실행은 실패하지 않는다 |
| 다음 턴 | 이번 메시지의 사진만 싣는다. 지난 사진은 다시 싣지 않는다 |
| 지시문 | 작업 종류에 묶지 않은 일반 문구다. 파일을 올리거나 고치는 도구에는 원본을 쓰라고 함께 적는다. 전체 장수와 입력에 실은 사진을 적는다. 싣지 못한 사진이 있으면 그 순번과 「도구로 읽지 말고 사용자에게 알린다」 를 적는다. 지난 메시지의 사진은 같은 폴더의 사본을 `vision_analyze` 로 한 번에 한 장씩, 앞 호출의 결과를 받은 뒤 다음 사진을 보라고 적는다. 흐름이 붙은 에이전트는 사진을 싣지 않으므로 지금처럼 모든 사진의 경로를 적고 `vision_analyze` 로 보게 한다 |

### 근거

운영판 Hermes v0.21.5(`v2026.9.24`)의 소스를 읽어 확인했다. 근거 줄은 [`hermes/docs/hermes-contract.md`](../../../hermes/docs/hermes-contract.md) 의 「`/v1/runs` 에 사진을 싣는 법」 이 갖는다.

- `/v1/runs` 는 `input` 의 마지막 항목의 `content` 를 목록 그대로 에이전트에 넘긴다. provider 어댑터가 `image_url` 파트를 그 provider 의 모양으로 바꾼다
- 모델이 이미지를 받지 않거나 판정하지 못하면 Hermes 가 보조 vision 모델의 설명 글로 바꿔 보낸다. 상류가 이미지를 거절하면 이미지를 뗀 사본으로 다시 시도한다.
  그래서 Control Plane 이 모델마다 지원 여부를 판정하지 않는다
- session 기록에는 이미지 대신 `[screenshot]` 자리표시자가 남는다. 다음 턴에 이미지가 다시 실리지 않는다

### 상한의 근거

운영 모델(`gpt-6.1-sol`, openai-codex)에 inline 사진을 보내 입력 토큰과 글씨 판독을 측정했다(2026-10-09). 측정은 Codex 클라이언트로 했고, Hermes 가 보내는 요청과 `detail` 값이 다를 수 있어 절대값보다 단계 사이의 비율을 근거로 쓴다.

Codex 클라이언트의 이미지 준비 정책과 모델 공급자의 실제 처리 한도는 구분한다. 클라이언트의 `high`·`auto` 크기 정책이 운영 Hermes의 직접 provider 호출이나 `gpt-6.1-sol`의 해상도 보장이라는 뜻은 아니다. 아래 수치는 당시 실험의 관측값이며 작은 글자 판독의 보장으로 쓰지 않는다.

| 긴 변 | 4:3 사진 한 장의 입력 토큰 | 4000px 원본 기준 글자 높이별 판독(4줄 중) |
| --- | --- | --- |
| 1600px | 2,281 | 30px 4, 45px 4, 60px 4, 90px 4 |
| 1280px | 1,441 | 30px 4, 45px 4, 60px 4, 90px 4 |
| 1024px | 922 | 30px 3, 45px 4, 60px 4, 90px 4 |
| 768px | 519 | 30px 2, 45px 4, 60px 4, 90px 4 |
| 512px | 231 | 30px 0, 45px 1, 60px 3, 90px 4 |

이미지 토큰은 화소 수에 거의 비례한다(약 850화소에 1토큰).

| 측정 | 결과 |
| --- | --- |
| 메뉴판 20줄, 원본 4000px 기준 글자 높이 36px 이상 | 1600, 1280, 1024, 768px 모두 20줄 |
| 같은 메뉴판, 글자 높이 26px | 1600px 20줄, 1280px 20줄, 1024px 19줄, 768px 11줄 |
| 사진마다 다른 다섯 자리 코드, 한 입력에 여러 장 | 1024px 20장 20/20, 1024px 30장 29/30, 768px 30장 28/30, 768px 40장 40/40 |
| 768×576 완전한 잡음 사진(원본이 768px)의 data URL | 품질 0.85 약 447KB, 0.7 약 328KB, 0.5 약 243KB, 0.35 약 187KB. 1600×1200 잡음 사본을 768 로 줄인 경로는 덜 거칠어 0.85 약 342KB, 0.6 약 200KB, 0.4 약 146KB |

| 상한 | 까닭 |
| --- | --- |
| data URL 합계 7MiB | Hermes API server의 요청 본문 상한은 10,000,000바이트다. 이미지에 최대 7,340,032바이트를 쓰고 나머지는 기억 문맥과 지시문, 입력 글과 JSON 구조의 자리로 남긴다. 기존 안전 예산은 유지한다 |
| 합계 화소 상한 제거 | 자체 비용 정책이었으며 외부 강제한도는 아니다. 바이트 여유가 있어도 30장 4:3 사진을 768px로 줄여 작은 글자 정보가 손실됐다. 품질을 먼저 보존하고 늘어난 이미지 입력 토큰과 반복 도구 호출의 비용은 별도로 측정한다 |
| 가장 작은 단계 768px | 바이트 예산을 맞추는 마지막 크기 단계다. 작은 글자·가격·품번의 판독을 보장하지 않는다. 더 큰 단계의 data URL이 예산에 들면 이 단계로 내리지 않는다 |
| 768px 의 품질 0.6, 0.4, 0.3 | 30장이 모두 실리게 하는 마지막 단계다. 보통 사진은 768px 품질 0.85 에서 한 장 100KB에서 150KB 라 이 단계에 오지 않는다. 최악인 완전한 잡음 사진 30장은 768×640 이면 품질 0.4 에서 약 6.2MB, 768×768 이면 0.4 에서 약 7.4MB 로 넘치고 0.3 에서 약 6.9MB 로 7MB 안에 든다 |
| 30장 | 한 입력에 30장에서 40장을 보내도 모델이 사진마다 코드를 거의 모두 읽었다. 지금의 화면 상한 30장을 그대로 두고, 그 장수가 모두 실리게 단계를 정했다 |
| 모든 사진을 같은 단계로 | 앞 사진만 크게 싣고 뒤 사진을 작게 실으면 사용자가 고른 순서가 화질을 정한다. 사진끼리 비교하는 질문에서 한쪽만 흐리다 |
| 긴 변 1600px 사본 | 원본이 3MB 를 넘으면 실행 공간의 파일 읽기가 가끔 잘려 `vision_analyze` 가 실패했다(운영에서 5장 중 2장). 사본은 대개 1MB 아래다. 처음에는 싣지 못한 사진을 사본 파일로 보면 잘림을 피한다고 봤지만, 아래 행처럼 사본 읽기도 잘렸다. 사본은 지난 메시지의 사진을 볼 때와 입력에 실을 때 쓴다. Hermes 의 `vision_analyze` 도 1568px 로 줄여 싣는다 |
| 이번 메시지 사진에 도구를 쓰지 않는다 | 운영에서 1.2MB에서 3MB 사이의 원본 여덟 장을 동시에 부른 호출이 모두 실패했다. 150KB에서 400KB 사이의 사본 아홉 장을 동시에 부른 호출도 여덟 장이 「image file is truncated」 로 실패했고, 차례로 두 번 부른 호출도 각각 실패했다. 로컬에서 Hermes 의 같은 읽기 경로로 0.65MB에서 2.6MB 사이의 파일 여덟 장을 동시에 640번 읽었을 때는 잘림이 없었다. 원인 층(Hermes 의 출력 수집, 운영의 Docker 중계, Docker exec)은 따로 조사한다. 그래서 이번 메시지의 사진은 모두 입력에 싣고, 지난 메시지의 사진만 한 장씩 도구로 본다 |

### 위협과 보관

- 사본 파일은 원본과 같은 사용자 폴더, 같은 대화 폴더에 있다. 실행 공간에는 지금처럼 그 사용자의 폴더만 읽기 전용으로 붙으므로 다른 사용자의 사본이 보이지 않는다. mount 는 바꾸지 않는다
- 사본은 원본과 같이 평문 파일이고, 원본과 함께 지운다. 파일 경로 규칙과 링크 검사는 원본과 같은 자리(파일 저장소 하나)가 갖는다
- 싣는 사진은 그 실행의 대화 주인이 그 대화에 올린 첨부뿐이다. 실행 입력을 만드는 자리에서 첨부의 대화와 올린 사용자를 확인한다(지금의 판정을 그대로 쓴다)
- Control Plane 데이터베이스에는 실행 입력을 저장하지 않으므로 이미지가 남지 않는다. 메시지 암호화([ADR-20261008 / data-encryption](ADR-20261008-data-encryption.md))와 겹치지 않는다
- Hermes 쪽: API 오류가 나면 Hermes 가 요청 전체를 진단 파일(`request_dump_*.json`)로 남겨 base64 가 그 안에 들어간다.
  압축이 그 턴에 돌면 원본 파트가 session 기록에 남을 수 있다. 둘 다 그 profile 의 저장소이고, 원본 사진 파일도 이미 평문으로 실행 공간에 있다.
  ADR-20261008 / data-encryption 의 「Hermes 의 저장은 평문」 범위 안이다. 대화를 지우면 session 은 지우지만 진단 파일은 남는다([`hermes/docs/hermes-contract.md`](../../../hermes/docs/hermes-contract.md) 의 「session 을 지우는 경로」)
- 모델 공급자에게는 전에도 `vision_analyze` 로 사진이 갔다. 받는 곳은 같다

### 대안 기각

- **원본을 그대로 싣는다**: 한 장 10MB 상한이라 한 장만으로 요청 상한을 넘을 수 있다. 토큰도 크다
- **보낼 때 메모리에서만 사본을 만든다**: 지울 파일이 생기지 않는다. 그러나 상한을 넘은 사진은 원본 파일을 읽어야 해서 잘림 문제가 그대로 남는다. 처음 설계였고, 넘친 사진도 같은 턴에 보게 하려고 바꿨다
- **여러 턴으로 자동으로 나눠 싣는다**: 30장을 10장씩 세 턴에 나눠 보내면 모든 사진이 입력에 실린다. 그러나 지난 턴의 사진은 Hermes 기록에 자리표시자로만 남아 사진끼리 비교하는 데 약하고, 사용자가 보낸 한 메시지가 여러 실행으로 갈라진다
- **대화의 모든 사진을 매 턴 다시 싣는다**: 지난 사진을 다시 볼 수 있다. 그러나 사진 많은 대화는 매 턴 요청 상한과 토큰 비용에 닿는다
- **모델의 vision 지원을 Control Plane 이 판정해 싣지 않는다**: Hermes 가 이미 판정하고 대체한다. 같은 판정을 두 곳에 두면 어긋난다
- **`vision_analyze` 지시를 없앤다**: 싣지 못한 사진과 지난 사진을 볼 길이 없어진다
- **사본을 서명한 짧은 수명 주소로 넘겨 공급자가 받아 가게 한다**: 요청 본문 상한에 닿지 않아 장수 제한이 없어진다. 그러나 운영 provider 인 openai-codex 의 클라이언트가 2026-06 에 http(s) 이미지 주소를 막았다(openai/codex #29417, #29419. 「느리고 권장하지 않는 경로」). 공급자가 버린 경로라 언제 끊길지 모르고, 끊기면 Hermes 가 이미지를 뗀 채 다시 시도해 모델이 사진을 보지 못한 채 답한다. 그 실패가 사용자에게 드러나지 않는다. 가족 사진을 처음으로 인터넷에서 받아 갈 수 있는 형태로 만드는 노출도 생긴다
- **앞 사진은 1600px, 넘친 사진만 작게 싣는다**: 앞 열 장의 화질이 그대로다. 그러나 화질이 사용자가 고른 순서로 갈리고, 30장일 때 토큰이 같은 단계로 모두 싣는 것보다 크다
- **`detail: low` 로 장수를 늘린다**: 사진 한 장의 토큰이 크게 준다. 그러나 운영 provider 인 openai-codex 의 클라이언트가 지원하지 않는다며 막는다. 768px 품질 단계로 30장이 이미 실린다
- **여러 턴에 나눠 고해상도로 보고 메모를 남긴다**: 사진마다 1600px 로 보고 그 내용을 글로 남긴 뒤 다음 턴에 쓴다. 화질 손실이 없다. 그러나 한 메시지가 여러 실행으로 갈라지고 메모를 저장할 자리가 새로 필요하다. 줄인 사진의 화질 문제가 운영에서 실제로 보이면 후속으로 정한다
- **넘친 사진과 줄인 사진의 세부를 `vision_analyze` 로 보게 한다**: 장수 제한 없이 세부를 다시 볼 수 있다. 그러나 운영에서 사본 읽기도 잘려 이 경로를 믿을 수 없다

### 얻는 것과 감당할 것

- 얻는 것: 큰 사진의 파일 읽기 잘림과 관계없이 모델이 사진을 본다. 한 번에 보낼 수 있는 30장이 모두 입력에 실려 이번 메시지 사진에는 도구 호출이 없고 턴이 짧다
- 감당할 것: 바이트 예산을 넘으면 사진을 더 작게 줄이거나 JPEG 품질을 낮춰 작은 글자 정보를 잃을 수 있다. 사본의 1600px 축소도 남는다. 실제 사진의 품질 검증과 원본 보충 경로가 필요하며, 재전송이나 분할 업로드를 해결책으로 삼지 않는다
- 감당할 것: 바이트 예산을 넘으면 보낼 때 사진마다 사본을 디코딩해 다시 줄인다. 1600px 사본이라 한 장에 수십 ms 이고 메모리는 장당 약 10MB 다. 올릴 때의 디코딩 차례(동시 둘)를 함께 쓰고, 차례를 기다리는 시간은 한 번 보낼 때 모두 합쳐 15초까지다. 이 일은 실행 기록을 만들기 전이라 실행 시작이 그만큼 늦는다
- 감당할 것: 올릴 때 사진을 디코딩한다. 디코딩은 원본 해상도를 줄여 읽어(subsampling) 메모리를 결과 크기에 가깝게 둔다. 화면은 고른 사진을 동시에 올리므로 사본 만들기는 업로드 트랜잭션 밖에서 하고 동시에 둘까지만 디코딩한다. 나머지는 차례를 30초까지 기다리고, 그래도 못 만든 사진은 보낼 때 만든다. 보낼 때는 실행 기록을 만들기 전이라 사진마다 5초, 한 번 보낼 때 모두 합쳐 15초까지만 기다리고, 그 안에 못 만들면 그 사진은 싣지 않고 사용자에게 다시 올려 달라고 안내한다
- 감당할 것: 업로드 응답이 사본을 만든 뒤에 온다. 서른 장을 한꺼번에 올리면 마지막 응답이 디코딩 차례만큼 늦다. 운영에서 응답 시간을 보고 길면 응답 뒤의 비동기 작업으로 옮긴다
- 감당할 것: 이 결정 앞의 버전으로 되돌리면 옛 지우기는 `.small.jpg` 를 지우지 않는다. 되돌린 동안 지운 사진의 사본이 남으므로, 다시 올린 뒤 운영 정리로 원본 없는 사본을 지운다
- 감당할 것: 사진마다 파일이 하나 더 생긴다. 사본은 원본보다 작아 저장량은 크게 늘지 않는다
- 감당할 것: 이미지 토큰이 실행 사용량의 입력 토큰에 섞여 따로 보이지 않는다
