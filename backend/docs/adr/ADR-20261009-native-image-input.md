## ADR-20261009 / native-image-input: 사진마다 줄인 사본 파일을 원본 옆에 두고, 이번 메시지의 사진은 그 사본을 실행 입력에 직접 싣는다

- **status**: `accepted`
- Date: 2026-10-09
- [ADR-020](ADR-020-사진은-공유-디렉터리에-두고-에이전트가-파일로-읽는다.md) 의 「대화 본문에 사진을 실을 수 없다」 를 바꾼다.
  사진을 공유 디렉터리에 두고 실행 공간에 붙이는 것([ADR-091](../../../docs/adr/ADR-091-사진-첨부는-사용자별로-저장하고-실행-공간에는-그-사용자만-붙인다.md))은 그대로다.
- 2026-10-09 개정: 고정 10장 상한을 화소 예산과 크기 단계로 바꿨다. 사진을 서명한 공개 주소로 넘기는 방식은 검토하고 접었다(「대안 기각」)

### 결정

**사진마다 긴 변 1600px JPEG 사본 파일을 원본 옆에 두고, 보내는 메시지의 사진은 그 사본을 `POST /v1/runs` 의 `input` 에 이미지 파트로 싣는다.**
사진이 많으면 모든 사진을 같은 크기 단계로 줄여 한 입력에 싣는다. 그래도 싣지 못한 사진은 같은 턴에 에이전트가 `vision_analyze` 로 사본 파일을 본다.
원본은 지금처럼 실행 공간의 사용자 폴더에 두고, 실행 입력의 파일 목록도 그대로 적는다.
편집, 업로드처럼 원본이 필요한 도구는 원본을 쓴다.

| 무엇 | 어떻게 |
| --- | --- |
| 싣는 모양 | `input` 을 user 메시지 하나의 목록으로 보낸다. `content` 는 글 파트(지금의 입력 전체), 그 뒤로 사진마다 「N번째 사진」 글 파트와 `image_url` 파트(`data:image/jpeg;base64,...`)를 잇는다 |
| 사진이 없을 때 | `input` 을 지금처럼 문자열로 보낸다. 사진 없는 실행의 요청은 바뀌지 않는다 |
| 사본 | 긴 변 1600px 이하, JPEG 품질 0.85, EXIF 회전 반영, 투명 배경은 흰색으로 채운다. 작은 사진은 키우지 않는다 |
| 사본 파일 | 원본과 같은 폴더의 `{첨부 번호}.small.jpg`. 올릴 때 만든다. 이 결정 전에 올린 사진처럼 사본이 없으면 보낼 때 만든다. 만들지 못해도 올리기와 실행은 실패하지 않는다 |
| 사본을 지우는 때 | 원본과 함께 지운다. 사용자 삭제, 보관 기간 정리, 대화 정리가 모두 같은 파일 저장소의 지우기를 지난다 |
| 한 턴에 싣는 양 | 화소 합계 1,920만(1600×1200 열 장)과 base64 합계 7MB 안이다. 긴 변 1600, 1280, 1024, 768px 단계 가운데 모든 사진의 화소 합계가 예산 안에 드는 가장 큰 단계를 고르고, 모든 사진을 그 단계로 싣는다. base64 합계가 7MB 를 넘으면 한 단계 내린다. 768px 에서도 넘치면 앞에서부터 예산까지 싣는다. 값은 코드 상수다 |
| 줄인 단계 | 1600px 단계는 사본 파일을 그대로 싣는다. 더 작은 단계는 보낼 때 사본을 메모리에서 다시 줄여 싣고 파일로 남기지 않는다. 작은 사진은 키우지 않는다 |
| 싣지 못한 사진 | 768px 에서도 예산을 넘은 사진, 사본을 만들지 못한 사진(JDK 가 읽지 못하는 WebP, 6천만 화소 초과, 디코딩 실패), 줄이다 실패한 사진이다. 지시문에 사진마다 사본 경로를 적고, 사본이 없으면 원본 경로를 적는다. 실행은 실패하지 않는다 |
| 다음 턴 | 이번 메시지의 사진만 싣는다. 지난 사진은 다시 싣지 않는다 |
| 지시문 | 작업 종류에 묶지 않은 일반 문구다. 파일을 올리거나 고치는 도구에는 원본을 쓰라고 함께 적는다. 전체 장수, 입력에 실은 사진과 그 긴 변, 싣지 못한 사진의 사본 경로 목록을 적고 「답에 필요한 만큼 각 경로를 `vision_analyze` 로 확인한다」 고 안내한다. 1600px 보다 줄여 실었으면 작은 글씨나 세부가 필요한 사진만 사본 파일을 `vision_analyze` 로 보라고 적는다. `vision_analyze` 는 한 번에 한 장씩, 앞 호출의 결과를 받은 뒤 다음 사진을 부르라고 적는다. 어떤 사진을 어떤 질문으로 볼지는 모델이 정한다. 지난 메시지의 사진은 같은 폴더의 사본을 보라고 적는다 |

### 근거

운영판 Hermes v0.21.5(`v2026.9.24`)의 소스를 읽어 확인했다. 근거 줄은 [`hermes/docs/hermes-contract.md`](../../../hermes/docs/hermes-contract.md) 의 「`/v1/runs` 에 사진을 싣는 법」 이 갖는다.

- `/v1/runs` 는 `input` 의 마지막 항목의 `content` 를 목록 그대로 에이전트에 넘긴다. provider 어댑터가 `image_url` 파트를 그 provider 의 모양으로 바꾼다
- 모델이 이미지를 받지 않거나 판정하지 못하면 Hermes 가 보조 vision 모델의 설명 글로 바꿔 보낸다. 상류가 이미지를 거절하면 이미지를 뗀 사본으로 다시 시도한다.
  그래서 Control Plane 이 모델마다 지원 여부를 판정하지 않는다
- session 기록에는 이미지 대신 `[screenshot]` 자리표시자가 남는다. 다음 턴에 이미지가 다시 실리지 않는다

### 상한의 근거

운영 모델(`gpt-6.1-sol`, openai-codex)에 inline 사진을 보내 입력 토큰과 글씨 판독을 측정했다(2026-10-09). 측정은 Codex 클라이언트로 했고, Hermes 가 보내는 요청과 `detail` 값이 다를 수 있어 절대값보다 단계 사이의 비율을 근거로 쓴다.

| 긴 변 | 4:3 사진 한 장의 입력 토큰 | 4000px 원본 기준 글자 높이별 판독(4줄 중) |
| --- | --- | --- |
| 1600px | 2,281 | 30px 4, 45px 4, 60px 4, 90px 4 |
| 1280px | 1,441 | 30px 4, 45px 4, 60px 4, 90px 4 |
| 1024px | 922 | 30px 3, 45px 4, 60px 4, 90px 4 |
| 768px | 519 | 30px 2, 45px 4, 60px 4, 90px 4 |
| 512px | 231 | 30px 0, 45px 1, 60px 3, 90px 4 |

이미지 토큰은 화소 수에 거의 비례한다(약 850화소에 1토큰).

| 상한 | 까닭 |
| --- | --- |
| base64 합계 7MB | Hermes API server 의 요청 본문 상한이 10MB(`MAX_REQUEST_BYTES`)다. 넘으면 413 으로 실행이 시작되지 않는다. 기억 문맥과 지시문, 입력 글이 남은 3MB 안에 든다 |
| 화소 합계 1,920만 | 같은 턴 안에서는 도구를 부를 때마다 이미지가 다시 실린다. 사용자가 올린 이미지는 Hermes 가 요청에서 빼지 않는다. 토큰이 화소에 비례하므로 화소로 묶는다. 값은 개정 전 상한(1600px 열 장)과 같아, 장수가 늘어도 도구 호출 한 번의 이미지 토큰(약 2만 3천)이 개정 전 최대보다 커지지 않는다 |
| 가장 작은 단계 768px | 원본 4000px 기준 45px 이상 글씨를 모두 읽었다. 512px 은 60px 글씨도 놓쳤다. 한 번에 올리는 상한 30장을 4:3 사진으로 모두 실어도 768px 이면 화소 합계가 약 1,330만이라 예산 안에 든다 |
| 모든 사진을 같은 단계로 | 앞 사진만 크게 싣고 뒤 사진을 작게 실으면 사용자가 고른 순서가 화질을 정한다. 사진끼리 비교하는 질문에서 한쪽만 흐리다 |
| 긴 변 1600px 사본 | 원본이 3MB 를 넘으면 실행 공간의 파일 읽기가 가끔 잘려 `vision_analyze` 가 실패했다(운영에서 5장 중 2장). 사본은 대개 1MB 아래라, 싣지 못한 사진을 사본 파일로 보면 그 잘림을 피한다. Hermes 의 `vision_analyze` 도 1568px 로 줄여 싣는다 |
| `vision_analyze` 를 한 장씩 | 운영에서 1.2MB에서 3MB 사이의 원본 여덟 장을 동시에 부른 호출이 모두 실패했다. 로컬에서 Hermes 의 같은 읽기 경로로 0.65MB에서 2.6MB 사이의 파일 여덟 장을 동시에 640번 읽었을 때는 잘림이 없어 원인을 확정하지 못했다. 사진을 거의 모두 입력에 실으므로 이 호출은 드물고, 차례로 부르는 비용이 작다 |

### 위협과 보관

- 사본 파일은 원본과 같은 사용자 폴더, 같은 대화 폴더에 있다. 실행 공간에는 지금처럼 그 사용자의 폴더만 읽기 전용으로 붙으므로 다른 사용자의 사본이 보이지 않는다. mount 는 바꾸지 않는다
- 사본은 원본과 같이 평문 파일이고, 원본과 함께 지운다. 파일 경로 규칙과 링크 검사는 원본과 같은 자리(파일 저장소 하나)가 갖는다
- 싣는 사진은 그 실행의 대화 주인이 그 대화에 올린 첨부뿐이다. 실행 입력을 만드는 자리에서 첨부의 대화와 올린 사용자를 확인한다(지금의 판정을 그대로 쓴다)
- Control Plane 데이터베이스에는 실행 입력을 저장하지 않으므로 이미지가 남지 않는다. 메시지 암호화([ADR-20261008 / data-encryption](ADR-20261008-data-encryption.md))와 겹치지 않는다
- Hermes 쪽: API 오류가 나면 Hermes 가 요청 전체를 진단 파일(`request_dump_*.json`)로 남겨 base64 가 그 안에 들어간다.
  압축이 그 턴에 돌면 원본 파트가 session 기록에 남을 수 있다. 둘 다 그 profile 의 저장소이고, 원본 사진 파일도 이미 평문으로 실행 공간에 있다.
  ADR-20261008 / data-encryption 의 「Hermes 의 저장은 평문」 범위 안이다. 대화를 지우면 session 은 지우지만 진단 파일은 남는다([`hermes/docs/hermes-contract.md`](../../../hermes/docs/hermes-contract.md) 의 「session 을 지우는 경로」)
- 모델 공급자에게는 전에도 `vision_analyze` 로 사진이 갔다. 받는 곳은 같다

### 대안 기각

- **원본을 그대로 싣는다**: 한 장 10MB 상한이라 한 장만으로 요청 상한을 넘을 수 있다. 토큰도 크다
- **보낼 때 메모리에서만 사본을 만든다**: 지울 파일이 생기지 않는다. 그러나 상한을 넘은 사진은 원본 파일을 읽어야 해서 잘림 문제가 그대로 남는다. 처음 설계였고, 넘친 사진도 같은 턴에 보게 하려고 바꿨다
- **여러 턴으로 자동으로 나눠 싣는다**: 30장을 10장씩 세 턴에 나눠 보내면 모든 사진이 입력에 실린다. 그러나 지난 턴의 사진은 Hermes 기록에 자리표시자로만 남아 사진끼리 비교하는 데 약하고, 사용자가 보낸 한 메시지가 여러 실행으로 갈라진다
- **대화의 모든 사진을 매 턴 다시 싣는다**: 지난 사진을 다시 볼 수 있다. 그러나 사진 많은 대화는 매 턴 요청 상한과 토큰 비용에 닿는다
- **모델의 vision 지원을 Control Plane 이 판정해 싣지 않는다**: Hermes 가 이미 판정하고 대체한다. 같은 판정을 두 곳에 두면 어긋난다
- **`vision_analyze` 지시를 없앤다**: 싣지 못한 사진과 지난 사진을 볼 길이 없어진다
- **사본을 서명한 짧은 수명 주소로 넘겨 공급자가 받아 가게 한다**: 요청 본문 상한에 닿지 않아 장수 제한이 없어진다. 그러나 운영 provider 인 openai-codex 의 클라이언트가 2026-06 에 http(s) 이미지 주소를 막았다(openai/codex #29417, #29419. 「느리고 권장하지 않는 경로」). 공급자가 버린 경로라 언제 끊길지 모르고, 끊기면 Hermes 가 이미지를 뗀 채 다시 시도해 모델이 사진을 보지 못한 채 답한다. 그 실패가 사용자에게 드러나지 않는다. 가족 사진을 처음으로 인터넷에서 받아 갈 수 있는 형태로 만드는 노출도 생긴다
- **앞 사진은 1600px, 넘친 사진만 작게 싣는다**: 앞 열 장의 화질이 그대로다. 그러나 화질이 사용자가 고른 순서로 갈리고, 30장일 때 토큰이 같은 단계로 모두 싣는 것보다 크다

### 얻는 것과 감당할 것

- 얻는 것: 큰 사진의 파일 읽기 잘림과 관계없이 모델이 사진을 본다. 한 번에 올리는 30장까지는 대개 모두 입력에 실려 사진마다 `vision_analyze` 호출이 없고 턴이 짧다
- 감당할 것: 사진이 열 장을 넘으면 입력의 사진이 1600px 보다 작아진다. 작은 글씨는 사본 파일을 `vision_analyze` 로 다시 봐야 한다. 지난 메시지의 사진과 싣지 못한 사진도 파일 읽기에 기대고, 한 장씩 차례로 보므로 그만큼 턴이 길어진다
- 감당할 것: 열 장을 넘으면 보낼 때 사진마다 사본을 디코딩해 다시 줄인다. 1600px 사본이라 한 장에 수십 ms 이고 메모리는 장당 약 10MB 다. 올릴 때의 디코딩 차례(동시 둘)를 함께 쓴다. 이 일은 실행 기록을 만들기 전이라 실행 시작이 그만큼 늦는다
- 감당할 것: 올릴 때 사진을 디코딩한다. 디코딩은 원본 해상도를 줄여 읽어(subsampling) 메모리를 결과 크기에 가깝게 둔다. 화면은 고른 사진을 동시에 올리므로 사본 만들기는 업로드 트랜잭션 밖에서 하고 동시에 둘까지만 디코딩한다. 나머지는 차례를 30초까지 기다리고, 그래도 못 만든 사진은 보낼 때 만든다. 보낼 때는 실행 기록을 만들기 전이라 사진마다 5초만 기다리고, 그 안에 못 만들면 원본 경로로 안내한다
- 감당할 것: 업로드 응답이 사본을 만든 뒤에 온다. 서른 장을 한꺼번에 올리면 마지막 응답이 디코딩 차례만큼 늦다. 운영에서 응답 시간을 보고 길면 응답 뒤의 비동기 작업으로 옮긴다
- 감당할 것: 이 결정 앞의 버전으로 되돌리면 옛 지우기는 `.small.jpg` 를 지우지 않는다. 되돌린 동안 지운 사진의 사본이 남으므로, 다시 올린 뒤 운영 정리로 원본 없는 사본을 지운다
- 감당할 것: 사진마다 파일이 하나 더 생긴다. 사본은 원본보다 작아 저장량은 크게 늘지 않는다
- 감당할 것: 이미지 토큰이 실행 사용량의 입력 토큰에 섞여 따로 보이지 않는다
