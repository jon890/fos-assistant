## ADR-071: 여러 출처의 문맥은 항목마다 출처와 권한과 신선도를 지닌 묶음으로 조립한다

- **status**: `accepted`
- `MEMORY_FACTS` 와 `MEMORY_READ` source 는 [ADR-20261008 / memory-facts](../../../docs/adr/ADR-20261008-memory-facts.md) 가 더한다. 지금 목록은 [`backend/docs/flow.md`](../flow.md) 가 갖는다.
- **결정**: Control Plane 이 실행 하나나 화면 하나를 위해 모으는 문맥을 **문맥 묶음**(context bundle)으로 다룬다.
  묶음은 항목의 목록이고, 항목마다 아래 칸을 지닌다. 칸의 값은 묶음 안에서 바뀌지 않는다.

  | 칸 | 뜻 |
  | --- | --- |
  | `source` | 항목이 온 곳. `MEMORY_ALWAYS`, `MEMORY_INDEX`, `DELEGATION_RESULT`, `CONNECTOR_RESULT`, `EXECUTION_STATE`, `FOLLOW_UP` |
  | `ref` | 원래 기록을 가리키는 참조. 본문을 담지 않는다 |
  | `scope`, `ownerUserId` | `USER` 나 `GROUP` 과 그 주인. 원래 기록의 값을 그대로 옮긴다 |
  | `sensitivity` | `NORMAL` 이나 `SENSITIVE`. 원래 기록의 값이고, 원래 기록에 이 칸이 없으면 `SENSITIVE` 로 둔다 |
  | `trust` | `USER_APPROVED`(사람이 받아들인 것), `CONTROL_PLANE`(Control Plane 이 직접 적은 기록), `AGENT`(다른 에이전트의 답), `EXTERNAL`(외부 서비스의 글) |
  | `asOf`, `freshness` | 그 내용이 참이던 시각과 `FRESH`, `STALE`, `UNKNOWN` |
  | `bodyMode` | `INLINE`, `TITLE_ONLY`, `OMITTED`. 본문을 싣는 방식 |

  **Hermes 에 넘기는 형태는 지금과 같다.** Runs API 의 `instructions` 와 `input` 두 글이다.
  묶음은 그 글을 만들기 전의 Control Plane 안 모델이고, 결과 항목은 글로 옮길 때 출처 머리줄을 붙인다.
  묶음의 원문은 저장하지 않는다. 실행 기록에는 항목의 `source`, `ref`, `bodyMode`, `freshness` 만 남긴다.

  권한과 민감도와 소유권은 아래 다섯 규칙으로 묶음을 지나도 사라지지 않게 한다.

  1. **항목은 그 source 의 기존 판정을 통과한 것만 묶음에 든다.** Memory 는 ADR-053 의 세 조건, 결과는 그 대화의 주인, 실행 상태는 실행 줄의 `user_id` 다. 묶음 단계에서 판정을 새로 만들거나 넓히지 않는다.
  2. **`SENSITIVE` 항목의 본문은 `instructions` 에 싣지 않는다.** 지금처럼 제목만 싣고 `memory_read` 로 읽게 한다.
  3. **`EXTERNAL` 항목은 늘 `<external-data>` 로 감싼다.** 그 글이 Memory 를 고치지 못하고, 그 안의 지시를 따르지 않는다.
  4. **`USER` 항목과 `GROUP` 항목을 한 항목으로 합치지 않는다.** 그룹의 다른 사용자가 같은 항목을 볼 수 있어, 합치면 개인 내용이 그룹 쪽으로 넘어간다.
  5. **커넥터 에이전트의 실행에는 묶음을 주지 않는다.** ADR-045 를 그대로 둔다.

  출처가 다른 항목이 같은 대상을 다르게 말하면 **Control Plane 은 하나를 고르지 않는다.**
  두 항목을 모두 출처와 시각을 붙여 싣고, 모델에게 하나를 고르지 말고 둘 다 말하라고 지시한다.
  사람의 지시와 사람이 받아들인 Memory 가 외부 결과보다 앞선다. 외부 결과는 Memory 를 고치지 않고, 바꿀 것이 있으면 제안만 한다(ADR-012).
- **맥락**: #158 은 일정, 메시지, 문서, 기억, 실행 상태를 한 사용자 상황으로 모으는 방향을 정했다. #159 가 그 첫 계약이다.
  지금 문맥을 모으는 곳은 둘이다.
  `ContextAssembler` 는 Memory 만 모아 `instructions` 한 글을 내고, `ChatService.runDelegationResults` 는 위임 결과와 승인한 동작의 결과를 `input` 에 잇는다.
  둘 다 글을 바로 만들어, 어느 줄이 어디서 왔고 언제의 내용인지가 글 안의 머리말로만 남는다.
  결과는 몇 초 뒤에 전하는 것을 전제로 시각을 싣지 않는다. 결과 전달을 다시 하는 길(#162)이 생기면 몇 시간 지난 결과가 지금의 일처럼 실린다.
  Living View(#161)와 먼저 알리기(#160)도 같은 기록의 출처를 보여야 해서, 출처를 가리키는 형식이 세 곳으로 갈라질 위험이 있다.
  #97 은 새 memory tier 와 별도 workflow engine 을 만들지 않고, USER/GROUP 과 ALWAYS/SEARCH/ARCHIVE 를 다시 설계하지 않는다고 정했다.
- **대안 기각**:
  - **합친 문맥을 새 저장소에 미리 만들어 둔다.** 벡터 저장소나 문맥 캐시가 여기 해당한다. 원래 기록의 권한을 복사해 두 곳에서 지켜야 하고, 원래 기록이 바뀌어도 사본이 남는다. #97 이 막은 새 memory tier 다.
  - **Hermes 에 구조화한 JSON 으로 넘긴다.** Runs API 는 `instructions` 와 `input` 글만 받는다. 칸을 더하려면 Hermes core 를 고쳐야 한다(ADR-001).
  - **Control Plane 이 커넥터를 직접 불러 최신 데이터를 묶음에 넣는다.** Control Plane 은 커넥터 뒤의 서비스를 모르고(ADR-043), credential 은 Hermes 쪽을 떠나지 않는다(ADR-050). 커넥터 데이터는 커넥터 에이전트가 실행해 남긴 결과로만 들어온다.
  - **묶음 원문을 실행 기록에 남긴다.** 민감 본문을 담는 저장소가 하나 더 생긴다. 지금처럼 지문(`instructions_hash`)과 참조만 남긴다.
  - **충돌을 Control Plane 이 풀어 하나만 싣는다.** 어느 쪽이 맞는지 Control Plane 이 판단할 근거가 없다. 틀리게 고르면 사용자는 버려진 쪽이 있었다는 것도 모른다.
- **결과**:
  - 얻는 것:
    - 결과가 언제의 것이고 어디서 왔는지가 모델에게 보인다. 오래된 결과를 지금 상태처럼 말하는 일을 줄인다.
    - 지금 화면과 먼저 알리기가 같은 `source` 이름과 `ref` 형식으로 출처를 보인다. 대화에 싣는 묶음과 화면의 판정이 같은 기록을 같은 이름으로 가리킨다.
    - 실행 기록의 참조로 어느 답에 어느 기록이 들어갔는지 나중에 찾을 수 있다. 본문을 다시 저장하지 않는다.
  - 감당할 것:
    - 결과 머리줄이 길어져 자동 turn 의 입력이 조금 늘어난다.
    - 출처 머리줄과 지시는 모델이 따르리라는 기대일 뿐이다. 감싸도 외부 글을 따르지 않는다는 보장은 없다(`ExternalData` 와 같다).
    - 충돌 표시는 Control Plane 이 구조로 알 수 있는 경우에만 붙는다. 뜻이 어긋나는 것을 찾는 일은 모델의 몫이다.
    - 묶음을 조립하는 시간이 첫 반응 시간에 들어간다. 요청 수신부터 Hermes 제출까지의 구간을 지표로 본다([`backend/docs/flow.md`](../flow.md) 의 「첫 반응 시간」).
- **적용 범위**: 항목 칸의 값, source 마다의 판정과 신선도 기준, 글로 옮기는 형식, 로그 규칙, 합성 시나리오는 [`backend/docs/flow.md`](../flow.md) 가 갖는다.
  Memory 의 층과 예산, `memory_read` 는 [`backend/docs/flow.md`](../flow.md) 가 그대로 갖는다.
