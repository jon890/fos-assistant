## ADR-20261016 / task-schedule-columns: 예약 작업의 일정은 작업 본체의 현재값으로 둔다

- **status**: `accepted`
- Date: 2026-10-16

### 맥락

작업 하나는 일정 하나만 갖는다.
기존 `task_trigger.task_id`의 유일 제약과 생성·수정 서비스가 이 관계를 강제하며, 일정 수정도 같은 줄을 갱신한다.
별도 일정 식별자에 독립적인 생명주기나 이력이 없는데도 조회와 잠금에서 작업과 일정을 따로 다뤘다.
단순한 일대일 현재값은 본체 컬럼에 둔다는 사용자 결정에 따라 이 관계를 합친다.

### 결정

일정은 `task`의 현재값으로 저장하고 `task_trigger`를 제거한다.
일정의 종류와 값, 시간대, 놓친 발화 처리, 다음 예정 시각과 마지막 처리 시각은 작업 본체가 갖는다.
컬럼의 정의는 [`data-schema.md`](../data-schema.md)의 「task」가 갖는다.

발화 기록은 `task_run`에 남기고 `(task_id, scheduled_for)`에 유일 제약을 둔다.
작업당 일정이 하나이므로 기존 `(trigger_id, scheduled_for)`와 같은 중복 방지 범위를 갖는다.
일정 수정과 상태 변경, 발화는 같은 `task` 행을 잠그고 최신 값을 다시 읽는다.
발화 기록 생성과 다음 예정 시각 갱신은 같은 짧은 트랜잭션에서 끝낸다.
turn을 시작하는 단계는 그 트랜잭션 밖에 둔다.

이관은 모든 작업에 일정이 하나씩 있는지, 발화 기록이 같은 작업의 일정을 가리키는지 먼저 검사한다.
위반 데이터는 자동 보정하지 않고 컬럼을 추가하기 전에 실패시킨다.
컬럼 준비, 데이터 복사, 제약 전환과 옛 테이블 제거를 나누며, 이미 적용한 마이그레이션은 고치지 않는다.
공개 API의 일정 요청과 응답 모양은 유지한다.

### 대안

- 별도 일정 테이블을 유지하면 현재값을 읽고 고칠 때마다 관계와 잠금을 함께 다뤄야 한다.
- 미래의 다중 일정 가능성만으로 별도 테이블을 유지하지 않는다. 실제 요구가 생기면 그때 ADR로 다시 정한다.

### 결과와 대체 범위

작업과 일정의 조회를 합치고, 일정 수정과 발화가 서로 다른 행을 잠그던 틈을 없앤다.
여러 일정을 붙이는 확장은 현재 구조에 포함하지 않는다.

[ADR-077](ADR-077-발화는-trigger-와-예정-시각의-유일-제약으로-한-번만-만들고-놓친-발화는-작업마다-정한다.md)의 유일 제약 키, 잠그는 행과 놓친 발화 설정의 저장 위치를 대체한다.
발화와 시작의 분리, 놓친 시각의 처리, 재기동 복구와 시작 제한 시간은 ADR-077을 유지한다.
이 결정은 일반 예약 작업과 매일 깨우기에 함께 적용한다.
