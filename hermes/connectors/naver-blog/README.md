# 네이버 블로그 커넥터

사용자가 「내 브라우저」 에 로그인해 둔 네이버 계정의 임시저장 글을 읽고 고치며, 블로그 글을 임시저장하는 범용 커넥터다. 코드는 [`hermes/connectors/naver-blog/`](.) 에 있다.
이 문서는 도구와 정책, 초안의 모양, 임시저장 글 읽기와 덮어쓰기, 보안, 설정 안내, 실제 계정으로 확인하는 절차를 갖는다.
결정과 근거는 [ADR-20261007 / naver-blog-connector](../../../docs/adr/ADR-20261007-naver-blog-connector.md) , [ADR-20261009 / naver-blog-primitives](../../docs/adr/ADR-20261009-naver-blog-primitives.md), [ADR-20261009 / naver-blog-overwrite](../../docs/adr/ADR-20261009-naver-blog-overwrite.md) 에 있다.
커넥터 공통 계약은 [커넥터 연결](../../../docs/features/connector.md) 과 [커넥터 도구 정책](../../../docs/features/connector-policy.md) 이 갖는다.

**발행하지 않는다.** 글은 임시저장 상태로 남고, 공개는 사용자가 네이버에서 직접 한다.

## 등록 칸

| 칸 | env | 비밀 | 무엇 |
| --- | --- | --- | --- |
| `blog_id` | `NAVER_BLOG_ID` | 아니다 | 글을 쓸 블로그의 아이디. `blog.naver.com/<아이디>` 의 그 값이다. 영문자, 숫자, `_`, `-` 로 50자까지 |

필수다. 운영자가 주는 값(`operator_env`)은 없다.
브라우저 주소는 사용자가 넣지 않는다. 일반 사용자는 서버 안의 주소를 알 수 없고 알아서도 안 된다.

설치가 주는 env 는 둘이다. 둘 다 사용자가 넣는 칸이 아니다.

| env | 선언 | 값 |
| --- | --- | --- |
| `NAVER_BLOG_ATTACHMENT_DIR` | `owner_attachments_env` | 바인딩 설치가 그 에이전트 주인의 첨부 디렉터리를 넣는다([ADR-20261007 / connector-owner-attachments](../../../docs/adr/ADR-20261007-connector-owner-attachments.md)) |
| `NAVER_BLOG_BROWSER_URL` | `owner_browser_env` | 주인의 「내 브라우저」 로 가는 Control Plane 중계 주소다. 바인딩 설치는 그 바인딩의 표식 주소를, 확인 도구 호출은 요청자의 호출 표식 주소를 넣는다. 중계가 꺼졌으면 빈 값이다([ADR-20261008 / browser-gateway-token](../../../backend/docs/adr/ADR-20261008-browser-gateway-token.md)) |

커넥터는 중계 주소를 Chrome 의 CDP 주소처럼 부른다. 중계 계약은 [사용자 브라우저](../../../docs/features/user-browser.md) 의 「중계」 가 갖는다.
`connector.json` 의 `owner_browser_login_url` 은 네이버 로그인 화면 주소다. 연결 화면이 그 주소를 「내 브라우저에서 로그인」 링크로 연다.
확인 도구는 `session_status` 다. 등록과 연결 확인 때 요청자의 「내 브라우저」 에 중계로 붙어 네이버 로그인 쿠키가 있는지 보고, 있으면 저장한다.

## 도구와 정책

MCP 서버 이름은 `naver-blog` 다.

| 도구 | 위험도 | 승인 | 상시 허락 | 카드 제목 | 하는 일 |
| --- | --- | --- | --- | --- | --- |
| `session_status` | `READ` | 없음 | | | 브라우저에 붙는지와 네이버 로그인 쿠키가 있는지 본다 |
| `list_drafts` | `READ` | 없음 | | | 임시저장 글의 번호, 제목, 고친 시각을 읽는다 |
| `read_draft` | `WRITE` | 매번 필요 | 줄 수 없다 | 네이버 임시저장 글 불러오기 · 자동저장 가능 | 글을 편집기에 불러와 읽는다. 불러오면서 자동저장이 발생할 수 있다 |
| `render_draft` | `READ` | 없음 | | | 초안을 검사하고 미리보기나 수동 등록용 HTML 을 돌려준다. 아무것도 쓰지 않는다 |
| `save_draft` | `WRITE` | 필요 | 줄 수 있다 | 네이버 블로그에 임시저장 | 초안을 검사하고 임시저장 작업을 시작한다 |
| `overwrite_draft` | `WRITE` | 필요 | 줄 수 없다 | 네이버 블로그 임시저장 글 덮어쓰기 | 기존 임시저장 글을 고치는 작업을 시작한다. 원래 글은 사본으로 먼저 남긴다 |
| `draft_job` | `READ` | 없음 | | | 임시저장 작업의 진행과 결과를 읽는다. 끝날 때까지 정한 시간만큼 기다린다 |

분류의 까닭이다.

- READ 도구 넷 중 상태 확인은 쿠키 이름만 보고 탭을 열지 않는다. 목록은 글쓰기 화면을 새 탭에 열지만 글을 불러오지 않는다. 미리보기는 커넥터 안에서 글을 만들 뿐이다. 작업 상태는 커넥터가 남긴 작업 파일만 읽는다
- 글 읽기는 편집기에 글을 불러오므로 자동저장이 발생할 수 있다. 기존 실측에서는 임시저장 글과 그 수가 바뀌지 않았지만 무부작용을 보장하지 못해 WRITE 로 분류한다. 승인 방식은 `required`, `grant: false`, `outbound: false` 다. READ 전용 실행은 거절하고 상시 허락이 있어도 매번 확인받는다
- 읽기 도구는 「작성 중인 글이 있습니다」 알림을 닫지 않는다. 「취소」 가 사용자가 쓰던 자동저장본을 버릴 수 있어서다
- 임시저장은 계정 안의 쓰기다. 임시저장 글은 그 계정 주인만 보고 네이버에서 지울 수 있다. 밖으로 나가지 않으므로 `"outbound": false` 이고 상시 허락을 줄 수 있다. Gmail 의 초안 만들기와 같은 분류다
- 상시 허락을 닫지 않은 까닭이 하나 더 있다. 사진 디렉터리 경로에 사용자 디렉터리 키(64자리 16진수)가 들어 승인 카드가 그 자리를 가린다. 상시 허락을 닫은 도구는 가려진 인자가 있으면 승인할 수 없다
- 발행 도구는 없다. 공개는 블로그 주인의 이름으로 나가므로 사람이 네이버에서 직접 한다
- 덮어쓰기는 사용자가 쓴 글을 바꾼다. 원래 글을 사본으로 남기지만 매번 사람이 바뀌는 내용을 보게 상시 허락을 닫는다(`"grant": false`). 인자에 가려지는 사진 디렉터리가 없어 승인할 수 있다
- 글을 지우는 도구는 없다
- 32자 이상의 id 를 받는 쓰는 도구가 없어 `identifiers` 선언은 없다

### 도구의 인자와 결과

| 도구 | 인자 | 결과 |
| --- | --- | --- |
| `session_status` | 없음 | `{browser: "connected", logged_in: true, blog_id}`. 로그인 쿠키가 없으면 `NAVER_BLOG_LOGIN_REQUIRED` 로 실패한다 |
| `render_draft` | 아래 「초안」 의 다섯 칸, `base`(덮어쓸 때 `read_draft` 가 준 `title`, `category`, `tags`, `body`, 선택), `photo_notes`(사진 번호를 키로 한 사진 설명, 선택), `artifact_path`(결과물 폴더 안의 `index.html` 이나 `<폴더>/index.html`, 폴더는 세 단계까지), `kind`(`preview` 나 `package`, 기본 `preview`) | `{problems: [], html, assets}`. 초안이 계약을 어기면 `html` 없이 `problems` 에 어긋난 자리를 문장으로 담는다. `assets` 는 미리보기가 부르는 스티커 그림을 결과물 폴더에 받아 둘 `[{path, source_url}]` 이다. `base` 를 주면 `changes` 와 `base_revision` 이 더 온다(아래 「임시저장 글 덮어쓰기」) |
| `list_drafts` | 없음 | `{count, drafts: [{draft_id, title, saved_at}]}`. 네이버 목록의 차례 그대로이고 앞의 200개까지, 제목은 200자까지다. `draft_id` 는 숫자로 된 글자, `saved_at` 은 ISO 시각이고 읽지 못하면 `null` 이다 |
| `read_draft` | `draft_id` | `{draft_id, revision, title, category, tags, body}`. 아래 「임시저장 글 읽기」 를 본다 |
| `save_draft` | 아래 「초안」 의 다섯 칸 | `{job_id, status}`. `job_id` 는 UUID 고, `status` 는 시작 확인 때 읽은 `running`, `succeeded`, `failed`, `unknown` 중 하나다 |
| `overwrite_draft` | `draft_id`(`read_draft` 와 같은 모양), `revision`(16자리 16진수), `changes`(1자에서 100,000자), `title`, `category`, `tags`, `body` | `{job_id, status}`. 상태는 `save_draft` 와 같다. 아래 「임시저장 글 덮어쓰기」 를 본다 |
| `draft_job` | `job_id`, `wait_seconds`(0~50, 기본 45) | 아래 「작업」 의 상태 |

## 임시저장 글 읽기

두 도구 모두 그 블로그의 글쓰기 화면을 새 탭에 열고, 끝나면 그 탭만 닫는다. 같은 블로그에 살아 있는 저장 작업이 있으면 탭을 열지 않고 `NAVER_BLOG_BUSY` 다. 읽기는 잠금을 잡지 않는다.
한 번의 읽기는 2분이 지나면 멈춘다. 근거와 실측한 편집기 동작은 [ADR-20261009 / naver-blog-primitives](../../docs/adr/ADR-20261009-naver-blog-primitives.md) 가 갖는다.

「작성 중인 글이 있습니다」 알림은 닫지 않는다. `list_drafts` 는 그 알림이 있어도 읽고, `read_draft` 는 글을 불러오지 않고 `NAVER_BLOG_EDITOR_IN_USE` 로 멈춘다.

`list_drafts` 는 편집기가 임시저장 목록을 열 때 부르는 목록 응답(`TempPostList.naver`)을 그 탭에서 같은 출처로 받는다. 편집기에 글을 불러오지 않는다.

`read_draft` 는 승인 카드에 보인 `draft_id` 그대로 승인 뒤에만 실행한다. 승인 대기 중에는 다시 부르지 않는다. 다른 탭의 작성 중인 글은 먼저 임시저장하거나 정리한다. 승인 보호는 연속 읽기와 다른 탭 미저장 글의 안전성을 증명하지 않는다. 그 실계정 검증은 별도로 남아 있고, 목록을 위해 탭을 여는 영향도 별도 검증 대상이다.

`read_draft` 는 차례대로 한다.

1. 목록 응답에서 그 `draft_id` 의 차례를 찾는다. 없으면 `NAVER_BLOG_DRAFT_NOT_FOUND` 다
2. 「임시저장된 글 보기」 단추로 목록 레이어를 열고, 응답의 제목이 그 차례의 글 단추 제목으로 시작하는지 본 뒤 누른다(화면은 긴 제목을 `…` 로 줄인다). 다르면 누르지 않고 실패한다
3. 편집기 문서(`getDocumentData()`)의 문서 번호가 그 `draft_id` 가 될 때까지 기다린다
4. 편집기 문서에서 제목과 본문을, 발행 설정에서 카테고리와 태그를 읽는다. 저장 단추는 누르지 않는다

본문은 새 글 초안과 같이 한 줄이 한 문단이다. 글 구성요소의 문단마다 한 줄이고, 문단 안의 줄바꿈은 공백이 된다.
글이 아닌 구성요소는 1부터 센 번호를 단 줄 하나다. 번호는 사진, 스티커, 지도, 구성요소 넷마다 따로 세고, 「구성요소」 는 편집기 종류가 달라도 한 번호를 함께 센다.

| 편집기 구성요소 | 본문의 줄 |
| --- | --- |
| `image` | `[기존 사진 <N>]` |
| `sticker` | `[기존 스티커 <N>]` |
| `placesMap` | `[기존 지도 <N>]` |
| 그 밖의 것 | `[기존 구성요소 <N>: <종류>]`. 종류 이름이 영문자, 숫자, `_`, `-` 로 40자를 넘지 않을 때만 붙는다 |

스티커 코드, 지도의 상호와 주소, 사진의 그림 주소는 싣지 않는다. 그 구성요소의 모양을 실측하지 못했다.
`[기존 …]` 줄은 그 글 안에서만 뜻이 있다. 새 글 초안에 있으면 검사가 거절한다.

`revision` 은 `[title, category, tags, 본문 줄 목록]` 을 JSON 으로 적은 글의 SHA-256 앞 16자리다. 줄 끝 `\r` 은 넣지 않는다.

## 임시저장 글 덮어쓰기

`read_draft` 로 읽은 글을 고쳐 같은 글에 저장한다. 근거는 [ADR-20261009 / naver-blog-overwrite](../../docs/adr/ADR-20261009-naver-blog-overwrite.md) 가 갖는다.

### 고친 글의 모양

덮어쓸 글은 `title`, `category`, `tags`, `body` 네 칸이다. 모양과 길이는 「초안」 과 같다.

- 본문에 `read_draft` 가 준 `[기존 사진 1]` 같은 줄을 둘 수 있다. 그 줄을 빼면 그 구성요소를 지우고, 줄의 차례를 바꾸면 구성요소의 차례가 바뀐다
- 같은 기존 구성요소 줄을 두 번 둘 수 없다
- 고친 뒤 다시 읽으면 기존 구성요소의 번호는 문서 차례대로 다시 매겨진다. `[기존 사진 2]` 를 `[기존 사진 1]` 앞에 두면 다시 읽은 본문에서는 그 둘이 `[기존 사진 1]`, `[기존 사진 2]` 다
- 카테고리와 태그는 앞뒤에 공백을 두지 않는다
- 승인 카드가 가리는 글이 없어야 한다. 32자 이상 이어진 영문과 숫자(긴 링크 조각, 해시), `Bearer` 토큰, 알려진 접두사의 key, JWT, `authorization:` 과 `password=` 같은 비밀 이름 뒤의 값이다. 덮어쓰기는 상시 허락이 없어 가려진 카드는 승인할 수 없다. 규칙은 Control Plane 의 `ToolDetailRedactor` 와 같다
- 새 사진, 스티커, 지도 줄(`[사진 N: …]`, `[스티커: …]`, `[지도: …]`)은 받지 않는다. 새 글로 저장하거나 네이버에서 직접 넣는다
- `photo_dir` 은 받지 않는다. `render_draft` 에 `base` 와 함께 주면 `problems` 다

### 미리보기와 바뀌는 내용

`render_draft` 에 고친 글과 함께 `base` 로 원래 글의 네 칸을 준다. `base` 가 있으면 위 「고친 글의 모양」 으로 검사하고, 기존 구성요소 줄이 `base` 의 본문에 있는지도 본다.
`kind` 는 `preview` 만 받는다. 바뀌는 내용에 실린 원래 글의 줄이 승인 카드에 가려져도 `problems` 다.

| 결과 칸 | 뜻 |
| --- | --- |
| `changes` | 바뀌는 내용 글. 100,000자를 넘으면 `problems` 다. 제목과 카테고리는 `제목: <원래> → <새>`, 태그는 `뺀 태그:`, `더한 태그:` 줄, 본문은 `본문:` 아래에 바뀐 줄을 `- `, `+ ` 로, 그 앞뒤 한 줄을 공백 두 칸으로 적는다. 건너뛴 자리는 `…` 한 줄이다. 바뀐 것이 없으면 `problems` 다 |
| `base_revision` | `base` 의 지문. `read_draft` 의 `revision` 과 같은 계산이다 |

미리보기 HTML 은 제목과 태그 아래, 본문 위에 바뀌는 내용을 보이고, 기존 구성요소 줄을 이름표로 그린다.

### 덮어쓰기 도구

`overwrite_draft` 는 `draft_id`, `revision`(`render_draft` 의 `base_revision`), `changes`(`render_draft` 의 `changes`) 와 고친 글의 네 칸을 받는다. 승인 카드에 이 인자가 모두 글로 보인다.
승인한 호출은 고친 글의 모양을 검사하고 브라우저와 로그인, 그 블로그의 잠금을 확인한 뒤 「작업」 과 같은 작업 프로세스를 띄운다. 결과는 `draft_job` 으로 읽는다.

작업은 차례대로 한다. 「작성 중인 글이 있습니다」 알림은 저장 작업처럼 「취소」 로 닫는다.

문단 비교는 같은 앞뒤 줄을 먼저 보존한다. 중복 줄은 앞에서 같은 줄부터 짝짓고, 남은 뒤쪽을 짝짓는다. 그 뒤 남은 두 구간의 `(원래 줄 수 + 1) × (고친 줄 수 + 1)`이 4,000,000을 넘으면 문단 꾸밈을 안전하게 보존할 수 없으므로 나눠 고치도록 안내한다. 미리보기는 승인할 변경 내용을 만들지 않고, 실행은 사본을 만들거나 원본에 문서를 넣기 전 `verify`에서 `editor_failed`로 멈춘다.

| 단계 | 하는 일 |
| --- | --- |
| `open` | 글쓰기 화면을 새 탭에 연다 |
| `load` | 「임시저장 글 읽기」 와 같은 방법으로 그 글을 불러온다. 목록에 없으면 `draft_not_found` 다 |
| `verify` | 불러온 글을 다시 읽어 지문이 `revision` 과 같은지, 다시 만든 바뀌는 내용이 `changes` 와 글자까지 같은지 본다. 다르면 `draft_changed` 나 `changes_mismatch` 로 멈춘다. 본문의 기존 구성요소 줄이 그 글에 없으면 `component_not_found` 다 |
| `backup` | 원래 문서를 복제해 문서 번호를 비우고 제목만 `[덮어쓰기 전 원본] <원래 제목>`(100자까지)으로 바꿔 새 탭의 빈 편집기에 넣는다. 넣은 뒤 그 탭의 문서 번호가 원래 글이나 목록의 다른 글을 가리키면 저장하지 않고 `editor_failed` 다. 카테고리와 태그를 원래 것으로 두어 임시저장한다. 목록 응답에 새 글 번호가 하나 생기고 그 제목이 맞으며, 원래 글의 제목과 고친 시각이 그대로여야 한다. 아니면 `backup_failed` 다. 원래 글이 바뀌었으면 `error.original_changed` 가 참이다. 그 탭은 닫는다 |
| `apply` | 처음 탭의 문서에서 제목과 글 구성요소를 바꾸고 기존 구성요소를 본문 줄 차례대로 놓아 편집기에 넣는다. 바뀌지 않은 문단은 원래 문단을 그대로 쓴다 |
| `settings` | 발행 설정의 카테고리를 고르고, 빠진 태그의 칩을 지우고 새 태그를 넣는다 |
| `save` | 편집기의 문서 번호가 그 글이고, 다시 읽은 제목과 본문이 `apply` 에서 만든 문서를 읽은 것과 같고, 카테고리와 태그 집합이 고친 글과 같은지 본 뒤 저장 단추만 누른다. 목록 응답에서 그 글의 고친 시각이 바뀌고 임시저장 수(응답의 `totalCount`)가 사본 하나만 는 것인지 본다 |
| `state` | 저장을 확인한 뒤 편집기의 네 칸 지문을 읽는다. 실패해도 작업은 성공이다 |

작업 상태의 모양과 `status` 의 뜻은 「작업」 과 같다. `save_clicked` 는 덮어쓰기의 저장 단추를 누르기 직전에 참이 된다. 사본의 저장 단추는 여기에 들지 않는다.

| `status` | `result` 나 `error` |
| --- | --- |
| `succeeded` | `{draft_id, backup_draft_id, backup_title, saved_before, saved_after, state}`. `saved_before` 는 사본을 만든 뒤의 임시저장 수라 덮어쓰기가 맞으면 `saved_after` 와 같다. `state` 는 `{revision}` 이고 읽지 못하면 `null` 이다 |
| `failed` | 아래 오류. 사본을 만든 뒤면 `error.backup_draft_id` 가 붙는다. `apply` 앞의 실패는 원래 글을 바꾸지 않았다(`original_changed` 는 예외). 그 뒤의 실패는 저장 단추를 누르지 않았다 |
| `unknown` | 저장 단추를 누른 뒤 확인하지 못했다. `error.backup_draft_id` 가 붙는다. 다시 덮어쓰지 않는다 |

작업 프로세스가 죽어 다음 상태 조회가 끝낸 작업(`timeout`)과, 사본의 저장 단추를 누른 뒤 목록을 확인하는 동안 시간 상한에 걸린 작업에는 `backup_draft_id` 가 붙지 않는다. 그때는 네이버 목록에서 `[덮어쓰기 전 원본]` 사본을 찾는다.

| `error.code` | 뜻 |
| --- | --- |
| `draft_not_found` | 그 글이 임시저장 목록에 없다 |
| `draft_changed` | 읽은 뒤에 그 글이 바뀌었다. 다시 읽어야 한다 |
| `changes_mismatch` | 승인한 바뀌는 내용이 지금 글과 고친 글의 차이와 다르다 |
| `component_not_found` | 본문의 기존 구성요소 줄이 그 글에 없다 |
| `backup_failed` | 원본 사본을 만들지 못했다. 사본이 생겼는지 모르면 `backup_draft_id` 없이 이 코드다 |
| `login_required`, `category_not_found`, `editor_failed`, `timeout` | 「작업」 의 같은 코드와 같다 |

## 초안

`render_draft` 와 `save_draft` 가 같은 다섯 칸을 받는다.
승인 카드가 인자를 키와 값으로 그대로 보이므로 본문은 사람이 읽는 글 한 덩어리다.

| 칸 | 모양 | 뜻 |
| --- | --- | --- |
| `title` | 글자, 1~100자 | 제목 |
| `category` | 글자, 1~50자 | 블로그에 이미 있는 카테고리 이름. 없으면 작업이 `category_not_found` 로 끝나고 있는 카테고리 이름을 돌려준다 |
| `tags` | 글자 배열, 0~30개. 하나에 1~30자, `#` 과 쉼표 없이 | 발행 설정의 태그 |
| `body` | 글자, 20,000자까지 | 본문. 한 줄이 편집기의 한 문단이다. 아래 지시 줄은 구성요소가 된다 |
| `photo_dir` | 절대 경로. 사진 지시가 있을 때 필수 | 대화 입력의 `[이번 메시지에 올린 사진]` 이 적은 디렉터리. 바인딩 주인의 첨부 디렉터리 아래여야 한다 |

`body` 의 줄 가운데 아래 모양과 정확히 같은 줄은 글이 아니라 구성요소다. 나머지 줄은 그대로 글자로 들어간다. 빈 줄은 빈 문단이다.

| 줄 | 들어가는 것 |
| --- | --- |
| `[사진 <N>: <파일 이름>]` | `photo_dir` 의 그 파일을 사진으로 올리고 `문서 너비` 를 적용한다. `N` 은 대화의 몇 번째 사진인지이고 사람이 읽으라고 둔다 |
| `[스티커: <스티커 코드>]` | 편집기 스티커 창에서 그 코드의 스티커를 넣는다. 코드는 영문자, 숫자, `_`, `-` 로 64자까지 |
| `[지도: <상호명> \| <주소>]` | 장소 검색에서 상호명과 주소가 모두 맞는 결과 하나를 지도 카드로 넣는다 |

```text
[스티커: sticker_hello]
안녕하세요 가상블로그입니다
오늘은 동네 국숫집에 다녀왔어요

[사진 1: 101.jpg]
간판부터 정겨운 느낌
[사진 2: 102.jpg]
[지도: 가상국수 | 서울특별시 가상구 예시로 1]
```

검사하는 것이다. 어긋나면 렌더는 `problems` 로, 임시저장은 `NAVER_BLOG_INVALID_INPUT` 이나 `NAVER_BLOG_PHOTO_INVALID` 로 끝난다.

- 칸의 모양과 길이. 사진은 50장, 스티커와 지도는 각각 30개까지
- 사진 파일 이름은 `/` 와 `..` 없이 `jpg`, `jpeg`, `png`, `webp`, `gif`, `heic` 확장자만 받는다
- `photo_dir` 의 실제 경로가 `NAVER_BLOG_ATTACHMENT_DIR` 의 실제 경로 아래여야 하고, 그 디렉터리부터 `photo_dir` 까지 어느 조각도 링크가 아니어야 한다. 그 env 가 비었으면 사진을 하나도 받지 않는다. 등록 화면의 확인 도구에서는 비어 있다
- 사진 파일은 `photo_dir` 바로 아래의 링크 아닌 보통 파일이고, 20MB 까지이며, 파일 머리가 그 확장자의 이미지 서명과 맞아야 한다
- 사진 파일을 연 뒤 디렉터리 검사를 다시 하고, 그 경로의 `lstat` 이 연 파일과 같은 파일인지 대조한다. 확인과 열기 사이에 위 디렉터리가 링크로 바뀌어도 밖의 파일을 읽지 않는다
- 경로 문제는 원인을 나누지 않는다. 디렉터리는 「사진 디렉터리를 쓸 수 없습니다.」, 파일은 「<N>번째 사진 자리의 사진을 쓸 수 없습니다.」 한 문장이다. 없음, 링크, 첨부 디렉터리 밖, 크기, 서명이 같은 문장이라 승인 없는 `render_draft` 로 다른 경로가 있는지 떠볼 수 없다. 작업 프로세스도 사진을 읽을 때 같은 env 로 다시 검사한다
- 같은 파일을 두 번 놓아도 된다. 사진 순서는 검사하지 않는다. 순서를 지키는 것은 스킬과 사용자의 확인이다
- 본문에 `[기존 사진 1]` 같은 기존 구성요소 줄(`read_draft` 의 본문 모양)이 있으면 거절한다

## 미리보기

`render_draft` 가 돌려준 `html` 을 에이전트가 `artifact_write` 로 `artifact_path` 에 쓴다. 대화 화면이 그 결과물을 답 아래에 보인다.

- 네이버 모바일 화면 폭으로 그린다. 사진 자리마다 몇 번째 사진인지와 `photo_notes` 의 설명을 붙인다. 설명은 미리보기에만 보이고 네이버에는 들어가지 않는다
- 사진은 바이트를 담지 않고 같은 대화의 첨부 주소를 상대 경로로 부른다. 파일 이름이 `<첨부 번호>.<확장자>` 인 사진만 그렇게 그리고, 다른 이름이면 이름표만 보인다. 계약은 [결과물 파일](../../../docs/features/attachment.md) 의 「같은 대화의 첨부 사진을 부를 때」 가 갖는다
- `artifact_path` 는 `index.html` 이나 `<폴더>/index.html` 이고 폴더는 세 단계까지 받는다. 사진 주소의 `../` 수를 그 깊이로 정한다(`index.html` 은 `../attachments`, `a/index.html` 은 `../../attachments`)
- 에이전트는 `artifact_write` 의 `path` 를 `artifact_path` 와 글자까지 같게 준다. 다른 깊이에 쓰면 사진 주소가 풀리지 않아 사진이 404 로 보이지 않는다
- 스티커는 네이버 편집기에 들어가는 것과 같은 그림으로 보인다. 결과물 화면은 외부 그림을 막으므로(`img-src 'self' data:`) HTML 은 `stickers/<코드>.png` 를 상대 경로로 부르고, 에이전트가 `assets` 의 항목마다 `artifact_write` 의 주소 방식(`source_url`)으로 그 그림을 같은 폴더에 받아 둔다
- OGQ 스티커 코드 `ogq_<묶음>-<번호>` 의 그림 주소는 `https://storep-phinf.pstatic.net/ogq_<묶음>/original_<번호>.png?type=p100_100` 이다. 그 모양이 아닌 코드와 받지 못한 그림은 이름표로 보인다
- 주소 방식은 Control Plane 의 `assistant.artifact.source.allowed-hosts` 에 `storep-phinf.pstatic.net` 이 있어야 된다. 없으면 `artifact_write` 가 거절하고 스티커는 이름표로 보인다
- 지도는 상호명과 주소 카드로 보인다. 네이버의 지도 그림은 저장할 때 편집기가 만들어 미리보기에서는 같게 그리지 못한다
- `kind: "package"` 는 자동 입력이 막혔을 때 사람이 붙여넣을 수동 등록용 묶음이다. 제목, 본문, 태그, 카테고리와 사진 자리를 차례로 보인다. 내부 경로는 담지 않는다

## 작업

### 입력 준비와 커서 실패 진단

글쓰기 화면은 제목 문단이 하나이고, 보이는 크기와 편집 가능한 상태를 갖출 때 준비된 것으로 본다.
제목과 본문의 표시 판정은 조상의 투명도와 표시 전환도 확인한다.
작성 중인 글 알림의 유지·취소 정책을 먼저 적용한다.
준비 직후 문단이 교체되거나 잠깐 숨겨지면 입력 단계는 기존 10회, 기본 대기 합계 3초 안에서 다시 찾는다.
제목 가운데를 다른 요소가 가리면 그 요소를 누르거나 우회하지 않는다.
클릭 뒤 선택 영역 양 끝이 현재 문단 안에 있고 접혀 있으며 실제 입력 초점이 같은 편집 영역에 있을 때만 글자를 넣는다.
JS Range로 커서를 강제로 옮기지 않으며, 입력 뒤 제목과 본문을 초안과 대조한다.

커서를 두지 못하면 `editor_failed`의 `error.focus_diagnostics`에 시도 수와 시도별 구조화된 상태만 남긴다.
각 상태는 요소 수(100까지), 크기·편집 가능·페이지 초점·페이지 표시·접힌 선택 영역 여부와 hit test, selection 양 끝, activeElement의 분류다.
분류는 `title`, `body`, `other`, `none`만 허용하고 시도와 상태는 10개까지다.
좌표, DOM 원문, 태그·클래스·id, 제목·본문·사진·URL·계정·환경값은 읽어 진단에 넣지 않는다.
브라우저 결과와 예외 직렬화 경계에서 허용 필드만 복사한다.
CDP 명령 실패와 중단은 기존 오류 문장을 유지하고, 작업 전체 시간 초과는 기존 `timeout` 계약을 따른다.
이 진단은 실패 시점의 상태이며 과거 실패 원인을 확정하는 자료가 아니다.

승인한 `save_draft` 는 아래를 확인한 뒤 분리된 작업 프로세스를 띄우고 작업 번호를 돌려준다. 확인 하나라도 실패하면 작업을 만들지 않는다.

1. 초안 검사와 사진 파일 확인
2. 브라우저에 붙는지와 로그인 쿠키. 꺼진 브라우저를 켜는 시간까지 45초를 기다린다
3. 그 블로그에 돌고 있는 작업이 없는지

작업은 새 탭에서 차례로 진행하고, 끝나면 성공이든 실패든 그 탭을 닫는다. 다른 탭은 읽지도 닫지도 않는다.

| 단계 | 하는 일 |
| --- | --- |
| `open` | 글쓰기 화면을 새 탭에 연다. 「작성 중인 글이 있습니다」 알림은 「취소」 로 닫는다 |
| `fill` | 제목과 본문 글자를 넣고 구성요소 자리에 자리표시 글을 둔다 |
| `photos` | 사진 자리마다 파일 선택 창을 가로채 사진 바이트를 넣고, 전송이 끝나면 `문서 너비` 를 적용한다 |
| `components` | 스티커와 지도 자리를 실제 구성요소로 바꾼다 |
| `settings` | 발행 설정을 열어 카테고리와 태그를 넣고 닫는다. 편집기의 애니메이션이 멈추기를 잠시 기다리고 발행 단추가 덮이지 않은 채 멈춰 있을 때 누르며, 레이어가 뜨지 않으면 세 번까지 누른다. 발행 확인 단추는 누르지 않는다 |
| `save` | 화면의 제목, 사진, 스티커, 지도, 카테고리, 태그가 초안과 같은지 본 뒤 `저장` 만 누르고 임시저장 수가 늘었는지 본다 |
| `state` | 저장을 확인한 뒤 편집기에 실제로 들어간 제목, 사진, 스티커, 지도, 카테고리, 태그를 읽는다. 이 단계가 실패해도 작업은 실패가 아니다 |

작업 상태는 `{job_id, status, stage, save_clicked, started_at, finished_at, result, error}` 다. `save_clicked` 는 저장 단추를 누르기 직전에 참이 된다.

저장 시작 응답은 `{job_id, status}` 다. 시작을 확인하는 동안 작업이 끝났으면 그 종료 상태를 그대로 돌려준다.
시작 응답이 `succeeded`, `failed`, `unknown` 이어도 받은 `job_id` 로 `draft_job` 을 바로 조회해 상세 결과와 오류를 확인한다.
`running` 이면 계속 조회하고, 완료 안내는 `draft_job` 이 확인한 저장 결과에 근거한다.
승인 엔진의 도구 호출 성공은 작업 접수를 뜻하며 실제 저장 성공과는 다르다.
`NAVER_BLOG_START_UNKNOWN` 은 작업이 시작됐는지 확인하지 못했다는 뜻이다. 자동으로 다시 저장하지 않고 사용자에게 임시저장 목록 확인을 부탁한다.

| `status` | 뜻 | 에이전트가 할 일 |
| --- | --- | --- |
| `running` | 돌고 있다. `stage` 가 지금 단계다 | 다시 부른다 |
| `succeeded` | 임시저장 수가 늘었다. `result` 는 `{state, saved_before, saved_after}` 다. `state` 는 `state` 단계가 읽은 제목, 사진 수와 `문서 너비` 를 적용한 사진 수, 스티커와 지도 수, 카테고리, 태그, 임시저장 수다. 저장을 확인한 뒤 그 읽기가 실패하면 `state` 는 `null` 이다 | 확인한 것만 완료라고 알린다. `state` 가 `null` 이면 임시저장 수가 늘었다는 것만 알린다 |
| `failed` | 저장하기 전에 멈췄다. 임시저장 글은 생기지 않았다 | `error.code` 에 따라 사용자에게 묻거나 알린다 |
| `unknown` | 저장 단추를 누른 뒤 늘었는지 확인하지 못했다. 누른 뒤의 연결 끊김, 예외, 시간 초과가 모두 여기 든다 | 다시 저장하지 않는다. 네이버의 임시저장 목록을 사용자에게 확인해 달라고 한다 |

| `error.code` | 뜻 | 덧붙는 것 |
| --- | --- | --- |
| `login_required` | 글쓰기 화면이 로그인이나 보안 확인(캡차, 기기 인증) 화면으로 넘어갔다. 우회하지 않는다 | |
| `category_not_found` | 그 이름의 카테고리가 없다 | `categories`: 있는 카테고리 이름 |
| `place_not_unique` | 상호명과 주소가 모두 맞는 결과가 하나가 아니다 | `place`: 찾던 상호명과 주소, `candidates`: 검색 결과의 상호명과 주소 |
| `photo_upload_failed` | 사진을 넣거나 전송을 끝내지 못했다 | `photo`: 몇 번째 사진 자리인지 |
| `editor_failed` | 그 밖에 화면이 기대한 상태가 아니었다 | `stage` 와 `message`: 무엇을 찾지 못했는지. `message` 는 커넥터가 정한 문장이다. 발행 설정을 열지 못했으면 `diagnosis` 가 붙는다: `publish_button`(`shown`, `disabled`, `hidden`, `missing`), 단추 가운데를 차지한 요소 `covered_by`, 보이는 레이어 `layers`. 요소는 태그와 앞 클래스 둘로만 적고 화면의 글은 싣지 않는다 |
| `timeout` | 작업이 10분 안에 끝나지 않았다 | |

작업 파일은 커넥터가 도는 컨테이너의 임시 디렉터리에 두고 24시간 뒤 지운다. 작업에 넘긴 초안 사본은 작업이 끝나면 지운다.
작업 프로세스는 10분이 지나면 탭을 닫고 `timeout` 으로 끝낸다. 작업 프로세스가 30초 넘게 갱신 시각을 쓰지 않았거나 11분이 지나도 끝나지 않았으면 다음 상태 조회가 그 작업을 `timeout` 으로 끝내고 잠금을 푼다. 저장 단추를 누른 뒤였으면 둘 다 `unknown` 이다. 끝난 작업의 상태는 다시 쓰지 않는다.
작업 프로세스가 살아 있는지는 5초마다 쓰는 갱신 시각으로만 본다. pid 로 프로세스를 찾지 않으므로 승인한 호출과 Hermes 의 MCP 서버가 PID 네임스페이스를 달리해도 살아 있는 작업을 끝내지 않는다. 그 대신 작업 프로세스가 죽었다는 판정이 최대 30초 늦어진다.
작업 프로세스와 정리 쪽 가운데 끝냄 표시 파일을 먼저 만든 쪽만 끝난 상태를 쓴다. 작업 프로세스는 그 파일이 있으면 heartbeat 와 단계도 기록하지 않는다.
작업 프로세스는 저장 단추를 누르기 직전에 상태를 기록하고 다시 읽어, 그 사이 정리 쪽이 작업을 끝냈으면 누르지 않고 멈춘다.
잠금은 블로그 아이디마다 하나다. 중계 주소는 바인딩마다 표식이 달라 같은 브라우저도 여러 주소로 오므로 주소로 잠그지 않는다. 다른 블로그의 작업은 서로 막지 않는다.

## 서버와 검사

[커넥터 만들기](../README.md) 의 「MCP 서버」 를 따른다. 같은 묶음 파일이 `--worker <작업 파일>` 인자로 작업 프로세스가 된다.
CDP 는 Bun 의 WebSocket 으로 직접 부르고 브라우저 자동화 라이브러리를 들이지 않는다.

일반 검사는 `tests/`의 가짜 CDP 서버가 중계처럼 HTTP 창구와 WebSocket 명령에 답한다.
커서 회귀는 전용 임시 profile의 로컬 headless Chrome에서 합성 HTML을 열어 실제 DOM과 CDP 입력을 검증한다.
제목·본문 입력 회귀는 `Control+A`를 쓰는 기존 키 계약에 맞춰 Linux Chrome 환경에서 실행한다.
실제 네이버와 사용자 브라우저에는 닿지 않는다. Chrome이 없으면 테스트를 생략하지 않고 실패한다.
기본 `bun run test`는 Linux에서 설치된 Chrome을 쓰고, macOS에서는 `scripts/test.Dockerfile`로 Linux Chromium과 Bun 1.3.14를 실행한다.
`scripts/check-connectors.sh`도 이 기본 경로를 부른다. macOS에는 실행 중인 Docker와 Git이 필요하다.
첫 실행은 이미지를 내려받아 만들고, 각 실행은 잠금 파일에 정해진 패키지를 설치한다.
검사에는 Git으로 추적하는 공개 코드와 합성 fixture만 복사한다. 개인 환경 파일, 사진과 실제 profile은 넣지 않고, 실행마다 임시 profile과 자기 컨테이너를 정리한다.
macOS Chrome의 기존 본문 Delete 명령 대기는 아직 해결하지 않았다. Linux 검사 성공은 macOS Chrome이나 실제 SmartEditor의 성공을 증명하지 않는다.
테스트용 실행 파일은 `FOS_TEST_CHROME`으로 지정할 수 있다. macOS 기본 검사에서는 컨테이너 안의 Linux 실행 경로로 해석한다.
직접 `bun test`를 부르면 Docker 실행기를 거치지 않으므로 macOS에서 같은 키 대기 문제가 남는다.

```bash
# cwd: 저장소 root
bun run --cwd hermes/connectors/naver-blog test
bun run --cwd hermes/connectors/naver-blog test -- ./tests/editor-focus.chrome.test.ts
bash scripts/check-connectors.sh
```

Chrome 부재, 이미지 생성·패키지 설치 실패와 회귀 실패는 비영 종료 코드로 전달한다. Linux CI는 기존 native Chrome 검사를 계속 실행한다.
합성 화면은 빈 입력 칸에서 입력과 사후 대조를 확인하며 SmartEditor의 내부 구현이나 운영 복구를 증명하지 않는다.
그 서버는 중계 주소의 경로 아래만 받고, 중계처럼 `Origin` 머리가 있는 WebSocket 연결을 거절한다.

- 받은 CDP 메서드를 허용 목록과 견준다. 목록 밖의 메서드가 오면 실패한다
- 연 주소가 그 블로그의 글쓰기 주소 하나뿐인지 본다
- 편집기 대역이 임시저장 목록 응답, 목록 레이어, `getDocumentData()` 를 흉내 내고, 읽기 도구가 저장 단추를 누르지 않는지와 차례가 어긋난 목록의 글을 누르지 않는지 본다
- 어느 단계에서도 발행 확인 단추(`tpb*i.publish`)를 누르는 식이 나가지 않는지 본다
- 사진 바이트가 파일 선택 창 이벤트의 `backendNodeId` 로 찾은 input 에 들어가는지 본다
- 결과와 오류에 중계 주소와 파일 경로가 나오지 않는지 본다
- 중계가 접두사 밖의 WebSocket 경로를 적으면 붙지 않는지 본다
- 작업이 잠금, 시작 확인, 시간 초과, 작업 파일 정리를 지키는지 본다

**대역 검사는 SmartEditor 의 화면이 바뀐 것을 알지 못한다.** 그 틈은 소유자의 실제 계정 확인으로 막는다.

## 보안

이 커넥터가 읽는 글은 그 계정의 임시저장 글 제목과 본문이다. 주인이 쓴 글이지만 다른 곳에서 붙여 넣은 글이 섞일 수 있어 모델에게는 자료이고 지시가 아니다.
그 밖에 모델을 속일 수 있는 글은 사용자가 보낸 사진과 대화, 같은 에이전트에 붙은 다른 커넥터가 읽어 온 글이다.

| 무엇 | 어떻게 |
| --- | --- |
| 브라우저 | 커넥터는 글쓰기 주소 하나만 새 탭으로 연다. 그 탭 안에서 같은 출처의 임시저장 목록 응답만 받는다. 발행, 글 삭제 단추를 누르는 코드가 없다. 발행 설정에서는 카테고리 고르기, 태그 넣기, 덮어쓸 때의 태그 칩 지우기 단추만 누른다 |
| 파일 | 바인딩 주인의 첨부 디렉터리(`NAVER_BLOG_ATTACHMENT_DIR`) 아래, 사진 디렉터리 바로 아래의 이미지 파일만 읽는다. 경로는 링크 없이 그 디렉터리 아래여야 해서 속은 모델이 다른 사용자의 첨부 디렉터리를 가리켜도 읽지 않는다. 확장자와 이미지 서명이 맞지 않으면 올리지 않는다. 그 사진은 주인 자신의 임시저장 글로만 간다 |
| 덮어쓰기 | 승인 뒤에만 시작하고 상시 허락이 없다. 카드에 지문과 바뀌는 내용, 고친 글이 보이고, 작업이 그 둘을 지금 글로 다시 대조한다. 고치기 전에 원래 글을 사본으로 남긴다 |
| 쓰기 | 임시저장은 승인 뒤에만 시작한다. 카드에 제목, 카테고리, 태그, 본문이 글로 보인다. 사진 디렉터리는 사용자 디렉터리 키가 가려져 보인다. 상시 허락을 주면 속은 모델이 임시저장 글을 만들 수 있다. 그 글은 계정 밖으로 나가지 않고 지울 수 있다 |
| 중계 주소 | 주소에는 바인딩마다 다른 접근 표식이 들어 있고, 중계는 그 표식의 주인의 브라우저에만 잇는다. 그 주소에 닿는 쪽은 주인의 네이버 계정을 조작할 수 있으므로 커넥터는 주소를 결과와 로그에 싣지 않는다 |
| 작업 오류 | `error.message` 는 커넥터가 정한 문장만 담고 화면 글을 옮기지 않는다. 네이버 화면에 뜬 알림 글이 모델 입력으로 가지 않는다 |
| 확인 도구 | 요청자의 「내 브라우저」 만 본다. 사용자가 주소를 넣지 않으므로 등록 화면으로 다른 주소에 닿는지 떠볼 수 없다. 결과는 로그인 쿠키가 있는지뿐이다 |

## 설정 안내

### 1. 「내 브라우저」 에서 네이버에 로그인하기

「내 브라우저」 화면에서 브라우저를 켜고 네이버에 로그인한다. 연결 화면의 「내 브라우저에서 로그인」 링크가 네이버 로그인 화면을 바로 연다.
로그인은 사람이 한다. 비밀번호와 인증번호를 대화에 붙이지 않는다. 「로그인 상태 유지」 를 켜야 브라우저를 다시 켜도 로그인이 남을 수 있다.

### 2. 연결 화면에 블로그 아이디 넣기

「연결」 화면에서 네이버 블로그를 고르고 블로그 아이디를 넣는다. 확인 도구가 「내 브라우저」 의 로그인 쿠키를 확인하면 연결된다.
브라우저가 꺼져 있었으면 켜는 동안 첫 확인이 실패할 수 있다. 잠시 뒤 「연결 다시 확인」 을 누른다.

### 3. 에이전트에 붙이기

글을 쓸 에이전트의 상세에서 이 연결을 붙인다. 그 에이전트에 `vision` 과 `skills` 도구가 켜져 있어야 지난 메시지의 사진을 읽고 커넥터 스킬을 읽는다. 이번 메시지의 사진은 실행 입력에 이미지로 실린다. 스킬이 블로그 글쓰기 Memory 를 `memory_read` 로 찾으므로 그 에이전트가 그 Memory 의 collection 을 받아야 한다.

### 4. 자기 문체를 쓰게 하기

커넥터 스킬은 꼭 지킬 규칙과 도구 쓰는 법만 갖는다. 자기 블로그의 말투, 카테고리마다 담을 것, 자주 쓰는 스티커 코드는 자기 Memory 에 남긴다.
스킬은 글을 쓰거나 고치기 전에 블로그 글쓰기에 관한 Memory 를 찾아 읽게 한다. 공개 저장소에는 두지 않는다.

### 로그인이 풀렸을 때

작업이 `login_required` 로 끝나거나 연결 확인이 `NAVER_BLOG_LOGIN_REQUIRED` 로 실패한다. 「내 브라우저」 에서 네이버에 다시 로그인하고 「연결」 화면에서 연결을 확인한다.

### 기존 연결 옮기기

브라우저 연결 주소 칸이 없어졌다. 자동으로 옮기는 코드는 없다. 까닭은 [ADR-20261007 / user-browser](../../../docs/adr/ADR-20261007-user-browser.md) 의 「네이버 블로그 이행(2026-10-08 추가)」 이 갖는다.
보관 파일에 남은 옛 `cdp_url` 값은 대시보드가 읽을 때 버려 쓰이지 않고, 사용자가 블로그 아이디를 다시 등록하면 보관 파일이 새로 쓰여 사라진다.

1. 배포 뒤 사용자는 「내 브라우저」 에서 네이버에 로그인하고 「연결」 화면에서 연결 확인을 한 번 누른다
2. 붙은 에이전트의 서버 정의가 바뀌므로 그 바인딩은 한 번 재시작 대기가 된다. 관리자가 공유 gateway 를 재시작하고 반영 완료를 누른다

## 실제 계정으로 확인하기

소유자는 배포 뒤와 네이버 편집기가 바뀐 것 같을 때 확인한다. 결과에는 계정과 주소를 적지 않는다.

1. 「연결」 화면에서 연결 확인이 성공한다
2. 사진 두 장을 첨부하고 스티커 하나와 지도 하나가 든 짧은 초안으로 미리보기를 만든다. 미리보기에 두 사진이 보인다
3. 임시저장을 승인한다. 작업 상태가 `succeeded` 이고 저장 전후 임시저장 수가 하나 늘었다
4. 네이버의 임시저장 목록에서 그 글을 열어 제목, 본문, 사진 두 장의 `문서 너비`, 스티커, 지도, 카테고리, 태그가 남았는지 본다
5. 대화에서 임시저장 글 목록을 묻는다. `list_drafts` 가 3 의 글을 맨 앞에 돌려준다
6. 그 글을 읽게 한다. `read_draft` 의 제목, 카테고리, 태그가 네이버 화면과 같고, 본문에 `[기존 사진 1]`, `[기존 사진 2]`, `[기존 스티커 1]`, `[기존 지도 1]` 이 글 줄 사이 제자리에 있다. 임시저장 수는 그대로다
7. 그 글의 본문 한 줄과 태그 하나를 고치게 한다. 미리보기의 본문 위에 바뀌는 줄이 보이고, 승인 카드의 `changes` 가 같다
8. 덮어쓰기를 승인한다. 작업 상태가 `succeeded` 이고 `saved_before` 와 `saved_after` 가 같다. 네이버 목록에 `[덮어쓰기 전 원본]` 사본이 하나 늘었다
9. 제목에 `&` 와 `<` 가 든 글로 7, 8 을 한 번 더 한다. 사본이 `backup_failed` 없이 생긴다
10. 원래 글을 열어 고친 줄과 태그가 들어갔고 사진 두 장, 스티커, 지도와 바뀌지 않은 문단의 꾸밈이 그대로인지 본다. 사본을 열어 고치기 전 글인지 본다
11. 원래 글과 사본을 지운다
