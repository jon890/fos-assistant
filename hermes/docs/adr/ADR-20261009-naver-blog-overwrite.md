## ADR-20261009 / naver-blog-overwrite: 네이버 블로그 임시저장 글 덮어쓰기는 원본 사본을 먼저 남기고, 승인 카드의 지문과 바뀌는 내용을 작업이 다시 대조한다

- **status**: `accepted`
- Date: 2026-10-09
- [ADR-20261009 / naver-blog-primitives](ADR-20261009-naver-blog-primitives.md) 의 읽기 도구 위에 쓰기 도구 하나를 더한다.

### 결정

**`overwrite_draft` 는 기존 임시저장 글을 제자리에서 고친다. 고치기 전에 원래 글을 새 임시저장 글로 남기고, 그 사본이 생긴 것을 확인한 뒤에만 고친다.**

| 항목 | 정한 것 |
| --- | --- |
| 위험도와 승인 | `WRITE`, `"outbound": false`, `"grant": false`. 덮어쓸 때마다 승인 카드를 거친다 |
| 인자 | `draft_id`, `revision`(그 글을 읽은 지문), `changes`(바뀌는 내용 글), `title`, `category`, `tags`, `body` |
| 고칠 수 있는 것 | 제목, 카테고리, 태그, 본문 글자. 기존 사진, 스티커, 지도, 그 밖의 구성요소는 그대로 두거나 빼거나 차례를 바꿀 수 있다 |
| 받지 않는 것 | 새 사진, 스티커, 지도 줄. 같은 기존 구성요소 줄을 두 번 쓰는 것. 승인 카드가 가리는 글(긴 영문과 숫자 덩어리 등)이 고친 글이나 바뀌는 내용에 있는 것 |
| 바뀌는 내용 | `render_draft` 에 원래 글(`base`)을 함께 주면 커넥터가 `changes` 와 `base_revision` 을 만든다. 에이전트는 그 둘을 그대로 `overwrite_draft` 에 넘긴다. 승인 카드에 그 글이 보인다 |
| 작업의 대조 | 작업은 그 글을 편집기에 불러와 다시 읽은 지문이 `revision` 과 같은지, 다시 만든 바뀌는 내용이 `changes` 와 글자까지 같은지 본다. 하나라도 다르면 아무것도 바꾸지 않고 멈춘다 |
| 되돌리기 | 원래 글의 편집기 문서를 복제해 문서 번호를 비우고 제목만 `[덮어쓰기 전 원본] <원래 제목>` 으로 바꿔 새 탭의 빈 편집기에 넣고 임시저장한다. 카테고리와 태그도 원래 것이다. 목록 응답에 새 글 번호가 생기고 그 제목이 맞으며 원래 글의 제목과 고친 시각이 그대로일 때만 다음으로 간다. 결과에 그 사본의 번호를 싣는다 |
| 고치는 방법 | 불러온 편집기 문서에서 제목과 글 구성요소를 바꾸고 기존 구성요소 객체를 본문 줄 차례대로 놓아 `setDocumentData()` 로 넣는다. 바뀌지 않은 문단은 원래 문단 객체를 그대로 써 글꼴과 꾸밈을 지킨다. 카테고리와 태그는 발행 설정 화면으로 고친다 |
| 저장 전 확인 | 넣은 뒤 편집기를 다시 읽은 제목과 본문이 만든 문서를 읽은 것과 같고, 카테고리와 태그 집합이 요청과 같아야 저장 단추를 누른다. 기존 구성요소 번호는 다시 읽을 때 문서 차례로 다시 매겨지므로 요청한 본문과 글자로 견주지 않는다 |
| 저장 확인 | 목록 응답에서 그 글의 고친 시각이 바뀌고 응답의 `totalCount` 가 사본 하나만큼만 늘었으면 성공이다. 단추를 누른 뒤 확인하지 못하면 `unknown` 이다 |
| 작업 | `save_draft` 와 같은 분리된 작업 프로세스와 블로그마다 하나인 잠금, `draft_job` 을 쓴다 |

### 맥락

사용자의 요청은 임시저장한 글을 고쳐 달라는 것이다([ADR-20261009 / naver-blog-primitives](ADR-20261009-naver-blog-primitives.md) 의 맥락).
관리자 계정의 테스트 글로 실측한 것이다(2026-10-09).

- 목록에서 불러온 글을 고쳐 저장 단추를 누르면 편집기가 `RabbitTempPostUpdate.naver` 로 같은 `logNo` 를 고친다. 응답에 같은 `logNo` 와 새 `modiDate` 가 오고, 임시저장 수는 그대로였다. 원래 내용은 남지 않는다
- 빈 편집기에서 저장 단추를 누르면 `RabbitTempPostWrite.naver` 가 새 `logNo` 를 만들고 수가 하나 는다
- 편집기 객체에 `getDocumentData()` 와 `setDocumentData()` 가 함께 있다

아래는 실측하지 못했다. 그래서 각 단계 뒤에 실측한 경로(목록 응답, 편집기 문서 다시 읽기)로 확인하고, 어긋나면 저장 단추를 누르기 전에 멈춘다.

- `setDocumentData()` 로 넣은 문서가 저장 단추로 그대로 저장되는지
- 빈 편집기에 넣은 문서가 새 글로 저장되는지(사본)
- 발행 설정의 태그 칩을 지우는 단추
- 목록 응답이 제목을 넣은 글자 그대로 주는지. HTML 이스케이프나 공백 정리를 하면 사본 확인이 제목을 맞추지 못해 `backup_failed` 로 멈춘다
- `setDocumentData()` 로 문서를 넣은 뒤 저장 단추를 누르기 전에 편집기의 자동저장이 원래 글에 무엇을 쓰는지. 그래서 `apply` 뒤의 실패는 「저장 단추를 누르지 않았다」 까지만 말한다

### 대안 기각

- **덮어쓰기에서도 새 사진, 스티커, 지도를 넣는다**: 이미 내용이 있는 글의 자리에 구성요소를 끼우는 편집기 조작을 실측하지 못했다. 실패하면 반쯤 고친 글이 남는다. 다음 단계로 둔다(사용자 결정, 2026-10-09).
- **되돌리기 없이 덮어쓴다**: 원래 내용이 사라진다. 네이버에는 임시저장 글의 이전 판이 없다.
- **원본을 커넥터의 작업 디렉터리에 JSON 으로 남긴다**: 그 파일을 다시 글로 만드는 도구가 따로 있어야 하고, 24시간 뒤 지워진다. 사용자가 네이버에서 바로 열 수 있는 사본이 낫다.
- **바뀌는 내용을 모델이 쓴다**: 모델이 실제와 다른 요약을 승인 카드에 올릴 수 있다. 커넥터가 만들고 작업이 다시 만들어 견준다.
- **글 전체를 지우고 새 글 입력처럼 다시 넣는다**: 기존 사진은 커넥터가 읽을 파일이 없어 다시 올릴 수 없다.
- **상시 허락을 연다**: 덮어쓰기는 사용자가 쓴 글을 바꾼다. 사본이 남더라도 매번 사람이 바뀌는 내용을 본다. 상시 허락을 닫은 도구는 가려진 인자가 있으면 승인할 수 없어, 그런 글은 `render_draft` 가 미리 거절한다(사용자 결정, 2026-10-09).

### 결과

- 얻는 것:
  - 에이전트가 임시저장 글을 읽고 고쳐 같은 글에 저장한다. 사용자는 승인 카드에서 바뀌는 줄을 본다.
  - 원래 글은 사본으로 남아 사용자가 네이버에서 비교하고 지울 수 있다.
- 감당할 것:
  - **덮어쓰기마다 임시저장 글이 하나 는다.** 사본은 사용자가 네이버에서 지운다.
  - **긴 링크나 해시가 든 글은 덮어쓸 수 없다.** 승인 카드가 그 덩어리를 가리고, 상시 허락을 닫은 도구는 가려진 카드를 승인할 수 없다. 스킬은 새 임시저장으로 남기거나 네이버에서 직접 고치게 안내한다. 가림 규칙은 Control Plane 의 것을 커넥터가 따라 적어 두었으므로, 그쪽이 바뀌면 커넥터도 바꾼다.
  - 원래 글에 사용자가 `[기존 사진 1]` 같은 글자를 직접 쓴 문단이 있으면 읽은 본문에서 실제 구성요소 줄과 구분되지 않는다. 그 줄을 남긴 채 덮어쓰면 `component_not_found` 로 멈추거나 실제 구성요소가 그 자리에 놓인다. 드물어 막지 않는다.
  - 지문은 제목, 카테고리, 태그, 본문 글자만 본다. 사진이나 인용구 안의 내용만 네이버에서 바뀌었으면 지문이 같아 대조를 지난다. 기존 구성요소는 덮어쓸 때 불러온 문서의 것을 번호로 고른다.
  - `setDocumentData()` 는 네이버가 공개한 계약이 아니다. 저장 전 다시 읽기가 어긋나면 `editor_failed` 로 멈추고, 그때 사본은 이미 남아 있다. 결과의 오류에 사본 번호를 싣는다.
  - 사본을 만든 뒤 원래 글을 고치기 전에 작업이 죽으면 사본만 남는다. 다시 덮어쓰면 사본이 하나 더 생긴다. 죽은 작업의 상태에는 사본 번호가 없다.
  - 사본을 저장할 때 편집기가 새 글이 아니라 원래 글을 고치면, 원래 글의 제목이 사본 제목으로 바뀐 채 `backup_failed` 로 멈춘다. 내용은 원래 그대로다.
